### Роли конструкций и ссылочные типы
- `defrecord` — shape-дескриптор с заполненными map-слотами + `user_protos`: данные и поведение, остаётся мапой.
- `deftype` — дескриптор с пустыми слотами, identity-равенство, возможны мутабельные поля. Реализация абстракций: своя коллекция, канал, транзиент.
- `reify` — `deftype` без имени. `extend-type` — патч чужого дескриптора. `deflayout` — байты (§4, низкоуровневый слой).
- **Мутабельные поля `deftype` — только с меткой, писать только изнутри** (как в Clojure): `set!` разрешён в телах методов самой формы `deftype` — в реализациях протоколов и интерфейсов внутри неё. Снаружи поле не записывается никак: ни `(set! (.-field x) v)`, ни через рефлексию; прочитать `(.-field x)` можно. Причина — мутация инкапсулирована в реализацию абстракции: транзиент мутирует свой массив внутри `conj!`, канал — свой буфер внутри `put!`, наружу торчат только протокольные операции. Пользователь объекта видит `ISeq`/`IChan`/что угодно, а не поле, которое можно поменять из любой точки программы.
- Что это даёт сверх Clojure: анализ знает все точки мутации — они внутри одной формы, поэтому «мутабельный тип» ставится по меткам полей, `set!`-эффект приписывается только тем методам, где он есть, остальные методы типа остаются чистыми; гарантия «`^:unsynchronized-mutable` трогает только поток-владелец» проверяется в конечном числе методов, а не по всей программе (из чужого потока — ошибка в dev, у JVM тихая гонка); `may-cycle` (§7) ставится по факту наличия мутабельных полей, угадывать нечего. Мутабельность — факт в решётке: объект вне reuse-анализа, при пересечении потока → SHARED.
- **Как это сделано** (2026-10-16; NOTES «Type descriptor», «Mutable fields»). Решения, которых текст выше не называл:
  - *Чтение и запись.* В теле метода мутабельное поле — не локал, а имя: обёртка метода (`field-wrap` в core.clj) кладёт тело в специальную форму `mutable-fields*`, и аналитор делает каждое чтение поля вызовом `(mutable-field* this i)`, а `set!` — `(set-field!* this i v)`; чтение после записи в том же теле видит запись. `set!` возвращает записанное значение, как на JVM. Неизменяемые поля по-прежнему локалы над `field*`, и `field*` мутабельного поля — ошибка: его чтение никогда не заимствуется и не считается чистым.
  - *Вложенная fn.* fn, сделанная внутри метода (и всё, что на ней стоит: `lazy-seq`, `reify`, `for`), читает поле таким, каким оно было в момент создания fn, и `set!` в ней — «Cannot assign to non-mutable», как у JVM, где замыкание копирует поле в своё. Аналитор оборачивает форму fn в `let*` по каждому полю, которое она называет.
  - *Снаружи.* `(.-f x)` читает мутабельное поле (на JVM оно приватно и недоступно); записи снаружи нет никакой: `(set! (.-f x) v)` — «Invalid assignment target». `defrecord` с мутабельным полем — ошибка: запись — значение, её базис читают `=` и `assoc`.
  - *Хинт.* `set!` пропускает значение через хинт поля так же, как конструктор (`^long` приводит, `^String` проверяет), поэтому факт хинта верен и для мутабельного поля.
  - *Хранение и `may-cycle`.* Мутабельное поле с хинтом `^long`, `^double` или `^float` хранит биты, а не значение: в слоте int64 или double, обход детей его пропускает, запись не упаковывает и не трогает счётчиков — в закрытой сборке чтение и `set!` такого поля по факту получателя идут без упаковки. С хинтом `^int`, `^short`, `^byte`, `^boolean`, `^char` поле держит только непосредственные значения. Ни такое, ни битовое поле ребром не бывает, так что тип с одними такими мутабельными полями (`Datom` datascript, `StringPBR` data.json) остаётся обычным: `may-cycle` ставит только мутабельное поле, которое может держать ссылку (без хинта, с хинтом класса или массива). Вне reuse-анализа остаётся лишь такой ссылочный экземпляр (`MUTABLE` никогда не уникален); ячейку умирающего уникального экземпляра без ссылочных полей переиспользовать можно — мутация его полей тут ничего не меняет. Экземпляр такого типа — ссылочный тип §7: рождается с `MUTABLE`, `REACH` и `REACH_LOCAL`, как volatile, и его `set!` — проверяемая запись (§7 «Проверка цикла в момент записи»).
  - *Владелец.* Поток-владелец — исполнение (корутина), создавшее экземпляр: его адрес лежит в слове после полей у типа с `^:unsynchronized-mutable` полем. Проверяет `set!` такого поля в dev — интерпретатор и dev-юниты; закрытая сборка не проверяет. Проверяется только опубликованный экземпляр: неопубликованный достижим из одного исполнения. Следствия: экземпляр, созданный в одном eval REPL (каждый eval — своя корутина), в следующем не пишется, и кэш хэша в `^:unsynchronized-mutable` поле, который заполняет чужой поток, — ошибка в dev; ответ — `^:volatile-mutable`, поле для записи из нескольких исполнений. Пробел на стороне тишины: адрес завершившейся корутины может достаться новой.
  - *Опубликованный экземпляр.* Ссылочное мутабельное поле опубликованного экземпляра читается в окне диспетчеризации, а запись — обмен слота и ожидание окон перед отпусканием старого значения (как `commit` атома), так что гонка двух потоков на таком поле — не use-after-free даже в закрытой сборке, а только гонка значений. `^:volatile-mutable` читает и пишет с `seq_cst`, `^:unsynchronized-mutable` — relaxed (запись опубликованного — `acq_rel`). Чтение и запись неопубликованного — обычные.
  - *Эффекты.* Чтение мутабельного поля — эффект `state` (ответ зависит от момента, ленивый `def` его не откладывает), `set!` — эффект записи (`atom`), как `vreset!`.

**Ссылочные типы.** `atom` (независимый, синхронный) — в ядре. `agent` (независимый, асинхронный) — тонкая библиотека в core.clj: значение и очередь действий в атомах, действие за раз (§4 «Агенты и ref'ы»). `ref`/`dosync` (координированный STM) — простая реализация: two-phase locking с захватом ref'ов по id, без MVCC; ретрай — только когда лок нужен против порядка id (§4 «Агенты и ref'ы»). Атомарность и изоляция сохранены; теряется неблокирующее чтение под нагрузкой, которого в мобильном приложении не бывает.
