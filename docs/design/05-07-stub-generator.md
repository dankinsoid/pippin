### Генератор стабов
**Вход — symbol graph, не `.swiftinterface`.** `swift symbolgraph-extract` работает с любым собранным `.swiftmodule`; у SPM-зависимостей, собранных из исходников, `.swiftinterface` нет вообще — то есть ровно там, где чужой код и нужен. Граф отдаёт JSON: публичные символы, метки и типы параметров с USR на каждое имя, дженерик-констрейнты, doc-комментарии, availability, отношения `conformsTo`. Clang importer даёт то же для ObjC — UIKit идёт той же трубой.

**Четыре факта про symbol graph, которые генератор обязан знать.** Каждый даёт не падающий генератор, а тихо неверный: риск §5 записан как «длинный хвост объявлений, которые не перепечатываются чисто», а замер (`docs/swift-reprint.md`) показал форму хуже — не непечатаемые объявления, а печатаемые неправильно.
- `functionSignature.parameters[]` теряет модификаторы владения: `hash(into hasher: inout Hasher)` приезжает туда просто `Hasher`. Значит `declarationFragments` надо разбирать тоже — из графа берётся не готовая сигнатура, а два источника, которые надо сшить. Там же лежит и `where`-клауза: `swiftGenerics.constraints` у члена расширения протокола бывает пуст, когда в печати стоит `where MenuItems : View`.
- у `swift.init` нет `returns` вовсе — что конструктор возвращает, генератор подставляет сам; иначе любой `init()` без аргументов выглядит как «всё переехало», хотя через границу едет ручка.
- член типа из чужого модуля называет владельца только отношением `memberOf`; в самом символе владельца нет.
- **ре-экспорты в графе не лежат.** `-module-name SwiftUI` не содержит ни `View`, ни `Text`, ни `VStack`, ни `ViewBuilder` — они в `SwiftUICore`, собранном с `-module-abi-name SwiftUI` и ре-экспортированном. Значит пайплайну `clj-анализ → список символов → symbolgraph → генератор` нужен шаг, который их разрешает, иначе генератор не найдёт символ, который на сайте вызова очевидно есть. Обнаруживается по данным, а не списком: USR'ы с именем самого модуля, которых ни один его граф не объявляет (в SwiftUI — 481 666 ссылок), плюс `@_exported import` из `.swiftinterface`; кандидат берётся, только если его ABI-имя совпадает с нашим.

**Генератор не понимает типы, а перепечатывает их.** Тип параметра приходит из графа уже записанным и эмитится как есть; резолвит его swiftc. Собственное решение одно — классификация внешнего конструктора типа по USR в вёдра: значение (числа, `String`, `Data`, `Date`), коллекция значений, замыкание, перечисление без ассоциированных значений, структура, чьи поля сами переезжают, всё остальное → opaque-ручка. Это не система типов, это switch. Три последних ведра — решения ниже, в этом же разделе. Отсюда главное свойство: ошибка генератора — ошибка компиляции, а не падение в рантайме; тайпчекер Swift стоит на выходе.

**Структуры по значению — shape-энкодер, не `Codable`.** Список полей у генератора есть, значит конвертация печатается прямой (см. «Swift → Clojure»), без экзистенциалов и поиска кейворда по строке.

**Два ответа §5 про структуры противоречили друг другу; противоречие снято (решено 2026-09-29).** Абзац выше говорит «структура по значению — прямая конвертация», а ведро «всё остальное → opaque-ручка» говорит обратное, и замер реализовал второе буквально: `URL`, `Locale`, `IndexSet`, `AttributedString` уехали ручками. Правило одно: **структура переезжает мапой, когда переезжают её собственные поля; бокс — фолбэк; ведро ручек — для ссылок и для того, что непрозрачно по существу** (`some View`, класс, структура с приватными полями или без публичного инициализатора). Зачем бокс вообще нужен и что он такое, записать здесь же: Swift-структура не ссылочный тип, поэтому «ручка на структуру» — это указатель на **бокс с копией**, а боксом обязан быть экземпляр класса, иначе нашему счётчику ссылок не за что держаться. В обратную сторону это уже сделано и называется `Value.Ref` (`Sources/Pippin/Value.swift:11`, `private final class Ref`).

**Равенство и хэш бокса печатаются из конформансов типа.** Тождество указателя защитимо для ручки на класс — оно хотя бы значит «тот же объект» — и незащитимо для боксированной структуры, где значит «тот же бокс», артефакт того, как мы её положили: два бокса с одинаковыми структурами не равны и хэшируются врозь, то есть структура ключом мапы молча врёт. Поэтому генератор печатает `==` и `hash(into:)` из `Equatable`/`Hashable` самого типа, а где у типа нет ни того, ни другого, ручка **отказывается быть ключом**, а не лжёт тихо. Побочное следствие, которое всплывает в этом документе дважды: те `Hasher`/`Encoder`/`Decoder`, которые «Как читать долю» ниже называет конформансной сантехникой, — это ровно **наш собственный** путь реализации, как уже было у фолбэка `Codable`. Уровня 1 это не трогает: у ObjC-объекта равенство остаётся тождеством (`Sources/CljCore/objc.c:72`) — там это ссылка, тождество защитимо, а `-isEqual:` запускал бы чужой код под замком мапы.

**Как печатается и как отказывает (решено 2026-10-02, первый срез).** Стаб печатает `SwiftStubs.box(v)`, а какую из трёх перегрузок взять — `Hashable`, `Equatable` или никакой, — решает `swiftc` по конформансам типа: конформанс, объявленный расширением в другом модуле, граф не покажет, а тайпчекер увидит. Дескриптор бокса — один на Swift-тип, с `==` и `hash(into:)` самого типа. Отказ — **ошибка, которую можно поймать**, а не `clj_fatal`: хэшировать бокс без `Hashable` (ключ мапы, член множества, `hash`) и сравнивать `=` два разных бокса типа без `Equatable` — ошибка с трейсом. Контракт ядра «`equals`/`hash` не бросают» при этом не ломается: слот записывает отказ на исполнение и отвечает 0/false, а бросает его операция, которая хэшировала, — вставка в HAMT, `hash`, `=`, `not=` (тот же путь, что уже несёт отменённость, выброшенную в `equals`, NOTES «Type descriptor»). Поиск отказавшего ключа (`get`, `contains?`) отвечает «нет» и отказ снимает: ответ верный, такого ключа нет ни в одной мапе, потому что вставка отказывает. Тождество как запасной ответ отвергнуто — это и есть та тихая ложь, ради которой абзац выше.

**Экземпляр класса — бокс с тождеством объекта (решено 2026-10-03, второй срез).** Полезная нагрузка — сам объект, а не копия. Тип бокса берётся по **динамическому** классу объекта, и конформансы читаются у этого класса в рантайме, а не выбираются `swiftc` по статическому типу, как у структуры. Причина — иерархия: статический тип на стабе бывает надклассом динамического, а один объект, вернувшийся из двух функций под двумя статическими типами, обязан лечь в один тип бокса, иначе два его бокса не `=` (боксы двух типов не равны никогда). Распаковка — динамическим кастом, поэтому бокс подкласса проходит туда, где ждут надкласс. `=` и `hash`: у `Hashable`-класса — его `==` и хэш; у `Equatable` — его `==`, а ключом он быть отказывается, как структура; **у класса без того и другого — тождество объекта** (`===`, хэш `ObjectIdentifier`). Для класса тождество — не артефакт упаковки, а факт «тот же объект»: абзац «Равенство и хэш бокса» называет его защитимым для ручки на класс, и так же уровень 1 сравнивает ObjC-объекты. Два бокса одного объекта, полученные двумя вызовами, `=` и дают один ключ; отказ здесь был бы ложной строгостью, ведь у класса есть честный ответ. Цена та же, что в Swift: изменённый после вставки `Hashable`-объект мапа теряет — это контракт `Hashable` и у самого Swift.

**В слоте фолбэка — рефлексия с кэшем по типу, а не `Codable` (решено 2026-09-29).** Рефлексия по хранимым полям типа не требует конформанса, одна дженерик-функция заменяет энкодер, печатаемый на каждый тип, и она умеет **конструировать** (`createInstance` плюс выставление полей), чего не умеют ни `Codable`, ни `Mirror`. Возражение про скорость относится к `Mirror`, а не к подходу: замер (структура из 3 полей, 200 тыс. итераций, `-O`, arm64) — `Mirror` 1694,5 нс на значение, загрузка по кэшированному смещению 1,1 нс, прямой доступ к полю ~0. `Mirror` медленный потому, что работает на каждое *значение*; рефлектор, кэширующий `typeInfo` на *тип*, читает поле примерно за наносекунду.

**Но для SDK-типов рефлексия — неверный главный путь, и это замерено тоже.** Что отдают метаданные: `URL` → `_url: NSURL`, `_parseInfo: Optional<URLParseInfo>`, `_baseParseInfo: …`; `Locale` → `identifier: String`, `locale: String`; `UUID` → полей нет вовсе; `IndexPath` → `_: Int`; `Measurement` → `value: Double`, `unit: String`. Это внутренности, а не публичная форма, и состав их меняется от релиза ОС к релизу. Писать их хуже, чем бесполезно: SDK-структура собрана с library evolution, и раскладывание полей **обходит инициализатор, установивший их согласие** (`_url` и `_parseInfo` у `URL` обязаны соответствовать друг другу). Ещё две цены, чтобы не всплыли потом: пол в 1,1 нс требует *типизированного* чтения, поэтому дженерик-рефлектор, возвращающий `Any`, боксит на каждом поле и до пола не достаёт — пол принадлежит печатаемому энкодеру; и метаданные рефлексии срезаются флагом сборки (`-reflection-metadata-level none`), значит это строка в `docs/portability.md`, а не гарантия. Итог: для своих и простых сторонних структур фолбэк — рефлексия; у SDK-структуры публичная форма живёт в **аксессорах**, поэтому `URL` честнее ручка с геттерами, чем «мапа своих полей».

**Мост — не сериализатор, поэтому четырём типам нужен явный переезд (замерено).** `JSONEncoder` спецкейсит все четыре, а обобщённый энкодер показывает неспециализированную `Codable`-форму, то есть внутреннее представление: у `JSONEncoder` получается `{"d":0, "b":"AQID", "u":"https://x.dev/a?q=1", "m":1.25}`, а у PropertyList `m` → `{exponent, isCompact, isNegative, length, mantissa}` и `u` → `{relative}`. Исключения JSON существуют потому, что на проводе есть только строки и числа; у нас моменты времени, байтовые массивы и точная десятичная — значения первого класса, значит исключения нужны и нам, но **другие**:
- **`Date` → `#inst`**, а не голый `Double`: число теряет и то, что это момент, и то, что эпоха у Apple — 2001, а не Unix. У нас есть `read-inst*`, `inst?`, `inst-ms`.
- **`Data` → байтовый массив**, а не base64: base64 — забота провода, а превращение байтов в строку и обратно — чистая потеря и чистая цена. У нас есть `byte-array` и `CLJ_T_ARRAY` с известным `elem`.
- **`Decimal` → `bigdec`**, и категорически не `Double`: `Decimal` существует ровно потому, что двоичная плавающая теряет копейки, а `1.25` у JSON выбрасывает это молча. У нас есть `bigdec`, `decimal?`.
- **`URL` → URI ядра** (поправлено 2026-10-08: `uri?` в ядре теперь есть, §3 «"Наш хост" — это C-ядро»; прежде здесь стояло «строка», за отсутствием своего значения). Как переезжает — §5 «Значения ядра на границе».

Вместо списка из четырёх стоять должно обобщение: **явный переезд нужен любому Swift-типу, чья `Codable`-форма — внутреннее представление, а не публичный смысл.** Это то же рассуждение, по которому §5 с самого начала выбрал shape-энкодер вместо `Codable`; четыре случая доказывают, что оно распространяется и на фолбэк.

**Перечисление переезжает кейвордом.** В вёдрах §5 правила для enum не было, поэтому по построению любое перечисление — ручка: замер показывает `Visibility` у SwiftUI как `swift.enum` на 3354 ручечных слота. Перечисление без ассоциированных значений — самое значение-подобное, что бывает, и ехать должно **кейвордом**: `:hidden`, а не ручка, полученная предварительным вызовом `Visibility.hidden`. Масштаб записан честно, чтобы его не перепродать: среди частых ручечных типов это 3354 слота из 136641 (2,5 %), и все они — `Visibility` у SwiftUI, а среди частых ручек Foundation перечислений нет вовсе; при этом различных enum-типов в графах четырёх модулей 273, то есть хвост больше, чем видно по голове. Перечисление **с** ассоциированными значениями — другая форма, здесь не решается.

**Опционалы, коллекции, кортежи: форма слота — из форм его частей (решено 2026-10-08, третий срез).** Генератор строит переезд слота рекурсивно, и элемент внутри коллекции переезжает ровно так, как переехал бы один: `T?` — nil или форма `T` (§5 «Swift → Clojure»: `Optional` → nil), в том числе результат `init?`; `[T]` — вектор, а на входе вектор или любой seq; `[K: V]` — мапа; `Set<T>` — множество; кортеж без меток `(A, B)` — вектор ровно этой длины, как кортежи ядра (§4 «Представление по наблюдению»); числа фиксированной ширины (`Int8`…`UInt64`, `UInt`, `Float`, `CGFloat`) — число, а значение за пределами типа — ошибка, а не перенос и не trap. Элемент, который не переезжает, делает отказом весь слот с причиной элемента. Четыре решения, которых раньше не было:
- `T??` — отказ: nil у Clojure один, и `.some(nil)` от `nil` не отличить; склеить их молча — та ложь, ради которой отказ громкий.
- две записи мапы, ставшие одним Swift-ключом, — ошибка на сайте вызова, а не «последняя выиграла»; `Set` на входе принимает только множество, потому что вектор с повторами схлопнулся бы молча. Обе строгости можно ослабить потом, а ослабленное обратно не сужается — тот же довод, что у §5 «Скаляры неявно, коллекции явно».
- кортеж с метками — отказ до триггера: его естественная форма — мапа по меткам, как у структуры, и строится она тем же путём, что структура-мапа.
- `UInt64`/`UInt` больше `Long/MAX_VALUE` переезжает `bigint`'ом и тем же `bigint`'ом возвращается.

Цена — копия на каждом переезде; порог размера, за которым коллекция дешевле ручкой (§5 «Коллекции на уровне 2»), не построен, и триггер его тот же — бенч границы.

**Перечисление кейвордом, структура мапой (решено 2026-10-08, третий срез).** Оба правила выше («Перечисление переезжает кейвордом», «структура переезжает мапой, когда переезжают её собственные поля») доведены до печати, и по дороге решено:
- **Кейворд случая — kebab его имени без пространства имён**, тем же `clj_objc_kebab`, что у вара члена: `:south-east` для `southEast`. Пространство не нужно: тип известен из сигнатуры слота, а `:hidden` пишут, не думая, чей он. Сырое значение не участвует — имя случая и есть его идентичность в Swift, а `rawValue` — данные, доступные варом `Тип.raw-value` и инициализатором `(Тип. :raw-value …)`. Кейворд не из случаев — ошибка со списком случаев.
- **Перечисление хотя бы с одним ассоциированным значением — бокс** по обычным правилам бокса (`==` и `hash` типа), а его случаи — строки отчёта: формы помеченного варианта в Clojure §5 не выбирал, и выбирать её здесь — без триггера. Члены перечисления любой формы — вары `Тип.член`, получатель — кейворд или бокс.
- **Мапа — только когда все хранимые свойства публичны и сами переезжают; иначе бокс.** Публичный symbol graph непубличного поля не показывает, и структура с приватным полем в нём неотличима от «мапы», а мапа без этого поля — молча потерянное состояние. Поэтому генератор вынимает второй граф, `-minimum-access-level private`, и смотрит в нём все хранимые свойства; `lazy` — тоже бокс (его геттер мутирует). Поле может быть другой структурой-мапой, в том числе через коллекцию — решение вычисляется неподвижной точкой.
- **Ключи — kebab-кейворды имён свойств, мапа на входе закрыта:** ключ, которого у структуры нет, — ошибка со списком ключей, недостающий — nil у опционального поля и ошибка у остальных. Открытая мапа молча проглотила бы опечатку в имени опционального поля; ослабить до неё можно потом, сузить обратно — нет. На выходе опциональное поле есть всегда, со значением nil: отсутствие и nil в Swift — одно и то же, а мапа одной формы сравнивается дешевле.
- **Обратно из мапы — публичный `init`, чьи метки — имена хранимых свойств тех же типов, плюс присваивание остальных публично устанавливаемых `var`;** из подходящих берётся покрывающий больше полей. Нет такого пути — структура переезжает только наружу (§5 «Структуры несимметричны»), и всё, что принимает её на вход, включая её же члены, — строка отчёта с этой причиной; читать её поля можно кейвордом.
- **Два Swift-имени, которые kebab склеивает** (`url` и `URL`), лишают тип кейвордной формы: каждый переезд — ошибка с обоими именами, а не выбор одного. Тип, чьи функции переезда отверг `swiftc`, становится боксом и называется в отчёте.

Члены структуры-мапы — те же вары `Тип.член`: получатель — мапа, `mutating` и сеттер возвращают новую мапу (§5 «`mutating`, `inout`»). Прямое построение shape-мапы с интернированным shape в статике (§5 «Swift → Clojure») не построено: мапа собирается `clj_map_from_items`, который для кейвордных ключей и так кладёт её shape'ом, но ищет shape на каждом переезде; триггер — переезд структуры в профиле.

**Генерируется замыкание от call-site'ов, а не поверхность SDK.** Жадная генерация Foundation + UIKit + SwiftUI кладёт swiftc и раздувает таблицу регистрации, из которой линкер ничего не выкинет, — это и есть причина, по которой «подключил и получил всё» ни у кого не взлетело. Закрытый мир (§6) даёт список host-символов, реально вызванных из Clojure; тянется он плюс типы из их сигнатур. Покрытие — 100 % вызванного, размер — по вызванному, руками не пишется ничего. Оговорка к «100 %»: она держится там, где тип аргумента известен статически; тип, приезжающий на сайт как ⊤ (через `deref`, неизвестный вызываемый), означает выбор инстанциации в рантайме, а промах — ошибку рантайма с перечислением существующих. Шаг пайплайна: `clj-анализ → список символов → symbolgraph → генератор → swiftc → линк`.

**Индекс и генерация — два артефакта из одного входа.** Так уживаются «генерируем только вызванное» с полнотой автодополнения и валидации. **Индекс** покрывает всю поверхность модулей, объявленных в `require-swift`: это дёшево (четыре модуля классифицированы за 34 с), лежит на диске и ключуется фингерпринтом `.swiftmodule` — тем же кэшем, который абзац «Кэш» ниже описывает как ускоритель сборки и который здесь же носитель подсказок. **Генератор** эмитит только символы, названные сайтами вызова: это дорогая половина — swiftc и размер бинарника. Значит: индексируем всё, генерируем вызванное. И классификатор — он же валидатор: индекс знает не только что символ есть, но и переезжает ли он и почему нет, поэтому LSP говорит в точке набора «это существует, но не переезжает, потому что …», а не молчит до сборки — ровно то, что §5c уже обещает. Новых механизмов ноль: `require-swift` задаёт область индекса (модули объявлены), сайты вызова — область генератора (символы найдены).

**Дженерики — список инстанциаций, а не барьер.** Генератор работает на сборке, значит мономорфизация доступна; нужен только список типов. **Множество инстанциаций ограничивают call-site'ы и только они (решено 2026-09-27).** Раздувание от шаблонов C++ и от мономорфизации Rust — настоящая проблема настоящих проектов, и оба инстанцируют то, что программа *использует*; инстанцировать всех конформеров констрейнта — строго больше этого, то есть хуже языков, которые от него уже болеют. С call-site'ами как границей N ≤ числа дженерик-сайтов и известно заранее, а рекурсия взорваться не может: сайт называет конкретный тип конечной глубины. Следствия — одни удаления: **настраиваемый порог уходит, и ограничение глубины тоже** — ни то, ни другое не нужно, а вместе с ними уходят лимиты глубины, необъяснимые пользователю. Не разрешилось — строка отчёта.

**Где аннотация обязательна — одной строкой:** параметр типа, встречающийся в позиции аргумента, резолвится в рантайме по тем инстанциациям, которые дали call-site'ы; встречающийся только в возврате — не резолвится и требует явной аннотации. Swift сам выводит возвратный случай из *контекста вызова* (типа переменной, которой присваивают), а у Clojure типового контекста нет — это отсутствующий вход, а не наша слабость, и генератор заранее видит, где именно аннотация обязательна. Целочисленные дженерик-параметры (value generics Swift, `InlineArray<3, Int>` с сахаром `[3 of Int]`) требуют её же: их множество неперечислимо по-новому — это не «типы в программе», а числа.

**Запись явного типового аргумента — `#/(List String)`, как в ClojureDart.** Почему она так выглядит, важнее эстетики: `<` и `>` в Clojure — обычные составляющие символов (`<`, `>`, `>=`, `<!`, `->`), поэтому ограничителями быть не могут, не поломав эти имена; плоский символ (`List<String>`) читается, но не вкладывается — `Map<String, List<int>>` пришлось бы разбирать внутри символа, а запятая там пробел. Dispatch-форма, переиспользующая синтаксис списка, — самое дешёвое добавление, не трогающее ничего.

**Что покупает рантайм-диспетчер.** В Swift **нет дженерик-значений**: дженерики живут на объявлениях, `let f: <T>(T) -> T` написать нельзя (`(any Equatable) -> Bool` — экзистенциал, а не дженерик), поэтому Swift-дженерик становится значением только в конкретной инстанциации. Эмиссия инстанциаций, которые дали call-site'ы программы, плюс диспетчер дают Clojure **одну полиморфную fn первого класса** — возвращают то, что система типов Swift запрещает. Множество при этом закрыто, поэтому неназванный тип — внятная ошибка рантайма со списком доступных инстанциаций. Ничего не домыслено.

**Отчёт генератора — часть продукта.** Не переезжает конечный список: макросы — раскрываются на месте использования; variadic generics, `@autoclosure`, property wrappers как API; нескопируемые типы (`~Copyable`) — держать их за ручкой, которую рантайм со счётчиком ссылок вправе размножить, нельзя; **значения с зависимостью по времени жизни** (`~Escapable`, `Span`/`RawSpan`/`MutableSpan`, заимствованные вьюхи) — их нельзя хранить, поэтому ручка, пережившая вызов, это use-after-free. Масштаб последнего замерен, чтобы его не выводили заново: таких символов 3 в Foundation и ни одного в SwiftUI, ArgumentParser и OrderedCollections, то есть это правило на будущее, а не сегодняшняя цена. Отчёт «что не переехало и почему, по модулю» уходит в LSP диагностикой (§5c) — узнаёшь в точке вызова, а не на сборке; рукописный глю живёт только внутри этого списка.

**Result builders из этого списка ушли (2026-09-28, по замеру).** Причина, которая там стояла — «синтаксическая трансформация компилятора, вызывать нечего», — неверна: `@ViewBuilder` преобразует *литерал замыкания, написанный на сайте вызова*, а не тип параметра. Параметр остаётся `() -> Content` при `Content: View`, и стаб передаёт замыкание *значением*, которого атрибут не касается: против `init(@ViewBuilder content: () -> Content)` тайпчекаются и сохранённое `() -> Text`, и ссылка на функцию, и собранный руками `TupleView<(Text, Text)>`. Значит это **другая запись**, а не отказ: вместо тела билдера — view-значение либо `TupleView`/`ViewBuilder.buildBlock`. Честный остаток узкий: *многооператорное тело билдера* из Clojure не написать. Масштаб ошибки виден по замеру — пока этот «отказ» стоял в списке, он один давал 70 % хвоста SwiftUI, а без него хвост SwiftUI — 2 % поверхности.

**Экзистенциалы оттуда же ушли (2026-09-28, по замеру).** Стоявшая там причина — «протоколы с Self-требованиями без primary associated types, экзистенциала не существует» — устарела: с SE-0309 (Swift 5.7) `any P` законный тип для любого протокола, и `any View` с `any Equatable` компилируются (проверено). Значит стаб такой параметр печатает и принимает, а Clojure передаёт в него ручку, полученную раньше, — это ведро ручек, а не отказ. Остаётся обычная цена ручки: прочитать её содержимое без аксессоров нельзя. Из отказа остаётся только случай, где стабу нужно *сконструировать* конформера, а публичного пути к нему нет, — но это асимметрия структур, а не экзистенциал.

**Как читать долю «переехало чисто».** Замер по **всей публичной поверхности** её занижает: большая часть того, что едет ручкой, — конформансная сантехника, к которой Clojure-программа не обращается. Самые крупные ручечные слоты Foundation — `inout Hasher` (350), `any Decoder` (279), `any Encoder` (260), `[Self.Element]` (175), а `Hasher`/`Encoder`/`Decoder` — это к тому же **наш собственный** путь реализации на этой границе: печатаемые для бокса `==` и `hash(into:)` и фолбэк «для типов, которых генератор не видел» (выше, «Равенство и хэш бокса», «В слоте фолбэка»). Посылка §5 в том, что генерация идёт за сайтами вызова, а не за поверхностью SDK, — значит доля, которая что-то решает, требует списка вызовов реального приложения. Инструмент готов и ответит в тот момент, когда список появится; §10 шаг 8 опирается именно на эту долю.

**Отказ громкий по построению; тихие риски — другой список.** Проценты приглашают прочитать их как «какая-то доля вызовов молча не сработает», поэтому ответ записан отдельно. Отказ громок тремя уже спроектированными способами: отчёт генератора называет его по модулю; §5c доставляет это LSP-диагностикой в точку вызова; а квалифицированное имя, не разрешающееся ни во что, — **ошибка анализа**, и она построена и работает сегодня (`Unable to resolve host type`). Отказавший символ до рантайма, значит, не доезжает. Молчать может другой набор, и ничего из него в процентах нет, потому что каждый пункт — *неверный успех*, а не отказ:
- **неверно напечатанное объявление, которое всё-таки компилируется** — пробелы symbol graph, перечисленные выше (потерянные модификаторы владения, пропавшая `where`-клауза, `swift.init` без `returns`): стаб, передающий по значению то, что должно быть `inout`, теряет мутацию вызывающего;
- **стёртая изоляция актора** — стаб компилируется, вызов уходит на неверный носитель, и то, что Swift ловит на компиляции, становится плавающим отказом в рантайме;
- **`consuming` на `~Copyable`** — ручка после вызова невалидна;
- **ручка ключом мапы** при тождестве указателя — выше, «Равенство и хэш бокса».

Проценты, стало быть, меряют охват, а список рисков короткий, конкретный, и каждый его пункт — обязанность генератора. Оговорка к громкости: сегодня её даёт аналитор, а половина «узнаёшь в точке вызова в редакторе» ждёт LSP, которого нет.

**Кэш.** Граф и индекс генератора — по фингерпринту `.swiftmodule` плюс версия компилятора, как кэш dylib'ов корпуса; SDK меняется раз в релиз. Холодный старт — раз на машину, тёплая сборка не трогает swiftc, пока Clojure-код не сослался на новый символ. Где кэш живёт и как чистится — §3 «Кэш».

**Прецеденты.** Kotlin/Native cinterop (headers/modulemap → вся ObjC-поверхность), Dart ffigen (libclang; Swift — через сгенерированную ObjC-совместимую обёртку), Xamarin (генерация из заголовков плюс рукописный слой метаданных, поставлялась предсобранной — ценой команды на годы). Из **Swift** напрямую не генерирует никто (для C++/ObjC/Java эта форма как раз обкатана — Codegen у React Native, ниже): машинно-читаемого интерфейса у Swift до symbol graph не было. Значит мы тут первые, и риск не в скорости сборки, а в длинном хвосте объявлений, которые не перепечатываются чисто.

**React Native — прецедент и для генератора, а не только для запасного выхода.** История там ровно наша: асинхронный батчащий мост с JSON-сериализацией и рукописными нативными модулями (`RCT_EXPORT_METHOD`) → **JSI** (C++-интерфейс, позволяющий JS держать ссылки на host-объекты и звать их синхронно, без JSON) плюс **TurboModules**, чьи биндинги печатает **Codegen** по типизированной TypeScript-спеке; **Fabric** увёл shadow-дерево в C++; **Hermes** отказался от JIT в пользу байткода на сборке, потому что iOS запрещает JIT вне WKWebView. Записать из этого надо два факта: модель «только данными» — та, которую RN десять лет разбирал обратно, и разбирал **генератором**, по нашей же причине — рукописный глю на метод не масштабируется по экосистеме модулей. И обратный голос: спека у RN **объявлена**, а не выведена, — это довод против выбора §5 выводить список символов из анализа. Записанное противоречие, не разворот.

**Запасной выход записан.** Если доля чисто переезжающих call-site'ов на реальном приложении окажется низкой, а хвост — дорогим, уровень 2 сворачивается до модели React Native: со Swift общаемся только данными (уровень 3), нативная сторона пишется руками под фиксированный протокол. **И падение меньше, чем звучит:** в React Native у JS доступа к ObjC-рантайму нет вовсе — он зовёт только модули, написанные кем-то руками; наш уровень 1 уже даёт `(.любой-метод x)` по всему `@objc`, динамически и без объявлений. Свёрнутый уровень 2 — это «React Native **плюс полный ObjC-рантайм**», а не React Native. Критерий и точка решения — §10 шаг 8.
