### Атомы
- Атом живёт в C-ядре, бэкенда на Swift-стороне нет (§3: ничего платформенного в ядре; Swift видит только `deref`/`swap!` через `Value`, мост к `Observable` — слой курсоров выше). Лок — `clj_lock` (`clj/lock.h`): `os_unfair_lock` под `__APPLE__`, `pthread_mutex_t` иначе, один интерфейс, один `#ifdef` — та же граница, что у `host`. Замер (M3 Pro, пара lock+unlock): unfair 2.1 нс / 4 байта, pthread 4.6 нс / 64 байта; под contention unfair передаёт приоритет владельцу (для этого он и создан), pthread — только с `PTHREAD_PRIO_INHERIT`. Адрес стабилен: атом — объект фиксированного размера, `clj_realloc` его не трогает. Все локи ядра (таблицы keyword/ns/протоколов/профайлера) — через него же. **Rwlock — нет:** взятие read-лока — атомарный RMW на общем счётчике, читатели дерутся за кэш-линию как за мьютекс (4 читателя: unfair 38 нс/оп, `pthread_rwlock` 448, размер 200 байт); окупается только при длинных read-секциях, которых в ядре нет и не должно быть — «много читают» решается иммутабельностью + эпохой (протокольный диспатч, вары), читатель не берёт ничего. Не CAS: lock-free refcounted-указатель = гонка retain/release, нужны hazard pointers или DCAS ради повторения JVM-дизайна.
- `f` выполняется ровно один раз, под локом. Лок атома — корутинный мьютекс (§4 «core.async», «Два лока»): без контенции тот же CAS, при контенции парк корутины вместо заморозки носителя; `f`, который ждёт, — линт, не ошибка. Watches — после отпускания лока. Вложенный `swap!` на тот же атом — trap (на JVM — бесконечный ретрай, оба баг). `deref` — без лока: seqlock, как у варов, — UI читает атом на каждый кадр и не должен ждать чужой `f`.
- **Affinity у атома снята.** `(atom x :affinity :main)` проверял носитель при каждом доступе, и `swap!` или `deref` с пула бросал ошибку. Проверка была диагностикой поверх shared-значения; разгрузку main без всякой пометки даёт BRC для главного потока (§4 «Представление значений»), а атом корректен с любого потока сам. Прыжок на main, как у `@MainActor` на мосту (§5 «Замыкания через границу»), тоже не берётся: работать нужно там, где позвали, а прыжок стоит оборота run loop на операцию и даёт дедлок, когда фоновая корутина держит `locking` и ждёт main, а main внутри синхронного входа из Swift блокируется на том же локе. Гарантия «где исполняется» остаётся у `go-main` и `affinity: .main` моста. Ключ `:affinity` у `atom` игнорируется, как любой неизвестный опционный ключ на JVM (`b_atom`, `CoroTests.mainAffinity`).
- **Трюк уникальности — снят.** `old = state; state = placeholder; new = f(old)` давал in-place внутри `f`, но бросок из `f` после in-place шага не может вернуть старую версию — её уже нет; JVM при броске оставляет состояние как было, и код на это опирается (`(swap! a (fn [s] (if ok (assoc s …) (throw …))))` — идиома отказа). Журнал отката признан слишком сложным за такую цену. Атом держит свою ссылку, `f` получает значение +0, `swap! assoc` копирует путь корень→лист: 91→288 нс на 16 ключах, 101→613 на 1000, 131→904 на 100k (bench/RESULTS.md, «Atoms»); `deref` того же атома изнутри `f` возвращает текущее (старое) значение, как на JVM.
- **Возврат трюка: «запись последней», а не «`f` не бросает».** Триггер — профиль с горячим `swap!` на большой мапе; только атом без watch'ей и валидатора (обоим нужен целый `old`). Порчу даёт не любой бросок из `f`, а бросок после первой записи на месте, поэтому условие: на каждом пути через `f` после первой consuming-операции над линией параметра 0 нет узла, который может бросить. Оно строго шире no-throw: идиома отказа ему удовлетворяет (бросок и запись на разных ветках), `(-> s (assoc …) (validate!))` — нет. Трюк вообще возможен потому, что `f` исполняется один раз под локом: в CAS-цикле JVM `old` остаётся в атоме — его видят читатели, параллельные `f` и ретрай, — отдать ссылку некому. Журнал отката — только для остатка (запись, потом проверка).
  - Факт — на функции, не на синтаксисе сайта: белый список `(swap! a assoc …)` ломается на `#(assoc % k v)`, `partial`, хелпере из вара. Пять consuming-нативов (`conj`, `assoc`, `dissoc`, `disj`, `with-meta`) объявляют его битом рядом с consuming-входом: по построению хеш и `equiv` ключа считаются на спуске, записи — на подъёме (map.c, `descend`/`ascend`). Для тел — вывод: прямой проход по телу с одним битом «линия параметра 0 уже записана на месте», рядом с liveness; результат — в сводку, в тот же слот, что объявленный, так хелпер становится листом. `update`/`update-in` (core.clj) — через вывод; `g` получает лист разделённым (+1), иначе её собственный in-place с броском портит состояние. Проверяет требование `swap!` на аргументе 1 — тот же механизм, что `{:effects #{}}` (§3).
  - Нынешний бит `throw` (NOTES «Facts», эффекты) для вывода не годится: он плоский — почти вся core-таблица `alloc|throw` — и порядка не знает. Нужны два уточнения: бросок по типам аргументов (`assoc` на мапе с ключом-кейвордом тотален — трансфер-функция, не строка таблицы) и позиция относительно первой consuming-записи. До них вывод консервативен: бросает всё, кроме объявленных нативов.
  - Ошибочный факт — тихая порча, поэтому в debug-сборке запись на месте под hand-over ставит флаг в execution, а путь броска на нём — trap; на каждый натив — тест: бросок из каждой точки (не-мапа, бросающий `equiv` ключа) оставляет атом нетронутым.
  - `deref` без лока и hand-over конфликтуют на окне hand-over: стороннему читателю нельзя отдать ни значение на полпути правки, ни старое — его нет; при снятом трюке `deref` брал лок, seqlock появился позже. Читатель на окне ждёт commit. У натива окно — один его вызов (как удержание лока), у лямбды — вся `f`, что спорит с «UI не ждёт чужой `f`»: путь лямбд — только с решением этого конфликта.
  - Порядок: (1) бит на пяти нативах, путь «consuming native» в `swap!`, debug-trap и тесты — основная масса `swap!` без аналитора; (2) путь «фрейм владеет параметром 0» для лямбд, консервативно, после решения о `deref`; (3) уточнения `throw` в решётке.
- Не актор: `swap!` обязан быть синхронным.
