## 6b. Карта оптимизаций: где живут, когда включать, что заложить заранее

### Три уровня
- **Рантайм** (оба режима, без анализа): пул по size-class, biased RC, shapes с деревом переходов, elements kinds, tuples, reuse при rc==1, trial deletion, hash-consing, корутины с affinity и прямой передачей, дескрипторы со слотами, self-optimizing узлы как inline cache.
- **Общий оптимизатор** (AST → AST с фактами, достаётся обоим режимам по построению): локальный вывод фактов, constant folding, lowering деструктуринга/`case`/`cond`, fusion, strictness, CSE, auto-transient, TCO самохвостовых → loop-узел, reuse, borrowed-аргумент на сайте вызова. В интерпретаторе — с эпохой вара как guard'ом и инкрементальными сводками; в компиляторе — по закрытому миру и фикс-пойнту.
- **Только компилятор:** закрытый мир, прямая линковка, tree shaking, межпроцедурный фикс-пойнт фактов, e-graphs, регионы и стек, unboxed-конвенция между функциями (worker/wrapper), tag-switch интринсики, PGO-guard'ы, PGO/BOLT layout бинаря, copy-and-patch eval (десктоп).

**Критерий границы — три оси, не бюджет.** Оптимизация попадает в интерпретатор, если проходит все три:
1. *Guard'уема:* применяется в точке (сайт вызова, узел доступа) и проверяется одним сравнением эпохи. Глобальное без точки проверки — tree shaking, снятие косвенности вара, удаление проверок целиком — только закрытый мир.
2. *AST-уровень:* меняет дерево, а не форму машинного кода. Регионам, стеку, unboxed-конвенциям и inline tag-switch в интерпретаторе некуда лечь.
3. *Линейна на форму:* фикс-пойнт — инкрементально по эпохам, на циклах widening сразу.
Всё, что проходит, достаётся интерпретатору **само** через общий оптимизатор; специально «переносить в интерпретатор» ничего не нужно, кроме self-optimizing узлов. Дальше этого не идти: интерпретатор — эталон семантики для дифференциальных тестов (интринсик vs слот, интерпретатор vs компилятор в CI), второй умный исполнитель = вторая поверхность расхождений. Скорость dev-режима берётся не из интерпретатора, а из скомпилированной базы с косвенностью (§3 «Два режима»), компилирующего eval на Маке и copy-and-patch — модель Julia, не CPython.

Self-optimizing узлы и статический вывод — один механизм специализации с двумя источниками: компилятор эмитит `int+` по выведенному типу; узел переписывает себя по наблюдению там, где статика дала ⊤ (в интерпретаторе всегда, в компиляторе как PGO-fallback).

### Флаги
- `-O0` — прямая линковка + lowering. Секунды на проект, отладочные сборки.
- `-O1` — плюс локальный вывод, fusion, reuse, auto-transient. Дефолт dev-сборок под устройство.
- `-O2` — плюс межпроцедурный фикс-пойнт, e-graphs, регионы, borrow inference, PGO. Релиз.

Инвариант на все проходы: бюджет на функцию, деградация в ⊤, никогда не падение. E-graph превысил лимит → extraction из того, что построено; фикс-пойнт не сошёлся за N итераций → widening; регион не доказан → heap. Компилятор на `-O2` может быть медленным, но никогда не «завис» и никогда не «не смог».

### Ранжированный список — что добавлять сверх принятого и когда
1. **Self-optimizing узлы интерпретатора** (Truffle node rewriting; quickening в CPython 3.11 — то же на байткоде). Узел `+` после первого вызова с int переписывается в `int+` с guard'ом и откатом. 2–5× в dev, и это же inline cache для shapes. Делать вместе с интерпретатором.
2. **E-graphs / equality saturation** (egg, ægraphs в Cranelift) для оптимизатора чистого кода. Архитектура, не проход: e-class хранит все эквивалентные формы, правила добавляют, extraction выбирает по стоимости — phase ordering исчезает. Для чистого кода легальны все алгебраические правила: fusion, CSE, folding, законы коллекций (`(map f (map g xs))`, `(assoc (assoc m k a) k b)`). Новая оптимизация = новое правило. Взрыв на AC-правилах лечится бюджетом узлов. Внедрять в момент появления оптимизатора: переделывать потом дорого.
3. **Copy-and-patch** (Xu & Kjølstad 2021; JIT в CPython 3.13) для `eval` на Маке: шаблоны машинного кода с дырками из тех же C-интринсиков, патч констант и адресов в рантайме — микросекунды вместо clang + dlopen (~100 мс), качество кода уровня `-O1`. Только десктоп (генерация кода). После стабилизации C-бэкенда.
4. **Hash-consing маленьких иммутабельных значений** (Lean `Expr`, Unison): keyword'ы уже интернированы, расширить на маленькие строки и shape-мапы с константными значениями → `=` по указателю, память схлопывается. Дёшево попробовать, мерить на макробенчмарке с JSON. После shapes.
5. **Field reordering в shapes по профилю доступа** — горячие поля в первую кэш-линию. Тривиально, когда есть shapes и dev-профиль.
6. **PGO/BOLT layout бинаря** — через clang-тулчейн, 5–15% на большой программе. Перед первым релизом.
7. **MLIR** как IR, если уходить от C-бэкенда: высокоуровневые операции (`assoc`, `map`) как диалект, постепенное понижение. Горизонт — годы; сейчас достаточно не завязывать оптимизатор на C-специфичное.
8. **Compact regions для app-state** (GHC) — ниша, пул даёт большую часть выигрыша.
9. **Effect handlers как компилируемый примитив** (evidence passing в Koka, OCaml 5) — в карман. Корутины = рантайм-реализация одного эффекта; handlers нужны только ради многократного возобновления (backtracking). Генераторы = `go` + канал с буфером 0; resumable exceptions (conditions/restarts из CL) = библиотека над `binding` (обработчик вызывается поверх стека, возврат = продолжить); backtracking = core.logic (miniKanren, потоки решений без продолжений — работает как есть и выигрывает от shapes/reuse на подстановках) и Datalog (Datascript).
10. **Content-addressed code** (Unison) — источник идей для кэша AST и эпох.

Не применимо или покрыто: полная supercompilation (взрыв кода, завершаемость); Cranelift (нишу закрывают C + copy-and-patch); автовекторизация (clang сам справляется над `deflayout`); NaN-boxing (§4).

**Partial evaluation / проекции Футамуры — принцип, а не задача:** интерпретатор и компилятор на одном дереве узлов, чтобы компилятор в C получался как PE интерпретатора по AST (узел `if` с известным условием → ветка, `+` с известными типами → без диспатча). Truffle делает первую проекцию промышленно.

### Интерпретатор до компилятора: что делать и в каком порядке

Всё ниже — работа интерпретатора и общего optimizer'а над `clj_node`; ничего не требует компилятора, и каждый пункт — с before/after на бенчах. Развилка «нужен ли компилятор и для чего» с замерами (профиль интерпретатора на реалистичных workload'ах, ручная эмиссия `-O0` горячей функции, `ns/node` и `ns/invoke` против Lua) — после пункта 5, когда интерпретатор станет тем, что честно сравнивать.

0. [x] **Дверь в компилятор — три инварианта, дешёвые сейчас:** `clj_node` иммутабелен и сериализуем (есть, §3), exec-состояние сбоку (есть), валидатор в CI — весь core.clj проходит `to_data → read → from_data` (ловит компилятор-враждебные конструкции в день появления). *Статус:* есть; первым уловом был `reify`, клавший объект типа в константу — теперь тип создаётся в рантайме через `reify-type*` с реестром по сайту.
1. [x] **Escape hatch раньше компилятора.** Горячий кусок объявляется примитивом: реализация на C/Swift, вызов из Clojure по имени — так уже построен core (`builtins.c`, `Value(function:arity:_:)`). Не хватает `Runtime.define` со стороны Swift и правила: примитив живёт рядом с Clojure-реализацией, которая остаётся его спецификацией, дифференциальный тест гоняет обе — тот же механизм, что для интринсиков. Граница честно: ускоряет библиотеки (hiccup-diff, JSON, сортировка), не код пользователя, и только крупнозернисто (переход Swift↔C — десятки нс). *Статус:* `Runtime.define`, `Runtime.differential`, `sort`/`compare` как первый примитив со спецификацией рядом; переход измерен — ~64 нс поверх C-builtin, верхняя граница оценки.
2. [x] **Тулинг сейчас, не потом** — единственная выгода компилятора, которая ощущается с первого месяца и не заменяется escape hatch. Теневой стек (push/pop на invoke, наносекунды) одним механизмом даёт стектрейс в uncaught exception, `:trace` в `ex-info` и дописку кадров в крэш-репорт из signal handler. `os_signpost` вокруг invoke под debug-флагом — flame graph в Instruments без своего UI. Счётчики вызовов и inclusive time в `exec_node` — это `(profile …)` для человека и dev-профиль для PGO, одна структура. Ассерты на счётчиках: per-type live counts, «REPL-форма не течёт». *Статус:* сделано целиком (shadow stack, `ex-trace`, крэш-хендлер, signposts, `profile`, live-object отчёты); после прямого входа в замыкание guard, shadow и инструментация — в шуме.
3. [x] **Конвенция счётчиков как правило рантайма, не как вывод.** Аргументы +0, возврат +1, retain только в точке записи в кучу (слот `let`/`recur`/`catch`, захват в замыкание, возврат локала из тела). В интерпретаторе аргументы живут в массиве вызывающего весь вызов — параметры замыкания borrowed безусловно, маска `owned` на кадре. Deref вара остаётся owned: заимствованный root при конкурентном `def` из REPL освобождает fn, чьё тело выполняется; снимается только вместе с immortal-корнями core (бутстрап) и эпохой для остальных. Бессмертные объекты: keyword, var, пустые коллекции — есть; интернированные символы и корни core-варов — добавить. Забирает основную долю того, что даёт borrow inference, без фикс-пойнта и закрытого мира. *Статус:* сделано; замер показал, что сама конвенция скорости не даёт (RC на не-shared — 5 инструкций), её ценность — договор о владении для reuse (п. 4) и компилятора; корни варов читаются +0 с отложенным освобождением заменённых fn-корней вместо immortal.
4. [x] **Эпоха + optimizer + интринсики + свёртка** — один шаг, здесь появляется фаза optimizer'а в конвейере.
   - *Эпоха определений*: одна глобальная, двигают `def`/`deftype`/`defmethod`/`extend` (поглощает protocol epoch). Inline cache в `exec_node` = `{epoch, cached}`; в REPL один `def` сбрасывает все кэши, они перегреваются за микросекунды — per-var эпоха не нужна. Сама по себе не оптимизация — фундамент для 5–7.
   - *Интринсики core*: таблица `{символ, арность} → {kind, C-функция}` → узел `INTRINSIC`, убирает кадр, диспатч и косвенность вара разом (~10 нс → 2–3 на builtin-вызов). Условие корректности: интринсик и core-функция зовут одну C-функцию (`b_add` в цикле зовёт `clj_add2`). Спекулятивно, пока мир открыт: отзыв по эпохе (до неё — guard `root == ожидаемый`, не дороже).
   - *Свёртка констант по чистоте*: таблица чистоты — те же записи, что интринсики; складываются INTRINSIC-узлы с const-аргументами; бросил при свёртке — узел остаётся (`(/ 1 0)` бросает в рантайме). Практическая ценность мала, ценность — optimizer.c на правильном месте: после анализа, до нумерации, переживает сериализацию.
   - *Reuse по последнему использованию*: флаг last-use на LOCAL-узле из локальной liveness внутри формы; `eval_borrowed` отдаёт владение → `conj` при rc==1 работает in-place. Без этого in-place из интерпретируемого кода не срабатывает никогда (builtin retain'ит перед consume). Это и есть auto-transient.
   *Статус:* сделано целиком: таблица из 52 интринсиков с guard'ом `root == boot-корень` (эпоха не понадобилась: guard не дороже), свёртка с двойной границей по кодеку (и аргументы, и результат сериализуемы), last-use только на чтениях, чей потребитель может владеть (arg0 consuming-интринсика, init `let`, `recur`, тело) — пометка аргументов обычных вызовов измерена и отвергнута (+2 нс/вызов); драйверы `reduce`/`into` отдают аккумулятор consuming-нативу с владением. Бенч: counting loop −48 %, loop conj −62 %, reduce conj −83 %.
5. [x] **Inline cache на варах и протоколах** — та же структура в `exec_node`. Прямая линковка вара: `{epoch, fn}`, fn retain'ится узлом, прямой вызов тела нужной арности мимо `clj_invoke`. Девиртуализация протоколов и мультиметодов: `{epoch, type → fn}`, одна реализация → прямой вызов, 2–4 → switch, дальше generic. Инлайн тела варной функции — не здесь: рост кода, переименование, deopt-альтернатива — территория компилятора, в интерпретаторе выигрыш только элизия кадра (механика п. 7). *Статус:* сделано иначе. Кэш на замыканиях не нужен и вреден: арность лежит в одном load от fn-узла, а любой retained-ключ образует циклы (exec → fn → exec) и пришпиливает пользовательский код к immortal-exec'ам core — вместо него прямой вход в тело (аргументы сразу в кадр callee). Протокольный кэш — 4 записи `{тип, impl, арность}` по serial метода и эпохе, impl'ы borrowed под seqlock. Натив в голове зовётся из буфера сайта напрямую. Бенч: closure call −28 %, protocol call −20 %.
6. [x] **Трансдьюсеры → IReduce → fusion.** Предусловий сегодня нет: ни трансдьюсерных арностей, ни `reduced`, ни IReduce (`reduce` ходит через `seq`). Порядок: трансдьюсеры и `reduced`/`transduce`/`eduction` — семантика; IReduce-быстрый путь (`reduce` по vector/range итератором без seq-объектов — крупный выигрыш сам по себе, chunked seqs рядом); проход optimizer'а: `reduce`/`into`/`vec` над пайплайном `map`/`filter`/… → `transduce (comp …)`, один раз на форму, переживает сериализацию; композиция без захвата локалов кэшируется в exec-узле — по инварианту побочных ячеек (NOTES, evaluator): CAS-заполнение, победитель immortal до публикации, проигравший освобождает копию до публикации, leak ограничен числом форм. Барьеры (`sort`, `group-by`) режут пайплайн — ожидания калибровать по этому. *Статус:* сделано; кэш композиции не понадобился — `comp` не строится, C-драйверы (`fused-reduce*`/`into*`/`count*`) применяют стадии из вектора, а `(xf rf)` обязан быть свежим (stateful-трансдьюсеры). 2-арный `reduce` не через `eduction` (тот сидирует `(f)`, ленивый — первым элементом). Guard — таблица boot-корней core-варов в `fusion.c`, узел `[:fused …]` хранит оригинал для фолбэка. `partition-all` из стадий исключён (векторы vs seq'и). Бенч: pipeline 182 → 30 нс/элемент.
7. [x] **Прямой вызов локальных функций.** `let`-связанные, не убегающие (только в позиции головы, не захвачены, не переданы) — escape-анализ внутри формы. Не текстовый инлайн, а вызов тела без создания замыкания и без `clj_invoke`: без роста кода и проблем с рекурсией. Вар не участвует, отзывать нечего. Реальные случаи: `letfn`, макро-сгенерированный код (`for`, `doseq`, destructure). *Статус:* реализовано (static link + узлы `DIRECT_FN`/`DIRECT_CALL`/`OUTER`), в обоих бэкендах. Пересмотр после появления `for`/`doseq`/`letfn` сделан замером по core.clj, встроенным библиотекам и обоим корпусам: из 68 `let`/`loop`-связанных `fn*` прямыми стали 20 (10 в core.clj, 1 в medley, 9 в тестах набора, 0 в библиотеках), 48 остались замыканиями (18 зовут себя из-под `lazy-seq`, 18 захвачены внутренним замыканием, 12 переданы значением, вариадических нет). Хелперы самих конструкций правило не проходят или их нет: `iter` у `for` зовёт себя из-под `lazy-seq`, `doseq` и destructure раскрываются в `loop`/`let` без fn, `letfn` связывает fn через volatile-ячейки, и ни одна не становится init'ом `let`. Буквально условие отката выполнено, но его посылка («выигрыш только на синтетике») устарела: прямым стал `up` в `update-in`, и `update-in` по пути из 3 ключей с проходом на 6.7 % быстрее, чем без него (CPU-время, медиана 21 парного прогона, квартили −10.9…−2.5 %); остальные прямые — `tf` в `derive` (в шуме), `root-bind` в `with-redefs-fn` и макро-хелперы, исполняемые при каждом раскрытии (`psig` в `fn`, `emit`/`do-mod`/`to-groups` в `for`, `step` в `doseq`, `emit` в `condp`, `var-ize` в `binding`); синтетика — −38 % на цикле с локальным хелпером. Откат к тому же уже не дешёвый: узлы читают facts, сводки, liveness, кодек и компилятор (эмиссия прямых fn, `clj_c_outer`, promoted-слоты, инлайн листа). `letfn` → прямые fn сделать корректно можно (форма `letfn*` со всеми именами в области до init'ов; наибольшая неподвижная точка — все fn прямые, понижается fn с непрямым использованием или вызываемая из тела понижённого соседа; понижённые остаются на ячейках, у прямых пропадает цикл через ячейку), но потребителя нет: все 7 `letfn`-fn обоих корпусов убегают (2 передаются значением, 2 зовут себя из-под `lazy-seq`, 1 захвачен `defn`, 2 вариадические), так что `:second-run-live-objects` не сдвинулся бы. Решение: не откатывать и не переделывать `letfn`; триггер `letfn*` — `letfn`, чьи fn только вызываются, в профиле (NOTES "Direct local fns").
8. [x] **Специализация по фактам** — `INTRINSIC_ADD → ADD_LONG` по наблюдённым типам, self-optimizing rewrite в exec-узле с guard'ом, не в `clj_node`. В интерпретаторе даёт мало (tag-check ~1 нс из 3, доминирует диспатч) — по профилю, не раньше.

- **Дескриптор:** `core_bits` и `user_protos` — поля с первого дня, чтобы `defprotocol` не менял layout.
- **Одно дерево узлов** у интерпретатора и компилятора — ради PE-подхода и общего механизма self-optimizing узлов.
- **Оптимизатор — отдельный проход над AST с фактами**, не размазанный по бэкендам: иначе e-graphs потом не вставить.
- **Интринсики — одна таблица C-функций**, из которой генерируются tag-switch компилятора, шаблоны copy-and-patch и слоты дескрипторов (дифференциальный тест поверх).
- **Формат dev-профиля** — с первого дня (типы на сайтах, shapes, реализации протоколов, горячие ветки); потребители: PGO-guard'ы, field reordering, BOLT.
- **Эпохи** варов, протоколов и shapes — единый механизм инвалидации кэшей.
- Не завязывать оптимизатор на C-специфичное — дверь в MLIR.
