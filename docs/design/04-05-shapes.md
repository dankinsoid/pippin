### Представление по наблюдению: shapes, tuples, elements kinds
**Мотивация.** 90% мап в Clojure-приложении — `{:id 1 :name "x"}` на 3–8 keyword-полей, то есть Swift-struct, а не словарь. Swift-struct: поле 0.3 нс, мутация — запись в слот. `PersistentArrayMap` (≤8, линейный скан `identical?` по интернированным keyword) уже неплох, но это линейный поиск + бокс + отдельный массив.

**Shapes** (hidden classes: Self 1989 → V8/SpiderMonkey/JSC, Ruby 3.2 object shapes, Truffle OSM, PyPy maps, key-sharing dict в CPython; иммутабельный прецедент — Erlang flatmaps: разделяемый keys-tuple, порог 32 ключа, дальше HAMT):
- Мапы с одним набором ключей делят объект Shape (ключи + индексы); в мапе — указатель на shape и значения inline. Одна аллокация, одна кэш-линия.
- Дерево переходов: `∅ --:id--> S1 --:name--> S2`. Литерал, цепочка `assoc` и JSON-парсер идут по одним рёбрам → один shape → мономорфный call site. Shape строится по ходу парсинга, generic-мапа не создаётся ни в первый раз, ни потом; со второго раза стоимость на ключ — intern строки в keyword + сравнение указателя в таблице переходов (обычно один элемент).
- Inline cache на call site: `(:name m)` → `if m.shape == cached → values[idx]`, ~1–2 нс. Полиморфный (2–4) → switch; мегаморфный → generic. В интерпретаторе кэш на узле AST; в компиляторе — статически из PGO-профиля; при статически известном shape (литерал, flow-типизация, схема) — прямое смещение без проверки. Layout детерминирован (порядок ключей — `compare`, не порядок построения), поэтому индекс ключа и таблица переходов `assoc`/`dissoc` считаются при компиляции без рантайм-состояния; проверяется только то, что значение не ушло в trie (33-й ключ, не-keyword, мета, словарный shape) — guard одним сравнением, медленный путь — обычный lookup. Известный shape + не убегает = мапы нет вообще: поля становятся локалами и регистрами (scalar replacement), и отложенный вопрос unboxed-полей на общем shape'е здесь не возникает.
- Unboxed поля по наблюдению (V8 field representations): `:count` всегда int64 → слот без бокса, проверка при записи. *Отложено (2026-10-07, NOTES «Shapes»):* у целых выигрыша нет — fixnum и так лежит в слове слота; выигрыш только у double, а наблюдение «всегда double» на shape'е, общем для всех мап с этим множеством ключей, либо делит множество ключей на shape по представлению (ломает «один shape на множество ключей»), либо требует тега в каждой мапе; `(:x m)` в боксовом контексте тогда аллоцирует бокс вместо retain — хуже базы, — а потребителя сырого double нет: в решётке нет факта значения мапы. Триггер — shapes в решётке фактов с видом слота.
- `assoc` при rc==1 — запись в слот; `(update m :count inc)` — буквально `m.count += 1`. При rc>1 — копия массива (≤32 слотов — одна кэш-линия, = один HAMT-узел).
- `defrecord` = именованный, заранее объявленный shape с гарантиями (opt-in: лишнее поле — ошибка). Один механизм вместо двух. У records свои углы (`dissoc` → мапа, `(= record map)` → false); shapes дают ту же скорость без них.
- Семантика неизменна: это мапа. `=` и `hash` структурные (одинаковый shape → сравнение массивов напрямую), `seq` в порядке shape (у hash-map порядок и так не определён); не-keyword ключ, nil-ключ, метаданные → generic.
- Интероп: shape = layout Swift-struct; `Codable`-энкодер получает shape по типу один раз и заполняет слоты.
- Не убегающая shape-мапа известной формы с unboxed полями на стеке (§7) = Swift-struct на стеке. Слои сходятся.

**Ограничения shapes:**
- ≤32 ключей (branching factor HAMT; линейный скан по указателям быстрее хэша до 32; копия — одна кэш-линия). Порог 8 у Clojure — про стоимость `equals` на JVM, у нас сравнение указателей.
- Не-keyword ключ → сразу generic.
- >8 различных детей у shape'а → shape «словарный», все мапы через него → HAMT. Это детектор динамических ключей (`{user-id → user}`).
- Потолок shape'ов на процесс (десятки тысяч); shape'ы интернированы и живут вечно.
- Порядок ключей: `{:id :name}` и `{:name :id}` — разные пути; канонизация при финализации по множеству ключей (кэш key-set → shape, O(k log k) один раз).
- Переход в HAMT односторонний и незаметный; обратно — никогда.

**Tuples.** Вектор фиксированного размера 2–6 с элементами inline: одна аллокация, `nth` — load по смещению без shift и хвоста, слоты могут быть unboxed (`[x y]` точки = два double). Литерал `[x y]` → tuple2, деструктуринг → два load, `conj` за ёмкость → промоушен в вектор. `MapEntry` = tuple2. Clojure JVM пробовал (1.8-alpha) и откатил из-за мегаморфных сайтов у HotSpot — у нас JIT'а нет, диспатч статический или tag-switch, аргумент исчезает. Ещё лучше — не аллоцировать пару: `(map (fn [[k v]] …))` после fusion передаёт `k v` двумя аргументами; `(seq shape-map)` отдаёт entries из (ключ shape, слот) лениво/на стеке; `(let [[a b] (f x)])` с известной формой — два возврата в регистрах.

*Сделано (2026-10-07, NOTES «Vector»):* кортеж — вторая раскладка того же типа `vector`, как shape у мапы: 1–6 элементов inline одной ячейкой (`clj_vector_from_array` — литерал в обоих бэкендах, reader, `vector`, каждый map entry), раскладку различает `shift = 0` в теле объекта, а не флаг заголовка (rc.c затирает заголовок мёртвого объекта до `each_child`). `conj` на `[]` строит trie, как раньше: `into`, `vec`, трансиенты начинаются там, и кортеж им дал бы только промоушен на седьмом элементе; `conj` в полный кортеж — промоушен в trie, односторонний. Пара — 56 байт против 104, создание с деструктурингом в скомпилированном коде вдвое дешевле (bench/RESULTS.md «Tuples»). Unboxed-слоты кортежа — по той же причине, что elements kinds ниже; не аллоцировать пару (fusion, два возврата) — работа компилятора, отложена с триггером.

**Векторы — elements kinds (V8).** Все int64 → unboxed `int64[]`, double → `double[]`, смешанные → boxed; переходы односторонние по наблюдению при записи. Это `vector-of :long`, только выведенный. *Отложено (2026-10-07, оценка в NOTES «Vector»):* у целых выигрыша нет — fixnum уже лежит в слове слота, `int64[]` не экономит ни байта, ни аллокации; выигрыш только у double (32-байтный бокс на элемент). Цена — заём в `clj_vector_nth` (+0, 156 вызовов): double-листу нечего одолжить, и либо все вызовы переходят на владеющий результат, либо чтение аллоцирует бокс — хуже базы, что запрещает общий принцип ниже; потребителя сырого double нет — в решётке нет факта элемента вектора. Триггер — факт элемента в решётке или первый `(vector-of :f32)` для Metal; до тех пор горячий цикл по double берёт `double-array`.

**Плоское представление по линейности (2026-10-09).** Сверх представления по наблюдению — представление по владению: вектор как плоский массив с push на месте, мапа с не-keyword ключами как open-addressing таблица с одной пробой, вместо trie с прыжками по узлам. Чем платит плоское — worst case: `assoc` на разделённом значении у trie O(log n) с копией пути, у плоского O(n) и n retain'ов боксовых детей. Поэтому допустимо в трёх случаях: уникальный владелец доказан (факты владения и последнего использования, межпроцедурно — те же, что для reuse и регионов, §7) или проверен (rc==1 на каждой операции, как `Array`/`HashMap` Lean 4); элементы unboxed (копия — memcpy без retain'ов; elements kinds); размер ниже порога, где memcpy дешевле копии пути (кортежи ≤6 уже так, вектор ≤32 — голый хвост). Переход односторонний и незаметный, как shape → trie: плоское под порог с fallback в trie при первом разделении выше порога; `vector?`, `=`, `hash` не меняются. Явные двойники есть — `transient`, `vector-of`, массивы (§3). Ближайший выигрыш — не в компиляторе: строители core (`into`, `frequencies`, `group-by`, `reduce` с `conj!`) линейны по построению и уже на трансиентах; трансиент мапы как плоская таблица, а `persistent!` без O(n) конверсии под порогом — правка рантайма для обоих режимов. Делать по переписи аллокаций (§7 «Убегание относительно скоупа»).

*Сделано для мапы (2026-10-10, NOTES «Map»):* трансиент мапы — третья раскладка того же типа, open-addressing таблица в порядке вставки, правится на месте при любом счётчике по контракту трансиента; `persistent!` до порога 16 (замер: копия плоской при разделении не дороже копии пути trie до 16 записей) отдаёт ту же таблицу, выше — trie, один раз O(n); только keyword-ключи возвращаются в shape по переходам. Посылка «строители уже на трансиентах» была неверна: `transient` был тождеством, `frequencies`/`group-by` — персистентным `assoc` по заимствованному аккумулятору, то есть копией пути на каждом шаге; теперь они на трансиентах, как на JVM. Не сделано: трансиент над большим trie (edit-токен JVM), сеты, вектор.

**Списки — ничего. Сеты** — ≤8 линейный массив, дальше HAMT; битовая маска только для статически известного keyword-универсума (литеральные сеты, enum) — оптимизация компилятора, не рантайма.

**Отвергнуто: SoA/колоночное хранение вектора мап одного shape'а.** `nth` обязан вернуть мапу — материализация или row-view, то есть третье представление мапы во всём рантайме; `assoc-in` одной ячейки — копия столбца O(n) или персистентные столбцы (и скан уже не плотный); `assoc` мапой другого shape'а → демоушен O(n), thrashing на границе; row-view снаружи держит весь вектор; паттерн доступа в UI строчный; fusion над AoS добирает половину выигрыша (слот по смещению в каждой строке). Место SoA — явный тип dataset/columnar (Arrow, tech.ml.dataset), не неявное представление `vector`.

**Общий принцип.** Представление выбирается по наблюдению, переходы односторонние, семантика неизменна. Критерий допустимости «магии»: никогда не хуже базы (медленный путь = сегодняшний HAMT, не deopt-обрыв как в V8); состояние инспектируемо (`(shape-of m)`, метрика моно/поли/мегаморфных сайтов в dev, размер дерева переходов); стоимость операций предсказуема. Fusion, reuse, регионы, shapes проходят; SoA — нет.

**Почему Clojure JVM так не делает.** Нет своих call site'ов (`(:name m)` → `Keyword.invoke` → `ILookup.valAt`, HotSpot кэширует класс, не shape); нет unboxed-слотов без Valhalla; GC делает аллокацию дешёвой; философия «знаешь ключи — `defrecord`», без скрытого глобального состояния; консерватизм core (структуры не менялись с 1.0). У нас все три технических условия есть: свои сайты, unboxed-слоты, дорогая аллокация как мотив.
