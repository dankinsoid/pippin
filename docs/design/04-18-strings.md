### Строки: UTF-8, индекс в code points (решено 2026-10-10)
**Хранение — UTF-8.** Весь внешний мир в UTF-8: исходники, файлы, сеть, JSON, POSIX, C-заголовки; строка уходит в C указателем на байты (`clj_string_bytes`, NUL в конце), без перекодирования. UTF-16 выбрали в 90-х Java, JS, Windows и Cocoa, когда считали, что 16 бит хватит на весь Юникод; он вдвое дороже на ASCII и такой же переменной длины, как UTF-8 (суррогатные пары), так что обещанного O(1) не даёт. Swift ушёл с UTF-16 на UTF-8 в Swift 5 по тем же причинам; JVM с Java 9 хранит Latin-1-строки по байту на символ (compact strings).

**Единица индекса — code point** (`count`, `subs`, `nth`, `index-of`, `char`, `seq` строки). `(count "😀")` — 1, `subs` не режет суррогатную пару, `char` — Unicode scalar (тег `110`, §4 «Представление значений»). Выбор из трёх:
- *единицы UTF-16, как JVM и cljs* — отвергнуто: `(subs "😀" 0 1)` на JVM даёт одинокий суррогат, а он невалиден в UTF-8. Воспроизвести это честно — только WTF-8 (UTF-8 с разрешёнными одиночными суррогатами, `OsString` в Rust, движки JS) и проверка с починкой на каждой границе с C, файлами, сетью, NSString: портить своё представление ради чужого бага;
- *графемы, как `Character` в Swift* — отвергнуто для core: разбиение требует таблиц свойств Юникода (на порядок медленнее), число графем меняется между версиями Юникода (недопустимо для `count`), расхождение с Clojure наибольшее. Графемы — библиотекой поверх того же представления (обрезка текста в UI, счёт символов для человека);
- *code points, как Python 3, `chars()` Rust, `unicodeScalars` Swift* — взято: самая быстрая из трёх (длина — счёт байтов не вида `10xxxxxx`, векторизуется), убирает половину класса «эмодзи пополам». Вторую половину (👨‍👩‍👧 — 5 code points, флаг 🇺🇸 — 2, разложенное `é` — 2) закрывают только графемы.

Это расхождение с JVM *и* с cljs (там строки JS, тоже UTF-16), то есть за пределом §3 «Предел расхождения — ClojureScript», и причина наша: хранение UTF-8, при котором семантика UTF-16 требует WTF-8. Видно оно только на символах вне BMP (эмодзи, редкие CJK). Третье сознательное расхождение после ленивых `def` (§4 «Var и ленивые def») и раскрутки брошенной корутины (§7). `jvm-hash` остаётся совместимым — он и так считается по единицам UTF-16; дифференциальный фаззер исключает из сравнения с JVM строки вне BMP по этому правилу.

**На границе с Apple индексы UTF-16** (`NSRange`, `shouldChangeCharactersIn`, `NSAttributedString`; LSP по умолчанию тоже): мост переводит code points ↔ UTF-16 одной функцией на тех же закладках (ниже).

**Со Swift — те же байты, не тот объект.** Нативная Swift-строка тоже UTF-8, но объект другой: 16-байтная структура со словом флагов и указателем на `__StringStorage` (свой заголовок Swift-объекта с атомарным счётчиком, `count`/`capacity`, флаги `isASCII`/`isNFC`, байты, хвост breadcrumbs); до 15 байт — прямо в структуре. Раскладка хранилища — внутренность stdlib, не ABI, и публичного способа обернуть чужие UTF-8 байты без копии нет. Поэтому через мост строка едет копией байт без перекодирования (§5 «Конверсия»); для ASCII это чистый `memcpy`, наша маленькая строка становится маленькой Swift-строкой без аллокации с обеих сторон. Без копии — только через свой подкласс `NSString`, отдающий указатель на UTF-8: Swift оборачивает его лениво, но каждая операция над такой строкой идёт через ObjC. Делать — если профиль реального экрана покажет копирование строк на границе, тот же триггер, что у остальной цены границы (§9). Индексы UTF-16 — не свойство Swift (у него `String.Index`), а API Foundation и UIKit, унаследованный от NSString; Swift сам переводит их по breadcrumbs (`Range(nsRange, in:)`). Перевод code points ↔ UTF-16 нужен только там, где через границу едет число-индекс, и для ASCII-строки он тождественный.

**Как целый индекс остаётся дешёвым.** Swift прячет целый индекс (`String.Index` — байтовое смещение из прошлого прохода, `index(_:offsetBy:)` — O(n)); Clojure не может, `count`/`subs`/`nth` — его API. Поэтому:
- *флаг ASCII в заголовке*, ставится при создании (байты всё равно копируются): индекс = смещение, `count` = `len`, всё O(1) — подавляющее большинство строк (ключи, идентификаторы, числа, JSON, CSV);
- *длина в code points* — один проход, кэш рядом с хэшем тем же механизмом ленивой публикации;
- *ленивые закладки* у не-ASCII строки длиннее порога (~64 байта): массив байтовых смещений каждого 64-го code point, строится при первом индексном доступе; индекс → закладка + скан ≤64, байт → индекс (позиции `index-of`, регулярки) — бинарный поиск. Строка неизменяема, кэш всегда корректен; у разделённой публикуется атомарно, как хэш. Breadcrumbs Swift — тот же приём, у него для UTF-16-вида моста с NSString.

**Маленькие строки — в значении, без указателя.** Тег `100` свободен: 3 бита длины и до 7 байт UTF-8 в слове (`NSTaggedPointerString` у Apple; сжатые 6- и 5-битные кодировки до 11 символов — вторая ступень, по замеру доли строк 8–11 байт). Ни аллокации, ни RC, ни освобождения; `=` — сравнение слов; `hash` из слова. Покрывает числа строкой, токены `split`, короткие ключи и коды. Цена — ветка в каждой строковой операции и то, что у маленькой строки нет указателя на байты: прямой доступ к `bytes` (сотни мест в C) переводится на API «одолжи байты» с буфером на стеке у вызывающего, и прямое чтение поля становится ошибкой компиляции — тот же приём, что у слотов (`object.h`). `identical?` на равных маленьких строках даёт true; в Clojure на строках он и так не гарантирован. Порядок: сначала единица индекса и флаг ASCII, потом API заимствования, потом тег.
