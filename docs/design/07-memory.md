## 7. Память

### RC vs GC — честно
- Для аллокационно-тяжёлого функционального кода **GC быстрый**: bump-аллокация, nursery-сборка ∝ живым объектам, никаких записей в счётчики. Наивный RC — самая медленная схема. Perceus/Lean хвастаются «скоростью GC», потому что до них RC до неё не дотягивал; обгоняют за счёт reuse. Цена GC — память 2–5× и паузы.
- **Rust быстр не потому, что освобождает, а потому, что не аллоцирует.** Rust на `im` (Arc-HAMT) в 10–50× медленнее `Vec`. Разрыв с идиоматичным Rust — свойство модели данных, не памяти. Закрывается там, где анализ превращает персистентную операцию в мутацию.
- Честная цель: там, где линейность доказана — Rust; где данные разделяются — паритет с любым языком на тех же структурах; не проиграть GC на промежуточных аллокациях за счёт аллокатора и reuse.

### На каждое значение три вопроса (ARC отвечает на все в рантайме самым дорогим способом)
1. **Убегает ли?** Нет → регион/стек, без счётчика. Да → heap.
2. **Единственный ли владелец?** Да → reuse/мутация. Нет → копия пути.
3. **Пересекает ли поток?** Нет → неатомарный. Да → атомарный.

Escaping — главная проблема для *потока управления*; для *данных* главная — sharing (32 retain — это вопрос 2, не 1).

### Что убирает анализ без аннотаций (Perceus / Lean 4 «Counting Immutable Beans»)
- **Borrow inference:** параметр только читается → +0. Убирает большую часть ARC на вызовах. Параметр утекает в результат → owned; вызывающий на последнем использовании → consume. Это и есть «inout»: `x = f(consume x)` — указатель вошёл, указатель вышел, счётчик не тронут.
- **Точные drop/dup** в точке последнего использования — то, что делает рантайм-проверку `count == 1` *успешной*, а не *ненужной*. Koka/Lean уникальность не доказывают, они ставят проверку (одна загрузка + сравнение) и следят, чтобы счётчик был 1.
- **Reuse:** проверка на каждом узле пути (не только корне) — мутируем до первого разделённого узла. Точнее transient'ов с edit-token; в компилированном коде transient'ы почти не нужны.
- **Escape analysis:** локальный для замыканий (переданы в известный интринсик → не убегают, O(1)); межпроцедурно — одна bottom-up проходка по графу вызовов (Go делает это на каждой компиляции). Дефолт — «убегает».
- **Регионы (Tofte–Talpin, MLKit, не Google ML Kit):** bump-аллокатор на скоуп, сброс при выходе, объекты без заголовка. Не убегающая копия узла заимствует детей — memcpy 10 нс без единого retain. Инвариант: heap-узел никогда не указывает на региональный; `original` переживает регион. Ловушка region leak в циклах → сброс на итерации `loop/recur` или fallback на RC. Промоушен в heap на неизвестной границе — консервативно или явно на выходе.
- **Стек:** для не убегающих объектов фиксированного маленького размера (бокс, замыкание с k захватами, tuple); регион — для не убегающих любого размера; куча — для убегающих. Порог из-за стека iOS (main 1 МБ, фоновые 512 КБ, корутины 64 КБ) — `alloca` переменного размера опасен. RC на стековом объекте — no-op: компилятор inc/dec не эмитит, флаг `stack` в заголовке — страховка. Интерпретатору недоступно. На таблицу бенчмарка (§4) не влияет — там результат `assoc` и есть выход замеряемой операции; относительно скоупа вызывающего это не так (ниже, «Убегание относительно скоупа»). Лучше стека — регистры (unboxed скаляры).

Лестница: fusion убирает временное совсем → регион делает временное бесплатным → reuse делает линейное мутацией → RC только на том, что живёт в двух версиях одновременно. Аннотации (`^:linear`) — только как гарантия, не как условие.

### Убегание относительно скоупа (2026-10-09)
Убегание — всегда *откуда*. Результат `assoc` убегает из функции, которая его вернула, но у вызывающего может не убегать: стек вызовов — вложенные скоупы, и регион вешается на любой из них. Для этого анализ межпроцедурный, снизу вверх по графу вызовов (как в Go): факт «свежесть результата» (§3) у `f` позволяет вызывающему положить результат `f` в свой регион. По-настоящему убегает только то, что покинуло стек: записано в атом/var/канал, захвачено сохранённым замыканием, опубликовано другому потоку. Для состояния приложения это итоговая версия после обработчика события; промежуточные — нет.

Внутри одного стека регион и reuse делят работу:
- **Накопление в цикле** (`reduce` с `assoc` на миллион шагов): старые узлы умирают на каждом шаге, в регионе они не умирают до сброса — это region leak. Здесь работает reuse при rc==1 (старая версия ничья, узел переписывается на месте, ноль аллокаций); регион со сбросом на итерации `loop/recur` — страховка, не инструмент.
- **Две версии живы одновременно** (diff, undo, сравнение): reuse невозможен, копия пути неизбежна, и регион — единственный способ снять её цену: копия узла — memcpy без единого retain детей, потому что дети заимствованы, пока жив скоуп.

Два ограничения остаются: неизвестная граница (хост, невидимая реализация протокола, переопределяемый var) — по умолчанию «убегает», закрытый мир таких границ оставляет мало (§9 «промоушен»); инвариант направления — heap-объект никогда не указывает на региональный, значит региональное значение, ушедшее в `reset!`, копируется в кучу в точке выхода.

Отсюда метрика для переписи аллокаций: не «умер ли объект в той же функции», а на какой глубине относительно кадра рождения он умер — внутри кадра, в вызывающем, выше, или пережил стек. Она показывает, какую долю закроет межпроцедурный регион, какую — reuse, а какая действительно уходит в состояние.

### Perceus и Lean 4: что взято техникой (2026-10-09)
Принцип (drop на последнем использовании, borrow inference, reuse при rc==1) взят выше; техника — по замеру на корпусе (§6b «Статус по замеру»): 38–51 % времени — аллокация и освобождение, из них каскад освобождения 12–29 %, и fn с lazy-seq аллоцируются один к одному.
- **Drop specialization.** У каждого типа свой inline drop вместо обобщённого обхода `each_child` с колбэком: дети-fixnum, keyword'ы и immortal пропускаются без декремента, объект без heap-детей уходит в free-list без обхода, последний ребёнок — хвостовым вызовом или итеративно. `each_child` остаётся сборщику циклов и отладке. Рантайм, оба режима.
- **Reuse по size-class, не по типу.** Умерший узел мапы годится под узел вектора того же размера; прямой reuse минует и free-list. Рантайм.
- **Drop-guided reuse для любых объектов**, не только коллекций: в точке, где умирает объект, а следом рождается объект того же размера, компилятор отдаёт ячейку вместо free+alloc. `map` над seq — входная ячейка умирает, выходная рождается; то же cons, замыкания, lazy-seq. Компилятор, проход над AST с фактами последнего использования до эмиссии C — не правило генератора.
- **Reuse specialization:** при переиспользовании пишутся только изменившиеся поля — `(cons (f x) rest)` поверх умершей `(cons x rest)` — одна запись в head, tail как лежал. Для shape-мап при rc==1 уже так.
- **Destructive match:** деструктуринг уникального значения переносит поля, а не retain'ит: `(let [[a b] pair] …)` на кортеже с rc==1 — два move, кортеж освобождён без retain'ов детей; то же `{:keys […]}` на shape-мапе. Компилятор.
- **Слияние dup/drop внутри тела:** `retain x … release x` без возможного освобождения между ними сокращаются; на вызовах уже +0 (§6b п. 3), внутри тел — нет. Компилятор.
- **Frame-limited reuse** (Lorenzen, Leijen 2022): reuse-токен живёт только в своём кадре, иначе память держится дольше нужного — та же дисциплина, что сброс региона на итерации.
- **TRMC** (tail recursion modulo cons, Koka): строгий строитель seq'а компилируется в цикл, дописывающий в хвост предыдущей ячейки. После fusion, для строгих строителей.
- **Ячейка lazy-seq без отдельного fn-объекта:** thunk — указатель на C-функцию и захваты в самой ячейке; после реализации обнуляется, как сейчас. По счётчикам — минус 16–23 % аллокаций на dependency, pipelines, combinatorics. Оба режима, если интерпретатор может положить замыкание inline дёшево; иначе — компилятор. *Сделано в обоих:* ячейка одна, слот `owner` различает thunk'и — fn, exec интерпретируемого дерева (рядом узел fn) или nil (рядом C-функция); интерпретатор выбирает для сайта свою запись exec-таблицы, дерево не меняется (NOTES "An interpreted `lazy-seq` site").

*Статус drop-guided reuse (2026-10-10):* сделан в компиляторе (dev и closed одинаково) отдельным проходом над кадром до эмиссии (NOTES "Compiler", «Drop-guided reuse»): `cons` строится в ячейке умирающего значения слота (токен живёт между двумя соседними операторами кадра — frame-limited), `cons` поверх умершей `cons` не трогает поля, которые остаются теми же (reuse specialization), `next`/`rest` последнего использования шагают уникальным vector-seq/range/string-seq на месте. Разделённое, бессмертное, ссылочные типы, финализируемое и стоящее в буфере кандидатов ячейку не отдают; `-DCLJ_NO_REUSE` выключает всё. Предел — конвенция +0: аргумент вызываемому не принадлежит, поэтому пары, которые нашла перепись (каскад освобождения в `concat`, копии мап в `update-in`), кадру не видны; их забирает borrow inference (`-O2`), не этот проход. Destructive match и слияние dup/drop не сделаны.

**Владеющие параметры — следующий рычаг reuse (2026-10-10).** По конвенции +0 (§6b п. 3) аргумент передаётся взаймы: ссылку держит вызывающий и отпускает после возврата. Поэтому `(defn step [s] (cons (inc (first s)) (rest s)))` не может отдать ячейку `s` под новый `cons`, даже когда у вызывающего это было последнее использование и rc==1: ячейка принадлежит вызывающему, и он отпустит её позже — use-after-free. То же `update-in`: `assoc` на заимствованном `m` копирует путь, который никому не нужен. Перепись аллокаций показала, что именно здесь пары reuse: 80 % объектов умирают на кадр и больше выше рождения, пары `cons` в dependency (82 %) — смерти в каскаде освобождения, копии мап nested-update — `assoc` на заимствованном параметре.
- *Почему +0 по умолчанию остаётся.* Большинство параметров только читаются; для них +0 — ноль операций со счётчиком на вызов, а +1 стоил бы retain у вызывающего (если значение ему ещё нужно) и release в конце вызываемого — чистые потери. Цена считается на вызове функции, а не на чтении внутри: `(:name user)` сам счётчик `user` не трогает ни при какой конвенции.
- *Решение — вывод владения по параметру* (Lean 4, «Counting Immutable Beans»): параметр *владеющий* (+1), если функция его потребляет — возвращает, сохраняет в структуру или на последнем использовании у неё есть пара для reuse; иначе заимствованный. На вызове владеющего: последнее использование у вызывающего — ссылка переходит без операций со счётчиком, внутри rc==1 и токен срабатывает; значение вызывающему ещё нужно — один retain, внутри rc==2, токен не срабатывает, результат верен.
- *Где известна конвенция вызываемого.* В закрытом мире — выводом снизу вверх по графу вызовов (межпроцедурный фикс-пойнт, `-O2`). В dev вар переопределяем, и вызов идёт через `clj_invoke` — поэтому две точки входа (worker/wrapper, как для unboxed, §6): обобщённая с +0 и прямая с выведенной конвенцией; обёртка делает retain и зовёт рабочую. Билтинам это частично уже дано — потребляющие интринсики получают коллекцию с последнего использования; не хватает пользовательских функций и функций `core.clj`, скомпилированных как обычные (`update-in`, `assoc-in`).

*Статус (2026-10-12):* сделано в компиляторе, dev и closed (§10 шаг 7в, NOTES «Compiler», «Owned parameters»). Вывод — по набору до эмиссии и без отдельного `-O2`: компилятор и так видит весь набор, а dev получает ту же маску через вторую точку входа под стражем корня вара. Отличие от Lean: «сохраняет в структуру» владения не даёт — наши конструкторы (литералы, `conj` элемента) делают retain своих входов, выигрыш только там, где ссылка действительно переходит. Добавлен поздний take: коллекция потребляющего интринсика, которую позже читает ещё один операнд, забирается в момент вызова. Предел, который осталось снять, — ребёнок, которого держит родитель: `(assoc m k (f (get m k)))` правит `m` на месте, но `(get m k)` оставляет ребёнку rc 2, и внутренний уровень копируется; лечит это take-out `get` (Lean `modify`), а не владение.

*Статус take-out `get` (2026-10-12):* сделан в компиляторе, dev и closed (NOTES «Compiler», «Owned parameters»). `get` слота, значение которого `assoc` того же слота кладёт обратно по тому же ключу, вынимает ребёнка +1, если уникальны и не опубликованы родитель (мапа, в том числе transient, или вектор), узлы пути и сам ребёнок: в записи до `assoc` лежит nil, кэш хэша сброшен. Форм две: `get` в операнде значения `assoc` с поздним take (уровни `update`, `update-in`, `assoc-in`) и `get` в init `let`, чьё тело читает слот последним в `assoc` (`assoc!` после инлайна — `group-by`). Дыру не видит никто: от `get` до `assoc` слот не читается ничем, кроме самого `assoc`, он мёртв после него и не читается обработчиками, так что throw или ветка мимо `assoc` оставляют родителя на освобождение; разделённый или rc>1 родитель, узел или ребёнок — обычный `get` в том же поиске. Страж `assoc` читается в `get`, до дыры: вынутое кладёт обратно встроенный `assoc`, переопределение `assoc` кодом самого f видно со следующего вызова — как в JVM, где корень читается до операндов. Интерпретатору не дано: позднего take в нём нет, родитель там и так копируется. Выключатели — `CLJ_NO_OPT=owned` и `reuse`. Замер (bench/RESULTS.md «Take-out get», прогоны 38270897697 против 38270902667): nested-update вынимает 200k значений за итерацию, 167k из 366k копий мап и 318k из 404k копий узлов стали правкой на месте, аллокаций −37 %, plain RC −57 %, closed/JVM 2,0 → 1,4×; векторы `group-by` растут на месте (group-freq 50k, pipelines 75k, medley 20k за итерацию). Остаток nested-update — let-слоты развёрнутого `get-in` чтения, державшие мапу пользователей до следующего связывания, — снят отпусканием мёртвых слотов (ниже, «Мёртвые слоты»).

*Мёртвые слоты (2026-10-12).* Слот кадра держал значение до перепривязки или выхода, если последнее чтение его только заимствовало (карта `get`, `count`, тест `if`, аргумент вызова): отпускание шло лишь при передаче (метка последнего использования, поздний take, владеющий параметр), перепривязке и teardown. Посылка задачи «чтение в одной ветке, другая ветка не отпускает» — частный случай: слот задерживался при любом заимствующем последнем чтении, с ветками и без; метки liveness верны, не хватало отпускания в плане слотов. Теперь reuse.c при разметке ставит drop там, где владеемый слот умирает: на входе ветки (умершее в тесте и читаемое только другой веткой), после записи связывания `let`/`loop` (умершее в init и сам слот, если его никто не читает), после тела `let`/`loop` (кроме хвоста кадра), после элемента `do`, перед перепривязкой `recur`. Слот, который заимствует ожидающий операнд объемлющего вызова, отпускается после вызова; то, что забрали take, передача или `next`/`rest`, отпускать нечего. Отпускается раньше только коллекция или seq ядра (`clj_c_drop` смотрит тип): их правит update на месте, а любое другое значение живёт до конца области, как в интерпретаторе, — хост может держать его без retain (делегат Cocoa слабый: в фикстуре objc безусловный drop освободил reify-делегата `NSXMLParser` до `parse`). Отпускание только переносится раньше, лишнего нет: после drop в слоте nil, перепривязка и teardown отпускают nil; ставится лишь там, где слот мёртв на всех путях (обработчики и `finally` держат читаемое живым всё тело `try`, внешний слот цикла жив через `recur`). Отладочная сборка проверяет план прямым проходом (`clj_verify_drops`, NOTES «Internal errors», инвариант 11). Интерпретатору выигрыша нет: вызовы +0 и take-out нет, родитель с детьми там копируется, держит ли слот ребёнка или нет, — он не менялся. Выключатель — `CLJ_NO_OPT=drop`. Цена компиляции: core.c +0,33 % байт, clang `-O0` в разбросе хоста, `-O2` +1,7 %. Замер (bench/RESULTS.md «Dead slots dropped», прогоны 38289663352 против 38288275413): nested-update — копий мап 199,4k → 33,2k за итерацию, копий узлов 86,0k → 52, аллокаций −29,8 %, plain RC −33,9 %; seq, который слот больше не держит, не отказывает следующему `cons` в токене — токенов взято больше в combinatorics (−9,4 % аллокаций), pipelines (−6,9 %), dependency (−3,8 %), async-libs (−20,8 %), async-broadcast (−9,5 %).
*Захваты thunk'а `lazy-seq` (2026-10-12).* Посылка «thunk выполняется не больше одного раза, значит может владеть захватами» неверна: бросок снимает заявку ячейки, и следующее форсирование запускает thunk снова (так и в Clojure; так же ждущие отменённого форсирующего), поэтому захват, потреблённый до броска, пропал бы для повтора. Верно более узкое: после вычисления операндов `cons` в хвостовой позиции (через `if`, `let`, `loop`, `do`, инлайн-тело, но не `try`) с хвостом-seq или nil thunk уже не может упасть, и ячейка его больше не запустит. Там, до токена drop-guided reuse, ячейка отпускает захваты — кроме прочитанных операндом напрямую (они заимствованы), — и значение токена, реализованный seq, который держал только захват, становится уникальным: смерть в каскаде публикации, которую перепись видела у пар dependency, превращается в `cons` в той же ячейке. Ячейку от замыкания (переопределённый `lazy-seq*` может вызвать его дважды) отличает `self`: у ячейки nil. Интерпретатору выигрыша нет — у него нет токенов, он держит захваты до публикации. Выключатель — `CLJ_NO_OPT=owned` (NOTES «Compiler», «A lazy-seq thunk lets its captures go at its tail cons»). Замер (bench/RESULTS.md «A lazy-seq thunk lets its captures go»): dependency — токенов взято 6,1k → 2,90M за итерацию, cons 3,14M → 251k, аллокаций −31,5 %; combinatorics −5,9 %, render −6,0 %; RC почти не двигается — отпускание лишь раньше. Цена компиляции: core.c +0,03 %.

**Объяснимость правки на месте: `--why-copy` (решено 2026-10-13).** Форма `inout` у нас уже есть, только выведенная: вызов на последнем использовании или с результатом, связанным вместо аргумента (`(let [m (f m)] …)`, `recur`), отдаёт значение с rc 1, и `assoc`/`conj`/`update` правят его на месте. Условие — не «rc не растёт внутри вызова», а «старое значение больше никто не увидит»: в Clojure `(f m)` обязано оставить `m` прежним, если `m` читается дальше. Чего у Swift-разработчика есть, а у нас нет, — видимости: `inout` написан в исходнике, а у нас правка на месте срабатывает молча и так же молча становится копией, когда значение захвачено, положено в коллекцию или держится слотом. Решение — диагностика, а не новый механизм: `--why-copy` (и колонка в dev-профиле) называет место в исходнике, где ожидаемая правка на месте стала копией, и держателя второй ссылки (слот, захват, коллекция, атом, заимствованный параметр). Второй ступенью — аннотация-утверждение `^:unique` на параметре: компилятор проверяет, что значение приходит уникальным на всех путях, dev предупреждает, если нет; на семантику не влияет. Атом таким не станет никогда: пока работает `f` в `swap!`, атом держит старое значение для других потоков и вотчей. Статическая уникальность вместо проверки rc в рантайме даёт мало — проверка стоит загрузку и сравнение. Делать после текущей волны fusion, по копиям, которые останутся на Datascript и group-freq (§10 шаг 7г).

**Регионы под вопросом (2026-10-13).** Регион бьёт по категории «аллокация + освобождение», а в профилях pipelines и group-freq её основная часть — ленивые ячейки и боксы, которые убирают fusion, take-out `vswap!` и распакованные double: ячейку, которой нет, регион не ускорит. Применимость упирается в доказательство, что объект не переживёт область, а 80 % объектов умирают выше кадра рождения — нужны сводки убегания параметров, которых нет (они же нужны стеку, §10 7б). MLKit без GC платил утечками и удержанием памяти до конца области; Perceus и Lean выбрали reuse и владение — наша линия. Оценка — 5–15 % на нагрузках с данными после fusion. Порядок: сводки убегания параметров; перепись после fusion — сколько объектов умирает внутри одной области и сколько стоит их освобождение; решение — по этим числам.

**Прецедент плоских коллекций.** `Array` и `HashMap` в Lean 4 — плоские с COW: `push` при rc==1 на месте, при разделении копия целиком, worst case O(n) принят осознанно; линейность не доказывается, только проверяется rc==1, а drop на последнем использовании делает проверку успешной. У нас это «плоское представление по линейности» (§4 «Shapes»).

**Что не переносится.** У Koka и Lean нет мутации — нет циклов и сборщика; у нас атомы и trial deletion (ниже). Perceus работает на IR с явными dup/drop; наш компилятор эмитит C по конвенции +0/+1, поэтому reuse-анализ — отдельный проход с фактами. Интерпретатору из списка достаются только рантаймные пункты.

### Что остаётся и надо делать инженерно
- Drop большой структуры синхронный O(n) в UI-потоке → отложенное освобождение в фоновую очередь, итеративные деструкторы.
- Циклы: lazy seq обнуляет `fn` после реализации (как Clojure); замыкания над иммутабельным циклов не образуют.
- Горячие счётчики (корень разделяемой мапы, core-функции, keyword'ы) → неатомарный/biased; BRC с main как единственным владельцем измерен и не взят (§4 «Представление значений»).
- Флаги заголовка — один набор на все механизмы памяти: SHARED (biased RC), stack/immortal, may-cycle и reaches-mutable (trial deletion). Место под них резервируется сразу (§6b): дописать бит в заголовок после того, как он стал layout'ом всех объектов, дороже, чем зарезервировать.

### Циклы: RC + trial deletion
**Где циклов нет по построению.** Иммутабельный объект ссылается только на то, что существовало в момент его создания → все рёбра направлены назад во времени → цикл требует ребра вперёд, то есть мутации. Персистентные структуры, records, tuples, layout'ы, замыкания над иммутабельным — циклы невозможны. DAG с любым sharing'ом (ромбы, одна мапа в тысяче мап) — не цикл, RC справляется. Положить «мапу в саму себя» нельзя: `assoc` создаёт новую мапу, содержащую старую. Правилом кандидата («бит — при записи вперёд») это не становится: член цикла, построенный до такой записи, бита не получает (§7 «Метка «ацикличен»», «Отвергнуто»).

**Где возможны:** атом → иммутабельные данные → замыкание, захватившее этот атом; `deftype` с мутабельными полями (parent ↔ child); нереализованные lazy seq (thunk хвоста держит голову — после реализации thunk сбрасывается, как в Clojure; корень обычно вар, не утечка); через границу Swift ↔ Clojure. `(def m {:self m})` при ленивых def — рекурсивное форсирование: thunk в состоянии «форсируется» при повторном входе бросает «рекурсивное определение» с именем вара (обязательный гвард).

**Ещё одно место, где циклы возможны: брошенная припаркованная корутина (найдено 2026-10-05, тестами самой core.async).** `go`, стоящий на `<!`, держит канал в своих приостановленных кадрах, а очередь канала держит ожидающего, который держит корутину; свой канал результата держит её тоже. Значит `go-loop`, чей канал программа уронила — неподписанный `mult`, `onto-chan!` в буфер, который никто не дренирует, — недостижим и при этом жив. На JVM такой блок собирает GC, у нас не собирает никто, и у программы есть только `cancel!`.

Собирать его **законно и строго лучше, чем не собирать**, и важно понять почему. Цикл собираем ровно тогда, когда извне на него нет ни одной ссылки: канал никто не держит — значит в него нельзя ни положить, ни закрыть; корутину никто не держит — значит её нельзя ни отменить, ни дождаться. То есть её парк **уже** не может вернуться, и сборка это не решает, а обнаруживает. Сборка корутину раскручивает (Фаза 3 ниже): `finally` выполняется, ресурс `with-open` закрывается, остальное отпускает RC. Если корутину кто-то ждёт, ссылка извне есть, и кандидатом она не становится.

Чего для этого не хватало — три отдельные вещи, ни одна не следовала из уже принятого; как закрыта каждая — в Фазе 3:
- **Оба ребра цикла обходу невидимы.** `each_child` корутины навещает `fn`, аргументы, результат и причину отмены, но не приостановленные кадры, где лежит канал; `each_child` канала навещает буфер и значения кладущих, но не ожидающих (их ссылки освобождаются отдельным путём при финализации). Закрыто ребром пробуждения и тем, что собственные ссылки кадров припаркованной корутины читаются (Фаза 3, «Кадры перечисляются»).
- **Корутины и канала нет в списке may-cycle.** Канал получил `REACH` с рождения, корутина входит в обход по типу.
- **Освободить припаркованную корутину запрещено инвариантом её типа:** `coro_finalize` начинается с `CLJ_ASSERT(!c->map)` — «умерла с замапленным стеком». Закрыто тем, что сборщик её не освобождает, а отменяет.

**Решение: RC — единственный механизм освобождения, сверху trial deletion** (Bacon–Rajan). Это не tracing GC: нет корней, нет обхода heap, нет stop-the-world, нет перемещения, нет safepoint'ов и stack maps, Swift-стек не участвует. Смотрит только на буфер кандидатов.
- Флаг `may-cycle` в дескрипторе: атомы, мутабельные `deftype`, thunk'и, замыкания с захватом мутабельного (capture set известен). Иммутабельные типы кандидатами не бывают. Кандидат = may-cycle-объект, у которого счётчик уменьшился до ненуля (атом становится кандидатом не при `swap!` — там декрементируется старое значение, — а когда отпускается ссылка на сам атом). Событие редкое. *Уточнено при реализации (ниже, «Сборщик циклов: как он устроен»): кандидат — любой объект с битом `reaches-mutable`, не только мутабельный: цикл атом → мапа → замыкание → атом становится мусором, когда отпускают последнюю внешнюю ссылку на мапу, и атом в этот момент не декрементируется вовсе.*
- Бит `reaches-mutable` в заголовке: OR битов детей при создании (детей и так трогаем при retain). Цикл может проходить через иммутабельные узлы (атом → мапа → замыкание → атом), поэтому trial deletion обязана спускаться в них — но только с установленным битом. У состояния приложения (строки, числа, keyword'ы, векторы) бит чистый, обход обрезается на первом уровне. Это acyclic-анализ Nim ORC, только в рантайме по содержимому: `Value` может содержать что угодно.
- Стоимость ∝ числу недавно отпущенных мутабельных объектов, а не размеру heap. Синхронно при пороге буфера (микросекунды при pruning) или инкрементально в idle. Буфер per-carrier (affinity) → без глобальной остановки.
- Прецеденты: CPython (RC + collector для контейнеров), Nim ORC (acyclic-типы статически). У Koka/Lean сборщика нет, потому что нет атомов.

Сборщик включён всегда — и в dev, и в prod (при чистых битах ~бесплатен). Следствие: `weak` — не необходимость для корректности, а семантический инструмент «не держать живым» (parent-pointer, кэш, observer). Думать о weak по-clojure'ски не нужно.
- Автоматический weak отвергнут: рантайм видит цикл, но не владение; неверное weak-ребро = преждевременное освобождение (zeroing → внезапный nil), хуже утечки. Эвристика «ребро, созданное мутацией, — обратное» технически верна, но `(reset! a handler)` — ребро, которое должно быть сильным.
- Back-pointers на каждый retain отвергнуты: родитель часто неизвестен (стек, регистр, Swift-контекст); память ×2; retain из инструкции превращается в аллокацию; обход предков на DAG квадратичен. И проверка при вставке отвечает не на тот вопрос: цикл легален, пока достижим, а утечка — недостижимый цикл, видна только при последнем декременте, где trial deletion и смотрит.

**Граница Swift ↔ Clojure — отдельно.**
- Конвенция: данные пересекают границу через `Codable`/примитивы; сырой `Value` в Swift — только для замыканий и host-обёрток.
- Host-объект (Swift-класс) в Clojure: trial deletion может пройти сквозь него — перечислить поля через Swift-метаданные (уже умеем для `Codable`), найти `Value`, продолжить обход. Не для замыканий (контекст непрозрачен) и не для `Any`. Типичный «ViewController хранит `Value`» — собираем.
- Замыкания в ролях callback/delegate — `WeakValue` по умолчанию в генераторе стабов: Apple держит делегатов weak, повторяем их конвенцию на своей стороне.
- Остаток — Swift-замыкание захватило `Value`, `Value` держит host-объект с этим замыканием — тот же retain cycle, что в чистом Swift, лечится `[weak self]`.
- Dev-детектор: счётчик экспортированных `Value` + trial deletion с местами создания из теневого стека — аналог memory graph debugger, показывает цикл с типами и строками `.clj`.
- `~Copyable` для `Value` отвергнут: move-only запрещает дублировать, а не хранить; цикл через поле остаётся; ergonomics в Swift 6 ограничена.

### Сборщик циклов: как он устроен
Решения, принятые при реализации (2026-10-07; код — `Sources/CljCore/cc.c`, NOTES «RC»).

**Биты.**
- В `flags` заголовка (заняты биты 0–4, тег владельца в debug — с 17-го): `MUTABLE` (5) — слоты заменяются после публикации, тип с `mutable_children`; `REACH` (6) — объект может лежать на цикле, это `reaches-mutable` раздела выше; `REACH_LOCAL` (15; до проверки цикла в момент записи — 7) — может лежать на цикле из неопубликованных объектов; `LAZY` (9) — под объектом может быть lazy seq или экземпляр `deftype`/`reify`, чей core-слот — fn программы: OR битов детей, как `REACH`, у lazy seq и у такого экземпляра — с рождения (`birth_flags` типа). Встроенная функция, тронувшая такой объект, исполняет код программы — thunk или метод, — так что вызов, который факты считают чистым, может парковаться (ниже, «Скомпилированный кадр»). Кандидатов `LAZY` не делает, по нему ходит обход заменённого корня вара (ниже, «Корень вара»), который от лишнего экземпляра только дольше.
- В слове `rc` — два старших бита: `WATCH` (31, узел на учёте у идущей сборки, которая держит на него ссылку) и `BUFFERED` (30, на объект указывает запись буфера кандидатов); под счёт остаётся 30 бит. Неопубликованный объект без `REACH_LOCAL` ни одного из них не получает, поэтому встроенные retain/release и `rc == 1` маски не платят; маска — на медленных путях. Объект с `BUFFERED` считается неуникальным (`rc == 1` ложно): reuse на нём откладывается до обработки записи.
- `REACH` при рождении — у мутабельного типа, способного на ребро вперёд: атом, канал, volatile, массив объектов. Иначе — OR битов детей в `clj_slot_init`/`clj_slot_store`: это единственные записи ребра (§4 «Запись в слот»), так что вычисление в двух примитивах покрывает конструкторы всех типов — коллекции, замыкание (через захваты), record и `deftype` (через поля; дескриптор — не слот, бит от него не наследуется). Копия `memcpy` (`with-meta` фнки, seq-view) копирует биты. `REACH_LOCAL` берётся только от неопубликованного ребёнка. Пропущенный бит — утечка, не порча: сборщик не спустится в узел и цикл через него не соберёт.
- Бита нет намеренно: у вара (immortal: пока вар жив, цикл через него не мусор, а вар жив всегда; rebind отпускает старый корень, и кольцо, висевшее на нём, становится кольцом из остального — его и собираем, обходом мимо битов: «Корень вара» ниже); у exec и узлов анализатора (реестр специализатора держит exec без ссылки и воскрешает через `retain_if_live`, значит сборщик не может его освободить; бит обнуляется при постройке exec, иначе его получала бы каждая фнка от своего кода); у дескриптора типа (реестр `users` без ссылок); у корутины (её обход входит по типу: Фаза 3 ниже); у lazy seq — `MUTABLE` есть, `REACH` только от thunk'а при создании, реализация бит не добавляет. Иначе каждая ячейка конвейера `map`/`filter` была бы кандидатом, а обход реализованной цепочки от каждого кандидата квадратичен. Кольцо, которое реализация замыкает через глобальный вар (`(def s (lazy-seq (cons 1 s)))` и переопределение `s`), обычный обход поэтому не видит; его находит обход заменённого корня («Корень вара» ниже). Через захваченный атом или volatile кольцо собирается обычным путём (бит пришёл от thunk'а).
- Хост-бокс детей не показывает и бита не имеет: цикл через Swift — граница выше.

**Кандидат.** Отпускание до ненуля объекта с `REACH` (опубликованного) или `ONCYCLE` (неопубликованного; до проверки цикла в момент записи — `REACH_LOCAL`, ниже), если `BUFFERED` ещё не стоит: декремент и бит одной операцией (у опубликованного — одним CAS: запись, взятая сборщиком до декремента, посчитала бы ссылку отпускающего внешней, и больше никто объект в буфер не положил бы) и указатель в буфер. Сюда же отпускание детей умирающего родителя: родитель мог быть последней внешней ссылкой.
- Буфер ссылки *не держит*, как у Бэкона и Раджана: иначе ацикличный объект, однажды отпущенный до ненуля, освобождался бы сборкой, а не последним release, и детерминированное освобождение (локи, хост-объекты, счётчик живых в тестах) пропало бы. Объект с `BUFFERED`, дошедший до нуля, разбирается сразу — дети, `unlink`, `finalize`, уход из счёта живых, — но его ячейка остаётся «зомби» (`rc` = `WATCH|BUFFERED` при нулевом счёте) до обработки записи, которая её и возвращает. Заголовок такого объекта при разборе не становится звеном списка: запись его читает.

**Конкурентность — решение.** Цикл однороден: дети опубликованного объекта опубликованы, значит цикл либо целиком shared, либо целиком локален. Отсюда два режима одного алгоритма.
1. *Локальный* — синхронный Bacon–Rajan в исполнении-владельце. Неатомарный счётчик трогает только владелец, второго мутатора нет, и вопроса конкурентности нет. Буфер — в `clj_coro` исполнения (корутина, переехавшая на другой носитель, уносит его с собой), обход останавливается на опубликованных узлах.
2. *Shared* — trial deletion на фоновом потоке, параллельно мутаторам. Мир не останавливается; вместо этого сборка проверяет, что прочитанное ею — согласованный снимок:
   - Сборщик держит счётную ссылку на каждый посещённый узел; на корень — try-retain по записи (CAS от ненулевого счёта: ячейка записи не возвращается, пока запись жива; ноль — зомби или объект на пути к нему, и запись ждёт следующей сборки). Удерживаемый узел не уникален, поэтому его не правят in place и не освобождают, а дети иммутабельного удерживаемого узла живы его слотами — retain на них безопасен.
   - На каждом узле сборщик одной атомарной операцией ставит `WATCH` и читает счёт. Бит снимает любой retain или release опубликованного объекта (`fetch_add` и так возвращает старое слово, проверка — тест бита), запись слота мутабельного опубликованного владельца и перенос ссылки в буфер. За сборку бит только снимается, поэтому ABA нет; повторное чтение счётчиков без бита ошибается — ссылка мутатора может «перепрыгивать» с узла на узел впереди чтений.
   - Мутабельные узлы. Канал и атом читаются под своим локом (trylock; занят — узел чёрный, без рёбер). Остальные (volatile, массив, lazy seq) — без лока, по протоколу: писатель пишет слот, ставит полный барьер, снимает `WATCH` владельца и только потом отпускает старое значение; сборщик ставит `WATCH` владельцу, читает слот, делает try-retain ребёнка (CAS от ненулевого счёта) и проверяет `WATCH` владельца снова. Так не читается ребёнок, которого уже держит уникально и правит in place кто-то другой.
   - Пока идёт сборка, опубликованный объект, дошедший до нуля, не освобождается, а откладывается целым (заголовок не тронут, дети не отпущены): try-retain по указателю, прочитанному без лока, не попадает в возвращённую память. Отложенное освобождает сам сборщик по окончании — работа уходит с мутатора.
   - Решение. Чёрные — узлы, потерявшие `WATCH`, и узлы с внешней ссылкой (счёт минус внутренние рёбра минус ссылки сборщика больше нуля); чернота протягивается по записанным рёбрам; остальные белые и освобождаются. Почему это верно: белый узел не тронут с момента своей метки, значит на момент начала проверки его счёт и слоты те, что прочитаны; все его входящие записанные рёбра — от белых (иначе почернел бы), чьи слоты тоже не тронуты. Значит в этот момент на белых нет ссылок, кроме друг друга и сборщика, то есть они мусор, а мусор стабилен. Устаревшее записанное ребро (слот с тех пор изменён) бывает только у узла, потерявшего `WATCH`, то есть у чёрного, и завышенное число внутренних рёбер под ним ничего не делает белым.
   - Вмешательство откладывает сборку, а не теряет её: у корней `BUFFERED` снимается в начале, так что мутатор, отпустивший во время сборки последнюю внешнюю ссылку, кладёт узел в следующий буфер, а корень, почерневший только из-за мутатора, сборщик кладёт туда сам.
   - Белый узел, на который указывает чужая запись (опубликован после того, как попал в локальный буфер исполнения), не возвращается, а становится зомби для той записи.

   Отвергнуто: остановка мира — нужны safepoint'ы у всех потоков, держащих `Value` (Swift, nREPL, пул блокирующих задач); Recycler (конкурентный вариант Бэкона и Раджана с RC, буферизованным по эпохам) — переделка RC на всех горячих путях; гибрид «unshared считается, shared трассируется» из запасного плана ниже — смена механизма памяти, а не надстройка над ним.

**Когда и чего стоит.**
- Отпускание, не дошедшее до нуля: неопубликованный объект без `REACH_LOCAL` — ни одной лишней инструкции (та же проверка флагов, другая константа маски); с `REACH_LOCAL` — вызов вне строки; опубликованный — тест бита в уже загруженных флагах и тест `WATCH` в слове, которое вернул `fetch_sub`. Кандидат — CAS (раз на объект за период) и push (локальный — без лока, общий — под локом буфера).
- Запись слота — OR бита ребёнка во владельца; у опубликованного мутабельного владельца ещё барьер и чтение `rc` (у канала и атома без барьера — их читают под локом). Освобождение опубликованного объекта — загрузка флага «идёт сборка».
- Shared-сборка — свой фоновый поток с QoS utility, ниже носителей (сборка уступает процессор мутаторам, чей мусор собирает): просыпается на первом кандидате пустого буфера и собирает через 500 мс или по 1024 кандидатам. На мутаторе — только push (буфер кусками по 1022 записи: push не копирует выросший массив под мьютексом).
- Локальная вне главного потока — синхронно при 256 кандидатах (внутри отпускания, без повторного входа) и на финише исполнения.
- Главный поток (носитель `is_main`): обход и освобождение посреди его работы не идут — пауза там пропущенный кадр. Его локальные кандидаты собираются в `kCFRunLoopBeforeWaiting` с бюджетом 1 мс на один холостой ход. На непрерывной прокрутке холостого хода нет: буфер растёт до 4096, дальше каждый новый кандидат передаёт фону самый старый — `clj_share` его подграфа (один проход без счётчиков) и push в общий буфер. Цена передачи — проход по неопубликованному подграфу одного кандидата и атомарный RC на нём впредь; худшая пауза — один такой проход, измерения в NOTES «RC». Корутина на главном носителе на финише передаёт фону весь свой буфер тем же способом.
- `clj_cc_collect()` — явная полная сборка вызывающего исполнения и общего буфера (тесты, `runtimeSettled`).

**Финализация в цикле.** Белое множество освобождается фазами: каждый белый отпускает своих не белых детей (рёбра к белым пропускаются); `finalize` всех белых; возврат памяти всех белых. `finalize` видит любого члена своего цикла целым, но не ребёнка вне цикла — как и в ацикличном пути, где `finalize` идёт после отпускания детей. Читать отпущенного ребёнка `finalize` не может и в ацикличном пути: опубликованный ребёнок, дошедший до нуля во время сборки, отложен ей и освобождается в её конце на её потоке, возможно, пока `finalize` родителя ещё идёт (так падал `exec_finalize`, обходивший дерево узлов ради inline-кэшей; NOTES «RC»).

**Корень вара: обход мимо битов** (решение 2026-10-08; код — `clj_rc_release_root` в `rc.c`, `collect_deep` в `cc.c`).
- *Что ловим.* Кольцо через lazy seq, которое реализация замкнула через глобальный вар: `(def s (lazy-seq (cons 1 s)))`, реализация, переопределение `s` — кольцо L → cons → L мусор, но ни у одного члена нет `REACH` (реализация бит не даёт, вар бита не имеет), и отпускание старого корня кандидата не делает.
- *Где.* Любая замена корня проходит `clj_var_bind_root`: `def` поверх существующего корня (и перезагрузка ns — это те же `def`), `alter-var-root` (и `with-redefs` поверх него), `intern` со значением, связывание скомпилированного юнита и вытряхнутого (`shaken`) вара, определение из Swift, `*ns*` у `in-ns`. Старый корень-fn, который ещё может читать идущее исполнение, ждёт в списке отложенных (`clj_eval_retire_root`) — его слив проходит тот же путь.
- *Как.* Старый корень отпускается «глубоко». Ссылка, оставшаяся ненулевой у объекта с `LAZY` или `REACH`, становится глубокой записью; дошедший до нуля разбирается, и то же правило действует на его детей — весь каскад глубокий. Иначе кольцо под ацикличной головой (цепочка `map`/`filter` над варом: голова уходит по RC, кольцо — на фронте реализации, где thunk'и держат ячейки друг друга) осталось бы. Запись — как у общего кандидата: декремент и `BUFFERED` одной CAS, без ссылки, так что детерминированное освобождение не страдает; если `BUFFERED` уже держит другая запись, объект остаётся ей, хотя она может быть обычной, с отсечением по `REACH`: запись со своей ссылкой держала бы объект дольше его последнего отпускания (так упали `AtomTests.publication` и `HierarchyTests.multimethodHierarchyOption`, проверяющие счёт живых сразу после отпускания). Кольцо, которое так упущено, — `REACH`-объект на нём уже в обычном буфере, а сквозь lazy seq без `REACH` обычная сборка не пройдёт; это остаётся.
- *Обход* — то же trial deletion общей сборки, отдельным графом после неё, но входит в узел с `LAZY` или `REACH`. Этого достаточно: цикл требует ребра, записанного после рождения его цели, то есть записи в `MUTABLE`-владельца (иммутабельный узел указывает только на старших, а правка на месте идёт только при единственной ссылке, и ребро на себя её отнимает). `MUTABLE` без `REACH` с рождения — только lazy seq, и он рождается с `LAZY`; иммутабельный узел на кольце получает бит следующего по кольцу. Значит, у каждого члена кольца есть `LAZY` или `REACH`, а мапа из миллиона строк не несёт ни того, ни другого: её корень даже не подаётся.
- *Где идёт.* Только на фоновом потоке сборщика (или в явном `clj_cc_collect`). Мутатор, главный поток в том числе, платит за запись CAS и push под мьютексом буфера, как за общего кандидата; каскад разбора тот же, что был у обычного RC.
- *Чем ограничен* (1М-мапа, перезагружаемая в цикле). Мапу, которую больше никто не держит, освобождает RC, записей ноль. Если держат (история версий в атоме) — одна запись на `def`, не на элемент, и дальше три предела. Пакет: записи ждут 500 мс, `def`'ы одной перезагрузки собираются в один граф, и общее у версий обходится один раз. Скважность: следующий глубокий обход — не раньше, чем через семь длительностей предыдущего, то есть не больше восьмой части ядра на QoS utility, сколько бы перезагрузок ни шло. Потолок: 2²⁰ узлов на граф (граф такого размера — десятки МБ), дальше узлы не добавляются, родитель отрезанного ребёнка чёрный; кольцо за потолком не собирается и не повторяется (счётчик `CLJ_CC_STAT_DEEP_CUT`).
- *Кольцо, живое на момент обхода* (его держит атом, `*1`, корутина, которая по нему идёт). Его последнее внешнее отпускание кандидата не сделает — битов нет. Поэтому чёрная сильно связная компонента с циклом (Тарьян по записанным рёбрам), в которой есть член без `REACH`, оставляет повтор (кольцо из одних `REACH` подаст себя само): счётная ссылка на одного члена, следующий обход через 1, 2, 4 … 64 с, пока кольцо живо; кольцо, ставшее мусором, очередной повтор находит белым. Ссылка повтора кольцо, которое и так живо, лишь держит до этого обхода. Корень, который мутатор тронул посреди обхода, подаётся снова битом, без ссылки, как у общей сборки. Кольцо, которое уже держит ждущий повтор, второго не получает.
- *`set!` привязки — нет.* Значение кадра `binding` обычно не опубликовано (кадр принадлежит исполнению, пока его не передали дочернему), и фону его не отдать без `clj_share` всего старого значения на мутаторе; локальный глубокий обход в исполнении-владельце синхронен и не ограничен — на главном потоке это пауза посреди работы. И одной `set!` мало: кадр, умирая, отпускает свои значения так же, значит, глубоким пришлось бы сделать и выход из каждого `binding`. Корень вара опубликован всегда, у фона он есть даром.
- *Что остаётся.* То же кольцо, отпущенное не заменой корня, а записью в атом (`(reset! a (lazy-seq (cons 1 @a)))` при глобальном `a`, затем `(reset! a nil)`) или выходом из `binding` после `set!`: глубокое отпускание там стояло бы на пути `swap!`. Кольцо больше потолка. Триггер — отчёт об утечке (NOTES «RC»).

**Фаза 3 — брошенная припаркованная корутина (выше, «Ещё одно место…»)** (решения 2026-10-08; код — `cc.c`, `coro.c`, `sched.c`, `chan.c`, NOTES «Coroutines»).
- *Корутина в обходе.* Входит по типу, без бита `REACH` (она `MUTABLE` с рождения, так что бит не приходит и от детей): бит сделал бы кандидатом каждое отпускание дескриптора до ненуля (колбэк `put!`, финиш `go`, свип эвакуации), а кандидатов и так дают каналы, у которых бит с рождения. Читается под своим `c->lock`, и вердикт один из трёх: *припаркована в собираемом парке* — узел-кандидат; *закончена* (`finish` отработал, слоты больше не меняются) — обычный узел; *иначе* (бежит, в очереди, парк несобираемый, уже отменена, хост ждёт её `on_done`) — чёрная, без рёбер. Пробуждение (`resume`, через которое идут и отмена, и `resume!`) снимает `WATCH` корутины, так что проснувшаяся посреди сборки чернеет при проверке.
- *Ребро ожидающий → корутина — ребро пробуждения.* Ожидающий держит `coro` голым указателем, поэтому ребро не счётное и в число внутренних не входит. Но обход по нему идёт (из канала в корутину: иначе брошенный канал, отпущенный после канала результата, корутины не достигал бы), и чернота по нему течёт в обе стороны: живой канал может её разбудить, а живая корутина может прочесть канал из своих кадров. Канал читает своих ожидающих под своей секцией и под замком ожидающего; незаявленный ожидающий значит, что его корутина ещё не проснулась и жива. Ожидающий колбэка `put!`/`take!` — другое: его fn держит только он, а его — только узел очереди, так что это счётное ребро канала (`cc_held`), которое разбор мусорного канала отдаёт и забывает, чтобы финализация не отпустила его второй раз.
- *Внутренние ссылки корутины.* Самоссылка припаркованной (ссылка исполнения, которую отпускает `finish`) и ссылка её таймера дедлайна: +1 к внутренним каждая. Дедлайн будит только отменой, а сборка — та же отмена раньше. Канал результата `go`/`future`, который корутина держала для `on_done` счётной ссылкой мимо `each_child`, стал слотом `done_value`: иначе канал результата всегда читался бы удерживаемым извне.
- *Источники пробуждения по видам парка.* Корутина белая, только если белы все её источники; несобираемый вид — чёрная.

  | парк | кто будит | собирается |
  |---|---|---|
  | `<!`, `>!`, `alts!`, `deref` промиса и `future` (`chan.c`) | операция над каналом, в очереди которого стоит ожидающий, или отмена | да, если белы все такие каналы: ожидающий считает очереди, где стоит (`queued`), обход — найденные из каналов графа; не совпало — чёрная. Так `alts!` требует всех своих портов, а не сработавшего и последнего |
  | несбрасываемый `<!` (join `go-scoped`) | только канал | нет: отмена его не будит |
  | порт `timeout` в `alts!` | поток таймеров | через счёт: его ссылка на канал внешняя, порт чёрный — корутина чёрная |
  | дедлайн | таймер дедлайна | ссылка таймера внутренняя (выше) |
  | ворота `suspend!` | `resume!`, `cancel!` через дескриптор корутины | да: дескриптор — счётная ссылка, белую корутину держать нечем |
  | `Thread/sleep` | поток таймеров | нет: проснётся сама и продолжит, а не отменится |
  | задание блокирующего пула (`clj_blocking`), ожидание писателя вывода | поток рантайма | нет |
  | очередь cmutex (атом, канал с трансдьюсером, `locking`, локи ref в `dosync`), заявка lazy seq (`forcing_held`) | исполнение, которое отпустит мьютекс или опубликует seq | нет: живой держатель разбудит наблюдаемо; держатель-мусор будет раскручен своей сборкой, раскрутка отпустит, и ждущий будет судим на следующем парке |
  | Swift `async` (`host-async-fn`) | Task, держащая промис через `Value` | через счёт: ссылка внешняя |
  | Swift `callAsync`, `callBlocking`, eval nREPL | хост ждёт `on_done` | нет: хостовый `on_done` — ожидающий, которого RC не видит |
  | agent `await` | промис-защёлка у действия агента | через счёт |
  | неявная корутина голого потока | — | никогда: бессмертна |
- *Одна точка входа* (решение 2026-10-08). `clj_park(w, wake)`: `clj_wake` — обязательный аргумент, значение строится только конструкторами `clj_wake_*` (вид и отменяемость), и `clj_lot_park` принимает его так же. Парк, забывший источник, не компилируется; `make park-audit` (в `make gates`) падает на переключении из корутины мимо `park` (`clj_coro_switch_out`, `clj_ctx_switch` вне пролога, эпилога и `park`), на вызове `clj_park`/`clj_lot_park` без конструктора и на литерале `clj_wake`.
- *Чем владеют кадры — решение.* Варианты и цена:
  1. Стек-карты в скомпилированном коде. C через clang их не даёт (statepoints — уровень LLVM IR), то есть отказ от C как цели или свой проход компилятора — самый дорогой.
  2. Записи кадров интерпретатора: кадр (`clj_frame`, слоты с маской владения) в записи теневого кольца и буферы аргументов `eval_all` — запись и снятие на каждом вызове горячего пути; только интерпретатор.
  3. Правило для встроенных функций C на стеке: каждая, держащая собственную ссылку поперёк вызова, который может парковаться (драйверы `reduce`, `swap!`, seq-функции, `clj_chan_deref_timeout`), регистрирует её; аудит — весь builtins.
  4. Кадры ничем не владеют поперёк парка: перенос собственных ссылок в список корутины перед вызовом, который может парковаться, — а при бесцветных корутинах это любой вызов, то есть новое соглашение о вызове обоих бэкендов.
  5. *Кадры не перечисляются* (взято 2026-10-08, действовало до 2026-10-19). Неучтённая собственная ссылка кадра лишь делает свою цель удерживаемой извне, чёрной — утечка, не ошибка: недосчёт внутренних рёбер безопасен (пересчёт, который дал бы консервативный скан, — нет). Заимствованные (+0) ссылки кадров считать не нужно, потому что белое множество с припаркованной корутиной сборщик не освобождает — он её отменяет и держит свои ссылки до конца сборки, а раскрутка отпускает всё через RC; память, которую может прочесть кадр, не возвращается, пока кадр жив. Цена — ноль. Этого хватало на парк, чей цикл держит куча: захват замыкания и параметр в обоих бэкендах читаются заимствованно, так что `go-loop` над захваченным каналом, `mult`, `onto-chan!`, `future` на промисе собирались. Не хватало на цикл, член которого держит только собственная ссылка кадра: вектор портов `alts!` (временный вектор кадра вызывающего, порты под ним чёрные) — `(go-loop [] (alts! [in stop]) …)` и `mix`; канал из `let` самого тела `go`; кольцо через владеющий параметр, ради которого вызывающий сделал retain.
- [x] *Кадры перечисляются: вариант 4 после владеющих параметров (план 2026-10-12), вариант 2, вариант 3 и частные объекты* (сделано 2026-10-19 по запросу пользователя, двумя заходами: первый — список, кольцо и частные объекты, второй — массив кадра, все вызовы эмиттера, код рантайма, буфер аргументов, широкий кадр, кольцо после переполнения; код — `compiler.c` `emit_frefs_push_with`, `roots_internal.h`, `eval.c` `run_body` и `eval_all`, `cc.c` `visit_frames`, `facts.c` `clj_facts_may_park`). У припаркованной корутины сборщик читает её собственные ссылки, и каждая — из того, что отпустила бы раскрутка её кадров: список исполнения (временные и переменные скомпилированных кадров, их массивы, переменные кода рантайма), кольцо интерпретатора (кадры и их буферы аргументов) и её неопубликованные объекты.
  - *Скомпилированный кадр* перед вызовом, который может парковаться, пишет свои ссылки в список исполнения (`clj_frefs` в заголовке кольца: он в `clj_coro`, не в стеке, и эвакуация его не трогает) и после вызова снимает их. Что пишется: живые владеющие временные, кроме аргументов, которые вызов забирает (владеющий параметр, массив прямого вызова; ячейка, переданная из умирающего слота, — уже не кадра), и владеющие C-переменные слотов, которые к этой точке могли получить значение (связанные раньше по тексту — значение слот держит и после своего `let`, до перепривязки или выхода; в цикле — любые слоты его тела; слот, отданный, съеденный или отпущенный, не пишется до новой привязки, ветви `if` объединяются, обработчик `try` видит слоты начала тела). «Может парковаться» — по фактам: сам вызов, без вычисления аргументов, несёт эффект `park` или `opaque`, или узел не пройден. Вызов, который факты считают чистым, кода программы не исполняет, кроме реализации lazy seq и core-метода `deftype`, до которых дотянется через аргумент, а их несёт бит `LAZY` (выше, «Биты»): такой сайт пишет то же, но под проверкой бита (`clj_c_lazy`, холодная ветка) у аргументов, чей факт допускает коллекцию, seq, fn, запись, атом или хостовый объект, и у локальной fn, которую он зовёт; снятие тогда — `if (FR)`. Встроенные, которые аргумент дальше типа, числа или идентичности не читают (арифметика, предикаты типа, `identical?`, `cons`, массивы, `field*`, `new*`), не проверяют. Lazy seq, до которого чистый вызов доходит иначе, опубликован (корень вара, атом) или сделан вызываемым, и тогда парк его thunk'а — в фактах вызываемого: `lazy-seq*` зовёт свою fn. Найдено оракулом (ниже, «Оракул»); цена — ниже, «Цена закрытия пробелов». Первая запись активации запоминает длину списка `F0`; каждая запись и снятие пишут длину целиком; между записью и снятием нет переходов, так что раскрутка по `CLJ_THROWN` проходит снятие; посадка `Stack overflow` восстанавливает длину своей точки (`clj_recovery`). Указатель на список берётся из носителя (`clj_shadow_running`, первое поле `clj_carrier`) раз на активацию и годен после парка: список — исполнения. Запись называет и массив кадра — тройкой `CLJ_FREF_CFRAME`, адрес `fr`, длина массива, — если массив может держать владеющий слот: слот `let`, `loop` или `catch`, rest, владеющий параметр или параметр прямой fn, параметр, который перепривязывает `recur`; при числе слотов больше 64 — все. Маску `fr.owned` и слоты сборщик читает там, где они лежат, так что слот, захваченный замыканием, прочитанный через статическую ссылку, и параметр прямой fn больше не выпадают. Переменные слотов берутся из маски, зафиксированной объявлением кадра, без типизированных в точке записи: тело fused подменяет набор продвинутых, быстрая ветка split затеняет слот переменной `int64_t` или `double`.
  - *Каждый вызов, который может парковаться, идёт через один помощник* (`emit_frefs_push_with`): invoke, прямой и владеющий вызов, интринсик (реализация lazy seq или fn переопределённого вара; коллекция, которую интринсик потребляет, и слот, который роняет токен reuse, — уже вызываемого), владеющие `next`/`rest`, take-out `get`, понижённый вызов (литерал исполняется внутри натива; узел `LOWERED` несёт эффекты литерала в фактах), fused-сайт вместе с состоянием стадий (`CLJ_FREF_ARRAY` над хвостом массива сайта), worker и его fallback, вызов вынесенной копии, переопределённый `lazy-seq*`. Worker объявляет список, как кадровая функция. Шаг мономорфизированного fused-сайта называет свой элемент поперёк вызова стадии и потребителя, если факты сайта допускают парк, а на сайте, который они считают чистым, — если элемент несёт `LAZY`. Где парк по построению запрещён — вызов ObjC (код хоста; тело, вызванное из него, исполняется под `host_depth`, §5 «Вызов внутрь») — ничего не нужно.
  - *Код рантайма* (вариант 3). C-функция рантайма, держащая собственную ссылку поперёк вызова кода программы, называет адрес своей переменной (`CLJ_ROOTS`, массив — адресами указателя и длины, `CLJ_ROOTS_SPAN`) в том же списке исполнения: несколько записей на вызов функции, не на элемент; снимает их выход из блока (`cleanup`), посадка `Stack overflow` восстанавливает длину. Сборщик читает переменную там, где она лежит. Инвариант: в каждой точке вызова, который может парковаться, названная переменная держит собственную ссылку или nil; переданная (потребляющий `conj` или `assoc`, владеющий шаг редьюсера) сначала очищается. Так названы аккумулятор редьюсера, seq и итератор обхода (`held`, `item`), `keep` и ключи `sort`, состояние fused-драйвера, `apply`, `swap-vals!`, наблюдатели атома и прочее. Драйвер `swap!` ничего не держит: старое значение — атома, новое называет он сам. Стек в куче называет поле каждого своего элемента (`CLJ_ROOTS_FIELD`: адреса указателя на массив структур и длины, размер структуры и смещение поля; читается, где лежит): стек кадров читателя — `meta` кадра, стек печати — `held` и `item` итератора кадра. Собственные значения, которые кадр стека держит массивом, лежат на общем стеке значений, названном `CLJ_ROOTS_SPAN`, а кадр помнит начало своих: элементы массива, который печатается, и аргументы открытых кадров `syntax-quote` (на формах читателя `syntax-quote` не паркуется — коллекции встроенные, символ разрешает рантайм, — но анализ видит вызовы через указатель, и имя дешевле доказательства). Копии узлов трая на разделяемом пути `assoc` и `dissoc` — ссылки, которые `descend` берёт у неуникального родителя, — в массиве пути в `edit`, названном одной записью на операцию; ключ, чьё равенство или хеш — код программы, паркуется ниже по пути. Уникальный путь ничего не пишет. Список разбуженных узлов канала (`wakes`) называет обходчик (`wakes_walk`): значение каждого узла и fn ожидающего-колбэка, которых очередь уже не держит, — колбэк, запущенный разбуждением, и шаг трансдьюсера под секцией могут парковаться; `flush_wakes` отцепляет узел до его разбуждения. Fn самого исполняющегося колбэка держит его ожидающий — утечка, не ошибка.
  - *Гарантия: проверка при сборке, а не эвристика* (сделано 2026-10-21 по запросу пользователя: каждое место, где ссылка может лежать, идёт через один механизм, который нельзя обойти, как `JS::Rooted` с rooting hazard analysis SpiderMonkey). `scripts/rooting-hazards.py` (`make rooting-hazards`, в `make gates`) — анализ C рантайма (`CljCore`, `CljCompiler`) по AST libclang активного Xcode, debug-конфигурация. Правило: C-локал (`clj_value`, массив или структура из них, `clj_value *`, указатель на объект кучи), живой поперёк вызова, который может парковаться, назван (`CLJ_ROOTS`/`CLJ_ROOTS_SPAN` в силе в точке вызова — переменная целиком или путь поля) или объявлен не требующим имени; иначе — ошибка сборки с файлом и строкой. «Может парковаться» — `CLJ_MAY_PARK` на `clj_park`, распространённое по графу вызовов всех единиц, и любой вызов через указатель на функцию, если поле, параметр или typedef не `CLJ_NO_PARK`; функция, положенная в `CLJ_NO_PARK`-слот (инициализатор дескриптора, присваивание, аргумент), сама проверяется на непаркуемость. Функция без тела здесь (libc, хост) не паркуется: парк под `host_depth` — ошибка; функция под `clj_lock` помечена `CLJ_NO_PARK` целиком — парк под замком тоже ошибка. «Живой» — по CFG функции: прочитан на каком-то пути до нового присваивания, или его адрес получает сам вызов; адрес, сохранённый иначе, держит переменную живой до конца её блока. Владение выводится по соглашению «аргументы заимствованы, результаты собственные»: локал, получивший результат вызова, собственный; копия заимствованного — заимствованная; аксессор (тело — один `return` чтения поля или приведения) возвращает +0 сам; параметр собственный, если он `CLJ_OWNED` или функция его отпускает; поле структуры собственное, если не помечено иначе. Пометки — пустые макросы `value.h`, которые анализ читает из исходника, так что в release они стоят ноль: `CLJ_BORROWED` (ссылка +0 или не ссылка; на функции — результат +0), `CLJ_NO_CYCLE` (никогда не освобождается частью мусорного цикла: строка, символ, число, кейворд, var, ns, дескриптор типа, узел анализатора, exec — недосчёт ссылки на такой объект не держит мусор), `CLJ_OWNED` (параметр, который функция потребляет), `CLJ_NO_PARK`, `CLJ_RING` (только `eval.c`: ссылку называет кольцо интерпретатора — слоты кадра и буферы аргументов). Ещё правила: названная переменная, отданная (`clj_release`, `CLJ_OWNED`-параметр) и не переприсвоенная к следующему вызову, который может парковаться, или отданная в сам такой вызов; названная до присваивания на каждом пути; названная копия +0. Стек в куче — поле структуры, указывающее на массив структур со ссылками: собственное поле каждого элемента держится, пока держится поле, и называется `CLJ_ROOTS_FIELD` поле за полем; связный список — тоже, и его называет обходчик всей переменной (`CLJ_ROOTS_WALK`: адрес, размер и функция `CLJ_NO_PARK`, которую сборщик зовёт над байтами припаркованной переменной); указатель внутрь такого стека и массив указателей на структуры — вид. Временное — собственный результат вызова, операнд другого вызова или инициализатора: пока вычисляется соседний операнд, который может парковаться, его не держит никакая переменная, и это ошибка, если поле инициализатора, куда он идёт, не `CLJ_BORROWED` и не `CLJ_NO_CYCLE`. Тот же инструмент держит правило слотов §4 «Запись в слот»: запись `.v` мимо `object.h` и голое поле `clj_value` объекта кучи (хосты `clj-load` и `clj-facts` — только это правило). Отрицательные фикстуры (`scripts/rooting-fixtures/`) — на каждое правило строка, которая обязана упасть, и чистые случаи рядом; `make rooting-hazards` проверяет обе стороны. Разметка рантайма: 212 точек `CLJ_ROOTS` (265 переменных и путей), 22 `CLJ_ROOTS_SPAN`, 3 `CLJ_ROOTS_FIELD`, 1 `CLJ_ROOTS_ARGS`, 10 `CLJ_ROOTS_WALK`, 178 `CLJ_BORROWED`, 227 `CLJ_NO_CYCLE`, 45 `CLJ_OWNED`, 57 `CLJ_NO_PARK`, 18 `CLJ_RING`. Найденные ошибки: названный seq, прочитанный сборщиком после отпускания (`hash_coll`), голова формы после закрытия её итератора (`macro_var`), названные значения, отданные потребляющему вызову, который может парковаться (`sort_items`, `clj_var_push_bindings`, читатель), утечки `group-by identity` и схемы `[:maybe [:or …]]`; правила стека в куче и временного (2026-10-21) — стеки читателя, печати и `syntax-quote` и 17 временных (`node_data.c`, `flat_take_entry`), а поля-виды получили пометки (`local.sym`, обратные указатели, списки варов и символов). Допущения, которые анализ не проверяет (их проверяет оракул ниже): вызываемый не хранит адрес локала дольше вызова; код release-конфигурации — тот же, что debug; пометки `CLJ_BORROWED`, `CLJ_NO_CYCLE`, `CLJ_RING` и `CLJ_NO_PARK` на функциях верны; `clj_resume_far` будит только ожидающего-корутину, колбэк канала — только `clj_resume` из канала.
  - *Оракул* (debug-сборки, `cc_oracle.c`; `CLJ_CC_ORACLE=0` выключает). Когда сборщик читает припаркованную корутину, каждый её неопубликованный объект, который может лежать на цикле (`REACH` или `REACH_LOCAL`), сверяется счётом: ссылок у него ровно столько, сколько назвало перечисление кадров плюс рёбра её других неопубликованных объектов и её собственные поля (тело, аргументы, результат, ожидающее исключение, отставленные корни, след спавна) плюс ссылка буфера кандидатов. Больше — собственная ссылка, которую ничто не называет (`cc/frame-missed`), меньше — названная заимствованная (`cc/frame-overnamed`). Неопубликованный объект трогает только его исполнение (проверка владельца), а опубликованный на него не ссылается, так что других держателей нет, и заимствованное слово на стеке счёта не меняет — ложной тревоги от него не бывает. Консервативный скан стека (`[sp, stack_hi)`, слова, которые аллокатор признаёт началом объекта известного типа: `clj_debug_object_at`) только находит объекты, которых перечисление не назвало, и место — функцию слова по цепочке frame pointer от сохранённого переключением кадра (`dladdr`). Оракул только читает и не меняет, что собирается. Опубликованных объектов он не судит: их держат и чужие исполнения; для них — фаззер утечек (NOTES «Fuzzing», «Leak fuzzing»). Первая находка оракула в фаззере: интерпретированное `(first (lazy-seq (cons (<! c) nil)))` паркуется внутри реализации, а lazy seq, собственный аргумент встроенной `first`, не назван никем (`cc/frame-missed`, слово в кадре `clj_lazy_thunk_run`, run 39586233174) — исправлено в интерпретаторе; та же форма скомпилированной (run 39589318892) — сайт `first`, который факты считают чистым, ничего не писал; закрыто проверкой `LAZY` (выше, «Скомпилированный кадр»).

Хостовый код вне этого: парк под `host_depth > 0` — ошибка (§5 «Вызов внутрь»), так что под точкой парка припаркованной корутины чужого кадра нет.
  - *Кадр интерпретатора* — запись кольца (`clj_shadow_frame.frame`) указывает на `clj_frame` тела; сборщик читает его владеющие слоты по маске `owned`, из блоба, если корутина эвакуирована (`clj_coro_parked_bytes`). Кадр от 64 слотов владеет всеми (параметры удержаны при входе), и маска у него — «все»; его длина лежит в слове перед слотами (`slots_alloc`), а маску «все» у кадра меньше 64 слотов получить нечем, так что она однозначна.
  - *Буфер аргументов интерпретатора* — запись `clj_argbuf` (значения, маска владения, невидимый кольцу кадр, предыдущая) в цепочке на кадре (`clj_frame.args`). Ставится, когда перед аргументом, который может парковаться (не чтение слота, захвата, внешнего слота, константы, вара), уже есть собственное значение, и держится через вызов, пока значения собственные; потребляющий интринсик снимает свой бит до вызова, а встроенная функция интринсика и встроенная функция, которую факты называют чистой (`clj_fn.leaf`: ни парка, ни непрозрачного эффекта, ни вызова переданной fn), буфер держат, только если собственный аргумент несёт `LAZY`: кода программы они не исполняют, кроме реализации lazy seq и core-метода `deftype`, — и всегда держит fn переопределённого вара; их вызов над чтениями — аргумент, который может парковаться, только если прочитанное несёт `LAZY` (корень вара не читается: переопределение может его освободить); кадр голого потока буферов не ставит вовсе (`ARGS_OFF`: бит `collectable` кольца корутины), и аргументы кадра, который сборка может читать, вычисляет отдельная функция (`eval_all_tracked`), так что цикл аргументов голого потока — прежний; кадр формы верхнего уровня, исполняемой в корутине (`eval` в `go`), ставит буферы, как любой, а записи кольца у него нет, так что цепочку его буферов называет запись `CLJ_FREF_ARGS` (`CLJ_ROOTS_ARGS`), а слоты — `CLJ_ROOTS_SPAN`; буфер больше 64 значений (`eval_all_wide`) — все они собственные — называет их счётом (`count`), а не маской, и держится до `argrec_end` вызывающего; буфер, становящийся кадром вызываемого (быстрый путь замыкания, прямой вызов), снимается до `run_body`. Вызов без собственного аргумента ничего не пишет. Кадр программы fused кольцо не видит — он читается через буфер её аргументов; строящаяся мапа литерала с ключами-кейвордами названа так же.
  - *Кольцо после переполнения.* Запись глубже ёмкости (8192) перезаписывает старую, и после возврата ниже под глубиной лежат записи вернувшихся кадров — их чтение было бы чтением мёртвой памяти и завышением. Самое дешёвое верное: флаг `wrapped` в заголовке кольца (сравнение глубины с маской на записи, ветка не берётся) — кольцо, однажды переполненное, сборщик не читает, и собственные ссылки интерпретатора такой корутины читаются как удерживаемые извне. Довод «до сторожевой страницы недостижимо» не взят: стек корутины задаётся (`clj_coro_set_stack_size`), и с поднятым стеком 8192 кадров интерпретатора достижимы.
  - *Частные объекты.* Неопубликованный объект корутины достижим только из её кадров и других её неопубликованных объектов: опубликованный ссылается только на опубликованных, а чужое исполнение неопубликованного не трогает (проверка владельца; в debug сборщик падает на `cc/private-owner`). Значит, счётные ссылки из её неопубликованных объектов на опубликованные — её внутренние рёбра. Сборщик входит в неопубликованный объект из собственной ссылки кадра и из вектора портов, который `alts!` одалживает ожидающему на время парка (`clj_waiter.ports`: интерпретатор держит его в буфере аргументов), каждый объект — один раз (таблица посещённых, потолок 256), кроме типов, которые реестр держит без ссылки, и записывает его рёбра к опубликованным как рёбра корутины.
  - *Почему верно* (продолжение «Решения» выше). Ребро корутина → X записывается только за счётную ссылку, которую держит корутина: слот её кадра или её неопубликованного объекта, каждый прочитан один раз. Список и маска не завышают: раскрутка кадра отпускает ровно его владеющие ссылки, а иначе отмена — которой сборка и является — отпускала бы дважды; пишется её подмножество. Новые виды — те же собственные ссылки. Маска массива скомпилированного кадра и маска буфера аргументов — ровно то, что отпустили бы `clj_c_release_slots` и `release_owned`; бит, переданный вызову (потребление, владеющий параметр, буфер, ставший кадром вызываемого), снят до вызова. Кадр от 64 слотов владеет всеми, и длина у него своя. Переменная кода рантайма держит собственную ссылку или nil в каждой точке вызова, который может парковаться (инвариант `CLJ_ROOTS`; передача очищает её до вызова — `make rooting-hazards` проверяет, что каждая собственная ссылка, живая поперёк такого вызова, названа, и что названная не отдана), блок, назвавший её, ещё не вышел, так что кадр, где она лежит, жив; массив назван длиной, которая не обгоняет присвоенное. Элемент шага fused — шага до его `release`. Запись под проверкой `LAZY` пишет то же множество, что безусловная, или ничего. Поле стека в куче держит собственную ссылку или nil у каждого элемента до длины (`meta` кадра читателя — `CLJ_UNBOUND`, пока не прочитан, и обнуляется до того, как отдана; закрытый итератор обнуляет `held` и `item`); общий стек значений печати и `syntax-quote` укорачивается до отдачи значений; список разбуждений отцепляет узел до разбуждения, и ожидающий-колбэк стоит на одном порту, так что его fn называется одним узлом. Ссылка пути трая собственная с `descend` до возврата вызываемого, а вызываемый отдаёт её (`bnode_own`, `ascend`) после последнего равенства и хеша своего уровня. Буфер со счётом не отдаёт ни одного значения вызову: быстрые пути, где буфер становится кадром вызываемого, — до 64 слотов. Цепочка буферов формы верхнего уровня — те же буферы, что у кадра из кольца, и кадр жив, пока блок, назвавший его, не вышел. Переполненное кольцо, которое могло бы показать вернувшийся кадр, не читается. Недосчёт лишь оставляет цель чёрной. В debug-сборке узел, в который пришло больше рёбер и ссылок сборщика, чем у него ссылок, — внутренняя ошибка `cc/overcount`, если в графе нет потерянного узла (устареть могут только рёбра потерянного). Белая корутина недостижима извне, а с ней её кадры и её неопубликованные объекты, так что их ссылки — ссылки мусора; у чёрной чернота течёт по записанным рёбрам. Всё читается под замком корутины при вердикте «припаркована»: проснуться она не может (`resume` берёт тот же замок), так что её кадры, список и объекты не меняются и живы; проснувшаяся после этого теряет `WATCH` и чернеет, а её рёбра — устаревшие рёбра чёрного узла.
  - *Цена* (corpus-bench, голова против main на одном раннере, 8 пар; run 39299378022, голова 70db41f). Геосреднее отношений: interp 1.045, core+interp 1.035, dev 1.009, closed 0.997; async closed: `async-pipeline` 0.934, `async-broadcast` 1.003, `async-libs` 1.107 (интервал 0.91–1.17 — шум раннера). Скомпилированные бэкенды в пределах шума. Интерпретатор выше границы в 2 %: A/B против `eval.c` из main поверх ветки (run 39299367250, шесть нагрузок) — interp 1.041, core+interp 1.028, из них `async-broadcast`, где кадры — корутин и буферы ставятся, 1.074, голые потоки 1.01–1.05. Голый поток буферов не ставит, и его цикл аргументов — цикл main; остаток — запись `args` и проверка `wrapped` в `run_body`, удержание буфера на медленном пути вызова и в `intrinsic_apply`, кадр шире на слово. До двух последних отсечек (`ARGS_OFF`, цикл вне линии) было 1.092 против того же базиса (run 39295364766). В ядре 1007 точек записи, 4107 ссылок (счётчики — `clj-compile --stats`, «frame references named»). Первый заход, без массива, рантайма и буферов, давал interp 0.978, core+interp 1.005, dev 1.002, closed 0.991 (run 39241140806), а его вариант без отсечек — dev 1.015 (run 39237280189): «может парковаться» тогда спрашивалось у поддерева вызова, с аргументами, и писались слоты, уже отданные.
  - *Чего это не собирает.* Цикл, член которого держит ссылка, которую ничто выше не называет: литерал коллекции и `def`, хеширующие или наблюдающие код программы; ключевой поиск интерпретатора в тип программы с `ILookup` и импл, который держит протокольный диспатч интерпретатора; встроенная функция переопределённого вара (`with-redefs` встроенной) на скомпилированном сайте, который факты считают чистым; опубликованный lazy seq (корень вара, атом), который реализует чистый вызов; экземпляр `deftype`, чей core-метод паркуется, сделанный скомпилированным вызываемым, которого факты считают чистым (его вызывающий не называет ничего, интерпретатор держит буфер на вызове любой fn программы); корутина, чьё кольцо переполнилось. Каждое — утечка, не ошибка; триггер — отчёт о брошенном парке такого вида (ниже) или остаток корпуса (NOTES «Corpus»). Закрыты 2026-10-21 (тесты `gapShapeIsCollected`, `aTopLevelFormsBuffersAreNamed`, фаззер утечек — формы реализации в скомпилированных бэкендах): собственные ссылки в памяти кучи C-кадра (стеки читателя, печати и `syntax-quote`, путь трая), временные внутри вызова или инициализатора, буферы кадра формы верхнего уровня и больше 64 значений, чистый вызов, реализующий паркующийся lazy seq или зовущий паркующийся core-метод `deftype`.
  - *Отчёт о брошенном парке* (`CLJ_PARK_REPORT_S`, по умолчанию выключен; NOTES «Coroutines»). Инструмент dev: будущий пропуск должен выглядеть отчётом, а не тихим ростом. Свип помечает, когда впервые увидел парк; сборка, оставившая чёрной корутину, припаркованную дольше порога, спрашивает, доходит ли до какого-нибудь её канала чернота, не проходящая через неё саму. Не доходит — значит, канал достижим только из корутины, и парк закончит лишь отмена: держит ли её владелец дескриптора или ссылка, которую сборщик не читает. Такой парк называется один раз (stderr и `CLJ_CC_STAT_PARK_REPORTS`). Выключенный, он не читает часов и ничего не обходит.
- *Сборка — отмена, а не освобождение.* Белое множество, в котором есть корутина в собираемом парке, не освобождается: каждой такой — `cancel!` (вид `:explicit`, раз в жизни: флаг `cc_collected`; корутина, которая в своём `finally` опять запарковалась на мусоре, остаётся — утечка, а не бесконечные сборки), ссылки сборщика отпускаются, белые корни подаются снова. Раскрутка идёт на носителе корутины, остальное делает RC, а кольца, которые после неё останутся, подают себя обычным отпусканием. Отличие от JVM — строка `docs/jvm-differences.md`.
- *Когда.* Основное — отпускание канала до ненуля: брошенный `go` даёт кандидатом свой канал результата или канал, на котором стоит. Подстраховка (корутина бежала в момент сборки, внешняя ссылка ушла без кандидата, вмешательство) — свип эвакуации: холодная припаркованная корутина подаётся раз на парк и повторно через 2, 4 … 256 проходов (до 64 с), пока стоит в том же парке; без свипа (`CLJ_EVAC_SWEEP_MS=0`) подстраховки нет. `clj_cc_collect` подаёт все припаркованные сразу. Главный поток: обход и отмена идут на фоновом потоке сборщика; раскрутка корутины с affinity главного — её собственный код на её носителе, как после `cancel!`.
- Решение «раскручивать или выбросить»: раскручивать. Выбросить нельзя: кадры владеют счётными ссылками, которые отпускает только раскрутка (ресурс `with-open`, локальные значения — без раскрутки они утекают, а перечислены они не все: см. «Чего это не собирает» выше), и заявками, которых ждут другие (заявка lazy seq, реализуемого через парк, — `forcing_held`; без раскрутки её ждущие висят вечно). Собранная корутина отменяется (`cancel!`), её `finally` выполняется на её носителе, а остальное доделывает RC — то же, что раньше руками делал `reclaimAbandoned` корпуса. Расхождение с JVM (там `finally` не выполняется) допустимо: наблюдать его может только сам `finally`; прецедент — `close()` генератора Python при сборке.

**Метка «ацикличен»: живое не обходится заново** (решение 2026-10-14; код — `cc.c`, `object.h`, `rc.c`; NOTES «RC»).
- *Что лечим.* Локальная сборка каждые 256 кандидатов обходит всё, что ниже её корней, через узлы с `REACH_LOCAL`, и находит это живым. Массив объектов рождается с битом, так что персистентная структура из массивов — B+-дерево datascript, `deftype`'ы над массивами, — несёт его целиком, а путь, который копирует каждая транзакция, подаёт кандидатами узлы, под которыми всё дерево: 67 % сэмплов datascript — сборщик, 30× JVM (bench/RESULTS.md, «Datascript»).
- *Решение — узел, который обход доказал лежащим вне цикла, помечается, и следующие обходы в него не входят.* Только в локальной сборке: неопубликованные узлы, поток владельца, заголовок пишется без атомиков. Три бита `flags`:
  - `ACYCLIC` (11) — ни узел, ни что-либо ниже него не лежит на цикле из неопубликованных узлов с `REACH_LOCAL`. Метка верна, пока адрес узла есть в таблице проверенных у исполнения и эпоха таблицы равна эпохе исполнения. Бит без записи (новая ячейка по старому адресу, сброшенная таблица) и запись без бита ничего не значат.
  - `GUARDED` (12) — у `MUTABLE`: от его неизменности зависит метка выше. Запись ребра в него поднимает эпоху исполнения, которое пишет, — все его метки разом недействительны.
  - `DIRTY` (13) — у `MUTABLE`: в него писали ребро с тех пор, как его в последний раз видела локальная сборка; обход бит снимает.
- *Когда ставится.* После `blacken`, по компонентам Тарьяна над чёрными узлами: узел помечается, если ни его компонента, ни компоненты ниже него, по записанным рёбрам, не содержат цикла и ниже нет «горячего» узла — `MUTABLE` с `DIRTY`, lazy seq до реализации, транзиентной мапы (её правят на месте при любом счёте) — и ни один узел ниже не держит неопубликованную транзиентную мапу без `REACH_LOCAL`: обход в неё не входит, а правка даст ей бит без записи, которую увидела бы метка. Каждый `MUTABLE`, достижимый из помеченного, получает `GUARDED`. Цикл ниже метку запрещает, хотя на самом узле его нет: мусор под пропущенным узлом (кольцо, которое держит только он) иначе ждал бы следующей сборки — в одном проходе его не нашли бы, а отпущенный узел отдал бы кольцо в буфер; живое кольцо где-то внизу оставляет структуру над собой обходимой. Массив, заполненный при постройке, так охраняется со второго обхода, а volatile, который пишут между сборками, не охраняется никогда, и меток над ним нет — иначе каждая его запись сбрасывала бы все метки.
- *Как используется.* Обход не входит в узел с верной меткой: ребро к нему не записывается, для графа он — как узел без бита. Кандидат с верной меткой уходит из буфера без обхода.
- *Отпускание помеченного кандидата не подаёт* (2026-10-14; `release_reaches_zero` в `rc.c`, `clj_cc_local_unfiled` в `cc.c`). Отпускание до ненуля неопубликованного узла с `REACH_LOCAL`, у которого стоит `ACYCLIC`, сначала спрашивает таблицу исполнения; при верной метке записи нет — ни `BUFFERED`, ни места в буфере, ни поиска при сборке, и узел остаётся уникальным для правки на месте. Почему ничего не теряется: Бэкон–Раджан находит мусорный цикл, если после того, как цикл стал мусором, в буфере есть его член. Мусором цикл делает отпускание последней внешней ссылки, и это отпускание члена M до ненуля (внутренние рёбра остаются). M в этот момент лежит на цикле, значит, по инварианту метки его метка не верна — запись, замкнувшая цикл, подняла эпоху или сняла бит, — и M подаётся, как раньше; если `BUFFERED` у M уже стоит, его запись ещё в буфере. Таблица — та же, что у сборки: неопубликованный объект отпускает только его владелец, а перенос между исполнениями уносит таблицу с собой. Пока идёт локальная сборка, отпускание из её разбора подаёт по-старому: таблица не должна начинаться заново под сборкой, которая её читает. Рубильник — `CLJ_NO_OPT=unfiled`.
- *Инвариант:* верная метка на X ⇒ ни X, ни узел, достижимый из X, не лежит на цикле из неопубликованных узлов с `REACH_LOCAL`. Поэтому пропуск X ничего не откладывает: если X мусор, его и всё под ним отпускает RC каскадом в том же проходе. Ошибка в метке даёт только утечку: пропущенный узел для сборки — внешний держатель (лишняя чернота), узлы под ним в граф не входят и белыми не станут. Неверного освобождения метка дать не может.
- *Почему держится.* В момент метки обход полон (локальный синхронен и без отсечек), и ниже X циклов нет. Новый цикл через узел V, достижимый из X, требует нового ребра; первое новое ребро на цикле, считая от V, выходит из узла U, который существовал при метке и достижим из X старыми рёбрами. Ребро в существующий объект пишется тремя путями, и каждый метку снимает:
  1. Запись в `MUTABLE` (массив, volatile, реализация lazy seq). U достижим из X, значит, при метке обход его видел и, раз метка поставлена, охранял: запись подняла эпоху его владельца — исполнения, чья таблица метку и держит. `GUARDED` снимает ещё только публикация, а опубликованный U на неопубликованном цикле не лежит.
  2. Правка на месте неизменяемого узла (reuse при `rc == 1`, take-out, `clj_realloc`). Правят, только когда оракул уникальности (`clj_is_unique`, `clj_is_unique_unshared`, `clj_rc_token_ok`) ответил «да» про U и про каждый узел от владеемой ссылки до U: иначе правку увидел бы второй держатель. У U единственный родитель, у того тоже, и так до владеемой ссылки, значит, X на этом пути, а оракул, ответив «да», снимает `ACYCLIC`. Если на пути `MUTABLE` (вектор, который держит только volatile, растёт на месте в `vswap!`), правка его значения кончается записью результата обратно в него — пункт 1. Ячейку токена и сдвинутую `clj_realloc` бит не переносит; запись `clj_slot_store`/`clj_slot_init` в узел с `ACYCLIC` снимает бит тоже, на случай правки без оракула.
  3. Транзиентная мапа правится при любом счёте. Над ней меток нет: в графе она горячая, а без `REACH_LOCAL` — ребёнок узла графа, который из-за неё горячий (глубже, за узлом без бита, цикл через неё не находит и обычный обход). Появиться ниже X позже она может только записью в существующий узел — пункты 1–2.
  Других записей ребра нет — только примитивы слотов (§4 «Запись в слот», `make rooting-hazards`). Публикация снимает все три бита: локальный обход в опубликованное не входит, а цикл с неопубликованным узлом опубликованных не содержит. Рождение бит не несёт: `clj_alloc` и `clj_cell_reborn` пишут флаги заново, копии `memcpy` переносят только биты достижимости.
- *Таблица проверенных* — открытая адресация по адресу, у исполнения рядом с его буфером кандидатов (переезжает с ним при `clj_cc_local_borrow`), со своей эпохой: устаревшая очищается при следующей сборке. Записи мёртвых узлов остаются, но новая ячейка рождается без бита и ими не помечена; на 2^17 записях таблица очищается целиком — одно повторное прохождение живого. Эпоха — у исполнения: неопубликованный объект пишет только его владелец, а оба перехода неопубликованного между исполнениями (эпилог корутины, задание блокирующего пула) уносят с собой и состояние сборки (`clj_cc_local_borrow`), так что запись поднимает эпоху того, чья таблица метку держит. Запись без идущего исполнения поднимает общую эпоху, которая входит в эпоху каждого. Чужие записи метки не сбрасывают — другой поток их не обесценивает.
- *Отладочная проверка.* В debug-сборке каждый 16-й пропуск помеченного узла (в тестах — каждый) проверяет ограниченным обходом, что X не достижим из себя, ниже нет горячего и каждый достижимый `MUTABLE` охраняется; нарушение — `clj_ice("cc/acyclic-mark")`.
- *Рубильник* — `CLJ_NO_OPT=acyclic`: меток нет, локальный обход полный. Утечка, которая с ним пропадает, — ошибка меток.
- *Отвергнуто.*
  - *Кандидат по возрасту: ребро вперёд поднимает бит при записи* (2026-10-14). Утверждение «Где циклов нет по построению» верно: цикл требует ребра к объекту не старше владельца, и такое ребро пишет только запись в существующий объект — `MUTABLE` (`aset`, `vreset!`, `reset!`/`swap!`, реализация lazy seq, `deliver`, корень вара, буфер канала, кадр корутины), правка на месте при единственной ссылке (тогда ячейка должна считаться родившейся заново: `vswap!` с `assoc` на месте даёт кольцо vol → U → vol, оба ребра которого — «назад» по рождению) или конструктор, который пишет слот после рождения ребёнка. Но в правило кандидата оно не переводится. Кандидатом должен быть любой член цикла — последнюю внешнюю ссылку отпускают на любом, — а член, построенный над мутабельным объектом до записи вперёд, бита не получил: бит поднимается позже и ниже, и вверх его не несёт ничто. `(let [a (object-array 1) l (Leaf. a) x [l]] (aset a 0 x))`: запись x в a — вперёд, бит у a (и у x, если ставить и значению), у l бита нет; последняя внешняя ссылка на l — кандидата нет, утечка. Поднять бит во всём подграфе значения, отсекая узлы старше владельца, неверно при двух рёбрах вперёд: w — массив, p = [w], u — массив, v = [p], z = [u]; `(aset w 0 z)` помечает z и u, `(aset u 0 v)` — v, а p старше u и отсечён; кольцо u → v → p → w → z → u, у p бита нет. Без отсечки это обход подграфа на каждую запись (`swap!` атома, созданного при старте, обходит всё состояние), и бит пишется в заголовок опубликованного узла, который читают без атомиков (NOTES «RC»). Верная форма — фильтр по времени: у члена N цикла на этом цикле есть ребро вперёд, записанное не раньше рождения N (идём от N против рёбер, пока предок младше; кольцо замкнуто, значит, встретится ребро от старшего к младшему R, записанное после рождения R, а R не старше N), так что подавать N нужно, только если после его рождения была хоть одна запись вперёд. Это требует штампа рождения в заголовке (места нет: `flags` занят, у `rc` 30 бит счёта, а адрес пул переиспользует) и ничего не даёт: запись вперёд — и реализация lazy seq, и заполнение свежего массива свежими детьми, они идут непрерывно, а отпускаемые узлы B+-дерева старые. Узлы persistent-sorted-set кандидатами делает не запись (массивы заполняются старшими), а бит массива с рождения, который и нужен, чтобы построенное над массивом было подаваемо. Взято узкое — отпускание помеченного не подаёт (выше). «Проверка цикла в момент записи» (ниже) снимает это возражение иначе: флаг получает вся компонента в момент замыкания, а не владелец ребра.
  - Массив теряет `REACH`, перестав меняться: заморожен записью в поле `deftype` или публикацией, `aset` возвращает бит. Владельцы, построенные, пока массив был заморожен, бита не получили: `(let [a (object-array 1) l (Leaf. a)] (aset a 0 l))` — кольцо l → a → l без бита у l, сборка из a в l не войдёт, утечка. Починить можно, только проставляя бит всему подграфу значения при каждой записи в однажды замороженный массив — обход без предела на каждый `aset`, навсегда; отказ в `aset` после публикации меняет язык (§3 «Инвариант: язык не меняется»).
  - Потолок на число узлов локального обхода: обход до потолка повторяется на каждой сборке, а кольцо за потолком — утечка, пока нет повтора, как у глубокого обхода. Лечит симптом.
  - Темп по объёму — порог буфера, растущий с числом узлов прошлого обхода, как куча GC растёт с живым: кольцо не теряется, но живое обходится, только реже, а зомби-ячейки буфера держат память пропорционально живому. Не нужен, пока повтор снимают метки.
- *Цена.* Запись ребра в неопубликованный `MUTABLE` без `DIRTY` — запись заголовка (у свежего массива — раз до первого обхода); с `GUARDED` — ещё инкремент эпохи исполнения. Оракул уникальности — тест бита в уже прочитанных флагах. Отпускание помеченного до ненуля — поиск в таблице вместо записи в буфер. Сборка — проход Тарьяна по графу, который она построила. Числа — bench/RESULTS.md, NOTES «RC».

**Проверка цикла в момент записи** (решение 2026-10-14; код — `clj_reach_from` и `clj_cc_edge_check` в `object.h`, `clj_cc_store_check` в `cc.c`; NOTES «RC»). Кандидат локальной сборки — неопубликованный объект с битом «на цикле», отпущенный до ненуля, а не любой с `REACH_LOCAL`: `REACH` значит «достигает изменяемого», и B-дерево из массивов datascript целиком подавало кандидатов, хотя циклов в нём нет. Цикл появляется в один момент — записью ребра, — и проверяется там.
- *Биты* (`flags`). `HEAPREF` (14): на изменяемый объект с `REACH_LOCAL` указало ребро кучи. Ставится такому ребёнку в каждом `clj_slot_init`/`clj_slot_store` и атомарной записи — вне строки, в `clj_cc_reach_local`, куда `clj_reach_from` уходит только за ребёнком с `REACH_LOCAL`, — и не снимается; опубликованный считается имеющим его, его заголовок не пишется. Только таким: проверяется запись лишь в изменяемый, а изменяемый без `REACH_LOCAL` (lazy seq, чей thunk не достигает неопубликованного изменяемого; биты изменяемого не меняются после рождения) не лежит ни на каком цикле, который локальная сборка могла бы освободить. Запись бита в заголовок каждого ребёнка стоила nested-update 3.3 % closed (run 38759117094). `ONCYCLE` (7, бит, который раньше занимал `REACH_LOCAL`: маска встроенного отпускания осталась прежней константой, а маска с 16-м битом стоила nested-update 5 % closed): объект на цикле неопубликованных объектов. Ставят проверка и локальная сборка; при записи ребра не наследуется (только копия узла берёт его у источника: `clj_reach_copy`, копии `with-meta`, ячейка токена). `REACH_LOCAL` переехал на 15-й (а `RETAINED` статистики — на 16-й): маски горячих путей остаются ниже 16-го бита, одна инструкция `movz` на arm64; тег владельца debug-сборки начинается с 17-го и занимает 15 бит.
- *Какая запись проверяется.* Ребро `X → Y`, оба неопубликованы, у `Y` есть `REACH_LOCAL`, и `X` — изменяемый тип (массив объектов, volatile, lazy seq, экземпляр `deftype` со ссылочным мутабельным полем — единственные изменяемые, которые бывают неопубликованными) с `HEAPREF`, или `Y = X`, или `X` — транзиентная мапа, которую правят при любом счёте (`flat_assoc`, явный `clj_cc_edge_check`; `HEAPREF` у неё нет, так что такая запись обходит всегда). Без `HEAPREF` у `X` путь от `Y` к `X` невозможен: его последнее ребро вело бы в `X` из кучи. Без `REACH_LOCAL` у `Y` локальная сборка в `Y` не войдёт, и цикла через него она не соберёт ни с проверкой, ни без. Неизменяемый `X` не проверяется: его правят на месте, только когда он уникален от владеемой ссылки вниз (п. 3 ниже).
- *Проверка* (`clj_cc_store_check`). Обход от `Y` по тем узлам, в которые входит локальная сборка (неопубликованные, с `REACH_LOCAL`, не реестровые), мимо узлов с верной меткой «ацикличен»; если встречен `X`, обратный обход от `X` по записанным рёбрам помечает `ONCYCLE` каждый узел, из которого `X` достижим, и сам `X`: с новым ребром это одна компонента. `Y = X` помечается без обхода.
- *Бюджет* — 256 узлов и 4096 прочитанных детей; у реализации lazy seq — 8 узлов и 64 ребёнка (ниже, «Ленивые seq»). Сверх него `X` подаётся в локальный буфер, как кандидат (`BUFFERED`), но без сборки и без передачи фону изнутри записи: слот ещё не записан. Локальная сборка, которая возьмёт запись, обходит от `X` без предела и помечает `ONCYCLE` каждую чёрную компоненту Тарьяна с циклом (тот же проход, что ставит метки «ацикличен»). Флага на одном `X` мало: члены кольца, построенные раньше, остались бы без него.
- *Кандидат* — отпускание до ненуля неопубликованного объекта с `ONCYCLE` (без верной метки «ацикличен», как раньше). Встроенные `clj_release` и `clj_drop_value` уходят на медленный путь по `ONCYCLE` вместо `REACH_LOCAL`: отпускание узла B-дерева — снова встроенный декремент.

*Инвариант I.* В любой момент у каждого цикла из неопубликованных узлов с `REACH_LOCAL` (цикла, который может собрать локальная сборка) все члены несут `ONCYCLE` или один из членов стоит в локальном буфере (`BUFFERED`).

*Следствие: у мусорного цикла есть подаваемый член в момент, когда он становится мусором.* Мусором цикл делает отпускание последней внешней ссылки — отпускание члена `M` до ненуля (внутренние рёбра остаются). Если член цикла в буфере, его запись обработают, когда цикл уже мусор, и пробное удаление от неё обойдёт цикл (все члены — с `REACH_LOCAL`) и освободит его. Иначе по *I* у `M` есть `ONCYCLE`, верной метки у члена цикла нет (её инвариант), и `M` подаётся.

*Доказательство I* — индукцией по записям рёбер. Флаг не снимается; запись буфера уходит только в сборку или, при публикации, в общий буфер, а опубликованный цикл не локальный.
1. Новый цикл появляется только с новым ребром `X → Y` и состоит из него и пути `Y →* X` из существующих рёбер; старые циклы держат *I* по предположению. Ребро без записи возникает только копией существующего (`memcpy` копии, `clj_slot_init_copied`, `clj_realloc`), а у новой копии-владельца нет входящих рёбер, пока она строится. Разрыв ребра циклов не создаёт.
2. Если `X` или `Y` опубликован, нового локального цикла нет: дети опубликованного опубликованы, так что от опубликованного `Y` к неопубликованному `X` пути нет, а цикл через опубликованный `X` — общий.
3. Неизменяемый `X` правят, когда он и каждый узел от владеемой ссылки `R` до него уникальны (оракул уникальности, токены reuse, `new*` на месте, take-out): у каждого один держатель, у `R` — только стек. Путь `Y →* X` поднимался бы по этой цепочке до `R` и требовал бы ребра в `R` из кучи. Значит, новое ребро в неизменяемый `X` цикла не замыкает. Исключение — транзиентная мапа, которую правят при любом счёте; она проверяется явно. Изменяемый узел на цепочке (вектор, который держит только volatile, растёт на месте в `vswap!`) отдаёт значение take-out'ом и получает его обратно записью в себя — проверяемой.
4. Изменяемый `X` и `Y ≠ X`: путь `Y →* X` кончается ребром `Z → X`, существующим до записи; оно записано примитивом, поставившим `X` бит `HEAPREF`, или скопировано с такого. Бит не снимается: ячейка по старому адресу (`clj_alloc`, `clj_cell_reborn`) рождается без него, но ребро на неё из кучи тогда висячее, а take-out (`clj_map_get_take`, `clj_volatile_conj_take`) обнуляет слот, и возврат — новая запись. Самоссылка `X → X` может потерять бит `X` (`clj_reach_from` пишет флаги владельца после ребёнка), но через неё к `X` не приходит никто, кроме `X`. Значит, проверка не пропускает запись из-за `HEAPREF`.
5. Все узлы пути — члены нового цикла, то есть (условие *I*) неопубликованы и с `REACH_LOCAL`; обход входит в каждый, если не отрезан меткой или бюджетом.
6. Метка не отрезает. Верная метка на `M` — ни один узел ниже `M` не лежит на цикле. Если `M` на пути, `X` ниже `M`, а запись в изменяемый `X` ниже метки — запись в охраняемый объект: `clj_reach_from` поднимает эпоху исполнения до проверки, и все его метки недействительны. Транзиентной мапы ниже метки не бывает (§7 «Метка «ацикличен»»).
7. В пределах бюджета обход находит `X`, и обратный проход помечает каждый узел каждого пути `Y →* X` среди обойдённых — то есть каждого члена каждого нового цикла (п. 5–6). Сверх бюджета `X` встаёт в буфер, и *I* держится этой записью. Сборка, которая её обработает, найдёт кольцо мусором (белое, освобождается) или живым — тогда его члены достижимы из `X` через узлы с `REACH_LOCAL`, чёрные, в одной компоненте с циклом, и помечаются; с этого момента *I* держат флаги.
8. Перенос неопубликованного между исполнениями уносит буфер (`clj_cc_local_borrow`); флаги — в заголовках.

Ошибка проверки даёт только утечку: лишний флаг — лишний кандидат, недостающий — несобранный цикл. Освобождает по-прежнему только пробное удаление.

- *Пути записи* (по коду; все идут через `clj_reach_from`, прочий код держит вне слотов `make rooting-hazards`). Проверяются: `aset` и встроенный `clj_c_aset` компилятора, `vreset!`/`vswap!` (и take-out `vswap-take*`), реализация lazy seq (`publish` в `seq.c`), `letfn` (его имена — volatile), транзиентная мапа. Без проверки по п. 3: правка на месте при `rc == 1` (reuse, токены, `new*`/`field*` на месте, take-out и возврат, `clj_realloc`), транзиентный вектор и trie-мапа (это сама коллекция, правится по уникальности). Опубликованы с рождения, локального цикла через них нет: атом, канал, промис и `deliver` (промис — канал), `delay` (атом внутри), корень вара, буфер канала, корутина и её кадры. `set!` ссылочного мутабельного поля `deftype` (§4 «Роли конструкций») — `clj_slot_store` в экземпляр, рождённый `MUTABLE` с `REACH_LOCAL`, как volatile, то есть с проверкой по п. 4: рёбра в экземпляр ставят ему `HEAPREF`, а неизменяемые поля он получает при рождении, когда входящих рёбер у него нет (п. 1). У опубликованного экземпляра запись — обмен слота (`clj_slot_exchange`) и по п. 2 ничего не проверяет. Битовое (`^long`, `^double`, `^float`) и непосредственное (`^int`, `^char`, …) мутабельное поле ребром не бывает: обход детей его пропускает или видит в нём не указатель, так что его `set!` циклов не создаёт и тип с одними такими полями не изменяемый.
- *Ленивые seq.* Правило «реализованную ячейку старше `X` в поиске можно не проходить» неверно. `(let [v (volatile! nil) r (doall (lazy-seq (cons v nil))) l (lazy-seq (cons 1 r))] (vreset! v l) (seq l))`: `r` реализована до рождения `l`, но через `v`, записанный позже, ведёт к `l`; ячейка `(seq l)`, которую строит реализация `l`, без обхода через `r` флага не получает, и её отпускание последним — утечка (`StoreCheckTests.lazySeqs`). Реализованная ячейка неизменна, но её подграф — нет: изменяемое под ней пишут и после. Поэтому у реализации бюджет мал — 8 узлов и 64 ребёнка, — а сверх него ячейка подаётся в буфер (п. 7 ниже). Большой бюджет почти всегда был бы превышен: значение ячейки seq над индексом достигает индекса, и у datascript 73.8k реализаций на итерацию обходили по 240 узлов, 67.0k из них упирались в бюджет, closed ×1.64 к main (run 38628605344; без бюджета — 860 узлов на реализацию). Без обхода вовсе (каждая реализация — запись в буфер) datascript closed 0.761 к main, но medley 1.083: его 18.0k реализаций на итерацию замыкают кольца в 3 узла, и обход в 8 узлов их помечает, не подавая ячейку (run 38743383391: medley без отсрочек, 5.9k найденных колец). Запись в буфер на реализацию — не больше, чем было до проверки, когда кандидатом был каждый узел с `REACH_LOCAL`, отпущенный до ненуля; большинство таких ячеек к сборке мертвы, и их запись лишь возвращает ячейку.
- *Опубликованные.* Атом, канал, корутина рождаются опубликованными, так что главный сценарий — замыкание над атомом в его же состоянии, `(swap! state assoc :on-click #(swap! state …))`, — и кольцо через промис целиком общие. Правило общей сборки не меняется: кандидат — опубликованный объект с `REACH`, а запись в опубликованный объект ничего не проверяет и не подаёт (лишнее: последнее внешнее отпускание члена общего кольца и так подаётся). Две записи на двух потоках, замыкающие одно кольцо атомов, собираются, как раньше. Перевести общую сборку на флаг значило бы писать бит в заголовок опубликованного объекта с фонового потока, а `clj_reach_from` пишет флаги уникального опубликованного владельца простой записью (`rc == 1`, без атомиков) — их пришлось бы сделать атомарными. Это отдельный шаг с отдельным триггером (ниже, «Состояние»).
- *Рубильник* — `CLJ_NO_OPT=store-check`: проверки нет, и `ONCYCLE` ставится везде, где появляется `REACH_LOCAL`: при рождении изменяемого типа и вместе с каждым `REACH_LOCAL`, который владелец берёт у ребёнка (глобал `clj_cc_kill_oncycle`, читается только в `clj_cc_reach_local`), а копия узла берёт оба бита у источника. Значит, `ONCYCLE ≡ REACH_LOCAL` — прежнее правило. Ставится до первого объекта.
- *Отладочная проверка.* В debug-сборке встроенное отпускание уходит на медленный путь и по `REACH_LOCAL`; каждое 16-е отпускание до ненуля объекта с `REACH_LOCAL` без `ONCYCLE` (в тестах проверки — каждое) строит без освобождения граф прежнего правила — тот, что построила бы локальная сборка от такого кандидата, до 1024 узлов, — и в каждой его компоненте с циклом требует `ONCYCLE` у всех членов или `BUFFERED` у одного, иначе `clj_ice("cc/store-check-missed")`. Не во время локальной сборки: её белые разбираются.
- *Перепись* (2026-10-14, run 38615918374, closed-сборка с `-DCLJ_STATS`, на итерацию; правило ещё без п. 3 — проверялись и неизменяемые владельцы с `HEAPREF`). ### Свой GC — перебор для v1
Теряет reuse (нет счётчика), детерминизм (паузы в 8 мс бюджете), простой интероп (два heap'а, handle table для Swift-held значений, несобираемые циклы через границу — задача уровня WebKit JS↔DOM). Даёт bump только если перемещающий, а перемещение требует точных корней. Mono на iOS с SGen доказывает, что GC на iOS возможен, но там весь heap свой. **Решение:** свой заголовок + пул + RC как политика; дверь для неперемещающего Immix-подобного остаётся открытой, если профиль потребует. Скорее всего — никогда.

**Запасной план, если RC себя не оправдает.** Записан заранее, чтобы решение принималось по числам, а не по усталости.
- *Триггер:* макробенч §10 (приложение из списка + сеть + рендер) в **скомпилированном** режиме проигрывает JVM-Clojure/Hermes на копирующих персистентных операциях, и профиль показывает, что это RC-трафик (атомарные пары на shared-данных, retain/release детей при копии узла), который reuse, fusion и регионы уже не снимают. Интерпретаторные цифры триггером не считаются. Сегодняшние ориентиры: копия узла на 16 детей под атомом ≈ 200 нс сверх in-place (`swap! assoc` 91 → 288), доля атомарных пар при состоянии в атоме 80 % ≈ 300 нс на тик.
- *Кандидат:* свой GC **без stop-the-world**: неперемещающий (адреса стабильны — интероп и `Unmanaged` на Swift-стороне не меняются), конкурентная маркировка с коротким снимком корней вместо паузы, консервативное сканирование C-стека (нативы и Swift-кадры не нуждаются в stack maps — цена перемещающего GC, которую мы не платим), точные корни только там, где они и так известны: слоты кадров интерпретатора, вары, атомы. Write barrier нужен только в точках мутации, а их список уже есть — это список публикаций `clj_share` (var/atom/volatile, ячейка lazy seq, in-place reuse, буфер канала); новые объекты рождаются помеченными. Иммутабельный heap делает такой GC дешёвым там, где Go платит барьером на каждой записи.
- *Предпочтительная форма — гибрид по классу объекта, не полный GC:* **unshared считается RC, shared трассируется.** Гонку на неатомарном счётчике обнаружить нельзя (потерянный инкремент молчит), но момент, когда она становится возможной, известен точно — публикация, тот же флаг. Опубликованный объект перестаёт считаться: retain/release на нём — уже существующая проверка флага и ничего вместо атомарной пары, то есть исчезают те самые 80 % атомарных пар при состоянии в атоме. Sweep трогает только пул (дети shared-объекта shared по инварианту). Циклы через опубликованное собираются трассировкой; если may-cycle типы (атомы, мутабельные deftype, thunk'и) класть в пул при создании, trial deletion не нужна — два механизма этого раздела схлопываются в один. Reuse при rc==1 остаётся на локальных данных, где он и работает. Трудности: корни — ссылки на shared лежат и внутри unshared-объектов, и на стеках: либо remembered set с барьером на записи ребёнка при конструировании (цена на самом горячем пути), либо маркировка идёт от корней сквозь unshared-объекты; во втором случае конкурентная маркировка гоняется с RC-освобождением unshared другим потоком — лечится per-thread сканированием в safepoint'ах (каждый поток маркирует свой стек и свою unshared-часть графа, как Go сканирует стеки); финализация shared-объектов (host-объекты, локи) недетерминирована. Прецедент с обратным критерием — Ulterior Reference Counting (Blackburn & McKinley 2003): молодые трассируются, старые считаются; у нас критерий — видимость из потока, не возраст.
- *Что теряется с полным GC:* reuse при rc==1 (auto-transient, последнее использование, in-place в `swap!`) — уникальность пришлось бы выводить статически; детерминированное освобождение host-объектов и локов; память ×2–5; trial deletion становится не нужна.
- *Переключение GC ↔ RC.* В рантайме — нет: чтобы вернуться на RC, счётчики надо вести всегда, то есть платить обе цены. **Во время сборки — да**, как `--mm:arc|orc|markAndSweep` у Nim или GC на выбор при трансляции PyPy: RC замкнут в `clj_retain`/`clj_release`/`clj_alloc`/`each_child`/`finalize`, GC-сборка делает retain/release no-op и добавляет корни и барьер. Условие, которое надо держать с сегодняшнего дня: никакой код вне этих точек не опирается на семантику счётчика, кроме проверок `clj_is_unique`, которые в GC-сборке честно отвечают «нет» (деградация в копию, не в ошибку). Один тест-инвариант: сьют проходит с `clj_is_unique ≡ false` — сборка `-DCLJ_NO_REUSE` (`make test-noreuse`, `clj_reuse_enabled()` как признак сборки) делает именно это, и все сьюты в ней зелёные, то есть инвариант теперь проверяется, а не только записан.
