## 4. Рантайм

### Представление значений
- **Не Swift-классы.** Свой заголовок объекта, raw-указатели (`Unmanaged`), свой аллокатор. Swift-классы удобны в первую неделю и закрывают дверь навсегда (атомарный ARC, `swift_allocObject` → malloc, нельзя сменить заголовок).
- **RC свой:** неатомарный по умолчанию, biased — флаг «shared» при **публикации**, после чего атомарный. Гонка за счётчик требует одновременной достижимости из двух потоков, а данные иммутабельны, поэтому список публикаций закрыт: запись в разделяемую мутабельную ячейку (var root/meta, атом и любой ref-тип, буфер канала, ячейка реализации lazy seq, интернированные таблицы и реестры рантайма — всё, что под локом читает любое исполнение), захват при spawn (`go`/`future`/`thread`), экспорт в Swift. `clj_share` обходит граф с обрезкой на уже shared-узлах; инвариант «дети shared — shared» держится на записи (in-place reuse при rc==1 шарит новый child), поэтому каждый объект помечается не более одного раза за жизнь — амортизированно O(1), без барьера на чтение.
  - **Смена потока — не триггер.** Парк/резюм go-блока и передача по каналу — handoff: объект в каждый момент трогает одна сторона, лок канала даёт happens-before, relaxed-счётчик корректен. Unshared ⇒ достижим только из одного стека — это и делает plain-запись флага владельцем безопасной. Владелец — исполнение (`clj_coro`, у голого потока — неявное), не поток; debug-сборка это проверяет (NOTES «RC»).
  - [ ] **Запись в слот — один inline-примитив, пропущенная публикация — ошибка компиляции.** Список публикаций закрыт, но держится на внимательности: забытый `clj_share` молчит (потерянный неатомарный инкремент не виден), ловит его только debug-проверка владельца и только на пути, который тест гоняет из двух исполнений. Решение — слот объекта кучи получает свой тип `clj_slot` (`struct { clj_value v; }`), и голое `obj->field = v` не компилируется. Входов три: `clj_slot_store(owner, slot, v)` — при shared-владельце публикует `v` до записи (это семь одинаковых `static store` в map/vector/set/sorted/queue/record/shape, сведённые в один); `clj_slot_init` — заполнение свежего объекта до его видимости, без проверки флага (debug: владелец не shared); `clj_root_store` — место вне кучи (C-глобал, реестр), публикует всегда. Контейнеры между исполнениями — атом, канал, корутина — рождаются shared, как вар: тогда `reset!`, `put!`, аргументы spawn и результат корутины публикуются тем же примитивом, и безусловные `clj_share` в них исчезают; вручную остаются граница FFI (`Value`, `objc-block`, `objc-reify`) и C-глобалы. Слот ссылочного типа пишется под его локом — примитив лок не берёт, debug-сборка проверяет, что он взят. Время жизни заимствований (`unlink`, `retain_if_live`) и чтение слота ссылочного типа без его лока примитив не закрывает — это не публикация. Потребители — оба бэкенда: если сгенерированный C пишет в слоты сам, генератор переходит на те же примитивы. В релизе цена нулевая (обёртка над словом). Не сделано: тип и примитивы, перевод полей (около 90 объявлений `clj_value` в заголовках ядра и массивы слотов узлов), рождение атома, канала и корутины shared, проверка в гейтах, что `.v` пишут только примитивы.
  - **Флаг монотонен.** Всё, что попало в атом или var, атомарно для всех навсегда, включая владельца; `assoc` на shared-мапе рождает shared-узлы, так что при состоянии приложения в одном атоме весь домен на атомарном пути после первого `reset!` — ровно baseline Swift ARC, проигрыша к нему нет, выигрыш только на транзиентах. Проверка, закрывающая вопрос: доля retain/release на shared-объектах (debug-счётчики на `clj_retain_slow`/inline-пути) на нагрузке с состоянием в атоме — мерить после конвенции +0/+1 (§6b, «Интерпретатор до компилятора», п. 3), иначе `(get db :k)` с возвратом +1 завышает долю. *Замерено* (bench/RESULTS.md, «Atoms»): на тике «два `swap!` с `assoc-in`/`update` плюс два чтения через `deref`/`get-in`» при состоянии в атоме 79–83 % пар retain/release идут по атомарному пути (0 % на том же тике над локальной мапой), ~80 пар на тик — порядка 300 нс, того же порядка, что один `swap! assoc` in place (140 нс) и в пять раз меньше его же с копией (765); для записи BRC ничего не решает — копия пути на swap дороже её retain'ов (трюк уникальности с тех пор снят, см. «Атомы»), а на чтении атомарная пара и есть вся цена RC; читает UI-состояние главный поток каждый кадр, поэтому BRC взят для него одного (ниже).
  - [ ] **BRC с одним владельцем — главным потоком.** Цена shared снимается с main и ложится на остальные потоки. Владелец фиксирован, поэтому id в заголовке не нужен: 16 зарезервированных бит `flags` становятся счётчиком main (`main16`), `rc` — счётчиком остальных, объект жив, пока сумма больше нуля. Не сделано: всё; порядок — после примитива записи в слот (выше), потому что он сводит записи в слоты к одному месту и аудит записей в `flags` проходит по нему.
    - Main работает только с `main16`, обычными load/store, с любым объектом — своим и опубликованным с пула; признак «я на main» — inline TLS. Пул работает только с `rc`: unshared — обычный путь, shared — атомарный, как сейчас.
    - Объект, аллоцированный на main, рождается shared. Пул видит только опубликованное, так что для него ничего не меняется, а публикация с main обхода не делает: `clj_share` на main упирается в уже помеченный корень. Исключение — результат блокирующей задачи, работавшей за go-main корутину: он аллоцирован на потоке пула, и main при его публикации обходит.
    - Переполнение `main16` — атомарный перенос половины в `rc`. Release на main при `main16 == 0` (ссылка пришла из чужого домена, например из канала) — атомарный декремент `rc`.
    - Освобождение по протоколу Choi 2018. `main16` дошёл до 0 — relaxed-загрузка слова `rc`: 0 — освобождение на месте без атомика (сумма ноль, retain некому); иначе `fetch_or` бита MERGED в `rc`: старый счётчик 0 — освобождает main, иначе объект слит, main дальше атомарен по `rc` (плюс свой обычный бит в `flags`, чтобы не читать чужое слово на каждой операции), освобождает обнуливший `rc`. Чужой release, уводящий `rc` в минус (ссылка, учтённая в `main16`), ставит QUEUED и кладёт объект в очередь main; main сливает на обороте run loop (`clj_sched_main_pump`).
    - `is_unique` на main — `main16 == 1` и `rc == 0`: reuse работает и на опубликованном.
    - Условия: после рождения слово `flags` пишет только main — поздние пометки IMMORTAL (`compiled.c` при публикации констант юнита, `runtime.c`, `builtins_number.c`, `error.c`) либо до видимости, либо атомарны; debug-проверка владельца уходит с этих бит; debug-счётчики и проверки, читающие `rc`, читают сумму. Без main-носителя (CLI, тесты без `clj_sched_main_install`) `main16` не трогает никто — сегодняшнее поведение.
    - Предел: BRC убирает атомарную инструкцию, но не конфликт за кэш-линию — `main16` и `rc` в одном заголовке, обычный store main тоже требует линию эксклюзивно. Горячий объект, который main и пул трогают одновременно (корень состояния, читаемый с обеих сторон), гоняет линию между ядрами и при BRC; там помогают только меньше retain'ов (заимствование +0) или immortal. Счётчик здесь хуже лока атома: лок конфликтует при двух писателях, а счётчик — и при одних читателях, потому что retain на чтении — запись.
    - Замер: rc-share (bench/RESULTS.md, «Atoms») на main до и после, и тот же тик на main, пока пул читает то же состояние; пул не должен сдвинуться.
  - **Отложенные альтернативы**, если доля окажется большей частью и вне main: BRC (Choi 2018) с владельцем-континуацией — владелец сохраняет быстрый путь на опубликованном, парк не ломает биас; цена — owner id и два счётчика в заголовке (cons 32 → 40 байт, скачок size class), протокол merge с очередью на владельца и переиспользование id континуаций (незавершённый merge при переиспользовании — порча памяти). Владелец-поток пула — id мало, lifecycle известен, но заголовок и merge те же, re-bias в BRC нет: всё аллоцированное до последней миграции медленно для нового потока навсегда — эквивалент «шарить при парке», хуже флага по этому множеству, лучше только тем, что владелец остаётся быстрым на своём опубликованном; закрепить корутину за носителем ради этого — потерять балансировку (§8). Зарезервированные биты заняты счётчиком main (выше), так что любой BRC сверх него — это +8 байт. Журнал счётчиков на поток (отложенный RC: retain — запись в буфер потока, сборщик применяет журналы по эпохам, как LXR и Levanoni–Petrank) снимает атомики со всех потоков, но shared освобождается с задержкой эпохи на потоке сборщика, reuse на shared пропадает, а потоки Swift и GCD вне эпох требуют атомарного запасного пути; это вариант внутри запасного плана §7, а не отдельное решение. Третья альтернатива, предпочтительнее BRC — **shared ⇒ без RC вообще**: опубликованный объект уходит в трассируемый пул (§7, «Запасной план»), retain/release на нём — та же проверка флага, что сегодня, но вместо атомарной пары ничего.
- **Аллокатор:** size-class пулы (HAMT-узел, cons, small-map, бокс, замыкание с k захватами), per-thread, bump внутри свежего слаба, free-list потом. Отбирает у GC главный козырь — дешёвую аллокацию.
- **Pointer tagging, не NaN-boxing.** Три младших бита (выравнивание 8) под immediates: fixnum 63 бит (`xx1`), keyword, bool, nil, char. `double` боксится в ⊤-контекстах и unboxed везде, где выведен — слоты shapes по наблюдению, `deflayout`, типизированные векторы, локалы. Почему не NaN-boxing: на arm64e старшие биты указателя занимает PAC-подпись, а NaN-boxing кладёт указатель в младшие 48 бит и конфликтует с ней (JSC пережил ценой спецобработки); int там только 32-битный против 64-битной семантики `long`; double'ы у нас и так unboxed там, где важно (UI-математика — `deflayout`/tuples). Fixnum 63 бит (один тег-бит) + бокс int64 на диапазон 2^62…2^63 (семантика переполнения `long` сохраняется, `unchecked-*` заворачивают в 64 битах) + BigInt по `+'`. Контракт языка — 64-битный `long`; fixnum — представление интерпретатора, не тип. Все известные расхождения с JVM с классом «править / осознанно / по триггеру» — `docs/jvm-differences.md`.
