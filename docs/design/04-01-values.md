## 4. Рантайм

### Представление значений
- **Не Swift-классы.** Свой заголовок объекта, raw-указатели (`Unmanaged`), свой аллокатор. Swift-классы удобны в первую неделю и закрывают дверь навсегда (атомарный ARC, `swift_allocObject` → malloc, нельзя сменить заголовок).
- **RC свой:** неатомарный по умолчанию, biased — флаг «shared» при **публикации**, после чего атомарный. Гонка за счётчик требует одновременной достижимости из двух потоков, а данные иммутабельны, поэтому список публикаций закрыт: запись в разделяемую мутабельную ячейку (var root/meta, атом и любой ref-тип, буфер канала, ячейка реализации lazy seq, интернированные таблицы и реестры рантайма — всё, что под локом читает любое исполнение), захват при spawn (`go`/`future`/`thread`), экспорт в Swift. `clj_share` обходит граф с обрезкой на уже shared-узлах; инвариант «дети shared — shared» держится на записи (in-place reuse при rc==1 шарит новый child), поэтому каждый объект помечается не более одного раза за жизнь — амортизированно O(1), без барьера на чтение.
  - **Смена потока — не триггер.** Парк/резюм go-блока и передача по каналу — handoff: объект в каждый момент трогает одна сторона, лок канала даёт happens-before, relaxed-счётчик корректен. Unshared ⇒ достижим только из одного стека — это и делает plain-запись флага владельцем безопасной.
  - **Флаг монотонен.** Всё, что попало в атом или var, атомарно для всех навсегда, включая владельца; `assoc` на shared-мапе рождает shared-узлы, так что при состоянии приложения в одном атоме весь домен на атомарном пути после первого `reset!` — ровно baseline Swift ARC, проигрыша к нему нет, выигрыш только на транзиентах. Проверка, закрывающая вопрос: доля retain/release на shared-объектах (debug-счётчики на `clj_retain_slow`/inline-пути) на нагрузке с состоянием в атоме — мерить после конвенции +0/+1 (§6b, «Интерпретатор до компилятора», п. 3), иначе `(get db :k)` с возвратом +1 завышает долю. *Замерено* (bench/RESULTS.md, «Atoms»): на тике «два `swap!` с `assoc-in`/`update` плюс два чтения через `deref`/`get-in`» при состоянии в атоме 79–83 % пар retain/release идут по атомарному пути (0 % на том же тике над локальной мапой), ~80 пар на тик — порядка 300 нс, того же порядка, что один `swap! assoc` in place (140 нс) и в пять раз меньше его же с копией (765); BRC не берём — копия пути на swap дороже её retain'ов (трюк уникальности с тех пор снят, см. «Атомы»; вывод про BRC не меняется).
  - **Отложенные альтернативы**, если доля окажется большей частью: BRC (Choi 2018) с владельцем-континуацией — владелец сохраняет быстрый путь на опубликованном, парк не ломает биас; цена — owner id и два счётчика в заголовке (cons 32 → 40 байт, скачок size class), протокол merge с очередью на владельца и переиспользование id континуаций (незавершённый merge при переиспользовании — порча памяти). Владелец-поток пула — id мало, lifecycle известен, но заголовок и merge те же, re-bias в BRC нет: всё аллоцированное до последней миграции медленно для нового потока навсегда — эквивалент «шарить при парке», хуже флага по этому множеству, лучше только тем, что владелец остаётся быстрым на своём опубликованном. Место под биты зарезервировано, схемы совместимы: флаг сейчас. Третья альтернатива, предпочтительнее BRC — **shared ⇒ без RC вообще**: опубликованный объект уходит в трассируемый пул (§7, «Запасной план»), retain/release на нём — та же проверка флага, что сегодня, но вместо атомарной пары ничего.
- **Аллокатор:** size-class пулы (HAMT-узел, cons, small-map, бокс, замыкание с k захватами), per-thread, bump внутри свежего слаба, free-list потом. Отбирает у GC главный козырь — дешёвую аллокацию.
- **Pointer tagging, не NaN-boxing.** Три младших бита (выравнивание 8) под immediates: fixnum 63 бит (`xx1`), keyword, bool, nil, char. `double` боксится в ⊤-контекстах и unboxed везде, где выведен — слоты shapes по наблюдению, `deflayout`, типизированные векторы, локалы. Почему не NaN-boxing: на arm64e старшие биты указателя занимает PAC-подпись, а NaN-boxing кладёт указатель в младшие 48 бит и конфликтует с ней (JSC пережил ценой спецобработки); int там только 32-битный против 64-битной семантики `long`; double'ы у нас и так unboxed там, где важно (UI-математика — `deflayout`/tuples). Fixnum 63 бит (один тег-бит) + бокс int64 на диапазон 2^62…2^63 (семантика переполнения `long` сохраняется, `unchecked-*` заворачивают в 64 битах) + BigInt по `+'`. Контракт языка — 64-битный `long`; fixnum — представление интерпретатора, не тип. Все известные расхождения с JVM с классом «править / осознанно / по триггеру» — `docs/jvm-differences.md`.
