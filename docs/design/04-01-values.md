## 4. Рантайм

### Представление значений
- **Не Swift-классы.** Свой заголовок объекта, raw-указатели (`Unmanaged`), свой аллокатор. Swift-классы удобны в первую неделю и закрывают дверь навсегда (атомарный ARC, `swift_allocObject` → malloc, нельзя сменить заголовок).
- **RC свой:** неатомарный по умолчанию, biased — флаг «shared» при **публикации**, после чего атомарный. Гонка за счётчик требует одновременной достижимости из двух потоков, а данные иммутабельны, поэтому список публикаций закрыт: запись в разделяемую мутабельную ячейку (var root/meta, атом и любой ref-тип, буфер канала, ячейка реализации lazy seq, интернированные таблицы и реестры рантайма — всё, что под локом читает любое исполнение), захват при spawn (`go`/`future`/`thread`), экспорт в Swift. `clj_share` обходит граф с обрезкой на уже shared-узлах; инвариант «дети shared — shared» держится на записи (in-place reuse при rc==1 шарит новый child), поэтому каждый объект помечается не более одного раза за жизнь — амортизированно O(1), без барьера на чтение.
  - **Смена потока — не триггер.** Парк/резюм go-блока и передача по каналу — handoff: объект в каждый момент трогает одна сторона, лок канала даёт happens-before, relaxed-счётчик корректен. Unshared ⇒ достижим только из одного стека — это и делает plain-запись флага владельцем безопасной. Владелец — исполнение (`clj_coro`, у голого потока — неявное), не поток; debug-сборка это проверяет (NOTES «RC»).
  - **Запись в слот — один inline-примитив, пропущенная публикация — ошибка компиляции.** Список публикаций закрыт, а держится он на типе, а не на внимательности: ребро объекта кучи — поле или элемент массива слотов, который обходит `each_child` — имеет тип `clj_slot` (`struct { clj_value v; }`), атомарное — `clj_atomic_slot`, голое `obj->field = v` не компилируется, чтение — `.v`. Входы: `clj_slot_store(owner, slot, v)` — при shared-владельце публикует `v` до записи (в него сведены семь одинаковых `static store` из map/vector/set/sorted/queue/record/shape); `clj_slot_init` — заполнение свежего объекта до его видимости, без проверки флага (debug: shared-владелец получает только опубликованное); `clj_slot_clear` — nil, публиковать нечего; атомарные `clj_slot_store_atomic`, `clj_slot_exchange`, `clj_slot_cas`; `clj_root_store` — место вне кучи (C-глобал реестра: таблица кейвордов, неймспейсы, reify-типы, ошибки загрузчика, фичи ридера), публикует всегда. Значение, которое объект держит для своего исполнения и `each_child` не обходит (ожидающее исключение корутины, её retired-корни), — `clj_private_value`, не слот. Контейнеры между исполнениями — атом, канал, корутина — рождаются shared, как вар: `reset!`, `put!` (буфер, очередь путтеров, передача тейкеру через узел очереди), аргументы spawn и результат корутины публикуются тем же примитивом, безусловные `clj_share` в них исчезли. Вручную остались граница FFI (`Value`, `objc-block`, `objc-reify`) и то, что едет не в слоте: колбэк `put!`/`take!` в `clj_waiter`, fn `thread` в задаче пула, реестры, хранящие объекты без своего C-глобала (таблицы протоколов, индекс специализатора, профайлер, кадры биндингов, пул констант юнита). Слот ссылочного типа пишется под его локом — примитив лок не берёт, debug-сборка проверяет, что он взят, там, где ответ дешёв (`clj_type.debug_lock_held`: атом, канал), кроме счётчика 1 — заполнения создателем. Перенос значения между слотами одного владельца (`memmove` узла, копия слота) законен: если владелец shared, значение уже опубликовано. Время жизни заимствований (`unlink`, `retain_if_live`) и чтение слота ссылочного типа без его лока примитив не закрывает — это не публикация. Потребители — оба бэкенда: сгенерированный C читает захваты через `clj_slot_values(f->env)` и в слоты сам не пишет. В релизе цена нулевая (A/B `clj-bench`, bench/RESULTS.md «Slot primitive»); `make slot-audit` (в гейтах) падает на `clj_value`-поле объекта кучи и на записи в `.v` мимо примитивов (NOTES «RC», «Slots»).
  - **Флаг монотонен.** Всё, что попало в атом или var, атомарно для всех навсегда, включая владельца; `assoc` на shared-мапе рождает shared-узлы, так что при состоянии приложения в одном атоме весь домен на атомарном пути после первого `reset!` — ровно baseline Swift ARC, проигрыша к нему нет, выигрыш только на транзиентах. Проверка, закрывающая вопрос: доля retain/release на shared-объектах (debug-счётчики на `clj_retain_slow`/inline-пути) на нагрузке с состоянием в атоме — мерить после конвенции +0/+1 (§6b, «Интерпретатор до компилятора», п. 3), иначе `(get db :k)` с возвратом +1 завышает долю. *Замерено* (bench/RESULTS.md, «Atoms»): на тике «два `swap!` с `assoc-in`/`update` плюс два чтения через `deref`/`get-in`» при состоянии в атоме 79–83 % пар retain/release идут по атомарному пути (0 % на том же тике над локальной мапой), ~80 пар на тик — порядка 300 нс, того же порядка, что один `swap! assoc` in place (140 нс) и в пять раз меньше его же с копией (765); для записи BRC ничего не решает — копия пути на swap дороже её retain'ов (трюк уникальности с тех пор снят, см. «Атомы»), а на чтении атомарная пара и есть вся цена RC; читает UI-состояние главный поток каждый кадр, поэтому BRC взят для него одного (ниже).
  - [ ] **BRC с одним владельцем — главным потоком.** Цена shared снимается с main и ложится на остальные потоки. Владелец фиксирован, поэтому id в заголовке не нужен: 16 зарезервированных бит `flags` становятся счётчиком main (`main16`), `rc` — счётчиком остальных, объект жив, пока сумма больше нуля. Не сделано: всё; примитив записи в слот, на который опирается аудит записей в `flags`, сделан.
    - **Кто освобождает, решает одно слово.** Решение зависит от обоих счётчиков, а атомарная инструкция видит одно слово, поэтому всё, что нужно знать пулу, лежит в слове `rc`, и main меняет это слово только атомарными RMW. Чтение `main16` с пула не годится даже seq_cst: два слова — это «проверить, потом действовать», и в гонке либо оба не освобождают (утечка), либо оба освобождают. Инвариант: **бит MERGED в слове `rc` стоит ⇔ у main нет ссылок в `main16`** (у Choi, Shull, Torrellas 2018 — «не слит ⇒ у владельца есть ссылки»).
    - Внутри эпизода (`main16 > 0`) main работает обычными load/store `main16` с любым объектом; признак «я на main» — inline TLS, состояние эпизода — зеркальный бит в `flags`, чтобы не читать слово `rc`. Пул работает только с `rc`: unshared — обычный путь, shared — атомарный, как сейчас; декремент — `fetch_sub`, который возвращает и счётчик, и MERGED.
    - Края эпизода. 0 → 1 на объекте с MERGED — атомарное снятие бита; гонки нет, потому что main делает retain из ссылки, которую держит, а при `main16 == 0` она учтена в `rc`, и `rc` до нуля не дойдёт. 1 → 0 — relaxed-загрузка слова `rc`: целиком 0 — освобождение на месте без атомика (сумма ноль, retain некому); иначе `fetch_or` MERGED: старый счётчик 0 — освобождает main, иначе освободит пул. Пул на нуле `rc`: MERGED стоит — освобождает сам, снят — освободит main. В любом порядке освобождает ровно один.
    - Ссылка, учтённая в `main16`, но отданная пулу (`put!` объекта main), уводит `rc` в минус при чужом release: пул ставит QUEUED и кладёт объект в очередь main, main на обороте run loop (`clj_sched_main_pump`) сливает одним RMW — `main16` и MERGED в `rc` — и при нулевой сумме освобождает. Release на main при `main16 == 0` — ссылка учтена в `rc`, объект слит — атомарный декремент. Переполнение `main16` — атомарный перенос половины в `rc`.
    - Рождение. Объект пула рождается с MERGED: объекты, которых main не касается, живут ровно как сегодня, а короткое касание с main стоит атомарной пары, то есть сегодняшней цены. Объект main рождается с `main16 = 1`, без MERGED и shared для пула: пул видит только опубликованное, для него ничего не меняется, а публикация с main обхода не делает (`clj_share` на main упирается в помеченный корень). Обычными остаются объекты main до `clj_sched_main_install` и результат блокирующей задачи, работавшей за go-main корутину (аллоцирован на потоке пула): при публикации они обходятся.
    - `is_unique` на main — `main16 == 1`, `rc == 0`, MERGED снят: reuse работает и на опубликованном.
    - Биты `flags`. Тег debug-проверки владельца нужен только unshared-объектам пула, `main16` — только объектам main и опубликованным, поэтому `clj_share` при публикации обнуляет тег, и переносить его не нужно. После рождения слово `flags` пишет только main: поздние пометки IMMORTAL (`compiled.c`, `runtime.c`, `builtins_number.c`, `error.c`, `chan.c`) либо до видимости, либо атомарны. Debug-счётчики и проверки, читающие `rc`, читают сумму. Без main-носителя (CLI, тесты без `clj_sched_main_install`) `main16` не трогает никто — сегодняшнее поведение.
    - [ ] **Отложенное слияние.** Край 1 → 0 не ставит MERGED сразу, а запоминает объект до оборота run loop: объект, который main трогает несколько раз за кадр (корень состояния, узлы, которые читает рендер), платит одну атомарную пару на кадр, а не на касание — почти autorelease pool с границей на обороте. Цена — последняя ссылка main освобождается на кадр позже, `is_unique` учитывает отложенный токен. Не сделано; триггер — замер числа эпизодов на кадр после основной схемы.
    - Предел: BRC убирает атомарную инструкцию, но не конфликт за кэш-линию — `main16` и `rc` в одном заголовке, обычный store main тоже требует линию эксклюзивно. Горячий объект, который main и пул трогают одновременно (корень состояния, читаемый с обеих сторон), гоняет линию между ядрами и при BRC; там помогают только меньше retain'ов (заимствование +0) или immortal. Счётчик здесь хуже лока атома: лок конфликтует при двух писателях, а счётчик — и при одних читателях, потому что retain на чтении — запись.
    - Замер: rc-share (bench/RESULTS.md, «Atoms») на main до и после, и тот же тик на main, пока пул читает то же состояние; пул не должен сдвинуться.
  - **Отложенные альтернативы**, если доля окажется большей частью и вне main: BRC (Choi 2018) с владельцем-континуацией — владелец сохраняет быстрый путь на опубликованном, парк не ломает биас; цена — owner id и два счётчика в заголовке (cons 32 → 40 байт, скачок size class), протокол merge с очередью на владельца и переиспользование id континуаций (незавершённый merge при переиспользовании — порча памяти). Владелец-поток пула — id мало, lifecycle известен, но заголовок и merge те же, re-bias в BRC нет: всё аллоцированное до последней миграции медленно для нового потока навсегда — эквивалент «шарить при парке», хуже флага по этому множеству, лучше только тем, что владелец остаётся быстрым на своём опубликованном; закрепить корутину за носителем ради этого — потерять балансировку (§8). Зарезервированные биты заняты счётчиком main (выше), так что любой BRC сверх него — это +8 байт. Журнал счётчиков на поток (отложенный RC: retain — запись в буфер потока, сборщик применяет журналы по эпохам, как LXR и Levanoni–Petrank) снимает атомики со всех потоков, но shared освобождается с задержкой эпохи на потоке сборщика, reuse на shared пропадает, а потоки Swift и GCD вне эпох требуют атомарного запасного пути; это вариант внутри запасного плана §7, а не отдельное решение. Третья альтернатива, предпочтительнее BRC — **shared ⇒ без RC вообще**: опубликованный объект уходит в трассируемый пул (§7, «Запасной план»), retain/release на нём — та же проверка флага, что сегодня, но вместо атомарной пары ничего.
- **Аллокатор:** size-class пулы (HAMT-узел, cons, small-map, бокс, замыкание с k захватами), per-thread, bump внутри свежего слаба, free-list потом. Отбирает у GC главный козырь — дешёвую аллокацию.
- **Pointer tagging, не NaN-boxing.** Три младших бита (выравнивание 8) под immediates: fixnum 63 бит (`xx1`), keyword, bool, nil, char. `double` боксится в ⊤-контекстах и unboxed везде, где выведен — слоты shapes по наблюдению, `deflayout`, типизированные векторы, локалы. Почему не NaN-boxing: на arm64e старшие биты указателя занимает PAC-подпись, а NaN-boxing кладёт указатель в младшие 48 бит и конфликтует с ней (JSC пережил ценой спецобработки); int там только 32-битный против 64-битной семантики `long`; double'ы у нас и так unboxed там, где важно (UI-математика — `deflayout`/tuples). Fixnum 63 бит (один тег-бит) + бокс int64 на диапазон 2^62…2^63 (семантика переполнения `long` сохраняется, `unchecked-*` заворачивают в 64 битах) + BigInt по `+'`. Контракт языка — 64-битный `long`; fixnum — представление интерпретатора, не тип. Все известные расхождения с JVM с классом «править / осознанно / по триггеру» — `docs/jvm-differences.md`.
