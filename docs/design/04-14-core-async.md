### core.async
- **`go` — один путь в обоих режимах:** корутины рантайма (§6b, уровень «рантайм»). `go` = спавн корутины на носителе с affinity, `<!`/`>!` = park с прямой передачей значения. Ни IOC-трансформа для интерпретатора, ни `Task` + `await` для компилятора — это была бы вторая реализация семантики с гарантированным расхождением. Ограничение «`<!` только в теле `go`» снимается: ждать может любая функция, «ждёт» — факт исполнения, а не тип (§5 «Замыкания через границу»). Swift `Task` остаётся только на мосту.
- **Каналы свои:** буфер + очереди припаркованных корутин под локом, `alts!` через общий флаг-победитель, `timeout` — таймер носителя. `AsyncStream` — не то (single consumer, нет backpressure), но его `BufferingPolicy` = sliding/dropping один в один.
- **Бесцветность — Loom-выбор, принятый с открытыми глазами.** Пауза видна в тексте только в листе (`<!`, `@`), не на промежуточных уровнях вызова; Swift и IOC-`go` метят каждый уровень. Что покупается: нет ряби `async` по стеку вызовов; higher-order код ждёт как есть (`map`, `reduce`, трансдьюсеры, протоколы — в цветном мире каждому нужна async-версия, `(map #(<! (fetch %)) urls)` в JVM core.async — runtime-ошибка); библиотеки не раздваиваются; `try/finally`, `loop`, `binding`, трейсы работают через парк без переизобретения; async Swift-замыкание из Clojure — обычная функция. Цвет в динамическом языке — издержки без выгоды: компилятора, который не даст позвать async из sync, нет, `<!` вне `go` в core.async — runtime-ошибка, цвет держится на конвенции. Что стоит: (1) невидимая реентерабельность — но она свойство паузы, не модели: между приостановкой и возобновлением состояние могло уехать в любой из трёх моделей, а в Clojure и без пауз (другой поток делает `swap!` когда угодно) — «`deref` — снимок, запись — функцией через `swap!`» корректно при любых парках; реально невидимость теряет только main-affinity с хостовыми объектами (парк отдаёт run loop, UIKit меняется под ногами — MainActor reentrancy без `await`); (2) парк там, где парковаться нельзя — закрывается требованием `:effects` (ниже); (3) «ожидание при синхронном входе из Swift» ловится в исполнении, не компилятором (`host_depth`, §5); (4) stackful-стеки (ниже). Бесцветный мир — надмножество: core.async-дисциплина («ждущая функция возвращает канал, ждём только в `go`») остаётся доступной конвенцией и линтом; обратное невозможно.
- **Рантайм не блокирует носитель.** Один механизм для всего блокирующего — blocking pool + парк (`spawn_blocking` у Tokio, netpoller-fallback у Go): чтение файла загрузчиком, sync Swift API, `thread` — уходят на выделенный поток, корутина паркуется до результата. Вывод (`clj_output`) — канал к одному потоку-писателю: переполнился — `println` паркуется (backpressure), не блокирует носитель; хостовый `out_fn` вызывается с писателя. В ядре нет `fopen`/`fread`/`fwrite`/`sched_yield` на пути корутины; `fprintf(stderr)`/`write(2)` — только fatal и crash. Аудит: каждый `clj_lock` и каждый syscall в ядре — против этого правила.
- **Два лока.** `clj_lock` (поток, не паркуется) — только внутренности рантайма: интернирование, таблицы ns/shape/протоколов, короткие секции; инвариант — **под `clj_lock` не бежит ни пользовательский код, ни IO**, backstop dev-режима ловит парк под ним. Второй инвариант того же лока: **рекурсия, чья глубина задана программой, не доходит под ним до guard-страницы.** Приземлить переполнение в точке восстановления — значит продолжить с полузаписанной таблицей лока, то есть обменять громкую смерть на тихую порчу; поэтому аналитор, проход фактов и вызовы интерпретатора останавливаются на общем запасе стека (`clj_stack_limit`), а «a runtime lock is held» в guard'е остаётся утверждением этого инварианта, а не путём восстановления. Цена названа: проход фактов, который бежит целиком под локом `clj_exec_derive`, отдаёт ⊤ на поддереве, на которое не хватило стека, — оптимизация, а не корректность (§3 «Инвариант: язык не меняется»). Корутинный мьютекс (`clj_cmutex`) — всё, что видит пользователь: `locking`, `promise`/`deliver`, форсинг lazy-seq (одноразовый лок вместо спина на `sched_yield`), `future`, `swap!`. Захват при контенции паркует корутину в очередь мьютекса, `unlock` передаёт лок первому ждущему; без контенции — тот же CAS, что у `os_unfair_lock`, поэтому `swap! inc` не дорожает (гейт в бенче). Короткий спин перед парком (Go `sync.Mutex`): парк/резюм ~50–100 нс, держатель на десятки нс дешевле переждать. Гибрид: `lock` не с корутины (host-поток, `thread`, `host_depth > 0`) блокирует поток, как `runBlocking`; для канала это остаётся ошибкой — секция лока короткая, ожидание канала бесконечно. Держать корутинный мьютекс через парк легально — это и есть его смысл (правило Tokio: `std::Mutex` для секций без `await`, `tokio::Mutex` через `await`).
- **Affinity как гарантия, не как скорость.** GCD-паттерн «`isMainThread` → inline, иначе `DispatchQueue.main.async`» и `@MainActor` — не лок без лока, а «сообщение владельцу»: асинхронно, результата нет, с фона — оборот run loop. У нас это `go-main` и affinity `:main`; атом, который трогают только с main, не контендится никогда, и мьютекс вырождается в один всегда проходящий CAS — экономить против него нечего. Что берётся из модели — гарантия «где исполняется»: тело `go-main` и все его возобновления — на main. Affinity у атома (ошибка при доступе не с main) снята, §4 «Атомы»: атом работает с любого потока. Порядок на носителе — очередь, переупорядочивания inline-ветки GCD нет.
- **Где парковаться нельзя — требование `:effects` на параметре**, тот же механизм, что `:effects` в properties `:=>` (§3): параметр `f` у `swap!` — `[:=> {:effects #{}} …]`, «без `:park`». Факт функции против требования по решётке, как типы. Три состояния, а не два: `:park` — «известно, что ждёт», отдельно от «про тело ничего не известно» (`OPAQUE` — неизвестный вызываемый), иначе первый же неизвестный вызов в теле читается как доказанный парк. Ошибка — там, где парк невозможен (`{:effects #{} :effects/severity :error}`): `dosync` (2PL — дедлок), sync-замыкания host-стабов (§5 «Замыкания через границу»), код под `clj_lock`; там известный `:park` → ошибка, ⊤ → предупреждение. Предупреждение-линт (severity по умолчанию) — там, где парк легален (корутинный мьютекс выше), но держать ресурс через ожидание — плохая практика: `f` у `swap!`/`swap-vals!`, валидаторы, тело `lazy-seq`; там известный `:park` → предупреждение, а ⊤ молчит — по правилу §3 «против выведенных требований ⊤ молчит»: на корпусе это 76 предупреждений «может ждать» без единого сигнала. Watch'и в список не входят: они вызываются уже после `unlock` атома (`atom.c`, `commit`), ресурс через ожидание не держится. Из решётки проверяется только `:park`: остальные биты описывают тело, запретить аллокацию сайт не может. Backstop — dev-проверка рантайма: парк при удерживаемом `clj_lock`, в `dosync`, при `host_depth > 0` → ошибка с трейсом до места ожидания, как для host-входа. Форсинг в этот список не входит: его одноразовый лок — корутинный мьютекс, читатели на нём паркуются и форсирующий их разбудит; запрещён там не парк, а `suspend!` — его гейт никто не откроет (счётчик `forcing_held`, ниже).
- **Контекст `go`:** носитель — пул (как core.async, не как `Task {}`: `go` из обработчика кнопки не должен тихо считать на main); наследуются динамические `binding`'и (конвейеринг frame'а при spawn, как `binding-conveyor-fn` у `go`/`thread`/`future`) и QoS текущего носителя. `go-main` — то же на main-носителе. `go` unstructured (как `Task.detached`); сверху `go-scoped`: дети джойнятся на выходе, ошибка ребёнка отменяет остальных и перебрасывается; `async let` = `plet` поверх него. Переход на main: affinity `:main` на канале или `go-main`. Sendable на Swift-стороне: значения иммутабельны, но бокс `Any` — `@unchecked` на обёртке.
- **Спавн начинается сразу, и порядок первого шага — не гарантия.** `go` ставит корутину в очередь и будит носитель; спавнящее исполнение продолжает работать, и первый шаг ребёнка может лечь между двумя его формами. Замер: блок видит счётчик спавнера на 0–15 из 1000 инкрементов у нас и на 1–1000 из 1000 на JVM-core.async 1.6.681 (на миллионе — 600–4000), то есть на JVM это тоже не порядок, а задержка dispatch-очереди в десятки микросекунд против нашего пробуждения в микросекунду; в ClojureScript порядок есть, но там нет и параллелизма. Код, который успевает «настроиться» после `go` — `(tap (mult ch) …)` после `mult` над заполненным буфером, — опирается на эту задержку, и у нас он проигрывает гонку (`docs/jvm-differences.md`, блок ASYNC-127 в тестах core.async). Альтернатива — spawn locality, «ребёнок не начинается до ближайшего парка спавнера» — отвергнута в §8: спавнер может не припарковаться никогда, и готовность корутины стала бы функцией чужого исполнения. Единственное, что язык обещает про порядок, — это каналы: нужен порядок, нужен и канал.
- **Рассматривается: QoS — класс на носителе, а не на `go`.** QoS — свойство потока, и QoS корутины есть QoS её носителя. Разделение слоёв чистое: корутины по носителям мультиплексируем мы, а с самими носителями обращается ядро — на каких кластерах они бегут (P или E на Apple Silicon), как конкурируют с остальным устройством и что душить под нагревом и в Low Power Mode. Своё планирование не заменяет из этого ничего: у Go тоже свой M:N-планировщик, и его неучастие в QoS на Darwin — известная претензия, а не позиция, тогда как рантайм Swift'овой конкурентности своим пулам класс ставит. Сейчас класс один на весь пул и это `DEFAULT`: `USER_INITIATED` — утверждение «пользователь этого ждёт», которого пул, держащий и обработчик нажатия, и фоновый разбор, честно сделать не может, а занижением `DEFAULT` не является — душатся `UTILITY` и ниже. `go-main` сюда не входит: `clj_sched_main_install` усваивает main-поток приложения, и ставить класс на потоке, которым мы не владеем, было бы спором с системой. Независимо от остального стоит донести QoS вызывающего через мост (`qos_class_self()` в `callAsync`/`callDetached`): сейчас работа Swift-`Task(priority: .background)` молча повышается до класса пула, а `.userInteractive` — понижается. Класс на `go` требует носителей по классам (по требованию, как глобальные очереди dispatch; низкие можно поднимать поверх dispatch-очереди, парковка всё равно наша), и тогда **escalation на парковке обязателен тем же шагом, а не позже**: корутина высокого класса, припаркованная на канале, который обязана наполнить низкая, получает низкую задержку, и ядро тут бессильно — зависимость выражена нашим каналом. Поднятие — перенос runnable-наполняющего в пул ждущего; уже бегущего перенести нельзя (нативный стек на том носителе), но это ограничено одним квантом, потому что наши корутины отдают управление на парковках и тиках цикла. Swift был вынужден добавить task escalation по той же причине. Поверхность, когда носители появятся, — переопределение уже записанного здесь наследования: `(go {:qos :utility} …)`, а `go-main` — сахар для `{:affinity :main}`, то есть один слот на один вопрос «где это бежит». Региональная форма (`with-qos`) отвергнута: она подразумевает миграцию бегущей корутины, обещание крупнее нужды. До носителей единственная честная ручка — `thread`: блокирующий пул исполняет одну работу на поток в моменте, поэтому класс там выставим на задачу, в отличие от носителя, который мультиплексирует много корутин.
- **`<!!`/`>!!` — алиасы `<!`/`>!`.** Версии, блокирующей поток, нет (DispatchSemaphore в пуле = priority inversion), а раз любая функция паркуется, семантика «дождаться значения» у них одна; на JVM `<!!` внутри `go` — баг (заморозил поток пула), у нас багом быть не может. Единственное место, где обе дают ошибку, — синхронный вход из Swift. Оставить символы неопределёнными нельзя: чужие тесты с `<!!` не загрузятся.
- **`thread` — не корутина пула:** тело с блокирующим IO заморозит носитель; выделенный поток (или носитель вне пула), результат — канал, как в core.async.
- **`future`/`promise` на корутинах:** `future` = корутина пула + `promise-chan` + кешированное исключение + отмена; `@f` паркует, не блокирует, из любой функции. Фьюча и промис — порты для `alts!` (на JVM нельзя). Таблица соответствий: `Task.detached` ↔ `go`, `await t.value` ↔ `@f` или `(<! promise-chan)` (`(<! (go …))` — одноразово: канал, не промис), `Task { @MainActor }` ↔ `go-main`, task group ↔ `go-scoped`.
- **Отмена — кооперативная, флаг на корутине** (в core.async её нет: `go` не убить, идиомы — control-канал в `alts!`, `close!` входа, `timeout`; `future-cancel` на JVM — `Thread.interrupt`, `go` его не видит). Флаг проверяется в точках парковки (`<!`, `>!`, `alts!`, `deref` фьючи, `timeout`) и там же, где deadline (`loop`-тик, вход в драйверы seq/reduce, §«Пролог»); припаркованная корутина резюмится с исключением отмены; `future-cancel`/`cancel!` ставит флаг; `go-scoped` при выходе и при ошибке ребёнка отменяет детей и ждёт их. Deadline `clj_deadline_set_ms` — частный случай «отмена по таймеру», переезжает из per-thread в per-корутину вместе с теневым стеком. Канал не отменяется — он труба, а не вычисление; сигнал остановки продюсеру — `close!` (`>!` возвращает `false`), как `AsyncStream.onTermination`.
- **Стеки корутин — резерв большой, коммит ленивый.** Бесцветность требует настоящего стека; копировать его в кучу, как Loom и Go, в C нельзя (указатели в кадры вызывающих). Резерв `mmap` без коммита: физическая цена припаркованной корутины — high-water mark, 1–2 страницы; на парке `madvise(MADV_FREE)` хвоста ниже текущей глубины. 1000 припаркованных ≈ 64 МБ виртуальных / ~8 МБ физических; 100 000 — серверный кейс, на телефоне не бывает. Резерв не 64 КБ: интерпретируемый кадр ~800 байт, 64 КБ = ~75 вложенных вызовов до «Stack overflow»; 256 КБ–1 МБ бесплатны, пока не тронуты.
- **Стек припаркованной корутины — только её.** Инвариант: всё, что трогает будящий (слот результата и claim-слово waiter'а, контекст задачи blocking pool, handler `alts!`, таймер), живёт в `clj_coro` или в куче — никогда в кадре парковщика. Это условие, при котором стек припаркованной корутины можно копировать *на тот же адрес*: §4 отвергает релокацию (указатели в кадры), но выкопировать живой кусок `[sp, верх)` в heap и вернуть его ровно туда же указателей не ломает.
- **Память припаркованной корутины — страница, не модель.** Физически припаркованная корутина держит одну страницу (16 КБ на Apple arm64: верх стека + голова shadow ring на одной странице), живых байт в ней 1–3 КБ; глубина растёт по страницам и на парке хвост отдаётся `madvise`. Ниже страницы на mmap-стек не опуститься, поэтому под давлением — **эвакуация холодных**: живые байты → heap-блоб точного размера, весь диапазон → `MADV_FREE_REUSABLE`, на resume memcpy обратно (~3 мкс на цикл). Не на каждом парке — по триггеру: memory pressure или sweep «припаркована дольше N мс»; горячий путь не трогается. 10 000 припаркованных: 160 МБ → единицы МБ. Трейс эвакуированной — из блоба или честный отказ; ASan — poison на время эвакуации. В карман, с триггером «page fault на resume или число VM-entries в профиле»: **дорожки** (greenlet с K стеками) — фиксированные K маппингов, корутина навсегда привязана к дорожке, при конфликте живые байты занимающей выкопировываются; страницы всегда тёплые, нет syscalls и mmap на корутину, но каждый resume при занятой дорожке — две memcpy там, где сейчас ноль, и глубокая корутина платит свою глубину в обе стороны.
- **Стек как объект — что берётся сверх бесцветности.** Доступ к стеку припаркованной корутины снаружи — тот же примитив, что уже держит эвакуацию, трейс припаркованной (`clj_coro_parked_trace`), резюм броском (отмена, дедлайн) и миграцию между носителями. Сверх них взято три вещи. (1) **Продюсер-корутина над push-API хоста** (`enumerateObjectsUsingBlock:`, `NSXMLParser`, `CGPathApply`, стриминговые парсеры): колбэк паркует продюсера, потребитель читает lazy-seq. Это библиотечная функция, а не форма языка (строка про генераторы в §8 в силе), и IOC-макросу она недоступна в принципе — колбэк зовёт C-код Foundation, который про машину состояний не знает; на JVM то же делается через `seque` и настоящий поток. (2) **Детерминированный планировщик для тестов**: один носитель и сид на выбор победителя `alts!`, порядок пробуждений из лота и срабатывание таймеров, чтобы конкурентный прогон воспроизводился и бисектился по сиду. Со stackful под него попадают и парки ядра (форсинг, `swap!`, backpressure вывода), а не только размеченные макросом, — а именно ядро и надо ловить: каналы, лот, эвакуация и отмена написаны здесь. (3) **`suspend!`/`resume!`** — липкий флаг рядом с отменой, проверяемый в тех же точках, но паркующий на гейт вместо броска: отладчик, паркующий одну корутину при живом REPL и UI, и background modes (audio, location, BLE), где приложение продолжает исполняться и фоновую работу надо придержать. Условие для (3): приостановка легальна только там, где ничего не удерживается — suspend под `clj_cmutex` даёт дедлок, — то же требование, что `:effects` для парка, и тот же dev-backstop по счётчику локов. Обычный уход в фон в этот список не входит (ниже).
- **Фон на iOS — ничего не делаем, замораживает система.** После `didEnterBackground` даётся ~5 с, затем процесс переходит в Suspended: ядро останавливает потоки там, где они стояли. Корутины замирают посреди чего угодно, и это безопасно именно потому, что не исполняется никто. Приостанавливать нечего; эвакуировать по нотификации — тоже: sweep (250 мс) в этом окне сам забирает всё, что припарковано дольше 250–500 мс, а десятки припаркованных корутин телефонного приложения — сотни килобайт, не та величина, по которой jetsam выбирает жертву (34 МБ из бенча — это 10 000 корутин, серверный кейс). Что в фоне действительно держит грязные страницы: кеш из 256 маппингов отработавших корутин (`madvise` на парке шёл ниже `sp`, high-water mark остаётся резидентным) и пулы аллокатора. Если хук на фон когда-нибудь появится, его содержимое — отдать их и записать состояние, а не эвакуировать. Помнить: приостановленный процесс не исполняет обработчик memory pressure, так что в фоне этот триггер не работает вовсе — при 10 000 корутин (не телефонный случай) эвакуацию пришлось бы звать явно.
- **Часы таймеров — те, что стоят во сне устройства.** `clj_profile_now` — `CLOCK_UPTIME_RAW`, далёкие дедлайны — dispatch-таймер от `DISPATCH_TIME_NOW`; ни те ни другие не идут, пока устройство спит. Следствие, принятое как семантика: `(timeout 5000)`, поставленный до блокировки экрана, срабатывает через 5 с после пробуждения, а не сразу, — таймаут ведёт себя как бюджет, и залпа просроченных таймеров на возврате нет. Мимо нас время идёт только в одном случае — приложение в фоне при бодрствующем устройстве. Политика, если он окажется важен: `timeout` — обещание о настенном времени, не сдвигается; дедлайн — бюджет на вычисление, сдвигается на длительность заморозки, а сама заморозка видна таймерному потоку без всякого UIKit (проснулся много позже своей цели). Система готового ответа не даёт: `Timer` и `DispatchSourceTimer` пропущенные срабатывания коалесцируют в одно, а `ContinuousClock`/`SuspendingClock` в Swift различают сон устройства, а не заморозку процесса.
- **`clojure.core.async.flow` — библиотека поверх `go` и каналов и второй уровень описания над корутинами.** Flow (core.async 1.8) — граф процессов данными: `{:procs {pid {:proc (process step-fn) :args …}} :conns [[[:a :out] [:b :in]]]}`; шаг — `(step-fn state in-id msg) → [state' {out-id [msgs]}]`, прочие арности — описание портов (0), init (1), переходы `::flow/pause`/`resume`/`stop` (2). Портируется исходником, как `agent`: цикл процесса — корутина пула, управляющий канал первым в `alts!`. С корутинами flow не конкурирует: корутина — механизм, её состояние — стек, который нельзя ни показать данными, ни перенести (выше); у flow состояние между шагами — значение, топология — литерал, сообщения в пути — в буферах наших же каналов.
  - **`:workload` вырождается в подсказку.** На JVM `:io` → `io-thread`, `:compute` → пул под вычисления, потому что блокирующий шаг заморозил бы поток; у нас блокирующее уходит в blocking pool само, и все три — корутина пула. Контракт `:compute` («не блокирует, не делает IO») зато проверяем, чего JVM не может: IO и блокировка у нас — парк, поэтому контракт — ровно требование `:effects` без `:park` на `step-fn`, severity предупреждения, как у `swap!`.
  - **Affinity** — `:affinity :main` в опциях `process`: процесс исполняется на main, как тело `go-main`; шаг с фактом «требует main» на процессе пула — та же проверка «UI из `go` на пуле». Лишний ключ опций, JVM-программ не касается.
  - **Пауза flow — не `suspend!`.** `pause` приходит сообщением и срабатывает между шагами, где состояние процесса согласовано; `suspend!` останавливает корутину посреди шага. Под детерминированным планировщиком (выше) flow воспроизводим по сиду без доработок — его циклы обычные корутины.
  - **Проверка графа.** Форма конфигурации (`:procs`, `:conns`, `:workload` как `:enum`) — схема на `create-flow` по якорю 1, опечатки в ключах и дополнение — как у hiccup (§3). Сверка `:conns` с `:ins`/`:outs` описаний словарём не выражается: это зависимое требование, порт в одном ключе мапы ссылается на результат 0-арности шага из другого. До расширения словаря — ⊤, как на JVM; триггер — первый flow в корпусе или приложении.
  - В карман, с триггером «работа должна пережить смерть процесса ОС» (синхронизация, очередь загрузок после jetsam): **снимок остановленного flow — данные** — состояния процессов и содержимое буферов каналов. Ни stackful-стек (указатели в кадры), ни IOC-машина этого не дают. Условие — состояния без хостовых объектов и каналов (внешние порты `::flow/in-ports` пересоздаются в init); восстановление — init из снимка вместо `:args`, расширение библиотеки, не языка.
- Акторы ≠ каналы: акторы для владения состоянием, каналы для потоков данных.
- **RC на границах go:** `go` шарит захваченное множество один раз при spawn (порождающий поток продолжает пользоваться локалами); всё, что go-блок аллоцирует после, — на быстром пути, пока не уйдёт через канал/атом. `>!`/`put!` шарит значение (putter держит его дальше) — move вместо share только вместе с ownership-анализом; на небуферизованном канале значение живёт в состоянии припаркованного putter'а — одно место в каждый момент. Парк/резюм не шарит ничего. `alts!` — исключение из handoff: один handler в очередях нескольких каналов, проигравшие на разных потоках сбрасывают его конкурентно → атомарен handler (обёртка с флагом-победителем), continuation внутри по-прежнему move победителю. Сам канал — обычный объект, shared при захвате/публикации.
