# Clojure для Apple-платформ — дизайн-заметки

Итог обсуждения. Стартовый вопрос был «Clojure поверх Swift как ClojureDart поверх Dart»; по ходу выяснилось, что правильная позиция — **Clojure на Apple-рантайме**: своё ядро на C, хост-интероп со Swift/ObjC через мост, а не транспиляция в Swift.

---

## 1. Почему Swift плохой хост «в лоб»

- **Нет eval / JIT.** На iOS JIT запрещён (`dynamic-codesigning` только у JSC и браузеров в ЕС). Swift REPL = LLDB + ORC JIT, медленный и глючный. `dlopen` подписанных dylib работает только в dev-сборках на симуляторе/Маке.
- **Нет рефлексии вызовов.** Дженерики мономорфизируются, `Mirror` read-only, Swift ABI (`swiftself`/`swifterror`, скрытые metadata/witness table параметры) libffi не умеет. Произвольный метод произвольного типа динамически не позвать.
- **SwiftUI — плохая цель.** Идентичность завязана на статические `some View`; динамический язык даёт только `AnyView`. UIKit (ObjC) — нормальная.
- **ARC.** Атомарный всегда, циклы через lazy seq, рекурсивный dealloc на длинных списках, `Any`-боксинг.
- **swiftc медленный** (type checker), сгенерированный код с существенциалами — секунды на файл.
- **Swift 6 strict concurrency** спорит с боксами `Any`.

Хорошие хосты — те, где код грузится в рантайме + GC + рефлексия: JVM, JS, CLR, BEAM, Lua, Python. Dart и Swift — нет; ClojureDart живёт AOT-only с hot restart Flutter'а.

**ObjC-рантайм** — отличный хост (Smalltalk поверх C): `objc_msgSend`, `objc_allocateClassPair`, `imp_implementationWithBlock`, `NSInvocation`. Прецеденты: Nu, F-Script, MacRuby, clojure-objc (2014), NativeScript (генерирует metadata на весь SDK). Но экосистема уезжает в Swift-only.

---

## 2. Три смысла слова «хост» и итоговый выбор

| | Clojure JVM | CLJS | ClojureDart | jank | **наш** |
|---|---|---|---|---|---|
| Во что компилируется | байткод | JS | Dart | LLVM IR | **C (позже LLVM IR)** |
| На чём рантайм | Java | CLJS | Dart | C++ | **C-ядро + Swift-обвязка** |
| Экосистема интеропа | Java | JS | Dart | C++ | **Swift + ObjC** |

Пользователь видит только третью строку. Первая — деталь реализации, как байткод для JVM. Это ближе к модели Clojure JVM (компиляция ниже языка хоста, в его рантайм), чем к ClojureDart (транспиляция в язык хоста).

## 3. Архитектура

### Слои
```
┌─────────────────────────────────────────────┐
│ Clojure-код пользователя                    │
├─────────────────────────────────────────────┤
│ Мост (Swift/ObjC):                          │
│  ObjC runtime · Swift metadata · Codable    │
│  адаптеры протоколов · сгенерированные стабы│  ← единственное, что компилирует swiftc
├─────────────────────────────────────────────┤
│ Ядро (C, портируемое):                      │
│  reader · analyzer · optimizer · interpreter│
│  codegen→C · HAMT/RC/аллокатор · core.async │
└─────────────────────────────────────────────┘
```
Дисциплина: ни одного `objc/runtime.h` в ядре. Всё платформенное — за одним C-интерфейсом `host`. Тогда порт на Linux/Android/WASM = только мост.

### Два режима исполнения
- **Dev — скомпилированная база + интерпретируемые дельты.** Dev-сборка под устройство компилируется на `-O1` (§6b) без прямой линковки: все вызовы через вар + эпоху, поэтому переопределение из REPL долетает и в скомпилированный код. Интерпретатор исполняет только то, что прислали в REPL — одну правящуюся функцию, не весь UI на 60 fps. REPL везде, включая устройство (единственный способ исполнить новый код на iPhone). Интерпретатор — source of truth семантики, компилятор — оптимизации поверх той же программы (`clj_node`) и обязан с ним совпадать; быстрым интерпретатор обязан быть тоже (§6b «Интерпретатор до компилятора»), просто не за счёт второй реализации семантики.
- **Prod — компилятор** в C → clang. Закрытый мир.
- **Компилирующий eval на Маке/симуляторе** (C → clang → dylib → dlopen, ~100 мс) — не третий режим, а инструмент: тесты в CI гоняются через компилятор (ловим расхождение семантик), профилирование без сборки всего приложения.

### Пайплайн
`reader → macroexpand → analyzer → optimizer (общий) → backend {closures | C}`

Правило «оптимизатор общий, бэкенды тупые»: всё, что наблюдаемо меняет семантику (порядок эффектов при fusion, TCO, момент реализации lazy seq), решается в общем проходе.

Два представления на выходе аналитора. `clj_node` — программа: иммутабельна после анализа, сериализуема, её читают оба бэкенда. `exec_node` — артефакт исполнения (eval-указатель, inline cache, счётчик профиля, rewrite-состояние): eval.c строит его одним проходом при подготовке дерева плотным массивом по node-id. Цена — один проход на загрузку и одна индирекция; взамен сериализуемый AST без спецслучаев, PGO-счётчики, не отравляющие кэш программы, и инвариант «eval.c не пишет в программу», проверяемый одним тестом: записать дерево, прочитать, исполнить, сравнить результат и эффекты.

### Аналитор как библиотека: где живёт анализ
**Вопрос.** Выведенные типы собирать только в компиляторе (интерпретатор игнорирует) или отдельным статическим анализатором? **Ни то ни другое:** в общем аналиторе, у которого три клиента.

**Почему не только в компиляторе.** Интерпретатору та же информация нужна для load-time решений: unboxed-узлы в `loop`, специализированный `get` по keyword, выбор арности. Иначе либо дублирование, либо расхождение «компилятор специализировал по типу, которого интерпретатор не видел».

**Почему не отдельный анализатор.** clj-kondo и Typed Clojure отдельные потому, что компилятор Clojure не спроектирован как библиотека — они дублируют ридер/резолв/модель ns и расходятся с ним в углах. У нас аналитор изначально библиотека: одна модель кода, одна таблица варов, один резолв. LSP получает то же дерево с теми же типами, что и бэкенды.

**Разложение по режимам:**
- Локальный вывод (внутри формы: литералы, сигнатуры интринсиков, `instance?`-guards, хинты `^long`) — всегда, в аналиторе, микросекунды. Клиенты: интерпретатор, компилятор, редактор.
- Межпроцедурный (сводки функций по графу вызовов, shape inference через границы) — за флагом закрытого мира: в компиляторе всегда, в dev — инкрементально по эпохам варов.
- Одна инфраструктура сводок: типы, эффекты (чистота), escaping, «может ждать» — не четыре прохода, а один с четырьмя полями в сводке функции.

**Два смысла «неизвестно» при одном движке:**
- Вывод ради оптимизации — sound и консервативный: неизвестно → бокс, без предупреждений, пользователь не замечает. Нужен с первого дня.
- Вывод ради проверки (gradual, `^:typed` на ns) — неизвестно → сообщение. Опция на потом; Clojure-сообщество сознательно живёт с Malli/spec на границах без статики внутри.

**Итог:** аналитор = библиотека со сводками; бэкенды и LSP — клиенты; закрытый мир — флаг, а не другой код.

### Покрытие вывода типов: три слоя
- **Слой 1, статика** — решётка фактов по использованию (см. ниже «Вывод фактов»), не только литералы и guard'ы: арифметика и циклы ~90%; код над литералами и известными shape'ами; после предикатов; требования к аргументам из тел функций. Ноль на границе — JSON/EDN/host/ввод, а в приложении, показывающем данные с сервера, это половина кода.
- **Слой 2, рантайм:** важна предсказуемость, не статика. JSON с одного эндпоинта → один shape (§4), сайты мономорфны, unboxed-поля по наблюдению. Struct-скорость без вывода — как V8 и `JSON.parse`.
- **Слой 3, схема на границе** (Malli/spec, опционально): `[:map [:id :int] …]` после валидации = статический shape и типы полей всему коду ниже. Как `Decodable` в Swift, но не обязательно. PGO из dev-профиля даёт guarded fast path и без схемы.
- **Непокрыто честно:** гетерогенные данные, мегаморфные сайты, мапы с динамическими ключами → generic HAMT = сегодняшний Clojure с лучшим аллокатором. Пол, не катастрофа.
- **Метрика** (§10): доля сайтов с известным типом / shape / неизвестным в аналиторе + доля моно/поли/мегаморфных сайтов в рантайме, на реальном `.cljc`-приложении (re-frame + парсинг). Ожидание: статика 40–50%, кэши добирают до ~90%, мегаморфных — единицы процентов. Проверить до того, как оптимизатор написан под гипотезу.

### Вывод фактов: решётка, два прохода, уточнения
**Суть.** Не система типов, а абстрактная интерпретация над решёткой фактов ради оптимизации и предупреждений. Язык остаётся динамическим: неизвестное = ⊤, ⊤ ничего не ломает (бокс + молчание), худший случай = Clojure как есть. Вывод — по использованию, без обязательных аннотаций; аннотации только в core-библиотеках и на границах по желанию.

**Собрано из прецедентов, не изобретено.** Julia — динамический язык, вывод ради оптимизации, абстрактная интерпретация над решёткой с widening, `@code_warntype` показывает, где не вывелось; ближайший образец. Dialyzer — success typings: вывод из использования, предупреждение только при доказанном конфликте, ноль ложных срабатываний, опциональные `-spec`; медленный из-за богатых типов и фикс-пойнта по всему приложению — учесть. Typed Racket occurrence typing / TypeScript type guards / Kotlin smart casts — уточнение на предикатах. Zig comptime — функции, возвращающие типы, выполняются при компиляции. Malli — схемы как данные, `m/=>` для функций. OCaml/HM — **не** образец: унификация делает язык типизированным, ошибка вместо ⊤.

**Решётка.** Факт = вид + решётка: ⊤ «не знаю», ⊥ «конфликт», join на слиянии веток, meet при уточнении, widening для сходимости. Обход дерева один; каждая форма даёт transfer-функцию для каждого вида факта. Сводка функции = все факты о параметрах и результате. Расширяемость — в видах фактов и transfer-функциях, декларативно; не открытый API «инжект кода в обход» (протекает AST, ломается при каждом изменении, три пользователя).

Виды фактов — все в одной решётке, один обход, один фикс-пойнт:
- **Тип**, включая singleton-типы (константы: `[:= :id]`; enum = объединение singleton'ов). Литеральный keyword в `(:id m)` — singleton, поэтому слот shape'а известен без спецслучая. Compile-time вычислимость — производный факт (чистота ∧ все входы singleton), отдельно не хранится.
- **Nullability** — отдельно от типа, уточняется независимо (`some?`, `if-let`, `when`); главный источник `(:field nil)`-багов.
- **Shape** — ключи и типы полей; из литералов, схем, парсинга, использования.
- **Escaping** — local / escapes / captured. Регионы, стек, reuse.
- **Может ждать** — suspends / no / ⊤. Гвард `swap!`, подсветка, main-thread.
- **Ownership** — owned/borrowed на параметрах, uniqueness на локалах. Perceus.
- **Эффекты** — множество: IO, atom-write, host-call, throws, nondeterministic, registration. Fusion, ленивые def, CSE. `registration` — запись в таблицы рантайма (вар, протокол, мультиметод, реестр `defdsl`, `derive`): отдельно от `atom-write`, потому что режим анализа (§5c) исполняет первое и пропускает второе.
- **Throws** — какие `ex-info`/host-ошибки; Swift `throws` через стабы. Убрать error-check в C там, где не бросает.
- **Thread affinity** — «требует main» (UIKit-стабы = `@MainActor`) / «любой». Статическая проверка «UI из `go` на пуле» — как Swift 6, но выведено.
- **Публикуется** — статическая версия SHARED-флага. Не «пересекает поток», а flow-анализ по закрытому списку стоков: запись в разделяемую ячейку (var, атом, канал, ячейка lazy seq), захват при spawn, экспорт в хост. Не течёт ни в один → неатомарный счётчик без рантайм-проверки; течёт → пометить при создании. Тот же анализ даёт move для `>!`: локал мёртв после отправки → передача единственного владельца, без share.
- **Свежесть результата** — функция возвращает только что созданное → у вызывающего reuse без проверки rc==1.
- **Строгость / потребление seq** — целиком тут же / частично / убегает. Eager вместо thunk'ов, не держать голову.
- **Захваты замыкания** — множество захваченных локалов и их факты.
- **Аллоцирует / нет** — для горячих путей, `^:no-alloc` в стиле `@nonallocating`.
- **Арность на сайте** — без seq для `& rest`, без диспатча.
- **Позиция хвостового вызова** — `musttail`.

Не делать: диапазоны чисел ради bounds-check elimination, termination, точные размеры коллекций — дорого, редко окупается.

Половина списка — то, что Swift 6 сделал обязательными аннотациями (`async`, `throws`, `Sendable`, `@MainActor`, `borrowing`, `@escaping`). У нас — выведено, ⊤ как честное «не знаю». Gradual в широком смысле.

**Два прохода.**
- Проход 1, bottom-up по графу вызовов: сводки функций из тел — требования к аргументам по использованию, факты результата. Рекурсия — фикс-пойнт с widening.
- Проход 2, top-down по сайтам: знание об аргументе у вызывающего meet-ится с требованием из сводки. ⊥ → предупреждение с **обеими** точками: «здесь используется как мапа с `:key` (строка N), сюда передаётся shape без `:key` (строка M)». Сообщения показывают места и shape'ы, не абстрактные типы (анти-OCaml).
- Не HM-унификация: constraint solving над решёткой ограниченной высоты — дешевле, никогда не падает жёстко.

**Уточнения (occurrence typing).** На предикатах, не на `if`. Предикат несёт факт «истина ⇒ аргумент X; ложь ⇒ аргумент Y». Core-предикаты (`some?`, `number?`, `map?`, `instance?`, `=`) — со сводками; `if`/`when`/`cond`/`case`/`and`/`or`/`if-let` — встроенные формы, применяющие уточнения условия к веткам. Для пользовательских предикатов уточнение выводится из тела: `(defn user? [x] (instance? User x))` получает refinement автоматически. Аннотация нужна только для непрозрачных (host) предикатов. Макросы расширяются в эти формы и получают уточнения бесплатно.

**Схемы.** Malli как синтаксис на уровне компилятора: `[:map [:id :int]]` → shape + типы полей; `(m/=> f [:=> [:cat :int] :int])` → сводка функции, meet с выведенной. Одна запись = валидация на границе + статика ниже. Функции для схем = дженерики (Zig comptime): `(defn vec-of [t] [:vector t])` — чистая функция, выполняется интерпретатором в compile-time, результат — данные. «Типы как данные» не нарушается: результат — данные. Правило: схемные функции чистые и вычислимы без рантайма.

**Три трудных места — и что решётка с ними делает.**
- Протоколы: `(:key value)` берёт сводку из реализации `IFn` у `Keyword` («аргумент `ILookup` ∨ nil»), не хардкод паттерна. Рядом структурный факт «если shape, то ключи ⊇ {`:key`}». Поправка: `(:key m)` без ключа в Clojure — nil, не ошибка → ценность вывода в *результате* (тип поля из shape, или «всегда nil» → предупреждение только в `:strict`), а не в требовании. Конформансы — по таблице (закрытый мир — полная; dev — известные, остальное ⊤). Вызов протокольного метода: результат = join по известным реализациям.
- Swift-типы не теряются: стабы рождаются из `.swiftinterface` вместе со сводками (`[:=> [:cat host/Date] host/String]`); host-типы — номинальные факты с иерархией из метаданных; `Codable`-конверсия даёт shape с типами полей точнее любого вывода. ⊤ только у ObjC-рантайма без объявлений и у `Value` из Swift без схемы.
- Мультиметоды: протокол с диспатчем по данным. Dev: таблица и иерархия мутабельны → результат ⊤, требования — только от функции диспатча. Закрытый мир: результат = join тел; dispatch-value singleton → точный метод. `prefer-method`/`:default` — ветки того же join.

Общее правило: сомнение → ⊤, ⊤ ничего не ломает.

**Строгость (на ns).** `:off` — только оптимизация, ни одного сообщения. `:warn` (дефолт) — только доказанные конфликты (⊥), Dialyzer-стиль. `:strict` — ⊤ на границах функций тоже предупреждение, «всегда nil» тоже; для кода, который хочет быть типизированным.

**Скорость компилятора — три предохранителя.** Решётка ограниченной высоты: полиморфизм ≤4 shape'ов (дальше ⊤), числа int/double/number/⊤, никаких бесконечных уточнений. Локальный вывод всегда (микросекунды); межпроцедурный фикс-пойнт — закрытый мир или инкрементально по эпохам варов: сводка хранится с эпохой, сайт использует её как inline cache, переопределение сдвигает эпоху → сайт откатывается на generic-путь и пересчитывает при следующем использовании; на циклах в dev — widening сразу. Widening после N итераций.

### Tagged-vector DSL: hiccup и данные с диспатчем по голове
Hiccup (`[:div {:class "x"} [:span "hi"]]`) — предел «код как данные»; минус — компилятор не подсказывает, опечатки в тегах и атрибутах всплывают в рантайме. У нас появится в любом случае: «SwiftUI через данные» = `[:vstack {:spacing 8} [:text "hi"]]`.

Отдельный механизм не нужен — частный случай решётки фактов:
- Элемент — вектор с singleton-keyword в голове. Реестр схем по тегу (`:text` → `[:cat [:map [:font :keyword]] :string]`) → аналитор проверяет атрибуты и детей как shape мапы: опечатка, неверный тип, лишний ребёнок — предупреждение в `:warn`. Пользовательский компонент `[my-view props]` — символ → сводка функции → shape props. Реестр = Malli-схемы, привязанные к тегу.
- Производительность: Reagent интерпретирует hiccup на каждом рендере; hicada/uix компилируют макросом — и теряют данные, после макроса `walk` невозможен. У нас компилятор специализирует литерал с известным тегом в прямое построение узла без макроса и с сохранением семантики: hiccup остаётся данными всегда.
- Правило то же, что у fusion: статическое построение только когда escaping доказал, что литерал потребляется известным рендерером из реестра. Уходит в неизвестную функцию, атом, `walk`, `update-in` → остаётся вектором. Чистая цепочка `(-> [:text "hi"] (assoc 1 {…}) render)` сворачивается при компиляции (чистота ∧ singleton-индекс ∧ константа) — модификаторы в коде складываются в статику.
- Динамически — view-узел, который всё ещё вектор: отвечает на `nth`/`count`/`seq`/`assoc`/`get` через дескриптор (тег + слоты атрибутов + дети); мутация — обновление слота по схеме тега или демоушен в обычный вектор, односторонне. Интерцепторы над произвольным деревом работают как сейчас.
- Предел честный: собранное в рантайме статически не проверить; закрывается тем же реестром в dev через instrument при построении.
- Другой рендерер = другой реестр; для него литерал ⊤ → вектор.

Обобщение — `defdsl`: реестр «тег → схема + известный потребитель» как источник фактов. Клиенты: hiccup, re-frame `[:event/name args]`, роуты reitit, honeysql, сам Malli. Даёт аналитору проверку, компилятору специализацию, LSP автодополнение тегов и атрибутов. Востребованность доказана: Elm Html, TSX, SwiftUI result builders типизированы; в Clojure для hiccup пишут clj-kondo-хуки.

## 4. Рантайм

### Представление значений
- **Не Swift-классы.** Свой заголовок объекта, raw-указатели (`Unmanaged`), свой аллокатор. Swift-классы удобны в первую неделю и закрывают дверь навсегда (атомарный ARC, `swift_allocObject` → malloc, нельзя сменить заголовок).
- **RC свой:** неатомарный по умолчанию, biased — флаг «shared» при **публикации**, после чего атомарный. Гонка за счётчик требует одновременной достижимости из двух потоков, а данные иммутабельны, поэтому список публикаций закрыт: запись в разделяемую мутабельную ячейку (var root/meta, атом и любой ref-тип, буфер канала, ячейка реализации lazy seq, интернированные таблицы), захват при spawn (`go`/`future`/`thread`), экспорт в Swift. `clj_share` обходит граф с обрезкой на уже shared-узлах; инвариант «дети shared — shared» держится на записи (in-place reuse при rc==1 шарит новый child), поэтому каждый объект помечается не более одного раза за жизнь — амортизированно O(1), без барьера на чтение.
  - **Смена потока — не триггер.** Парк/резюм go-блока и передача по каналу — handoff: объект в каждый момент трогает одна сторона, лок канала даёт happens-before, relaxed-счётчик корректен. Unshared ⇒ достижим только из одного стека — это и делает plain-запись флага владельцем безопасной.
  - **Флаг монотонен.** Всё, что попало в атом или var, атомарно для всех навсегда, включая владельца; `assoc` на shared-мапе рождает shared-узлы, так что при состоянии приложения в одном атоме весь домен на атомарном пути после первого `reset!` — ровно baseline Swift ARC, проигрыша к нему нет, выигрыш только на транзиентах. Проверка, закрывающая вопрос: доля retain/release на shared-объектах (debug-счётчики на `clj_retain_slow`/inline-пути) на нагрузке с состоянием в атоме — мерить после конвенции +0/+1 (§6b, «Интерпретатор до компилятора», п. 3), иначе `(get db :k)` с возвратом +1 завышает долю. *Замерено* (bench/RESULTS.md, «Atoms»): на тике «два `swap!` с `assoc-in`/`update` плюс два чтения через `deref`/`get-in`» при состоянии в атоме 79–83 % пар retain/release идут по атомарному пути (0 % на том же тике над локальной мапой), ~80 пар на тик — порядка 300 нс, того же порядка, что один `swap! assoc` in place (140 нс) и в пять раз меньше его же с копией (765); BRC не берём — копия пути на swap дороже её retain'ов (трюк уникальности с тех пор снят, см. «Атомы»; вывод про BRC не меняется).
  - **Отложенные альтернативы**, если доля окажется большей частью: BRC (Choi 2018) с владельцем-континуацией — владелец сохраняет быстрый путь на опубликованном, парк не ломает биас; цена — owner id и два счётчика в заголовке (cons 32 → 40 байт, скачок size class), протокол merge с очередью на владельца и переиспользование id континуаций (незавершённый merge при переиспользовании — порча памяти). Владелец-поток пула — id мало, lifecycle известен, но заголовок и merge те же, re-bias в BRC нет: всё аллоцированное до последней миграции медленно для нового потока навсегда — эквивалент «шарить при парке», хуже флага по этому множеству, лучше только тем, что владелец остаётся быстрым на своём опубликованном. Место под биты зарезервировано, схемы совместимы: флаг сейчас. Третья альтернатива, предпочтительнее BRC — **shared ⇒ без RC вообще**: опубликованный объект уходит в трассируемый пул (§7, «Запасной план»), retain/release на нём — та же проверка флага, что сегодня, но вместо атомарной пары ничего.
- **Аллокатор:** size-class пулы (HAMT-узел, cons, small-map, бокс, замыкание с k захватами), per-thread, bump внутри свежего слаба, free-list потом. Отбирает у GC главный козырь — дешёвую аллокацию.
- **Pointer tagging, не NaN-boxing.** Три младших бита (выравнивание 8) под immediates: fixnum 63 бит (`xx1`), keyword, bool, nil, char. `double` боксится в ⊤-контекстах и unboxed везде, где выведен — слоты shapes по наблюдению, `deflayout`, типизированные векторы, локалы. Почему не NaN-boxing: на arm64e старшие биты указателя занимает PAC-подпись, а NaN-boxing кладёт указатель в младшие 48 бит и конфликтует с ней (JSC пережил ценой спецобработки); int там только 32-битный против 64-битной семантики `long`; double'ы у нас и так unboxed там, где важно (UI-математика — `deflayout`/tuples). Fixnum 63 бит (один тег-бит) + бокс int64 на диапазон 2^62…2^63 (семантика переполнения `long` сохраняется, `unchecked-*` заворачивают в 64 битах) + BigInt по `+'`. Контракт языка — 64-битный `long`; fixnum — представление интерпретатора, не тип. Все известные расхождения с JVM с классом «править / осознанно / по триггеру» — `docs/jvm-differences.md`.

### Var и ленивые def
**Проблема.** Загрузка ns в Clojure = последовательное выполнение файла: `def` вычисляется в момент загрузки. Старт платит за всё — `(def client (make-client))` создаёт объект, даже если он никогда не понадобится. Обходы (`delay` + `@`, `defonce`) уродливы. Swift-глобальный `let` устроен иначе: `swift_once` + accessor — инициализация при первом обращении, потокобезопасно, дальше одна проверка токена.

**Решение — в Var, без нового синтаксиса.** У Var уже есть косвенность: `deref` читает корень с проверкой эпохи (inline cache, §6). Корень получает третье состояние — «не вычислен, thunk». Первый `deref` форсит thunk под тем же `Mutex` (семантика `dispatch_once`), остальные видят значение. Одна лишняя ветка в уже существующей проверке. Одинаково в интерпретаторе и компиляторе.

**Что лениво по умолчанию:**
- Чистые `def` (по анализу эффектов из §6) — лениво. Момент вычисления чистого выражения ненаблюдаем, кроме стоимости и времени исключения.
- `defn` — по сути уже лениво, не меняется.
- Формы с эффектами — `defmethod`, `extend-type`, `derive`, `def` с IO, любой top-level не-`def` — eager, порядок загрузки сохраняется (на нём держатся регистрации).
- Неизвестный эффект (интероп без сводки) — eager, консервативно.
- Явно: `^:lazy` / `^:eager`.

**Следствия:**
- Загрузка ns = регистрация варов с thunk'ами; вместе с кэшем AST старт iOS-приложения ≈ 0, а не «выполнить всю программу до `main`».
- Dev-режим: флаг, форсирующий все ленивые def сразу после загрузки файла — ошибки всплывают при загрузке, как раньше, а не при первом использовании. В проде — лениво.
- Компилятор в закрытом мире убирает ветку проверки там, где вар доказанно уже форсирован.

### Порядок объявлений (hoisting)
**Почему в Clojure «то, что ниже, недоступно».** Файл компилируется по одной top-level форме за раз: прочитал, проанализировал, выполнил, следующая. Это условие REPL-модели — файл есть стенограмма сессии. Глубже — макросы: встретив `(foo x)`, компилятор обязан знать, макрос это или функция, а узнать можно только после выполнения `defmacro`. Многопроходный резолв как в Swift/Java невозможен, пока макросы выполняются во время компиляции. На практике мешает мало: `declare` для взаимной рекурсии, bottom-up порядок файла (многие считают фичей), нельзя положить публичный API в начало.

**Решение — два режима.**
- Загрузка файла: анализатор видит все формы → pre-pass собирает имена всех `def`/`defn`/`defprotocol`/`defmulti` и регистрирует их как unbound-вары (неявный `declare`). Затем формы выполняются по порядку. Forward-ссылки на функции работают: замыкание захватывает вар, к моменту вызова он связан. Семантически ничего нового — ровно то, что `declare` делал руками.
- REPL, одиночная форма: контекста файла нет, неизвестный символ остаётся ошибкой компиляции. Иначе опечатка из compile-error превращается в unbound-var в рантайме.
- Правило, которое остаётся: `defmacro` — строго до использования. Как Swift-макросы: определены раньше, в другом месте.

**Синергия с ленивыми def.** Единственный опасный сценарий hoisting — вычисление значения при загрузке до связывания зависимости: `(def x (helper))`, `helper` ниже. С ленивыми `def` `x` форсится при первом использовании, когда файл загружен целиком. Hoisting убирает `declare`, ленивость убирает ошибки порядка в `def`-значениях; вместе остаётся одно правило — про макросы.

### Персистентные структуры — где деньги
Копия HAMT-узла на 32 слота = memcpy 256 байт (~10 нс) **+ 32 retain детей** (~150 нс атомарных). `assoc` копирует 2–4 узла. Borrow inference тут не помогает — дети реально приобретают владельца. Лечится только: неатомарный счётчик; reuse (не копировать); регион (не считать); меньший branching (16).

**Бенчмарк** (`bench/RESULTS.md`, fd4cbf4 → b11f641, M3 Pro): C HAMT vs `TreeDictionary` (swift-collections, CHAMP на Swift-классах) vs мутабельный `Dictionary`.
- До пула: 1.2–1.8×. Гипотеза «свой RC даёт кратный выигрыш» не подтвердилась — обе стороны на 60–70% мерили системный malloc. Модель «32 retain на копию» верна только для полных узлов (при n=100k корень и второй уровень полные, ~67 retain на путь); у маленьких мап узлы разрежены.
- После per-thread size-class пула: `assoc` с отпущенной старой версией 82→39 нс при 1k (пул vs malloc в одном прогоне, Swift-колонки сходятся в 1–4%); tree/C 2.0–3.7× на `assoc`, 1.5–2.7× на `dissoc`, `get` без изменений (не аллоцирует). Персистентный `assoc` при уникальности — в 2× от мутабельного `Dictionary` (39 vs 20), не в 3×.
- Атрибуция выигрыша: аллокатор > неатомарный RC (~1.5× на больших мапах с живыми версиями) > хэш (`get` при n=10: 2.7 vs 11.8 — почти целиком `Hasher`/SipHash) > обвязка.
- Reuse при rc==1 есть у обоих (`TreeDictionary` — через `isKnownUniquelyReferenced` на `var`). Тест на идентичность указателя корня — регрессионный.
- `TreeDictionary` округляет ёмкость узла до степени двойки (slack под рост). У нас логический размер точный, физический — size-class пула: тот же эффект бесплатно. Решение.
- Открыто: хэш-паритет; peak RSS и возврат страниц пулом (`madvise`); cross-thread free (объект освобождается не владельцем пула); многопоточный read-mostly сценарий — единственный, где `TreeDictionary` может проиграть кратно, не измерен.

**Вывод:** Swift-ARC пригоден. Свой рантайм лучше по архитектуре (аллокатор, C-бэкенд, reuse, biased RC, портируемость); в скорости — 2–3× на главной операции, не 5–10×.

**Бенчмарки как экспонат.** Мерить против прямых конкурентов — JVM-Clojure после прогрева (только на Маке: на устройстве JVM нет), ClojureScript под JSC, `TreeDictionary`; для struct-like — Swift-struct как потолок, — не только против `Dictionary`. **Главный конкурент на устройстве — React Native на Hermes**: байткодный интерпретатор без JIT (JIT на iOS запрещён всем одинаково), мост JSI, нативный UI — та же архитектура, что у нас; тот же `.cljc` через ClojureScript на Hermes сравнивается напрямую. Ожидание по режимам: интерпретатор проигрывает JVM и Swift на compute (JIT ~10–30×) и на копирующих персистентных операциях (GC копирует узел без retain'ов), выигрывает на старте, памяти, in-place при уникальности и против Hermes; «между JVM и Swift» — задача компилятора, проверяется только когда он есть. Атрибуция, а не итог; A/B в одном прогоне; RSS рядом с нс; обязательно сценарии, где проигрываем. История `RESULTS.md` по коммитам (гипотеза → опровержение → причина → исправление) ценнее финальных цифр — неудачные прогнозы не вычищать. Микробенчмарки объясняют «почему», макро (парсинг JSON, re-frame-цикл, рендер списка на одном `.cljc` на трёх платформах) — «насколько»; заголовочная цифра — макро.

### Представление по наблюдению: shapes, tuples, elements kinds
**Мотивация.** 90% мап в Clojure-приложении — `{:id 1 :name "x"}` на 3–8 keyword-полей, то есть Swift-struct, а не словарь. Swift-struct: поле 0.3 нс, мутация — запись в слот. `PersistentArrayMap` (≤8, линейный скан `identical?` по интернированным keyword) уже неплох, но это линейный поиск + бокс + отдельный массив.

**Shapes** (hidden classes: Self 1989 → V8/SpiderMonkey/JSC, Ruby 3.2 object shapes, Truffle OSM, PyPy maps, key-sharing dict в CPython; иммутабельный прецедент — Erlang flatmaps: разделяемый keys-tuple, порог 32 ключа, дальше HAMT):
- Мапы с одним набором ключей делят объект Shape (ключи + индексы); в мапе — указатель на shape и значения inline. Одна аллокация, одна кэш-линия.
- Дерево переходов: `∅ --:id--> S1 --:name--> S2`. Литерал, цепочка `assoc` и JSON-парсер идут по одним рёбрам → один shape → мономорфный call site. Shape строится по ходу парсинга, generic-мапа не создаётся ни в первый раз, ни потом; со второго раза стоимость на ключ — intern строки в keyword + сравнение указателя в таблице переходов (обычно один элемент).
- Inline cache на call site: `(:name m)` → `if m.shape == cached → values[idx]`, ~1–2 нс. Полиморфный (2–4) → switch; мегаморфный → generic. В интерпретаторе кэш на узле AST; в компиляторе — статически из PGO-профиля; при статически известном shape (литерал, flow-типизация, схема) — прямое смещение без проверки.
- Unboxed поля по наблюдению (V8 field representations): `:count` всегда int64 → слот без бокса, проверка при записи.
- `assoc` при rc==1 — запись в слот; `(update m :count inc)` — буквально `m.count += 1`. При rc>1 — копия массива (≤32 слотов — одна кэш-линия, = один HAMT-узел).
- `defrecord` = именованный, заранее объявленный shape с гарантиями (opt-in: лишнее поле — ошибка). Один механизм вместо двух. У records свои углы (`dissoc` → мапа, `(= record map)` → false); shapes дают ту же скорость без них.
- Семантика неизменна: это мапа. `=` и `hash` структурные (одинаковый shape → сравнение массивов напрямую), `seq` в порядке shape (у hash-map порядок и так не определён); не-keyword ключ, nil-ключ, метаданные → generic.
- Интероп: shape = layout Swift-struct; `Codable`-энкодер получает shape по типу один раз и заполняет слоты.
- Не убегающая shape-мапа известной формы с unboxed полями на стеке (§7) = Swift-struct на стеке. Слои сходятся.

**Ограничения shapes:**
- ≤32 ключей (branching factor HAMT; линейный скан по указателям быстрее хэша до 32; копия — одна кэш-линия). Порог 8 у Clojure — про стоимость `equals` на JVM, у нас сравнение указателей.
- Не-keyword ключ → сразу generic.
- >8 различных детей у shape'а → shape «словарный», все мапы через него → HAMT. Это детектор динамических ключей (`{user-id → user}`).
- Потолок shape'ов на процесс (десятки тысяч); shape'ы интернированы и живут вечно.
- Порядок ключей: `{:id :name}` и `{:name :id}` — разные пути; канонизация при финализации по множеству ключей (кэш key-set → shape, O(k log k) один раз).
- Переход в HAMT односторонний и незаметный; обратно — никогда.

**Tuples.** Вектор фиксированного размера 2–6 с элементами inline: одна аллокация, `nth` — load по смещению без shift и хвоста, слоты могут быть unboxed (`[x y]` точки = два double). Литерал `[x y]` → tuple2, деструктуринг → два load, `conj` за ёмкость → промоушен в вектор. `MapEntry` = tuple2. Clojure JVM пробовал (1.8-alpha) и откатил из-за мегаморфных сайтов у HotSpot — у нас JIT'а нет, диспатч статический или tag-switch, аргумент исчезает. Ещё лучше — не аллоцировать пару: `(map (fn [[k v]] …))` после fusion передаёт `k v` двумя аргументами; `(seq shape-map)` отдаёт entries из (ключ shape, слот) лениво/на стеке; `(let [[a b] (f x)])` с известной формой — два возврата в регистрах.

**Векторы — elements kinds (V8).** Все int64 → unboxed `int64[]`, double → `double[]`, смешанные → boxed; переходы односторонние по наблюдению при записи. Это `vector-of :long`, только выведенный.

**Списки — ничего. Сеты** — ≤8 линейный массив, дальше HAMT; битовая маска только для статически известного keyword-универсума (литеральные сеты, enum) — оптимизация компилятора, не рантайма.

**Отвергнуто: SoA/колоночное хранение вектора мап одного shape'а.** `nth` обязан вернуть мапу — материализация или row-view, то есть третье представление мапы во всём рантайме; `assoc-in` одной ячейки — копия столбца O(n) или персистентные столбцы (и скан уже не плотный); `assoc` мапой другого shape'а → демоушен O(n), thrashing на границе; row-view снаружи держит весь вектор; паттерн доступа в UI строчный; fusion над AoS добирает половину выигрыша (слот по смещению в каждой строке). Место SoA — явный тип dataset/columnar (Arrow, tech.ml.dataset), не неявное представление `vector`.

**Общий принцип.** Представление выбирается по наблюдению, переходы односторонние, семантика неизменна. Критерий допустимости «магии»: никогда не хуже базы (медленный путь = сегодняшний HAMT, не deopt-обрыв как в V8); состояние инспектируемо (`(shape-of m)`, метрика моно/поли/мегаморфных сайтов в dev, размер дерева переходов); стоимость операций предсказуема. Fusion, reuse, регионы, hoisting, shapes проходят; SoA — нет.

**Почему Clojure JVM так не делает.** Нет своих call site'ов (`(:name m)` → `Keyword.invoke` → `ILookup.valAt`, HotSpot кэширует класс, не shape); нет unboxed-слотов без Valhalla; GC делает аллокацию дешёвой; философия «знаешь ключи — `defrecord`», без скрытого глобального состояния; консерватизм core (структуры не менялись с 1.0). У нас все три технических условия есть: свои сайты, unboxed-слоты, дорогая аллокация как мотив.

### Низкоуровневый слой: числа, layout, память
**Как это делают динамические языки.** Четыре стратегии: (1) горячее не в этом языке — NumPy/BLAS, Neanderthal; свою математику так не напишешь; (2) типизированное подмножество — Common Lisp `declare` + SBCL, Clojure `^long` и примитивные массивы, Cython/Numba; Julia сильнее всех: вывод + специализация, обычный код на числах = C, `struct` с конкретными полями имеет C-layout; (3) контроль layout'а — LuaJIT FFI `ffi.cdef`, Julia `struct`, TypedArray, Clojure `deftype` с примитивными полями; (4) FFI в C. Наш дизайн даёт все четыре: автоматика (вывод + unboxed слоты + elements kinds — путь Julia) для 90% кода, явные инструменты с гарантиями — для остального.

**Из clojure.core как есть:** `^long`/`^double`, примитивные массивы (`long-array`, `aget`/`aset`, `amap`/`areduce`), `vector-of`, `loop/recur` без боксов, `unchecked-*` и `*unchecked-math*`, `bit-*`, `deftype` с примитивными и `^:unsynchronized-mutable` полями + `set!` в методах, `transient`, `definline`, `volatile!`. Покрывает «unboxed цикл над массивом» — ~60% числового кода.

**Чего нет, потому что JVM не умел, а C умеет:**
- Ширина чисел: `i8…i64`, `u8…u64`, `f32`, `f16` как типы полей и элементов, арифметика без промоушена в long/double. Metal-буферы, аудио, сеть.
- Layout структур: вложенные структуры по значению (inline, не указателем), inline-массивы фиксированного размера в полях, `^:packed`, выравнивание. JVM структур не имеет — `deftype` там класс со ссылками.
- Значимые типы без RC: копируются по значению, без заголовка — как Swift-struct. `Vec3`, `Color`, `Rect` — 24 байта в регистрах вместо аллокации.
- Типизированные массивы структур `(array Vertex n)` с inline-элементами. Здесь SoA живёт легально — как явный тип, не магия над `vector`.
- SIMD: `(simd :f32 4)` → C vector extensions, операции интринсиками.
- Чужая память: `view` над `MTLBuffer`/`mmap`/C-буфером с интерфейсом массива; голый `ptr` и арифметика — только в ns с `^:unsafe` (ниже, «Чужая память»).
- Интроспекция: `(sizeof T)`, `(offsetof T :x)`, `(alignof T)` — без этого не заполнить `MTLBuffer` под шейдер.
- Интринсики: `popcount`, `clz`, `ctz`, rotate, `fma`, saturating.
- Гарантии: `^:no-alloc`, `:strict`-ns, `^:inline` (§3, решётка фактов). `:strict` подсвечивает каждый бокс — аналог `@code_warntype`, главный инструмент числового кода: «где я потерял тип».
- SIMD/Accelerate/vDSP/BLAS — просто стабы, без моста через `Value`; C-функции с сигнатурой из заголовка вызываются напрямую с unboxed аргументами (у Clojure JVM — JNI/Panama).

Не добавлять: мутабельные локалы (`set!` на `let`) — семантический разлом, `loop/recur` и мутабельные поля `deftype` покрывают; ручное управление памятью вне `^:unsafe`.

**`deflayout` — layout как данные.**
```clojure
(deflayout Vertex
  [[:pos [:f32 3]]
   [:uv  [:f32 2]]
   [:color :u32]])
```
Той же формы, что схемы; вычисляется при компиляции (как схемные функции), порождает C-struct, знает sizeof/offsetof/alignof; та же декларация может породить Metal-совместимую структуру для шейдера.

Представление в рантайме — два состояния одного значения, как Swift-struct:
- Типизированный контекст (поле другого layout'а, элемент `(array Vertex n)`, unboxed-локал с известным типом) — inline байты без заголовка.
- Динамический контекст — бокс: heap-объект `{rc, tag=LAYOUT, descriptor*}` + payload. `Value` получает один новый тег; intrinsics с tag-switch — одну ветку «смотри в дескриптор». Это `Any`-бокс существенциала в Swift, только явно.
- Дескриптор — shape с фиксированным layout'ом: ключи → смещение + тип поля (у shape: ключи → индексы). Вся динамическая семантика — от shape-мап: `(:pos v)` через `ILookup` по дескриптору, `=` по полям, hash, print, seq. `(assoc v :color c)` — копия байт + запись → новый бокс; персистентность бесплатно, потому что копия, а не разделение. Мутация — только `^:unsafe` или `aset` в типизированный массив.
- Ограничение isbits (из Julia): внутри layout'а только скаляры, вложенные layout'ы, inline-массивы. Никаких `Value`/ссылок. Копия = memcpy, RC не участвует, GC-корней нет, кладётся в `MTLBuffer` и передаётся в C как есть. Структура со ссылками — это `deftype`, другая вещь. Граница: layout = байты, deftype = объект.
- Бокс при потере типа: `(aget verts i)` с известным типом — unboxed в регистрах/на стеке; с ⊤ — бокс (аллокация). Как Julia isbits. `:strict`/`^:no-alloc` подсвечивает.
- Арифметика на layout'ах не встроена — `extend-type Vec3 IAdd` или функции, диспатч по дескриптору. Исключение: SIMD-layout'ы `[:f32 4] ^:simd` — интринсики знают операции напрямую.
- Интероп: дескриптор → C-struct для кодогена; Swift `@frozen`/C-импортированные структуры совместимы по layout'у → memcpy; произвольные Swift-struct — проверка `MemoryLayout` при сборке моста, иначе поле за полем.
- Стоимость добавления: тег + тип дескриптора, наследующий shape, + ветка в 3–4 intrinsics. Остальное — переиспользование сделанного для мап.

**Чужая память — view, не указатель.** Clojure сам памяти не знает: массивы — единственный мутабельный буфер в core, остальное host-interop (`ByteBuffer`, Panama `MemorySegment`+`Arena`, `coffi`/`dtype-next`; в CLJS — `TypedArray`; jank отдаёт голый C++). Позиция последовательная: язык про значения, буфер — escape hatch, и массив уже такой hatch. Мы её продолжаем: чужая память — это массив, чьи байты живут не у нас, а не новый вид значения.
- `(view buf Vertex)` — объект с интерфейсом `(array Vertex n)`: `aget`/`aset`/`alength`, элемент — layout по значению (copy-in/copy-out), `(slice v off len)` вместо арифметики. Bounds-check по умолчанию, `^:unsafe` снимает — та же цена отказа, что у `unchecked-*`. Для анализа `aset` на view — тот же эффект, что `aset` на массив; в решётке ничего нового. Один интерфейс на три хранилища: inline-массив, `MTLBuffer`, `mmap`.
- **Владение — три вида, явно** (Panama пришёл к тем же трём за три итерации: `ofAuto`/`ofConfined`/`global`): *borrowed* — view держит RC на Swift-владельца (`MTLBuffer`), память жива, пока жив view; *owned* — `(mem-alloc n)` → RC-объект, `free` в деструкторе; *arena* — `(with-arena [a] …)`, освобождение при выходе из scope, обращение после — trap, не UB.
- Голый `ptr` — opaque значение на FFI-границе (пришло из C, отдать в C), разыменовать нельзя. В `^:unsafe` ns — `(unsafe-view p Vertex n)` без владельца и `ptr-get`/`ptr-set!` по смещению: слой для авторов биндингов, не прикладного кода. Модель Swift та же: `UnsafeRawPointer` сам по себе бесполезен, читают через `UnsafeRawBufferPointer`/`withMemoryRebound` с размером и типом.
- View — только над `array` и чужой памятью. Над persistent-значением (`(view some-vector :i64)`) — нет: сломает персистентность через чёрный ход.

**Самодостаточность против нормы.** Слой нужен, чтобы за скоростью не уходить в C, — но «скорость» должна приходить с безопасного этажа: вывод типов + unboxed слоты + `deflayout` + типизированные массивы закрывают hot loop без единого `unsafe`. `^:unsafe` — не «быстрый режим», а граница с чужим кодом: биндинг к C API, который возвращает указатель, и ничего больше. Метрика в dev: число `^:unsafe` ns в проекте; в прикладном коде оно должно быть нулём, в библиотеке биндингов — по одному на API. Отдельный вопрос — писать ли на этом слое сам рантайм (HAMT, аллокатор): нет, ядро на C (§3 «Слои»), слой рассчитан на пользовательский числовой код, не на self-hosting.

**Числовая башня** (нет Java, нет bignum в Swift stdlib). `BigInt`, `BigDecimal`, `Ratio` — типы рантайма на C поверх GMP/MPFR (LGPL — динамически) или permissive (`libtommath`/`mini-gmp`), либо своя. Продвижение как в Clojure: `+` на int64 переполняется → исключение, `+'`/`*'`/`inc'` — автопромоушен. Диспатч по тегу в интринсике, unboxed fast path int64/double, медленный путь — C-функция bignum. Своя библиотека высокой точности — на C или на Clojure с `:strict`: limb-массивы = `(vector-of :long)` + unboxed loop.

**Критерий достаточности.** На этом слое можно написать particle-систему без единого бокса с прямой записью в `MTLBuffer`. Если нет — инструментов не хватает.

### Атомы
- Атом живёт в C-ядре, бэкенда на Swift-стороне нет (§3: ничего платформенного в ядре; Swift видит только `deref`/`swap!` через `Value`, мост к `Observable` — слой курсоров выше). Лок — `clj_lock` (`clj/lock.h`): `os_unfair_lock` под `__APPLE__`, `pthread_mutex_t` иначе, один интерфейс, один `#ifdef` — та же граница, что у `host`. Замер (M3 Pro, пара lock+unlock): unfair 2.1 нс / 4 байта, pthread 4.6 нс / 64 байта; под contention unfair передаёт приоритет владельцу (для этого он и создан), pthread — только с `PTHREAD_PRIO_INHERIT`. Адрес стабилен: атом — объект фиксированного размера, `clj_realloc` его не трогает. Все локи ядра (таблицы keyword/ns/протоколов/профайлера) — через него же. **Rwlock — нет:** взятие read-лока — атомарный RMW на общем счётчике, читатели дерутся за кэш-линию как за мьютекс (4 читателя: unfair 38 нс/оп, `pthread_rwlock` 448, размер 200 байт); окупается только при длинных read-секциях, которых в ядре нет и не должно быть — «много читают» решается иммутабельностью + эпохой (протокольный диспатч, вары), читатель не берёт ничего. Не CAS: lock-free refcounted-указатель = гонка retain/release, нужны hazard pointers или DCAS ради повторения JVM-дизайна.
- `f` выполняется ровно один раз, под локом. Watches — после отпускания лока. Вложенный `swap!` на тот же атом — trap (на JVM — бесконечный ретрай, оба баг). `deref` тоже под локом — дёшево.
- **Трюк уникальности — снят.** `old = state; state = placeholder; new = f(old)` давал in-place внутри `f`, но бросок из `f` после in-place шага не может вернуть старую версию — её уже нет; JVM при броске оставляет состояние как было, и код на это опирается (`(swap! a (fn [s] (if ok (assoc s …) (throw …))))` — идиома отказа). Журнал отката признан слишком сложным за такую цену. Атом держит свою ссылку, `f` получает значение +0, `swap! assoc` копирует путь корень→лист: 91→288 нс на 16 ключах, 101→613 на 1000, 131→904 на 100k (bench/RESULTS.md, «Atoms»); `deref` того же атома изнутри `f` возвращает текущее (старое) значение, как на JVM. Возврат трюка — только для атомов без watch'ей и валидатора и только при одном из двух: доказанное отсутствие броска в `f` (факт `throws` решётки §3) или журнал отката — что дешевле, когда профиль покажет горячий `swap!` на большой мапе.
- Не актор: `swap!` обязан быть синхронным.

### Подписки (вместо Observable-макроса)
- `add-watch` — на весь атом; уровень путей — слой выше (cursor/reaction, re-frame).
- Подписки по путям в trie. После `swap!` обход trie: `new[k] === old[k]` → ветка пропущена. Стоимость ∝ (изменившиеся пути ∩ подписанные), не размер состояния. Нет подписчиков → ноль.
- Автотрекинг без макроса на уровне `deref` (TLS-контекст), а не полей — так делает reagent. Гранулярность атом/курсор.
- **Мост к SwiftUI:** курсор реализует `Observable` руками через `ObservationRegistrar` с одним свойством `value`. Инструментирована одна точка на курсор, не каждое поле модели. `@Observable`-макрос дорог именно потому, что у класса нет другой точки перехвата; у атома точка одна — `swap!`.

### Функции
Clojure-fn ≠ Swift-замыкание: несколько арностей, `IFn` на keyword/map/vector/set, метаданные, identity, `apply`, свой RC и конвенция +0. Скомпилированная fn = `{header, table[arity]→C-функция, env}`. На границе — адаптеры в обе стороны (`Value.callAsFunction`, host-fn для Swift-closure).

### Протоколы и типы — свои, в обоих режимах
- `defprotocol`/`deftype`/`reify`/`extend-type` — своя таблица диспатча (как в CLJS/ClojureDart), не хостовые типы. Компилятор может опустить `deftype` в struct с vtable — это представление, не семантика.
- `extend-type` на Swift-типы работает (диспатч по метаданным типа), новый тип не нужен.
- **`reify` — четыре случая:**
  1. Clojure-протокол → таблица, бесплатно.
  2. `@objc`-протокол/класс → живой класс из ObjC-рантайма (делегаты, `UIView`-подклассы — всё UIKit). Полностью динамически, из REPL.
  3. Swift-only протокол → **предкомпилированный адаптер** на протокол (type-eraser, методы уходят в интерпретатор). Один раз на протокол, кодоген по `.swiftinterface` (макросы не видят чужие декларации). Associated types → generic-адаптер, инстанцируемый через `_typeByName`. Список реально нужных — пара десятков.
  4. Подкласс Swift-only класса с vtable → только заранее сгенерированный `open class` прокси. Честно закрыто; в Apple-фреймворках таких классов мало.
- **Не** генерировать честные конформности из `deftype` в компиляторе — расхождение семантик между режимами (то, за что SCI платит годами). Адаптер — единый контракт; компилятор может его инлайнить.

### Дескриптор типа: core-интерфейсы как слоты
Не Swift-протоколы (из C недоступны, стоят экзистенциалов) — **дескриптор типа со слотами**, как `tp_*` в CPython или метатаблицы Lua. `clj_type` уже он: `each_child/finalize/hash/equals` — первые слоты, `clj_invoke` — первый диспатч по типу. Дальше — расширение, не переписывание.

```c
struct clj_type {
    clj_header h; const char *name;
    uint64_t core_bits;            // битсет реализованных core-интерфейсов: (map? x) = один AND
    seq, first, next, count, lookup, conj, invoke, equals, hash, each_child, finalize;
    proto_table *user_protos;      // defprotocol'ы: id протокола → таблица; NULL пока
};
```

- **Core-интерфейсы** (`ISeq`, `IFn`, `ILookup`, `Counted`, `IPersistentCollection`, `Associative`, `IEquiv`, `IHash`, позже `IMeta`) — фиксированные слоты, ноль поиска: тег → дескриптор → слот → вызов. Пользовательские `defprotocol` — отдельная таблица по id, потому что их неограниченно много. Иерархию Java-интерфейсов (`IPersistentMap extends ILookup, Counted, …`) заменяет `core_bits`: `satisfies?`/`sequential?`/`coll?` — один AND, без обхода иерархии.
- **`invoke` — один слот** `(self, args, n)`. Арность — свойство объекта (`clj_fn` держит таблицу арностей), не типа.
- **`seq` обязателен, `first`/`next` — опциональный fast path.** Источник истины — seq-объект: `(first v)` = `(first (seq v))`, как `RT.first`. Прямые `first`/`next` на коллекции оправданы только там, где `seq` — O(1) view без аллокации (вектор, string, range, позже array-map); для HAMT `seq` и так строит объект. Дефолт через `seq` — норма, fast path — для четырёх-пяти типов.
- **Трейты вместо абстрактных классов** (`ASeq`, `APersistentMap` на JVM): `desc = ASEQ_TRAIT; desc.first = my_first;` — структурное копирование в C. Sequential equality/hash уже написаны один раз (`coll.c`) — это и есть `ASEQ_TRAIT`.
- **`deftype`/`reify`/`extend-type`** создают или патчат дескриптор: слот указывает на трамплин, который зовёт Clojure-функцию (интерпретатор) или сгенерированную C-функцию (компилятор). Host-обёртки тоже имеют дескриптор — поэтому `extend-type` на Swift-тип работает без создания типа.
- **Мутабельность и потоки.** Патч слота — под глобальным мьютексом протоколов; публикация трамплина — release-store, чтение — acquire (не relaxed: иначе читатель видит указатель раньше тела трамплина; JVM-Clojure живёт с benign race в `extend`, нам не стоит). Каждый патч инкрементирует **глобальную эпоху протоколов** — та же механика, что у варов: inline-кэши на узлах AST и PGO-guard'ы компилятора кэшируют результат диспатча по типу и без эпохи `extend-type` из REPL не долетит до уже закэшированных сайтов.
- **Граница запрета:** «встроенный тип × core-интерфейс» — write-once, `(extend-type String ISeq …)` невозможен (CLJS позволяет — и это источник загадочных багов между библиотеками). «Любой тип × пользовательский протокол» через `user_protos` — разрешён, это основной сценарий `extend-type`. Открыть проще, чем закрыть.
- **Интринсики компилятора** (tag-switch с inline-ветками: `first` на cons — прямой load) — дубль слота, не замена; интерпретатор ходит только через слоты. Страховка — дифференциальный property-тест: генератор коллекций × таблица `(intrinsic x) == (slot-call x)` по всем core-операциям; он же ловит разъезд интерпретатор/компилятор.
- **Кэш `hash` и `meta` — не в дескрипторе** (он общий на тип), а в объекте. Но и не в общем заголовке: `clj_header` — 16 байт без padding, `hash + meta` = ещё 16 на каждый cons и boxed double (cons 32 → 48). Layout заголовка — приватная деталь компиляции, не ABI (Swift читает только через функции), поэтому резервировать место заранее незачем: `hash` кэшируется per-type там, где окупается (map — уже, vector/string/symbol — по мере надобности), `meta` — поле только у IObj-типов (корни коллекций, symbol, fn, var), как в Clojure. Исключение — cons и `()`: у них нет поля, флаг заголовка `CLJ_FLAG_META` означает «есть хвостовое слово meta»; 40-байтный вариант аллоцируют только reader (позиция формы) и `with-meta`, cons из lazy-seq остаётся 32 байта (классы пула 32/40/48 — иначе +25 % на самый массовый объект).
- **Swift-сторона** получает протоколы *поверх* слотов: `Value: Sequence, Collection, Hashable` — конформансы, реализованные вызовом слотов через C ABI. В обратную сторону — Swift-тип участвует в `ISeq`, если его host-обёртка получила дескриптор с трамплинами в стабы.

Прецеденты: CPython `tp_iter`/`tp_call`/`tp_as_mapping`, Lua `__index`/`__call`, Racket CS record-type descriptors с properties, Ruby C API, jank (то же на C++-шаблонах). Наше добавление — битсет для `satisfies?`, эпоха и трамплины интерпретатора и компилятора в одном слоте.

### Роли конструкций и ссылочные типы
- `defrecord` — shape-дескриптор с заполненными map-слотами + `user_protos`: данные и поведение, остаётся мапой.
- `deftype` — дескриптор с пустыми слотами, identity-равенство, возможны мутабельные поля. Реализация абстракций: своя коллекция, канал, транзиент.
- `reify` — `deftype` без имени. `extend-type` — патч чужого дескриптора. `deflayout` — байты (§4, низкоуровневый слой).
- **Мутабельные поля `deftype` — только с меткой, писать только изнутри** (как в Clojure): `set!` разрешён в телах методов самой формы `deftype` — в реализациях протоколов и интерфейсов внутри неё. Снаружи поле не записывается никак: ни `(set! (.-field x) v)`, ни через рефлексию; прочитать `(.-field x)` можно. Причина — мутация инкапсулирована в реализацию абстракции: транзиент мутирует свой массив внутри `conj!`, канал — свой буфер внутри `put!`, наружу торчат только протокольные операции. Пользователь объекта видит `ISeq`/`IChan`/что угодно, а не поле, которое можно поменять из любой точки программы.
- Что это даёт сверх Clojure: анализ знает все точки мутации — они внутри одной формы, поэтому «мутабельный тип» ставится по меткам полей, `set!`-эффект приписывается только тем методам, где он есть, остальные методы типа остаются чистыми; гарантия «`^:unsynchronized-mutable` трогает только поток-владелец» проверяется в конечном числе методов, а не по всей программе (из чужого потока — ошибка в dev, у JVM тихая гонка); `may-cycle` (§7) ставится по факту наличия мутабельных полей, угадывать нечего. Мутабельность — факт в решётке: объект вне reuse-анализа, при пересечении потока → SHARED.

**Ссылочные типы.** `atom` (независимый, синхронный) — в ядре. `agent` (независимый, асинхронный) — тонкая библиотека: значение + serial executor, mailbox = канал функций. `ref`/`dosync` (координированный STM) — простая реализация: two-phase locking с захватом ref'ов по id, без MVCC и ретраев. Атомарность и изоляция сохранены; теряется неблокирующее чтение под нагрузкой, которого в мобильном приложении не бывает.

### Мультиметоды
Целиком в рантайме (MultiFn + таблица + иерархия + кэш диспатча под тем же Mutex). Хост всплывает только в `isa?` на хостовых типах — читать суперкласс из class metadata, конформанс через `swift_conformsToProtocol`, `@objc` — через `class_getSuperclass`.

### core.async
- **`go` — один путь в обоих режимах:** корутины рантайма (§6b, уровень «рантайм»). `go` = спавн корутины на носителе с affinity, `<!`/`>!` = park с прямой передачей значения. Ни IOC-трансформа для интерпретатора, ни `Task` + `await` для компилятора — это была бы вторая реализация семантики с гарантированным расхождением. Ограничение «`<!` только в теле `go`» снимается: ждать может любая функция, «ждёт» — факт исполнения, а не тип (§5 «Замыкания через границу»). Swift `Task` остаётся только на мосту.
- **Каналы свои:** буфер + очереди припаркованных корутин под локом, `alts!` через общий флаг-победитель, `timeout` — таймер носителя. `AsyncStream` — не то (single consumer, нет backpressure), но его `BufferingPolicy` = sliding/dropping один в один.
- Кооперативный пул нельзя блокировать — как 8-поточный пул core.async. `<!!`/`>!!` не давать (DispatchSemaphore в пуле = priority inversion).
- `go` unstructured (как `Task.detached`); сверху `go-scoped`. Переход на main: affinity `:main` на канале или `go-main`. Sendable на Swift-стороне: значения иммутабельны, но бокс `Any` — `@unchecked` на обёртке.
- Акторы ≠ каналы: акторы для владения состоянием, каналы для потоков данных.
- **RC на границах go:** `go` шарит захваченное множество один раз при spawn (порождающий поток продолжает пользоваться локалами); всё, что go-блок аллоцирует после, — на быстром пути, пока не уйдёт через канал/атом. `>!`/`put!` шарит значение (putter держит его дальше) — move вместо share только вместе с ownership-анализом; на небуферизованном канале значение живёт в состоянии припаркованного putter'а — одно место в каждый момент. Парк/резюм не шарит ничего. `alts!` — исключение из handoff: один handler в очередях нескольких каналов, проигравшие на разных потоках сбрасывают его конкурентно → атомарен handler (обёртка с флагом-победителем), continuation внутри по-прежнему move победителю. Сам канал — обычный объект, shared при захвате/публикации.

### Ошибки и стектрейсы
- **Компилятор:** `#line N "app/core.clj"` в сгенерированном C → DWARF с `.clj` → Xcode-брейкпоинты, символикация крэшей через dSYM, Instruments — всё штатное. Читаемое манглирование имён + деманглер. `:line/:column` через macroexpand.
- **Интерпретатор:** теневой стек кадров (push/pop, наносекунды), обработчик сигнала дописывает его в крэш-репорт (custom keys / буфер).
- **Одна модель ошибок:** `ex-info` ↔ `ClojureError: Error {message, data, clojureTrace, cause}`; Swift `throws` → `ex-info` с `:host/error`.
- **Async:** в dev при создании `go`/`lazy-seq`/`future` запоминать кадр создания → «spawned from».
- **Логи:** `swift-log` через стаб, Logger на ns, Clojure-мапа → `Logger.Metadata` напрямую.
- Крэши рантайма: debug-сборка с ассертами на счётчиках, canary в заголовках, ASan (на C работает из коробки).

**Локация в коде — для логов, аналитики, трейсов.** Clojure наполовину умеет: `(meta &form)` в макросе даёт `:line`/`:column` места вызова, `*file*` и `*ns*` связаны при загрузке — так работает timbre. Дыры: в функции локацию вызывающего взять негде; `:file` в мете формы нет; имени охватывающей функции нет; вложенные раскрытия теряют позицию — у формы из syntax-quote нет `:line`, ошибка показывает на сгенерированный код. Три аддитивных решения, принцип один: **локация — место в исходнике пользователя, а не в ближайшем слое обёрток; обёртки прозрачны по умолчанию.**
- **Мета формы богаче** (как в CLJS): `:file :line :column :end-line :end-column :ns :fn` (охватывающий top-level вар). Аналитор ведёт цепочку `:origin` через раскрытия (Racket syntax objects, Rust `Span`): каждая раскрытая форма помнит, из какой получена. Закрывает вложенные макросы и даёт LSP отображение диагностики из глубины раскрытия на строку исходника.
- **`(location)` — макрос в core**, не reader-тег: `#location` без namespace зарезервирован за Clojure, а `.cljc` с ним не прочитается на JVM. Раскрывается в литеральную shape-мапу — singleton в решётке, hash-consed, ноль аллокаций; `#line` в C из него же. Идёт по `:origin` до ближайшей формы, написанной пользователем; `(location :expansion)` — сырая позиция, для отладки макросов.
- **`^:track-caller` на `defn`** — аналог Rust `#[track_caller]` и Swift `line: Int = #line`: функция получает локацию вызывающего без обёртки в макрос, внутри читается `(caller-location)`. Аналитор на прямых вызовах подкладывает скрытый аргумент-константу — ту же shape-мапу, что у `(location)`, где `:fn` — охватывающий вар *вызывающего*. Транзитивность по правилу Rust: track-caller-функция, зовущая track-caller-функцию, передаёт *свой* скрытый аргумент, а не текущий сайт — враппер прозрачен без ручного проброса `file:`/`line:`, как приходится в Swift. Через `apply` или как значение — `nil`. На JVM мета игнорируется, `(caller-location)` → `nil`, `.cljc` не ломается.

## 5. Интероп

### Главное разделение: данные vs вызовы
Swift-рантайм отдаёт **данные** динамически (метаданные полей, get/set по смещению, тип по имени, generic-инстанциация, конформансы), но **не вызовы** (произвольный метод с сигнатурой, известной в рантайме). Интерпретатор и компилятор в интеропе равны — оба зовут только то, что заранее в мосту.

### Что умеет Swift-рантайм (wickwirew/Runtime, Echo и ниже)
Можно: метаданные типов, поля по смещению, `_typeByName` (включая generic-инстанциации), `x as? any P` (единственный настоящий динамический вызов — по известному протоколу на любом типе), `dlsym` по mangled-имени + `unsafeBitCast` к известному типу, `@_dynamicReplacement`, ObjC-рантайм на Swift-классах (`@objc dynamic` методы), патчинг vtable (хак), `_openExistential`.
Нельзя: создать Swift-тип, добавить конформанс, позвать функцию с рантайм-сигнатурой (Swift ABI), eval/загрузить код на устройстве.

### Три уровня, одновременно
1. **ObjC-рантайм** — всё `@objc` (UIKit, Foundation, AVFoundation…), из REPL, без пересборки. ~70% реального приложения.
2. **Зарегистрированный мост для Swift-only** — таблица функций, Expo-Modules-стиль: руками по мере надобности, генерация *глю*, не *покрытия*. Из `.swiftinterface` честно генерируется только не-дженерик поверхность. «Подключил SwiftUI — получил всё» не выйдет (никто не сделал; UniFFI/swift-bridge существуют именно поэтому).
3. **Данные через границу** — Clojure отдаёт описание, Swift исполняет. Для SwiftUI это не компромисс, а архитектура: view-дерево как данные, Swift-рендерер с фиксированным набором компонентов. Elm/re-frame.

Граница: Clojure — «мозг» (состояние, логика, данные, сеть), Swift — «руки» (рендер, hot paths, Metal). Переход стоит десятки нс: ноль для UI-событий, приговор для пиксельного цикла.

Реальная потеря без eval Swift: нельзя из REPL исследовать Swift-only API, которого нет в мосту.

### Swift → Clojure
- **`Value`** — один тип на границе: struct над raw-указателем, RC в `init`/`deinit`, конвертеры примитивов, литералы, `Optional` → nil, `callAsFunction`. Вызов `clj.fn("app/handle")(args)` → `clj_invoke` по C ABI.
- **Структуры — `Codable`:** `CLJEncoder/CLJDecoder`, как JSONEncoder, но результат — персистентная мапа с keyword-ключами. Официальный механизм, покрывает почти все модели. Рефлексия из Runtime — fallback для не-Codable.
- **Без копирования — host-value:** `UIView`, `DateFormatter`, дорогие структуры — opaque объект, `(:field obj)` по метаданным по требованию, `ILookup`; первый `assoc` материализует в настоящую мапу.
- **Владение:** `Value` в Swift = +1; deinit может прийти в любом потоке → экспортированный объект переходит на атомарный счётчик (biased RC). Swift-объекты у нас — `Unmanaged` retain.
- **Замыкания в обе стороны** с первого дня.

### Замыкания через границу: цвет живёт в Swift
Clojure-функция цвета не имеет: с корутинами ждать может любая, «ждёт» — событие исполнения, а не тип. Swift-замыкания цвет имеют. Мост читает цвет из Swift-сигнатуры и адаптирует; Clojure-сторона ничего не помечает.

**Каноническая форма одна — `Value`.** Три способа позвать, выбор на Swift-стороне и всегда статический (Swift сам не даст позвать `async` из sync):
- `callAsFunction(_ args: Value…) throws -> Value` — синхронно на потоке вызывающего.
- `callAsync(_ args: Value…) async throws -> Value` — спавнит корутину, Swift-Task приостанавливается через `withCheckedContinuation` до результата; внутри функция ждёт свободно.
- `callDetached(…) -> Task<Value, Error>` — запустить и не ждать. «Промис» есть, но его попросили явно.

Типизированные адаптеры сверху — `closure<A,B,R>() -> (A,B) throws -> R` и `closureAsync()`: дженерик-обёртка создаётся там, где сигнатура известна (стабы из `.swiftinterface` знают тип параметра; ObjC — `@convention(block)` с сигнатурой из type encoding; рукописный Swift — явно). Арность и типы проверяются при создании обёртки, не при вызове. Замыкание держит `Value` (+1 → SHARED, атомарный счётчик). Ошибки: `throws`-сигнатура → `ClojureError`; не-`throws` (большинство UIKit) — в dev `fatalError` с Clojure-трейсом, в prod лог + значение по умолчанию, настраивается на стабе.

**Swift-closure → Clojure** — host-fn с одной арностью. Синхронное — прямой вызов. `async` — вызов запускает Task, текущая корутина приостанавливается, результат возвращается значением; для Clojure это синхронная функция.

**Ошибка «ожидание внутри синхронного host-вызова».** Внутри Clojure-мира не возникает никогда: Clojure-код всегда на корутине (точка входа, `go`, обработчики UI-бэкенда, REPL-eval, main-носитель с affinity `:main` крутит корутины из run loop). Возникает только на синхронном входе из Swift: Swift ждёт значение сейчас, приостановиться нельзя — та же причина, что у sync-замыкания без `await`. Политика: ошибка. **Не** блокировка — поток не замораживается никогда; **не** возврат `Task` — это динамическая раскраска по факту исполнения, footgun core.async «получил канал вместо значения», и побочные эффекты до точки ожидания уже случились. `callBlocking` — явный opt-in на не-main потоках. Выходы: `callAsync`, `(go …)` в колбэке, `callBlocking`.

Гвард — `host_depth`: трамплины инкрементируют при входе из Swift и декрементируют при выходе; ожидание разрешено только при `host_depth == 0`, даже если технически под Swift-фреймами лежит стек корутины (реентерабельность посреди чужой операции, например layout-колбэка). Статически: стаб знает, что параметр — sync-замыкание, а у переданной функции есть факт «может ждать» → предупреждение при компиляции. Для сравнения: `DispatchSemaphore.wait()` на main в Swift — тихий фриз; у нас ошибка с трейсом до места ожидания.

### ABI
- Сгенерированный C ↔ ядро — C ABI (`@_cdecl` на Swift-части рантайма).
- Стабы ↔ Swift-фреймворки — Swift ABI, целиком внутри swiftc.
- `@objc` — ObjC ABI, стабилен десятилетиями, дёргается динамически.
Swift ABI руками не трогаем; понадобится только если LLVM-IR-бэкенд захочет звать Swift без стабов — причина начинать с C.

## 5b. UI-слой
**Принцип: язык не знает про UI.** На уровне компилятора — только `defdsl` (§3). Всё остальное — библиотека.

**Дилемма.** Прямое соответствие нативному (Reagent → React, ClojureDart → Flutter) работает, потому что хост уже декларативный. У Apple такого хоста нет: SwiftUI декларативен, но закрыт (данные в фиксированный набор), UIKit открыт, но императивен — `UIView` строится и мутируется, деревом не описывается. Кто-то должен превратить дерево в `addSubview`/`remove`/`setNeedsLayout`.

**Решение — слои по образцу React Native; изобретается только один:**
1. **Реконсилер** — единственная новая часть. Диффит два hiccup-дерева, зовёт бэкенд `create`/`update`/`remove`. Персистентность: неизменённые поддеревья — `identical?` по указателю, не обход — дешевле React props-diff. Компонент = функция → hiccup, подписан на курсоры атома (§4 «Подписки») → перерисовывается только он (модель Reagent). Сотни строк, не Flutter.
2. **Бэкенд** — реестр тегов с тремя функциями на тег. UIKit: `:label` → `UILabel`, `:stack` → `UIStackView`, атрибуты → свойства, `:on-tap` → target через ObjC-рантайм. Тонкая таблица, как host components в RN.
3. **Escape hatch** — `[:native (fn [] any-uiview)]` и `reify` `@objc`-подклассов. Гибкость UIKit не абстрагируется, а оборачивается.
4. **SwiftUI-бэкенд** — тот же реестр, другая реализация: данные в фиксированный набор Swift-компонентов. Для системных вещей, не для всего.

**Layout — Yoga** (flexbox из RN, библиотека на C): ложится в ядро, считает фреймы, UIKit-вью получают `frame`. Быстро, детерминированно, переносимо. Auto Layout медленный на больших деревьях и не переносится.

**Кроссплатформа — разрешить, не проектировать.** Ловушка общего словаря — наименьший общий знаменатель; Flutter обошёл её, владея рендерингом целиком. RN-модель: словарь тегов per-backend (`:uikit/blur` легален), общее подмножество складывается по факту. Другая платформа = другой бэкенд с пересекающимся словарём.

**Итог:** не «свой UI-фреймворк», а «реконсилер + Yoga + таблица тегов над UIKit»; SwiftUI — второй бэкенд для того, что есть только в нём.

## 5c. Инструментарий: nREPL, LSP
**nREPL — сразу.** REPL-интеграция редакторов (Calva, CIDER, Conjure) идёт через nREPL, не через LSP; для Clojure-разработчика это важнее LSP. Протокол в рантайме — bencode + `eval`/`load-file`/`complete`/`info`, сотни строк — и существующие клиенты подключаются к интерпретатору на симуляторе или устройстве как к обычному Clojure.

**clojure-lsp — как есть.** Синтаксис наш = Clojure: навигация, rename, find references, форматирование, рефакторинги, неиспользованные вары (clj-kondo под капотом) работают с первого дня. Не дублировать.

**Свой LSP — тонкий клиент аналитора-библиотеки (§3), когда решётка фактов заработает.** Ценность только в том, чего clojure-lsp не знает:
- диагностика: ⊥-конфликты с двумя точками, `:strict`-предупреждения, «всегда nil»;
- hover: выведенный тип, shape, nullability, эффекты, owned/borrowed;
- semantic tokens: подсветка «может ждать», `^:unsafe`-зон;
- inlay hints: бокс/unboxed — `@code_warntype` в редакторе; призрачный префикс `await`/`try` перед вызовом неявно async/throws-функции — убедительнее одной подсветки, т.к. текст, а не только цвет;
- автодополнение из `defdsl`-реестров (теги и атрибуты hiccup) и из `.swiftinterface` для стабов;
- go-to в host-код: от `(.string formatter)` к Swift-декларации.

Два сервера на один файл (VS Code и Neovim умеют): clojure-lsp — рефакторинги, наш — семантика. Позже, если аналитор станет полнее clj-kondo (у нас резолв есть, у kondo нет), можно закрыть и синтаксический слой — не приоритет.

Сервер — JSON-RPC над аналитором, на нашем же Clojure, скомпилированном в нативный бинарь (dogfooding, быстрый старт). Требование к аналитору — инкрементальность на уровне формы с эпохами варов — уже есть от dev-режима.

**Макросы раскрываются по-настоящему.** clj-kondo макросы не исполняет — отсюда хуки: каждый пользовательский макрос надо описывать отдельно, иначе всё внутри него — ⊤ или ложные срабатывания; на практике проще отключить kondo целиком. У нас аналитор содержит интерпретатор и раскрывает любой макрос как компилятор: тело `defmacro` выполняется, результат анализируется. Ничего описывать не нужно, hiccup-макросы и DSL проверяются как обычный код. Цена — аналитор обязан **исполнять** top-level формы проекта, иначе реестр `defdsl` пуст, протоколы не зарегистрированы, схемы не вычислены. Исполнять всё нельзя: `(start-server!)` на открытие файла недопустимо. Ответ — та же классификация эффектов, что у ленивых `def` (§4): **режим анализа** загрузки ns — формы с эффектом `registration` (`defmacro`, `defdsl`, `defprotocol`, `defmethod`, `extend-type`, схемы) исполняются, чистые `def` остаются thunk'ами, формы с IO-эффектами пропускаются, неизвестный эффект → пропуск. Нераскрывшийся из-за пропуска макрос → ⊤ дальше по форме, не ошибка. Режим общий для LSP и компилятора: компилятору для раскрытия макросов в закрытом мире нужно загрузить те же ns, и без этого режима AOT поднимает серверы из `defonce`, как в JVM-Clojure.

**Рассматривается: бит `macro-time` на варе — спрос, а не разрешение.** Эффекты говорят, что *безопасно* исполнить, не что *нужно*. Для чистых `def` спрос даёт ленивость сама: раскрытие зовёт `helper` → форсится thunk. Бит нужен там, где спросом не форсится: top-level записи в реестры через атом (`atom-write` → сейчас пропуск → макрос по реестру даёт ⊤; с битом форма исполняется, если её цель достижима из тела макроса), IO на macro-time (`(def schema (slurp …))` — LSP пропускает, AOT исполняет), фазы для компилятора (macro-only хелперы вон из образа на устройство — Racket phases, но выведенные). Вычисление — достижимость от каждого `defmacro` по множеству ссылок на вары из сводок (поле нужно tree-shaking'у и так); монотонный бит, без второго прохода по дереву — повторно только исполняются отложенные формы по готовому `clj_node`. Ограничения: граф неточен при `resolve`/higher-order → бит консервативный, fallback тот же ⊤; отложенная форма исполняется позже своей позиции. Мера: на загрузке core — сколько thunk'ов реально форсится против «исполнить всё, кроме IO»; если выигрыша нет, бит остаётся только ради фаз и ждёт tree-shaking'а.

## 6. Компилятор

### Разблокирующий шаг — закрытый мир
Без него ничего не работает. С ним: вары → прямые вызовы (`^:dynamic` и `with-redefs` остаются косвенными), tree shaking core, протоколы → CHA (одна реализация → прямой вызов, несколько → switch), мультиметоды со статической иерархией → switch, `apply`/вариадики с известной арностью без seq.

### Оптимизации по источнику права

**Локальный вывод типов (ClojureDart-стиль):** литералы, core-сигнатуры, `instance?`-guards → unboxed `loop/recur`; `(:key m)` с литералом → предвычисленный хэш; `defrecord` → struct со смещениями; shape inference для литеральных мап. См. §3 — вывод живёт в общем аналиторе, не в компиляторе.

**Чистота (анализ эффектов транзитивно по закрытому миру):** fusion/deforestation пайплайнов `map/filter/reduce` → один цикл (легально: порядок эффектов lazy seq не гарантирован); strictness (lazy seq, потребляемая тут же → eager); CSE, вынос инвариантов; частичное вычисление литералов/конфигов/регэкспов. Автоматическая ленивость чистых `def` — см. §4 «Var и ленивые def»; требует сводки эффектов на top-level форму.

**Иммутабельность:** авто-transient'ы (reuse/FBIP), `borrowing`-конвенция, Sendable blanket, кэши хэша/равенства.

**Поток управления:** `recur` → цикл, самохвостовые вызовы → TCO (безопасно: отличие только в глубине стека), деструктуринг → прямые обращения, `case` → switch, не убегающие замыкания без контекста.

**Приоритет:** прямая линковка → вывод типов → fusion → авто-transient'ы. Первые два дают большую часть скорости, дальше LLVM.

**Что ломается:** `resolve`, `ns-publics`, `eval` → статические таблицы или ошибка компиляции; `with-redefs` — тесты в интерпретаторе.

### Что переносится в интерпретатор (load-time, локально)
Резолв варов при загрузке с эпохой (inline cache без JIT), деструктуринг, `case`-switch, constant folding, локальные unboxed-узлы в `loop`, арность/apply, TCO, авто-transient'ы (свойство рантайма), не убегающие замыкания. С оговоркой: fusion через список интринсиков с инвалидацией; локальный анализ эффектов; кэш AST между запусками. Не переносится: всё, что требует закрытого мира → рантайм-кэши (мономорфный inline cache на протоколах). Критерий границы — три оси, см. §6b.

### JIT — нет. PGO — да.
Минусы JIT: на iOS невозможен; прогрев; память (code cache, профили, stack maps); недетерминизм (deopt storm посреди анимации); второй компилятор со своими багами; проектировать под него надо с первого дня; батарея и RWX-память. **Замена:** профиль собирается в dev-режиме интерпретатором (типы на call site, реализации протоколов, горячие ветки) → компилятор делает спекулятивную специализацию с guard'ами статически. Теряется только адаптация к данным, которых в dev не было.

### Инлайнинг без JIT
Проблема JVM с tuples — специфика JIT: инлайнинг HotSpot зависит от inline cache на сайте; три класса → мегаморфный → itable-стаб ~10 нс. У нас тип известен статически или по тегу, и оба пути инлайнятся.
- Операции рантайма (`nth`, `get`, `+`, `first`) — интринсики. Представление известно → прямой код; нет → inline tag-switch: маска по заголовку, быстрые ветки inline, медленный путь — вызов. Switch инлайнится на каждом сайте, ~1 нс; статический компилятор может позволить себе разбухание кода, которое JIT не может.
- Пользовательские функции: закрытый мир → прямые вызовы → инлайнит LLVM; маленькие чистые — `always_inline`. Higher-order с литеральной `fn` → после fusion цикл с телом inline.
- Каталог функциональных оптимизаций (GHC: оптимизатор ≈ инлайнер + то, что он разблокирует): beta-reduction, case-of-case; worker/wrapper = наши два входа (боксовый + примитивный, как `IFn$LL`); специализация по тегу/типу; fusion = инлайнинг higher-order до исчезновения промежуточных структур; let-floating, strictness, eta-expansion, join points (= `musttail`-блоки). Сверху Koka/Lean: Perceus, reuse, defunctionalization.
- Не инлайнится: `(f x)` с `f`-значением неизвестного происхождения — цена первоклассных функций, у Swift с замыканиями та же. Лечится PGO-спекуляцией: `if (f == foo) { тело foo } else { call }` — JIT-овский inline cache, выписанный статически. Протоколы — так же: известный набор реализаций → switch, тела inline.

### Бэкенд: C через clang
swiftc медленный на 80% из-за type checker, который сгенерированному коду не нужен. Варианты: явный Swift (3–5× быстрее, всё равно секунды); SIL (нестабилен, нужен frontend); **C через clang (10–50× быстрее swiftc, Chicken/Nim/Ferret)**; LLVM IR напрямую (jank, максимум контроля, больше работы). Начинать с C, IR — когда C-семантика начнёт мешать.

Что C даёт сверх Swift: `__attribute__((musttail))` (гарантированный tail call, у Swift нет), неатомарный RC, свой аллокатор и layout, computed goto для интерпретатора, ошибки как return-код (не дороже `throws`), ASan из коробки, `#line` в `.clj`.

`borrowing`/`consuming` не нужны: ownership выведен, в C выражается отсутствием `inc`/`dec` (Perceus). OSSA оптимизировал Swift-ARC, которого больше нет. LLVM-оптимизации (инлайнинг, LTO, векторизация) остаются через clang.

## 6b. Карта оптимизаций: где живут, когда включать, что заложить заранее

### Три уровня
- **Рантайм** (оба режима, без анализа): пул по size-class, biased RC, shapes с деревом переходов, elements kinds, tuples, reuse при rc==1, trial deletion, hash-consing, корутины с affinity и прямой передачей, дескрипторы со слотами, self-optimizing узлы как inline cache.
- **Общий оптимизатор** (AST → AST с фактами, достаётся обоим режимам по построению): локальный вывод фактов, constant folding, lowering деструктуринга/`case`/`cond`, fusion, strictness, CSE, auto-transient, TCO самохвостовых → loop-узел, reuse, borrowed-аргумент на сайте вызова. В интерпретаторе — с эпохой вара как guard'ом и инкрементальными сводками; в компиляторе — по закрытому миру и фикс-пойнту.
- **Только компилятор:** закрытый мир, прямая линковка, tree shaking, межпроцедурный фикс-пойнт фактов, e-graphs, регионы и стек, unboxed-конвенция между функциями (worker/wrapper), tag-switch интринсики, PGO-guard'ы, PGO/BOLT layout бинаря, copy-and-patch eval (десктоп).

**Критерий границы — три оси, не бюджет.** Оптимизация попадает в интерпретатор, если проходит все три:
1. *Guard'уема:* применяется в точке (сайт вызова, узел доступа) и проверяется одним сравнением эпохи. Глобальное без точки проверки — tree shaking, снятие косвенности вара, удаление проверок целиком — только закрытый мир.
2. *AST-уровень:* меняет дерево, а не форму машинного кода. Регионам, стеку, unboxed-конвенциям и inline tag-switch в интерпретаторе некуда лечь.
3. *Линейна на форму:* фикс-пойнт — инкрементально по эпохам, на циклах widening сразу.
Всё, что проходит, достаётся интерпретатору **само** через общий оптимизатор; специально «переносить в интерпретатор» ничего не нужно, кроме self-optimizing узлов. Дальше этого не идти: интерпретатор — эталон семантики для дифференциальных тестов (интринсик vs слот, интерпретатор vs компилятор в CI), второй умный исполнитель = вторая поверхность расхождений. Скорость dev-режима берётся не из интерпретатора, а из скомпилированной базы с косвенностью (§3 «Два режима»), компилирующего eval на Маке и copy-and-patch — модель Julia, не CPython.

Self-optimizing узлы и статический вывод — один механизм специализации с двумя источниками: компилятор эмитит `int+` по выведенному типу; узел переписывает себя по наблюдению там, где статика дала ⊤ (в интерпретаторе всегда, в компиляторе как PGO-fallback).

### Флаги
- `-O0` — прямая линковка + lowering. Секунды на проект, отладочные сборки.
- `-O1` — плюс локальный вывод, fusion, reuse, auto-transient. Дефолт dev-сборок под устройство.
- `-O2` — плюс межпроцедурный фикс-пойнт, e-graphs, регионы, borrow inference, PGO. Релиз.

Инвариант на все проходы: бюджет на функцию, деградация в ⊤, никогда не падение. E-graph превысил лимит → extraction из того, что построено; фикс-пойнт не сошёлся за N итераций → widening; регион не доказан → heap. Компилятор на `-O2` может быть медленным, но никогда не «завис» и никогда не «не смог».

### Ранжированный список — что добавлять сверх принятого и когда
1. **Self-optimizing узлы интерпретатора** (Truffle node rewriting; quickening в CPython 3.11 — то же на байткоде). Узел `+` после первого вызова с int переписывается в `int+` с guard'ом и откатом. 2–5× в dev, и это же inline cache для shapes. Делать вместе с интерпретатором.
2. **E-graphs / equality saturation** (egg, ægraphs в Cranelift) для оптимизатора чистого кода. Архитектура, не проход: e-class хранит все эквивалентные формы, правила добавляют, extraction выбирает по стоимости — phase ordering исчезает. Для чистого кода легальны все алгебраические правила: fusion, CSE, folding, законы коллекций (`(map f (map g xs))`, `(assoc (assoc m k a) k b)`). Новая оптимизация = новое правило. Взрыв на AC-правилах лечится бюджетом узлов. Внедрять в момент появления оптимизатора: переделывать потом дорого.
3. **Copy-and-patch** (Xu & Kjølstad 2021; JIT в CPython 3.13) для `eval` на Маке: шаблоны машинного кода с дырками из тех же C-интринсиков, патч констант и адресов в рантайме — микросекунды вместо clang + dlopen (~100 мс), качество кода уровня `-O1`. Только десктоп (генерация кода). После стабилизации C-бэкенда.
4. **Hash-consing маленьких иммутабельных значений** (Lean `Expr`, Unison): keyword'ы уже интернированы, расширить на маленькие строки и shape-мапы с константными значениями → `=` по указателю, память схлопывается. Дёшево попробовать, мерить на макробенчмарке с JSON. После shapes.
5. **Field reordering в shapes по профилю доступа** — горячие поля в первую кэш-линию. Тривиально, когда есть shapes и dev-профиль.
6. **PGO/BOLT layout бинаря** — через clang-тулчейн, 5–15% на большой программе. Перед первым релизом.
7. **MLIR** как IR, если уходить от C-бэкенда: высокоуровневые операции (`assoc`, `map`) как диалект, постепенное понижение. Горизонт — годы; сейчас достаточно не завязывать оптимизатор на C-специфичное.
8. **Compact regions для app-state** (GHC) — ниша, пул даёт большую часть выигрыша.
9. **Effect handlers как компилируемый примитив** (evidence passing в Koka, OCaml 5) — в карман. Корутины = рантайм-реализация одного эффекта; handlers нужны только ради многократного возобновления (backtracking). Генераторы = `go` + канал с буфером 0; resumable exceptions (conditions/restarts из CL) = библиотека над `binding` (обработчик вызывается поверх стека, возврат = продолжить); backtracking = core.logic (miniKanren, потоки решений без продолжений — работает как есть и выигрывает от shapes/reuse на подстановках) и Datalog (Datascript).
10. **Content-addressed code** (Unison) — источник идей для кэша AST и эпох.

Не применимо или покрыто: полная supercompilation (взрыв кода, завершаемость); Cranelift (нишу закрывают C + copy-and-patch); автовекторизация (clang сам справляется над `deflayout`); NaN-boxing (§4).

**Partial evaluation / проекции Футамуры — принцип, а не задача:** интерпретатор и компилятор на одном дереве узлов, чтобы компилятор в C получался как PE интерпретатора по AST (узел `if` с известным условием → ветка, `+` с известными типами → без диспатча). Truffle делает первую проекцию промышленно.

### Интерпретатор до компилятора: что делать и в каком порядке

Всё ниже — работа интерпретатора и общего optimizer'а над `clj_node`; ничего не требует компилятора, и каждый пункт — с before/after на бенчах. Развилка «нужен ли компилятор и для чего» с замерами (профиль интерпретатора на реалистичных workload'ах, ручная эмиссия `-O0` горячей функции, `ns/node` и `ns/invoke` против Lua) — после пункта 5, когда интерпретатор станет тем, что честно сравнивать.

0. **Дверь в компилятор — три инварианта, дешёвые сейчас:** `clj_node` иммутабелен и сериализуем (есть, §3), exec-состояние сбоку (есть), валидатор в CI — весь core.clj проходит `to_data → read → from_data` (ловит компилятор-враждебные конструкции в день появления). *Статус:* есть; первым уловом был `reify`, клавший объект типа в константу — теперь тип создаётся в рантайме через `reify-type*` с реестром по сайту.
1. **Escape hatch раньше компилятора.** Горячий кусок объявляется примитивом: реализация на C/Swift, вызов из Clojure по имени — так уже построен core (`builtins.c`, `Value(function:arity:_:)`). Не хватает `Runtime.define` со стороны Swift и правила: примитив живёт рядом с Clojure-реализацией, которая остаётся его спецификацией, дифференциальный тест гоняет обе — тот же механизм, что для интринсиков. Граница честно: ускоряет библиотеки (hiccup-diff, JSON, сортировка), не код пользователя, и только крупнозернисто (переход Swift↔C — десятки нс). *Статус:* `Runtime.define`, `Runtime.differential`, `sort`/`compare` как первый примитив со спецификацией рядом; переход измерен — ~64 нс поверх C-builtin, верхняя граница оценки.
2. **Тулинг сейчас, не потом** — единственная выгода компилятора, которая ощущается с первого месяца и не заменяется escape hatch. Теневой стек (push/pop на invoke, наносекунды) одним механизмом даёт стектрейс в uncaught exception, `:trace` в `ex-info` и дописку кадров в крэш-репорт из signal handler. `os_signpost` вокруг invoke под debug-флагом — flame graph в Instruments без своего UI. Счётчики вызовов и inclusive time в `exec_node` — это `(profile …)` для человека и dev-профиль для PGO, одна структура. Ассерты на счётчиках: per-type live counts, «REPL-форма не течёт». *Статус:* сделано целиком (shadow stack, `ex-trace`, крэш-хендлер, signposts, `profile`, live-object отчёты); после прямого входа в замыкание guard, shadow и инструментация — в шуме.
3. **Конвенция счётчиков как правило рантайма, не как вывод.** Аргументы +0, возврат +1, retain только в точке записи в кучу (слот `let`/`recur`/`catch`, захват в замыкание, возврат локала из тела). В интерпретаторе аргументы живут в массиве вызывающего весь вызов — параметры замыкания borrowed безусловно, маска `owned` на кадре. Deref вара остаётся owned: заимствованный root при конкурентном `def` из REPL освобождает fn, чьё тело выполняется; снимается только вместе с immortal-корнями core (бутстрап) и эпохой для остальных. Бессмертные объекты: keyword, var, пустые коллекции — есть; интернированные символы и корни core-варов — добавить. Забирает основную долю того, что даёт borrow inference, без фикс-пойнта и закрытого мира. *Статус:* сделано; замер показал, что сама конвенция скорости не даёт (RC на не-shared — 5 инструкций), её ценность — договор о владении для reuse (п. 4) и компилятора; корни варов читаются +0 с отложенным освобождением заменённых fn-корней вместо immortal.
4. **Эпоха + optimizer + интринсики + свёртка** — один шаг, здесь появляется фаза optimizer'а в конвейере.
   - *Эпоха определений*: одна глобальная, двигают `def`/`deftype`/`defmethod`/`extend` (поглощает protocol epoch). Inline cache в `exec_node` = `{epoch, cached}`; в REPL один `def` сбрасывает все кэши, они перегреваются за микросекунды — per-var эпоха не нужна. Сама по себе не оптимизация — фундамент для 5–7.
   - *Интринсики core*: таблица `{символ, арность} → {kind, C-функция}` → узел `INTRINSIC`, убирает кадр, диспатч и косвенность вара разом (~10 нс → 2–3 на builtin-вызов). Условие корректности: интринсик и core-функция зовут одну C-функцию (`b_add` в цикле зовёт `clj_add2`). Спекулятивно, пока мир открыт: отзыв по эпохе (до неё — guard `root == ожидаемый`, не дороже).
   - *Свёртка констант по чистоте*: таблица чистоты — те же записи, что интринсики; складываются INTRINSIC-узлы с const-аргументами; бросил при свёртке — узел остаётся (`(/ 1 0)` бросает в рантайме). Практическая ценность мала, ценность — optimizer.c на правильном месте: после анализа, до нумерации, переживает сериализацию.
   - *Reuse по последнему использованию*: флаг last-use на LOCAL-узле из локальной liveness внутри формы; `eval_borrowed` отдаёт владение → `conj` при rc==1 работает in-place. Без этого in-place из интерпретируемого кода не срабатывает никогда (builtin retain'ит перед consume). Это и есть auto-transient.
   *Статус:* сделано целиком: таблица из 52 интринсиков с guard'ом `root == boot-корень` (эпоха не понадобилась: guard не дороже), свёртка с двойной границей по кодеку (и аргументы, и результат сериализуемы), last-use только на чтениях, чей потребитель может владеть (arg0 consuming-интринсика, init `let`, `recur`, тело) — пометка аргументов обычных вызовов измерена и отвергнута (+2 нс/вызов); драйверы `reduce`/`into` отдают аккумулятор consuming-нативу с владением. Бенч: counting loop −48 %, loop conj −62 %, reduce conj −83 %.
5. **Inline cache на варах и протоколах** — та же структура в `exec_node`. Прямая линковка вара: `{epoch, fn}`, fn retain'ится узлом, прямой вызов тела нужной арности мимо `clj_invoke`. Девиртуализация протоколов и мультиметодов: `{epoch, type → fn}`, одна реализация → прямой вызов, 2–4 → switch, дальше generic. Инлайн тела варной функции — не здесь: рост кода, переименование, deopt-альтернатива — территория компилятора, в интерпретаторе выигрыш только элизия кадра (механика п. 7). *Статус:* сделано иначе. Кэш на замыканиях не нужен и вреден: арность лежит в одном load от fn-узла, а любой retained-ключ образует циклы (exec → fn → exec) и пришпиливает пользовательский код к immortal-exec'ам core — вместо него прямой вход в тело (аргументы сразу в кадр callee). Протокольный кэш — 4 записи `{тип, impl, арность}` по serial метода и эпохе, impl'ы borrowed под seqlock. Натив в голове зовётся из буфера сайта напрямую. Бенч: closure call −28 %, protocol call −20 %.
6. **Трансдьюсеры → IReduce → fusion.** Предусловий сегодня нет: ни трансдьюсерных арностей, ни `reduced`, ни IReduce (`reduce` ходит через `seq`). Порядок: трансдьюсеры и `reduced`/`transduce`/`eduction` — семантика; IReduce-быстрый путь (`reduce` по vector/range итератором без seq-объектов — крупный выигрыш сам по себе, chunked seqs рядом); проход optimizer'а: `reduce`/`into`/`vec` над пайплайном `map`/`filter`/… → `transduce (comp …)`, один раз на форму, переживает сериализацию; композиция без захвата локалов кэшируется в exec-узле — по инварианту побочных ячеек (NOTES, evaluator): CAS-заполнение, победитель immortal до публикации, проигравший освобождает копию до публикации, leak ограничен числом форм. Барьеры (`sort`, `group-by`) режут пайплайн — ожидания калибровать по этому. *Статус:* сделано; кэш композиции не понадобился — `comp` не строится, C-драйверы (`fused-reduce*`/`into*`/`count*`) применяют стадии из вектора, а `(xf rf)` обязан быть свежим (stateful-трансдьюсеры). 2-арный `reduce` не через `eduction` (тот сидирует `(f)`, ленивый — первым элементом). Guard — таблица boot-корней core-варов в `fusion.c`, узел `[:fused …]` хранит оригинал для фолбэка. `partition-all` из стадий исключён (векторы vs seq'и). Бенч: pipeline 182 → 30 нс/элемент.
7. **Прямой вызов локальных функций.** `let`-связанные, не убегающие (только в позиции головы, не захвачены, не переданы) — escape-анализ внутри формы. Не текстовый инлайн, а вызов тела без создания замыкания и без `clj_invoke`: без роста кода и проблем с рекурсией. Вар не участвует, отзывать нечего. Реальные случаи: `letfn`, макро-сгенерированный код (`for`, `doseq`, destructure). *Статус:* реализовано (static link + узлы `DIRECT_FN`/`DIRECT_CALL`/`OUTER`), но в core.clj кандидатов не нашлось — все `step`-хелперы живут под `lazy-seq` и обязаны быть замыканиями; выигрыш пока только на синтетике (−29 % цикл с локальным хелпером). Решение: оставить, пересмотреть при появлении `for`/`doseq`/`letfn` — если их хелперы тоже не проходят escape-правило, откатить (проход, три вида узла и static link изолированы, откат дешёвый).
8. **Специализация по фактам** — `INTRINSIC_ADD → ADD_LONG` по наблюдённым типам, self-optimizing rewrite в exec-узле с guard'ом, не в `clj_node`. В интерпретаторе даёт мало (tag-check ~1 нс из 3, доминирует диспатч) — по профилю, не раньше.

### Что заложить заранее — иначе потом не поменять
- **Value:** pointer tagging (§4) — решено.
- **Заголовок объекта:** rc и флаги (SHARED, stack/immortal, may-cycle, reaches-mutable) — место резервировать сейчас. `hash` и `meta` — per-type поля по решению §4 «Дескриптор типа»; решать, где они живут, тоже сейчас, дописать в заголовок потом нельзя.
- **Дескриптор:** `core_bits` и `user_protos` — поля с первого дня, чтобы `defprotocol` не менял layout.
- **Одно дерево узлов** у интерпретатора и компилятора — ради PE-подхода и общего механизма self-optimizing узлов.
- **Оптимизатор — отдельный проход над AST с фактами**, не размазанный по бэкендам: иначе e-graphs потом не вставить.
- **Интринсики — одна таблица C-функций**, из которой генерируются tag-switch компилятора, шаблоны copy-and-patch и слоты дескрипторов (дифференциальный тест поверх).
- **Формат dev-профиля** — с первого дня (типы на сайтах, shapes, реализации протоколов, горячие ветки); потребители: PGO-guard'ы, field reordering, BOLT.
- **Эпохи** варов, протоколов и shapes — единый механизм инвалидации кэшей.
- Не завязывать оптимизатор на C-специфичное — дверь в MLIR.

## 7. Память

### RC vs GC — честно
- Для аллокационно-тяжёлого функционального кода **GC быстрый**: bump-аллокация, nursery-сборка ∝ живым объектам, никаких записей в счётчики. Наивный RC — самая медленная схема. Perceus/Lean хвастаются «скоростью GC», потому что до них RC до неё не дотягивал; обгоняют за счёт reuse. Цена GC — память 2–5× и паузы.
- **Rust быстр не потому, что освобождает, а потому, что не аллоцирует.** Rust на `im` (Arc-HAMT) в 10–50× медленнее `Vec`. Разрыв с идиоматичным Rust — свойство модели данных, не памяти. Закрывается там, где анализ превращает персистентную операцию в мутацию.
- Честная цель: там, где линейность доказана — Rust; где данные разделяются — паритет с любым языком на тех же структурах; не проиграть GC на промежуточных аллокациях за счёт аллокатора и reuse.

### На каждое значение три вопроса (ARC отвечает на все в рантайме самым дорогим способом)
1. **Убегает ли?** Нет → регион/стек, без счётчика. Да → heap.
2. **Единственный ли владелец?** Да → reuse/мутация. Нет → копия пути.
3. **Пересекает ли поток?** Нет → неатомарный. Да → атомарный.

Escaping — главная проблема для *потока управления*; для *данных* главная — sharing (32 retain — это вопрос 2, не 1).

### Что убирает анализ без аннотаций (Perceus / Lean 4 «Counting Immutable Beans»)
- **Borrow inference:** параметр только читается → +0. Убирает большую часть ARC на вызовах. Параметр утекает в результат → owned; вызывающий на последнем использовании → consume. Это и есть «inout»: `x = f(consume x)` — указатель вошёл, указатель вышел, счётчик не тронут.
- **Точные drop/dup** в точке последнего использования — то, что делает рантайм-проверку `count == 1` *успешной*, а не *ненужной*. Koka/Lean уникальность не доказывают, они ставят проверку (одна загрузка + сравнение) и следят, чтобы счётчик был 1.
- **Reuse:** проверка на каждом узле пути (не только корне) — мутируем до первого разделённого узла. Точнее transient'ов с edit-token; в компилированном коде transient'ы почти не нужны.
- **Escape analysis:** локальный для замыканий (переданы в известный интринсик → не убегают, O(1)); межпроцедурно — одна bottom-up проходка по графу вызовов (Go делает это на каждой компиляции). Дефолт — «убегает».
- **Регионы (Tofte–Talpin, MLKit, не Google ML Kit):** bump-аллокатор на скоуп, сброс при выходе, объекты без заголовка. Не убегающая копия узла заимствует детей — memcpy 10 нс без единого retain. Инвариант: heap-узел никогда не указывает на региональный; `original` переживает регион. Ловушка region leak в циклах → сброс на итерации `loop/recur` или fallback на RC. Промоушен в heap на неизвестной границе — консервативно или явно на выходе.
- **Стек:** для не убегающих объектов фиксированного маленького размера (бокс, замыкание с k захватами, tuple); регион — для не убегающих любого размера; куча — для убегающих. Порог из-за стека iOS (main 1 МБ, фоновые 512 КБ, корутины 64 КБ) — `alloca` переменного размера опасен. RC на стековом объекте — no-op: компилятор inc/dec не эмитит, флаг `stack` в заголовке — страховка. Интерпретатору недоступно. На таблицу бенчмарка (§4) не влияет — узлы результата `assoc` убегают по определению. Лучше стека — регистры (unboxed скаляры).

Лестница: fusion убирает временное совсем → регион делает временное бесплатным → reuse делает линейное мутацией → RC только на том, что живёт в двух версиях одновременно. Аннотации (`^:linear`) — только как гарантия, не как условие.

### Что остаётся и надо делать инженерно
- Drop большой структуры синхронный O(n) в UI-потоке → отложенное освобождение в фоновую очередь, итеративные деструкторы.
- Циклы: lazy seq обнуляет `fn` после реализации (как Clojure); замыкания над иммутабельным циклов не образуют.
- Горячие счётчики (корень разделяемой мапы, core-функции, keyword'ы) → неатомарный/biased.
- Флаги заголовка — один набор на все механизмы памяти: SHARED (biased RC), stack/immortal, may-cycle и reaches-mutable (trial deletion). Место под них резервируется сразу (§6b): дописать бит в заголовок после того, как он стал layout'ом всех объектов, дороже, чем зарезервировать.

### Циклы: RC + trial deletion
**Где циклов нет по построению.** Иммутабельный объект ссылается только на то, что существовало в момент его создания → все рёбра направлены назад во времени → цикл требует ребра вперёд, то есть мутации. Персистентные структуры, records, tuples, layout'ы, замыкания над иммутабельным — циклы невозможны. DAG с любым sharing'ом (ромбы, одна мапа в тысяче мап) — не цикл, RC справляется. Положить «мапу в саму себя» нельзя: `assoc` создаёт новую мапу, содержащую старую.

**Где возможны:** атом → иммутабельные данные → замыкание, захватившее этот атом; `deftype` с мутабельными полями (parent ↔ child); нереализованные lazy seq (thunk хвоста держит голову — после реализации thunk сбрасывается, как в Clojure; корень обычно вар, не утечка); через границу Swift ↔ Clojure. `(def m {:self m})` при hoisting и ленивых def — рекурсивное форсирование: thunk в состоянии «форсируется» при повторном входе бросает «рекурсивное определение» с именем вара (обязательный гвард).

**Решение: RC — единственный механизм освобождения, сверху trial deletion** (Bacon–Rajan). Это не tracing GC: нет корней, нет обхода heap, нет stop-the-world, нет перемещения, нет safepoint'ов и stack maps, Swift-стек не участвует. Смотрит только на буфер кандидатов.
- Флаг `may-cycle` в дескрипторе: атомы, мутабельные `deftype`, thunk'и, замыкания с захватом мутабельного (capture set известен). Иммутабельные типы кандидатами не бывают. Кандидат = may-cycle-объект, у которого счётчик уменьшился до ненуля (атом становится кандидатом не при `swap!` — там декрементируется старое значение, — а когда отпускается ссылка на сам атом). Событие редкое.
- Бит `reaches-mutable` в заголовке: OR битов детей при создании (детей и так трогаем при retain). Цикл может проходить через иммутабельные узлы (атом → мапа → замыкание → атом), поэтому trial deletion обязана спускаться в них — но только с установленным битом. У состояния приложения (строки, числа, keyword'ы, векторы) бит чистый, обход обрезается на первом уровне. Это acyclic-анализ Nim ORC, только в рантайме по содержимому: `Value` может содержать что угодно.
- Стоимость ∝ числу недавно отпущенных мутабельных объектов, а не размеру heap. Синхронно при пороге буфера (микросекунды при pruning) или инкрементально в idle. Буфер per-carrier (affinity) → без глобальной остановки.
- Прецеденты: CPython (RC + collector для контейнеров), Nim ORC (acyclic-типы статически). У Koka/Lean сборщика нет, потому что нет атомов.

Сборщик включён всегда — и в dev, и в prod (при чистых битах ~бесплатен). Следствие: `weak` — не необходимость для корректности, а семантический инструмент «не держать живым» (parent-pointer, кэш, observer). Думать о weak по-clojure'ски не нужно.
- Автоматический weak отвергнут: рантайм видит цикл, но не владение; неверное weak-ребро = преждевременное освобождение (zeroing → внезапный nil), хуже утечки. Эвристика «ребро, созданное мутацией, — обратное» технически верна, но `(reset! a handler)` — ребро, которое должно быть сильным.
- Back-pointers на каждый retain отвергнуты: родитель часто неизвестен (стек, регистр, Swift-контекст); память ×2; retain из инструкции превращается в аллокацию; обход предков на DAG квадратичен. И проверка при вставке отвечает не на тот вопрос: цикл легален, пока достижим, а утечка — недостижимый цикл, видна только при последнем декременте, где trial deletion и смотрит.

**Граница Swift ↔ Clojure — отдельно.**
- Конвенция: данные пересекают границу через `Codable`/примитивы; сырой `Value` в Swift — только для замыканий и host-обёрток.
- Host-объект (Swift-класс) в Clojure: trial deletion может пройти сквозь него — перечислить поля через Swift-метаданные (уже умеем для `Codable`), найти `Value`, продолжить обход. Не для замыканий (контекст непрозрачен) и не для `Any`. Типичный «ViewController хранит `Value`» — собираем.
- Замыкания в ролях callback/delegate — `WeakValue` по умолчанию в генераторе стабов: Apple держит делегатов weak, повторяем их конвенцию на своей стороне.
- Остаток — Swift-замыкание захватило `Value`, `Value` держит host-объект с этим замыканием — тот же retain cycle, что в чистом Swift, лечится `[weak self]`.
- Dev-детектор: счётчик экспортированных `Value` + trial deletion с местами создания из теневого стека — аналог memory graph debugger, показывает цикл с типами и строками `.clj`.
- `~Copyable` для `Value` отвергнут: move-only запрещает дублировать, а не хранить; цикл через поле остаётся; ergonomics в Swift 6 ограничена.

### Свой GC — перебор для v1
Теряет reuse (нет счётчика), детерминизм (паузы в 8 мс бюджете), простой интероп (два heap'а, handle table для Swift-held значений, несобираемые циклы через границу — задача уровня WebKit JS↔DOM). Даёт bump только если перемещающий, а перемещение требует точных корней. Mono на iOS с SGen доказывает, что GC на iOS возможен, но там весь heap свой. **Решение:** свой заголовок + пул + RC как политика; дверь для неперемещающего Immix-подобного остаётся открытой, если профиль потребует. Скорее всего — никогда.

**Запасной план, если RC себя не оправдает.** Записан заранее, чтобы решение принималось по числам, а не по усталости.
- *Триггер:* макробенч §10 (приложение из списка + сеть + рендер) в **скомпилированном** режиме проигрывает JVM-Clojure/Hermes на копирующих персистентных операциях, и профиль показывает, что это RC-трафик (атомарные пары на shared-данных, retain/release детей при копии узла), который reuse, fusion и регионы уже не снимают. Интерпретаторные цифры триггером не считаются. Сегодняшние ориентиры: копия узла на 16 детей под атомом ≈ 200 нс сверх in-place (`swap! assoc` 91 → 288), доля атомарных пар при состоянии в атоме 80 % ≈ 300 нс на тик.
- *Кандидат:* свой GC **без stop-the-world**: неперемещающий (адреса стабильны — интероп и `Unmanaged` на Swift-стороне не меняются), конкурентная маркировка с коротким снимком корней вместо паузы, консервативное сканирование C-стека (нативы и Swift-кадры не нуждаются в stack maps — цена перемещающего GC, которую мы не платим), точные корни только там, где они и так известны: слоты кадров интерпретатора, вары, атомы. Write barrier нужен только в точках мутации, а их список уже есть — это список публикаций `clj_share` (var/atom/volatile, ячейка lazy seq, in-place reuse, буфер канала); новые объекты рождаются помеченными. Иммутабельный heap делает такой GC дешёвым там, где Go платит барьером на каждой записи.
- *Предпочтительная форма — гибрид по классу объекта, не полный GC:* **unshared считается RC, shared трассируется.** Гонку на неатомарном счётчике обнаружить нельзя (потерянный инкремент молчит), но момент, когда она становится возможной, известен точно — публикация, тот же флаг. Опубликованный объект перестаёт считаться: retain/release на нём — уже существующая проверка флага и ничего вместо атомарной пары, то есть исчезают те самые 80 % атомарных пар при состоянии в атоме. Sweep трогает только пул (дети shared-объекта shared по инварианту). Циклы через опубликованное собираются трассировкой; если may-cycle типы (атомы, мутабельные deftype, thunk'и) класть в пул при создании, trial deletion не нужна — два механизма этого раздела схлопываются в один. Reuse при rc==1 остаётся на локальных данных, где он и работает. Трудности: корни — ссылки на shared лежат и внутри unshared-объектов, и на стеках: либо remembered set с барьером на записи ребёнка при конструировании (цена на самом горячем пути), либо маркировка идёт от корней сквозь unshared-объекты; во втором случае конкурентная маркировка гоняется с RC-освобождением unshared другим потоком — лечится per-thread сканированием в safepoint'ах (каждый поток маркирует свой стек и свою unshared-часть графа, как Go сканирует стеки); финализация shared-объектов (host-объекты, локи) недетерминирована. Прецедент с обратным критерием — Ulterior Reference Counting (Blackburn & McKinley 2003): молодые трассируются, старые считаются; у нас критерий — видимость из потока, не возраст.
- *Что теряется с полным GC:* reuse при rc==1 (auto-transient, последнее использование, in-place в `swap!`) — уникальность пришлось бы выводить статически; детерминированное освобождение host-объектов и локов; память ×2–5; trial deletion становится не нужна.
- *Переключение GC ↔ RC.* В рантайме — нет: чтобы вернуться на RC, счётчики надо вести всегда, то есть платить обе цены. **Во время сборки — да**, как `--mm:arc|orc|markAndSweep` у Nim или GC на выбор при трансляции PyPy: RC замкнут в `clj_retain`/`clj_release`/`clj_alloc`/`each_child`/`finalize`, GC-сборка делает retain/release no-op и добавляет корни и барьер. Условие, которое надо держать с сегодняшнего дня: никакой код вне этих точек не опирается на семантику счётчика, кроме проверок `clj_is_unique`, которые в GC-сборке честно отвечают «нет» (деградация в копию, не в ошибку). Один тест-инвариант: сьют проходит с `clj_is_unique ≡ false` — сборка `-DCLJ_NO_REUSE` (`make test-noreuse`, `clj_reuse_enabled()` как признак сборки) делает именно это, и все сьюты в ней зелёные, то есть инвариант теперь проверяется, а не только записан.

| Идея | Почему нет |
|---|---|
| Транспиляция в Swift-исходник | swiftc медленный, атомарный ARC, `Any`-бокс, всё равно нужны стабы |
| Swift-классы для Clojure-значений | закрывает свой RC/аллокатор/заголовок навсегда |
| Swift-замыкания как Clojure-fn | одна арность, нет IFn/meta/identity/apply, атомарный контекст |
| Honest-конформансы из `deftype` в компиляторе | расхождение семантик с интерпретатором |
| Actor для атома | `swap!` становится `await` |
| CAS-атом | retain/release гонка на указателе, hazard pointers ради JVM-дизайна |
| JIT | iOS; замена — PGO из dev-профиля |
| Свой GC | см. §7 |
| `<!!`/`>!!` | блокировка кооперативного пула |
| Генерация покрытия всего Swift SDK | дженерики не эрейзятся; никто не сделал |
| `delay` + `@` как способ ленивых глобалов | ленивость встроена в Var, синтаксис не нужен |
| Явный `declare` для forward-ссылок | hoisting имён при загрузке файла; в REPL-форме — по-прежнему ошибка |
| Вывод типов только в компиляторе / отдельный анализатор | один аналитор-библиотека с тремя клиентами: интерпретатор, компилятор, LSP |
| SoA для вектора мап одного shape'а | `nth` хуже базы, персистентность ломается; место — явный dataset-тип |
| Порог 8 ключей как у `PersistentArrayMap` | 32: сравнение указателей, не JVM-`equals`; DTO с бэкенда — 5–25 полей |

| HM/OCaml-унификация | делает язык типизированным; у нас решётка с ⊤, success typings |
| Открытый API для инжекта кода в обход дерева | протекает AST; расширение декларативное: факты на варах, refinements на предикатах, схемные функции |

| Ссылки/`Value` внутри `deflayout` | ломает isbits: копия перестаёт быть memcpy, появляются RC-корни в буферах; для этого `deftype` |
| Голый указатель с арифметикой как публичный тип | view = адрес + размер + владелец, арифметика — `slice`; `ptr` только на FFI-границе и в `^:unsafe` |
| SoA неявно над `vector` | явный `(array Layout n)` — см. низкоуровневый слой §4 |
| Зашить SwiftUI/UIKit в компилятор | язык знает только `defdsl`; UI — библиотека с бэкендами |
| Компиляция hiccup макросом (hicada/uix) | теряет данные; у нас специализация компилятором с сохранением семантики |
| Общий кроссплатформенный словарь тегов | LCD-ловушка; словарь per-backend, пересечение по факту |
| Auto Layout как основной layout | медленный, не переносится; Yoga на C в ядре |
| Свой LSP с нуля вместо clojure-lsp | синтаксический слой готов; свой — только семантика из решётки |
| Хуки для макросов в LSP (модель clj-kondo) | аналитор раскрывает макросы интерпретатором; загрузка проекта в режиме анализа по эффектам форм |
| Интерпретатор в прод-сборке | 2.5.2 + честная проверка полноты компилятора |
| Reader-тег `#location` | ненамespace'нные теги зарезервированы; `.cljc` не прочитается на JVM; макрос `(location)` делает то же |
| Неявная локация у всех функций | стоимость на каждом вызове и утечка в ABI; Swift и Rust тоже opt-in — `^:track-caller` |
| Swift-протоколы для core-интерфейсов | недоступны из C; слоты дескриптора |
| `invoke[N_ARITIES]` в дескрипторе | арность — свойство объекта |
| `extend-type` встроенного типа на core-интерфейс | write-once; разрешено только на пользовательские протоколы |
| Возврат `Task` из синхронного вызова при ожидании | динамическая раскраска по факту исполнения |
| Блокировка потока при ожидании в sync-вызове | только явный `callBlocking`, не на main |
| Пометка Clojure-функций как async | цвет читается из Swift-сигнатуры на мосту |
| Tracing GC ради циклов | trial deletion над may-cycle-кандидатами; RC остаётся единственным освобождением |
| Автоматический weak по обнаружении цикла | рантайм не знает владения |
| Back-pointers на каждый retain | память ×2, retain → аллокация, отвечает не на тот вопрос |
| `~Copyable` для `Value` | не запрещает хранить, ломает ergonomics |
| Полноценный MVCC STM для `ref` | редко используется; 2PL по id ref'ов |
| NaN-boxing | PAC на arm64e, 32-битный int, double и так unboxed там, где важно |
| Генераторы / resumable exceptions / backtracking как фичи языка | корутины + `binding` + core.logic |
| Оптимизации без бюджета | любой проход деградирует в ⊤, а не падает |

## 9. Открытые вопросы
- **REPL на устройстве — нужен ли вообще.** Это единственное решение, убирающее второй режим исполнения целиком: без него интерпретатор не нужен — компилирующий eval на Маке (clang → dylib, затем copy-and-patch) даёт полноценный REPL, а на устройстве остаётся «пересобрал и запустил» (модель ClojureDart с hot restart — и главная жалоба на него). С ним — две реализации семантики навсегда, пусть и с общим оптимизатором и дифференциальными тестами. Решать рано, не по ходу. *Решено на сейчас (2026-09-17):* `eval` — только интерпретатор; компилирующий eval — не цель, `CLJ_EVAL=compiled` остаётся диагностикой для дифференциальных прогонов (на macOS 14+ каждый первый `dlopen` нового dylib ждёт YARA-скан syspolicyd, ~0.3 с, поэтому единица на форму непригодна; если компилирующий eval когда-нибудь понадобится — объектник в память через `MAP_JIT`, tcc или ORC, не файл на форму). Какой из двух режимов остаётся — решается после всех оптимизаций по бенчмаркам на реальном коде, не раньше.
- Формат сериализации AST для кэша между запусками. Единственный сценарий, где можно повторить Julia-проблему time-to-first-plot (вывод + кодоген на горячем пути первого вызова): **холодная загрузка core** (~8k строк) без кэша. Всё остальное защищено — в интерпретаторе нет кодогенерации, решётка ограниченной высоты, сводки по запросу. Цель: сотни миллисекунд холодно, ~0 с кэшем AST и фактов; Julia пришла к тому же через pkgimages.
- Ровно какие Swift-протоколы попадут в стартовый список адаптеров.
- Промоушен региональных значений на неизвестной границе — консервативно в heap или копирование на выходе.
- Branching factor HAMT (32 vs 16) при неатомарном RC — измерить.
- Как выглядит `require-swift` и фоновая пересборка dev-клиента на практике.
- Android/WASM — только если появится второй мост; ядро готово по построению.

## 10. Первые шаги (по порядку)
1. **Бенчмарк HAMT** — сделано (§4): свой RC + пул 2–3× на `assoc` против `TreeDictionary`; аллокатор важнее счётчика.
   - **1b. Бенчмарк shapes/tuples.** Struct-like набор: 5–8 keyword-полей, `(:field m)` моно- и полиморфно, `(assoc m :field v)`, `(update m :count inc)` при уникальной и разделённой ссылке — против Swift-struct и `[String: Any]`, плюс `defrecord`. Tuples: `[x y]` create/destructure, `(map (fn [[k v]]))` над мапой из 8 и 1000 ключей, `zipmap` — против кортежа и `[(K, V)]`. Цели: доступ к полю ≤2 нс, update при уникальности ≤10 нс, не убегающая пара — 0.
2. Ядро на C: значения, заголовок, size-class аллокатор, HAMT/vector, RC неатомарный + biased.
3. Reader → analyzer → closure-компилирующий интерпретатор с локальными оптимизациями + nREPL (§5c). Теневой стек. Узлы self-optimizing с первого дня, дерево узлов — общее с будущим компилятором (§6b).
   - **3b. Метрика покрытия типов** (§3): доли известный тип / shape / неизвестно в аналиторе и моно/поли/мегаморфных сайтов в рантайме на реальном `.cljc`-приложении — до того, как оптимизатор написан под гипотезу.
4. Мост уровня 1 (ObjC-рантайм) + `Value` + `Codable`-энкодер. `reify` на `@objc`.
5. core.async на корутинах рантайма (§4, один путь в обоих режимах) + свои каналы.
6. Компилятор в C: закрытый мир, прямая линковка, вывод типов, `#line`. Тесты через компилятор в CI. Оптимизатор — отдельный проход над AST с фактами; e-graphs закладывать сразу, не «потом» (§6b). Флаги `-O0`/`-O1`/`-O2`. *Статус:* v0 сделан (NOTES, «Compiler»): генератор `clj_node` → C поверх боксов, компилированный core.clj за `-DCLJ_COMPILED_CORE`, `--closed` с прямой линковкой и снятыми guard'ами, `#line`, тесты и корпус через компилятор (`make test-compiled`, `corpus-compiled`, `test-eval-compiled`); фактов, unboxing и tree shaking нет.
7. Межпроцедурный borrow inference, регионы. Локальные reuse (last-use) и fusion уже в общем оптимизаторе (§6b) и достаются компилятору по построению.
8. Адаптеры Swift-протоколов и генератор стабов; dev-client флоу.
9. UI: реконсилер над hiccup + UIKit-бэкенд из ~10 тегов + Yoga. Критерий: экран списка с подписками на курсоры перерисовывает только изменившиеся строки.
10. Свой LSP над аналитором (§5c) — после того, как решётка фактов заработает.

**Критерий приёмки ядра — чужие тесты, своя память.** `core.clj` из репозитория Clojure взять нельзя: он написан против `clojure.lang.*` и Java-интеропа (`(. clojure.lang.RT (first coll))`, `proxy`, `gen-class`, `Thread`), так его не взял ни один альтернативный хост; ClojureCLR держит его дословно только потому, что реализовал сами классы — shim такого рода привязал бы core к боксовому JVM-API и не дал бы нести в ней факты. Тесты — другое дело:
- переносимая часть `test/clojure/test_clojure/*` (`sequences`, `data_structures`, `control`, `fn`, `def`, `macros`, `logic`, `string`, частично `numbers`) через наш `clojure.test`; JVM-специфичные (`java_interop`, `reflection`, агенты на `Thread`) — вон;
- **core-test** — кроссплатформенный набор для clojure.core, которым проверяются ClojureDart, Basilisp, jank;
- дифференциальный фаззинг против JVM-Clojure как оракула: случайные выражения над core-функциями и сгенерированными коллекциями, сравнение через EDN. Попутно решить, совпадать ли с JVM по значениям `hash` (CLJS совпадает намеренно).
- полное соответствие публичного API `clojure.core`: механический дифф `(ns-publics 'clojure.core)` JVM-Clojure против нашего — имя, арности из `:arglists`, макрос/функция. Не «похожий core», а тот же: чужой код и библиотеки должны грузиться без правок. Исключения — только JVM-по-природе (`proxy`, `gen-class`, `definterface`, `bean`, `monitor-enter`), каждое со строкой в §8; `future`, `agent`, `pmap`, `locking` — реализуются на корутинах, не исключаются.
- **корпус реального кода** — `.cljc`-библиотеки, зависящие только от `clojure.core` (на практике ещё `clojure.string`/`set`/`walk`) и core.async: medley, malli, datascript, instaparse, core.match, meander, edamame, tools.reader, сама core.async и код на ней. Три роли: приёмка (библиотека грузится, её собственные тесты проходят через наш `clojure.test` — чужой код бьёт по углам, которых тесты core не трогают); приоритеты API (дифф `ns-publics` даёт список, корпус — веса: что реальный код зовёт часто, делается первым); бенчмарки и метрика 3b (те же библиотеки на JVM и у нас; доля известных типов/shape'ов и моно/полиморфных сайтов на реальном коде — до того как оптимизатор пишется под гипотезу) и вход компилятора (`-O0` эмиссия целой библиотеки, не одной функции).
Один прогон — через оба бэкенда: это и есть дифференциальный тест интерпретатор/компилятор. После каждого теста — 0 живых объектов (свой аллокатор делает это бесплатным) + ASan; иначе тесты проверяют поведение, но не память. Тест, падающий по дизайну (ленивые `def`, hoisting, write-once core-слоты, отсутствие `<!!`, trap на вложенном `swap!`), попадает в allowlist только со ссылкой на строку §8; allowlist без строки в §8 — запрещён.

**Forcing function: приложение в App Store.** Небольшое приложение целиком на языке в сторе — самый сильный экспонат (проверяемо, чужие телефоны, ревью Apple) и самый жёсткий тест дизайна: заставляет пройти прод-путь, который откладывался за интерпретатором.
- Тип: список с бэкендом — JSON → shapes, подписки на курсоры → перерисовка строк, core.async на сети, UIKit-бэкенд из десятка тегов. Там, где Clojure-модель должна быть удобнее Swift. Не Metal/аудио/WKWebView — это работа хоста, язык ни при чём.
- Guideline 2.5.2: интерпретатор в бинаре легален без загрузки кода извне, но в прод-сборке его нет вообще — только скомпилированный C. Это и есть проверка, что компилятор покрывает язык целиком.
- Первые цифры на устройстве до UI: размер бинаря (рантайм + tree-shaken core — единицы МБ), старт без паузы (ленивые def + hoisting + кэш AST перестают быть теорией).
- Крэши: `#line` в C и теневой стек — до релиза; символикация через dSYM проверена на TestFlight.
- Переворачивает порядок списка выше: компилятор нужен раньше полного интерпретатора. Интерпретатору для разработки хватит «достаточно», компилятору для релиза — «целиком».
