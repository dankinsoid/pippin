# Clojure для Apple-платформ — дизайн-заметки

Итог обсуждения. Стартовый вопрос был «Clojure поверх Swift как ClojureDart поверх Dart»; по ходу выяснилось, что правильная позиция — **Clojure на Apple-рантайме**: своё ядро на C, хост-интероп со Swift/ObjC через мост, а не транспиляция в Swift.

---

## 1. Почему Swift плохой хост «в лоб»

- **Нет eval / JIT.** На iOS JIT запрещён (`dynamic-codesigning` только у JSC и браузеров в ЕС). Swift REPL = LLDB + ORC JIT, медленный и глючный. `dlopen` подписанных dylib работает только в dev-сборках на симуляторе/Маке.
- **Нет рефлексии вызовов.** Дженерики мономорфизируются, `Mirror` read-only, Swift ABI (`swiftself`/`swifterror`, скрытые metadata/witness table параметры) libffi не умеет. Произвольный метод произвольного типа динамически не позвать.
- **SwiftUI — плохая цель.** Идентичность завязана на статические `some View`; динамический язык даёт только `AnyView`. UIKit (ObjC) — нормальная.
- **ARC.** Атомарный всегда, циклы через lazy seq, рекурсивный dealloc на длинных списках, `Any`-боксинг.
- **swiftc медленный** (type checker), сгенерированный код с существенциалами — секунды на файл.
- **Swift 6 strict concurrency** спорит с боксами `Any`.

Хорошие хосты — те, где код грузится в рантайме + GC + рефлексия: JVM, JS, CLR, BEAM, Lua, Python. Dart и Swift — нет; ClojureDart живёт AOT-only с hot restart Flutter'а.

**ObjC-рантайм** — отличный хост (Smalltalk поверх C): `objc_msgSend`, `objc_allocateClassPair`, `imp_implementationWithBlock`, `NSInvocation`. Прецеденты: Nu, F-Script, MacRuby, clojure-objc (2014), NativeScript (генерирует metadata на весь SDK). Но экосистема уезжает в Swift-only.

## 2. Три смысла слова «хост» и итоговый выбор

| | Clojure JVM | CLJS | ClojureDart | jank | **наш** |
|---|---|---|---|---|---|
| Во что компилируется | байткод | JS | Dart | LLVM IR | **C (позже LLVM IR)** |
| На чём рантайм | Java | CLJS | Dart | C++ | **C-ядро + Swift-обвязка** |
| Экосистема интеропа | Java | JS | Dart | C++ | **Swift + ObjC** |

Пользователь видит только третью строку. Первая — деталь реализации, как байткод для JVM. Это ближе к модели Clojure JVM (компиляция ниже языка хоста, в его рантайм), чем к ClojureDart (транспиляция в язык хоста).

## 3. Архитектура

### Слои
```
┌─────────────────────────────────────────────┐
│ Clojure-код пользователя                    │
├─────────────────────────────────────────────┤
│ Мост (Swift/ObjC):                          │
│  ObjC runtime · Swift metadata · Codable    │
│  адаптеры протоколов · сгенерированные стабы│  ← единственное, что компилирует swiftc
├─────────────────────────────────────────────┤
│ Ядро (C, портируемое):                      │
│  reader · analyzer · optimizer · interpreter│
│  codegen→C · HAMT/RC/аллокатор · core.async │
└─────────────────────────────────────────────┘
```
Дисциплина: ни одного `objc/runtime.h` в ядре. Всё платформенное — за одним C-интерфейсом `host`. Тогда порт на Linux/Android/WASM = только мост.

### Два режима исполнения
- **Dev — интерпретатор.** REPL везде, включая устройство (единственный способ исполнить новый код на iPhone). Не обязан быть быстрым.
- **Prod — компилятор** в C → clang. Закрытый мир.
- **Компилирующий eval на Маке/симуляторе** (C → clang → dylib → dlopen, ~100 мс) — не третий режим, а инструмент: тесты в CI гоняются через компилятор (ловим расхождение семантик), профилирование без сборки всего приложения.

### Пайплайн
`reader → macroexpand → analyzer → optimizer (общий) → backend {closures | C}`

Правило «оптимизатор общий, бэкенды тупые»: всё, что наблюдаемо меняет семантику (порядок эффектов при fusion, TCO, момент реализации lazy seq), решается в общем проходе.

### Аналитор как библиотека: где живёт анализ
**Вопрос.** Выведенные типы собирать только в компиляторе (интерпретатор игнорирует) или отдельным статическим анализатором? **Ни то ни другое:** в общем аналиторе, у которого три клиента.

**Почему не только в компиляторе.** Интерпретатору та же информация нужна для load-time решений: unboxed-узлы в `loop`, специализированный `get` по keyword, выбор арности. Иначе либо дублирование, либо расхождение «компилятор специализировал по типу, которого интерпретатор не видел».

**Почему не отдельный анализатор.** clj-kondo и Typed Clojure отдельные потому, что компилятор Clojure не спроектирован как библиотека — они дублируют ридер/резолв/модель ns и расходятся с ним в углах. У нас аналитор изначально библиотека: одна модель кода, одна таблица варов, один резолв. LSP получает то же дерево с теми же типами, что и бэкенды.

**Разложение по режимам:**
- Локальный вывод (внутри формы: литералы, сигнатуры интринсиков, `instance?`-guards, хинты `^long`) — всегда, в аналиторе, микросекунды. Клиенты: интерпретатор, компилятор, редактор.
- Межпроцедурный (сводки функций по графу вызовов, shape inference через границы) — за флагом закрытого мира: в компиляторе всегда, в dev — инкрементально по эпохам варов.
- Одна инфраструктура сводок: типы, эффекты (чистота), escaping, «может ждать» — не четыре прохода, а один с четырьмя полями в сводке функции.

**Два смысла «неизвестно» при одном движке:**
- Вывод ради оптимизации — sound и консервативный: неизвестно → бокс, без предупреждений, пользователь не замечает. Нужен с первого дня.
- Вывод ради проверки (gradual, `^:typed` на ns) — неизвестно → сообщение. Опция на потом; Clojure-сообщество сознательно живёт с Malli/spec на границах без статики внутри.

**Итог:** аналитор = библиотека со сводками; бэкенды и LSP — клиенты; закрытый мир — флаг, а не другой код.

### Покрытие вывода типов: три слоя
- **Слой 1, статика:** арифметика и циклы ~90%; код над литералами и известными shape'ами; после guard'ов. Ноль на границе — JSON/EDN/host/ввод, а в приложении, показывающем данные с сервера, это половина кода.
- **Слой 2, рантайм:** важна предсказуемость, не статика. JSON с одного эндпоинта → один shape (§4), сайты мономорфны, unboxed-поля по наблюдению. Struct-скорость без вывода — как V8 и `JSON.parse`.
- **Слой 3, схема на границе** (Malli/spec, опционально): `[:map [:id :int] …]` после валидации = статический shape и типы полей всему коду ниже. Как `Decodable` в Swift, но не обязательно. PGO из dev-профиля даёт guarded fast path и без схемы.
- **Непокрыто честно:** гетерогенные данные, мегаморфные сайты, мапы с динамическими ключами → generic HAMT = сегодняшний Clojure с лучшим аллокатором. Пол, не катастрофа.
- **Метрика** (§10): доля сайтов с известным типом / shape / неизвестным в аналиторе + доля моно/поли/мегаморфных сайтов в рантайме, на реальном `.cljc`-приложении (re-frame + парсинг). Ожидание: статика 40–50%, кэши добирают до ~90%, мегаморфных — единицы процентов. Проверить до того, как оптимизатор написан под гипотезу.

### Dev client (паттерн Expo)
Dev-сборка = ядро + интерпретатор + все мосты для подключённых фреймворков. REPL грузит Clojure поверх. Новая Swift-зависимость или новый протокол для `reify` → генерация стаба + пересборка dev-шелла (редко). `(require-swift 'Foundation.DateFormatter)` в REPL может триггерить генерацию и фоновую пересборку. Hot reload через `@_dynamicReplacement` + dylib — для правок *Swift*-стороны моста.

## 4. Рантайм

### Представление значений
- **Не Swift-классы.** Свой заголовок объекта, raw-указатели (`Unmanaged`), свой аллокатор. Swift-классы удобны в первую неделю и закрывают дверь навсегда (атомарный ARC, `swift_allocObject` → malloc, нельзя сменить заголовок).
- **RC свой:** неатомарный по умолчанию, biased — флаг «shared» при пересечении потока/экспорте в Swift, после чего атомарный.
- **Аллокатор:** size-class пулы (HAMT-узел, cons, small-map, бокс, замыкание с k захватами), per-thread, bump внутри свежего слаба, free-list потом. Отбирает у GC главный козырь — дешёвую аллокацию.
- Tagged/unboxed скаляры там, где вывод типов сработал.

### Var и ленивые def
**Проблема.** Загрузка ns в Clojure = последовательное выполнение файла: `def` вычисляется в момент загрузки. Старт платит за всё — `(def client (make-client))` создаёт объект, даже если он никогда не понадобится. Обходы (`delay` + `@`, `defonce`) уродливы. Swift-глобальный `let` устроен иначе: `swift_once` + accessor — инициализация при первом обращении, потокобезопасно, дальше одна проверка токена.

**Решение — в Var, без нового синтаксиса.** У Var уже есть косвенность: `deref` читает корень с проверкой эпохи (inline cache, §6). Корень получает третье состояние — «не вычислен, thunk». Первый `deref` форсит thunk под тем же `Mutex` (семантика `dispatch_once`), остальные видят значение. Одна лишняя ветка в уже существующей проверке. Одинаково в интерпретаторе и компиляторе.

**Что лениво по умолчанию:**
- Чистые `def` (по анализу эффектов из §6) — лениво. Момент вычисления чистого выражения ненаблюдаем, кроме стоимости и времени исключения.
- `defn` — по сути уже лениво, не меняется.
- Формы с эффектами — `defmethod`, `extend-type`, `derive`, `def` с IO, любой top-level не-`def` — eager, порядок загрузки сохраняется (на нём держатся регистрации).
- Неизвестный эффект (интероп без сводки) — eager, консервативно.
- Явно: `^:lazy` / `^:eager`.

**Следствия:**
- Загрузка ns = регистрация варов с thunk'ами; вместе с кэшем AST старт iOS-приложения ≈ 0, а не «выполнить всю программу до `main`».
- Dev-режим: флаг, форсирующий все ленивые def сразу после загрузки файла — ошибки всплывают при загрузке, как раньше, а не при первом использовании. В проде — лениво.
- Компилятор в закрытом мире убирает ветку проверки там, где вар доказанно уже форсирован.

### Порядок объявлений (hoisting)
**Почему в Clojure «то, что ниже, недоступно».** Файл компилируется по одной top-level форме за раз: прочитал, проанализировал, выполнил, следующая. Это условие REPL-модели — файл есть стенограмма сессии. Глубже — макросы: встретив `(foo x)`, компилятор обязан знать, макрос это или функция, а узнать можно только после выполнения `defmacro`. Многопроходный резолв как в Swift/Java невозможен, пока макросы выполняются во время компиляции. На практике мешает мало: `declare` для взаимной рекурсии, bottom-up порядок файла (многие считают фичей), нельзя положить публичный API в начало.

**Решение — два режима.**
- Загрузка файла: анализатор видит все формы → pre-pass собирает имена всех `def`/`defn`/`defprotocol`/`defmulti` и регистрирует их как unbound-вары (неявный `declare`). Затем формы выполняются по порядку. Forward-ссылки на функции работают: замыкание захватывает вар, к моменту вызова он связан. Семантически ничего нового — ровно то, что `declare` делал руками.
- REPL, одиночная форма: контекста файла нет, неизвестный символ остаётся ошибкой компиляции. Иначе опечатка из compile-error превращается в unbound-var в рантайме.
- Правило, которое остаётся: `defmacro` — строго до использования. Как Swift-макросы: определены раньше, в другом месте.

**Синергия с ленивыми def.** Единственный опасный сценарий hoisting — вычисление значения при загрузке до связывания зависимости: `(def x (helper))`, `helper` ниже. С ленивыми `def` `x` форсится при первом использовании, когда файл загружен целиком. Hoisting убирает `declare`, ленивость убирает ошибки порядка в `def`-значениях; вместе остаётся одно правило — про макросы.

### Персистентные структуры — где деньги
Копия HAMT-узла на 32 слота = memcpy 256 байт (~10 нс) **+ 32 retain детей** (~150 нс атомарных). `assoc` копирует 2–4 узла. Borrow inference тут не помогает — дети реально приобретают владельца. Лечится только: неатомарный счётчик; reuse (не копировать); регион (не считать); меньший branching (16).

**Бенчмарк** (`bench/RESULTS.md`, fd4cbf4 → b11f641, M3 Pro): C HAMT vs `TreeDictionary` (swift-collections, CHAMP на Swift-классах) vs мутабельный `Dictionary`.
- До пула: 1.2–1.8×. Гипотеза «свой RC даёт кратный выигрыш» не подтвердилась — обе стороны на 60–70% мерили системный malloc. Модель «32 retain на копию» верна только для полных узлов (при n=100k корень и второй уровень полные, ~67 retain на путь); у маленьких мап узлы разрежены.
- После per-thread size-class пула: `assoc` с отпущенной старой версией 82→39 нс при 1k (пул vs malloc в одном прогоне, Swift-колонки сходятся в 1–4%); tree/C 2.0–3.7× на `assoc`, 1.5–2.7× на `dissoc`, `get` без изменений (не аллоцирует). Персистентный `assoc` при уникальности — в 2× от мутабельного `Dictionary` (39 vs 20), не в 3×.
- Атрибуция выигрыша: аллокатор > неатомарный RC (~1.5× на больших мапах с живыми версиями) > хэш (`get` при n=10: 2.7 vs 11.8 — почти целиком `Hasher`/SipHash) > обвязка.
- Reuse при rc==1 есть у обоих (`TreeDictionary` — через `isKnownUniquelyReferenced` на `var`). Тест на идентичность указателя корня — регрессионный.
- `TreeDictionary` округляет ёмкость узла до степени двойки (slack под рост). У нас логический размер точный, физический — size-class пула: тот же эффект бесплатно. Решение.
- Открыто: хэш-паритет; peak RSS и возврат страниц пулом (`madvise`); cross-thread free (объект освобождается не владельцем пула); многопоточный read-mostly сценарий — единственный, где `TreeDictionary` может проиграть кратно, не измерен.

**Вывод:** Swift-ARC пригоден. Свой рантайм лучше по архитектуре (аллокатор, C-бэкенд, reuse, biased RC, портируемость); в скорости — 2–3× на главной операции, не 5–10×.

### Представление по наблюдению: shapes, tuples, elements kinds
**Мотивация.** 90% мап в Clojure-приложении — `{:id 1 :name "x"}` на 3–8 keyword-полей, то есть Swift-struct, а не словарь. Swift-struct: поле 0.3 нс, мутация — запись в слот. `PersistentArrayMap` (≤8, линейный скан `identical?` по интернированным keyword) уже неплох, но это линейный поиск + бокс + отдельный массив.

**Shapes** (hidden classes: Self 1989 → V8/SpiderMonkey/JSC, Ruby 3.2 object shapes, Truffle OSM, PyPy maps, key-sharing dict в CPython; иммутабельный прецедент — Erlang flatmaps: разделяемый keys-tuple, порог 32 ключа, дальше HAMT):
- Мапы с одним набором ключей делят объект Shape (ключи + индексы); в мапе — указатель на shape и значения inline. Одна аллокация, одна кэш-линия.
- Дерево переходов: `∅ --:id--> S1 --:name--> S2`. Литерал, цепочка `assoc` и JSON-парсер идут по одним рёбрам → один shape → мономорфный call site. Shape строится по ходу парсинга, generic-мапа не создаётся ни в первый раз, ни потом; со второго раза стоимость на ключ — intern строки в keyword + сравнение указателя в таблице переходов (обычно один элемент).
- Inline cache на call site: `(:name m)` → `if m.shape == cached → values[idx]`, ~1–2 нс. Полиморфный (2–4) → switch; мегаморфный → generic. В интерпретаторе кэш на узле AST; в компиляторе — статически из PGO-профиля; при статически известном shape (литерал, flow-типизация, схема) — прямое смещение без проверки.
- Unboxed поля по наблюдению (V8 field representations): `:count` всегда int64 → слот без бокса, проверка при записи.
- `assoc` при rc==1 — запись в слот; `(update m :count inc)` — буквально `m.count += 1`. При rc>1 — копия массива (≤32 слотов — одна кэш-линия, = один HAMT-узел).
- `defrecord` = именованный, заранее объявленный shape с гарантиями (opt-in: лишнее поле — ошибка). Один механизм вместо двух. У records свои углы (`dissoc` → мапа, `(= record map)` → false); shapes дают ту же скорость без них.
- Семантика неизменна: это мапа. `=` и `hash` структурные (одинаковый shape → сравнение массивов напрямую), `seq` в порядке shape (у hash-map порядок и так не определён); не-keyword ключ, nil-ключ, метаданные → generic.
- Интероп: shape = layout Swift-struct; `Codable`-энкодер получает shape по типу один раз и заполняет слоты.
- Не убегающая shape-мапа известной формы с unboxed полями на стеке (§7) = Swift-struct на стеке. Слои сходятся.

**Ограничения shapes:**
- ≤32 ключей (branching factor HAMT; линейный скан по указателям быстрее хэша до 32; копия — одна кэш-линия). Порог 8 у Clojure — про стоимость `equals` на JVM, у нас сравнение указателей.
- Не-keyword ключ → сразу generic.
- >8 различных детей у shape'а → shape «словарный», все мапы через него → HAMT. Это детектор динамических ключей (`{user-id → user}`).
- Потолок shape'ов на процесс (десятки тысяч); shape'ы интернированы и живут вечно.
- Порядок ключей: `{:id :name}` и `{:name :id}` — разные пути; канонизация при финализации по множеству ключей (кэш key-set → shape, O(k log k) один раз).
- Переход в HAMT односторонний и незаметный; обратно — никогда.

**Tuples.** Вектор фиксированного размера 2–6 с элементами inline: одна аллокация, `nth` — load по смещению без shift и хвоста, слоты могут быть unboxed (`[x y]` точки = два double). Литерал `[x y]` → tuple2, деструктуринг → два load, `conj` за ёмкость → промоушен в вектор. `MapEntry` = tuple2. Clojure JVM пробовал (1.8-alpha) и откатил из-за мегаморфных сайтов у HotSpot — у нас JIT'а нет, диспатч статический или tag-switch, аргумент исчезает. Ещё лучше — не аллоцировать пару: `(map (fn [[k v]] …))` после fusion передаёт `k v` двумя аргументами; `(seq shape-map)` отдаёт entries из (ключ shape, слот) лениво/на стеке; `(let [[a b] (f x)])` с известной формой — два возврата в регистрах.

**Векторы — elements kinds (V8).** Все int64 → unboxed `int64[]`, double → `double[]`, смешанные → boxed; переходы односторонние по наблюдению при записи. Это `vector-of :long`, только выведенный.

**Списки — ничего. Сеты** — ≤8 линейный массив, дальше HAMT; битовая маска только для статически известного keyword-универсума (литеральные сеты, enum) — оптимизация компилятора, не рантайма.

**Отвергнуто: SoA/колоночное хранение вектора мап одного shape'а.** `nth` обязан вернуть мапу — материализация или row-view, то есть третье представление мапы во всём рантайме; `assoc-in` одной ячейки — копия столбца O(n) или персистентные столбцы (и скан уже не плотный); `assoc` мапой другого shape'а → демоушен O(n), thrashing на границе; row-view снаружи держит весь вектор; паттерн доступа в UI строчный; fusion над AoS добирает половину выигрыша (слот по смещению в каждой строке). Место SoA — явный тип dataset/columnar (Arrow, tech.ml.dataset), не неявное представление `vector`.

**Общий принцип.** Представление выбирается по наблюдению, переходы односторонние, семантика неизменна. Критерий допустимости «магии»: никогда не хуже базы (медленный путь = сегодняшний HAMT, не deopt-обрыв как в V8); состояние инспектируемо (`(shape-of m)`, метрика моно/поли/мегаморфных сайтов в dev, размер дерева переходов); стоимость операций предсказуема. Fusion, reuse, регионы, hoisting, shapes проходят; SoA — нет.

**Почему Clojure JVM так не делает.** Нет своих call site'ов (`(:name m)` → `Keyword.invoke` → `ILookup.valAt`, HotSpot кэширует класс, не shape); нет unboxed-слотов без Valhalla; GC делает аллокацию дешёвой; философия «знаешь ключи — `defrecord`», без скрытого глобального состояния; консерватизм core (структуры не менялись с 1.0). У нас все три технических условия есть: свои сайты, unboxed-слоты, дорогая аллокация как мотив.

### Атомы
- `Mutex` (`Synchronization`, iOS 18+) или `OSAllocatedUnfairLock`, не голый `os_unfair_lock` (нужна стабильность адреса). Не CAS: lock-free refcounted-указатель = гонка retain/release, нужны hazard pointers или DCAS ради повторения JVM-дизайна.
- `f` выполняется ровно один раз, под локом. Watches — после отпускания лока. Вложенный `swap!` на тот же атом — trap (на JVM — бесконечный ретрай, оба баг). `deref` тоже под локом — дёшево.
- **Трюк уникальности:** `old = state; state = placeholder; new = f(old)` — внутри `f` значение уникально → in-place обновление.
- Не актор: `swap!` обязан быть синхронным.

### Подписки (вместо Observable-макроса)
- `add-watch` — на весь атом; уровень путей — слой выше (cursor/reaction, re-frame).
- Подписки по путям в trie. После `swap!` обход trie: `new[k] === old[k]` → ветка пропущена. Стоимость ∝ (изменившиеся пути ∩ подписанные), не размер состояния. Нет подписчиков → ноль.
- Автотрекинг без макроса на уровне `deref` (TLS-контекст), а не полей — так делает reagent. Гранулярность атом/курсор.
- **Мост к SwiftUI:** курсор реализует `Observable` руками через `ObservationRegistrar` с одним свойством `value`. Инструментирована одна точка на курсор, не каждое поле модели. `@Observable`-макрос дорог именно потому, что у класса нет другой точки перехвата; у атома точка одна — `swap!`.

### Функции
Clojure-fn ≠ Swift-замыкание: несколько арностей, `IFn` на keyword/map/vector/set, метаданные, identity, `apply`, свой RC и конвенция +0. Скомпилированная fn = `{header, table[arity]→C-функция, env}`. На границе — адаптеры в обе стороны (`Value.callAsFunction`, host-fn для Swift-closure).

### Протоколы и типы — свои, в обоих режимах
- `defprotocol`/`deftype`/`reify`/`extend-type` — своя таблица диспатча (как в CLJS/ClojureDart), не хостовые типы. Компилятор может опустить `deftype` в struct с vtable — это представление, не семантика.
- `extend-type` на Swift-типы работает (диспатч по метаданным типа), новый тип не нужен.
- **`reify` — четыре случая:**
  1. Clojure-протокол → таблица, бесплатно.
  2. `@objc`-протокол/класс → живой класс из ObjC-рантайма (делегаты, `UIView`-подклассы — всё UIKit). Полностью динамически, из REPL.
  3. Swift-only протокол → **предкомпилированный адаптер** на протокол (type-eraser, методы уходят в интерпретатор). Один раз на протокол, кодоген по `.swiftinterface` (макросы не видят чужие декларации). Associated types → generic-адаптер, инстанцируемый через `_typeByName`. Список реально нужных — пара десятков.
  4. Подкласс Swift-only класса с vtable → только заранее сгенерированный `open class` прокси. Честно закрыто; в Apple-фреймворках таких классов мало.
- **Не** генерировать честные конформности из `deftype` в компиляторе — расхождение семантик между режимами (то, за что SCI платит годами). Адаптер — единый контракт; компилятор может его инлайнить.

### Мультиметоды
Целиком в рантайме (MultiFn + таблица + иерархия + кэш диспатча под тем же Mutex). Хост всплывает только в `isa?` на хостовых типах — читать суперкласс из class metadata, конформанс через `swift_conformsToProtocol`, `@objc` — через `class_getSuperclass`.

### core.async
- **`go` — два пути:** (1) IOC-трансформ в state machine на обычном Clojure — host-agnostic, единственный вариант для интерпретатора (иначе каждый шаг eval `async`); (2) в компиляторе — `Task {}` + `await`, ограничение core.async «`<!` только в теле `go`» совпадает с function coloring буквально.
- **Каналы свои:** буфер + очереди continuation'ов под локом, `alts!` через общий флаг-победитель, `timeout` — `Task.sleep`. `AsyncStream` — не то (single consumer, нет backpressure), но его `BufferingPolicy` = sliding/dropping один в один.
- Кооперативный пул нельзя блокировать — как 8-поточный пул core.async. `<!!`/`>!!` не давать (DispatchSemaphore в пуле = priority inversion).
- `go` unstructured как `Task.detached`; сверху `go-scoped`. `@MainActor`-hop: executor на канале или `go-main`. Sendable: значения иммутабельны, но бокс `Any` — `@unchecked` на обёртке.
- Акторы ≠ каналы: акторы для владения состоянием, каналы для потоков данных.

### Ошибки и стектрейсы
- **Компилятор:** `#line N "app/core.clj"` в сгенерированном C → DWARF с `.clj` → Xcode-брейкпоинты, символикация крэшей через dSYM, Instruments — всё штатное. Читаемое манглирование имён + деманглер. `:line/:column` через macroexpand.
- **Интерпретатор:** теневой стек кадров (push/pop, наносекунды), обработчик сигнала дописывает его в крэш-репорт (custom keys / буфер).
- **Одна модель ошибок:** `ex-info` ↔ `ClojureError: Error {message, data, clojureTrace, cause}`; Swift `throws` → `ex-info` с `:host/error`.
- **Async:** в dev при создании `go`/`lazy-seq`/`future` запоминать кадр создания → «spawned from».
- **Логи:** `swift-log` через стаб, Logger на ns, Clojure-мапа → `Logger.Metadata` напрямую.
- Крэши рантайма: debug-сборка с ассертами на счётчиках, canary в заголовках, ASan (на C работает из коробки).

## 5. Интероп

### Главное разделение: данные vs вызовы
Swift-рантайм отдаёт **данные** динамически (метаданные полей, get/set по смещению, тип по имени, generic-инстанциация, конформансы), но **не вызовы** (произвольный метод с сигнатурой, известной в рантайме). Интерпретатор и компилятор в интеропе равны — оба зовут только то, что заранее в мосту.

### Что умеет Swift-рантайм (wickwirew/Runtime, Echo и ниже)
Можно: метаданные типов, поля по смещению, `_typeByName` (включая generic-инстанциации), `x as? any P` (единственный настоящий динамический вызов — по известному протоколу на любом типе), `dlsym` по mangled-имени + `unsafeBitCast` к известному типу, `@_dynamicReplacement`, ObjC-рантайм на Swift-классах (`@objc dynamic` методы), патчинг vtable (хак), `_openExistential`.
Нельзя: создать Swift-тип, добавить конформанс, позвать функцию с рантайм-сигнатурой (Swift ABI), eval/загрузить код на устройстве.

### Три уровня, одновременно
1. **ObjC-рантайм** — всё `@objc` (UIKit, Foundation, AVFoundation…), из REPL, без пересборки. ~70% реального приложения.
2. **Зарегистрированный мост для Swift-only** — таблица функций, Expo-Modules-стиль: руками по мере надобности, генерация *глю*, не *покрытия*. Из `.swiftinterface` честно генерируется только не-дженерик поверхность. «Подключил SwiftUI — получил всё» не выйдет (никто не сделал; UniFFI/swift-bridge существуют именно поэтому).
3. **Данные через границу** — Clojure отдаёт описание, Swift исполняет. Для SwiftUI это не компромисс, а архитектура: view-дерево как данные, Swift-рендерер с фиксированным набором компонентов. Elm/re-frame.

Граница: Clojure — «мозг» (состояние, логика, данные, сеть), Swift — «руки» (рендер, hot paths, Metal). Переход стоит десятки нс: ноль для UI-событий, приговор для пиксельного цикла.

Реальная потеря без eval Swift: нельзя из REPL исследовать Swift-only API, которого нет в мосту.

### Swift → Clojure
- **`Value`** — один тип на границе: struct над raw-указателем, RC в `init`/`deinit`, конвертеры примитивов, литералы, `Optional` → nil, `callAsFunction`. Вызов `clj.fn("app/handle")(args)` → `clj_invoke` по C ABI.
- **Структуры — `Codable`:** `CLJEncoder/CLJDecoder`, как JSONEncoder, но результат — персистентная мапа с keyword-ключами. Официальный механизм, покрывает почти все модели. Рефлексия из Runtime — fallback для не-Codable.
- **Без копирования — host-value:** `UIView`, `DateFormatter`, дорогие структуры — opaque объект, `(:field obj)` по метаданным по требованию, `ILookup`; первый `assoc` материализует в настоящую мапу.
- **Владение:** `Value` в Swift = +1; deinit может прийти в любом потоке → экспортированный объект переходит на атомарный счётчик (biased RC). Swift-объекты у нас — `Unmanaged` retain.
- **Замыкания в обе стороны** с первого дня.

### ABI
- Сгенерированный C ↔ ядро — C ABI (`@_cdecl` на Swift-части рантайма).
- Стабы ↔ Swift-фреймворки — Swift ABI, целиком внутри swiftc.
- `@objc` — ObjC ABI, стабилен десятилетиями, дёргается динамически.
Swift ABI руками не трогаем; понадобится только если LLVM-IR-бэкенд захочет звать Swift без стабов — причина начинать с C.

## 6. Компилятор

### Разблокирующий шаг — закрытый мир
Без него ничего не работает. С ним: вары → прямые вызовы (`^:dynamic` и `with-redefs` остаются косвенными), tree shaking core, протоколы → CHA (одна реализация → прямой вызов, несколько → switch), мультиметоды со статической иерархией → switch, `apply`/вариадики с известной арностью без seq.

### Оптимизации по источнику права

**Локальный вывод типов (ClojureDart-стиль):** литералы, core-сигнатуры, `instance?`-guards → unboxed `loop/recur`; `(:key m)` с литералом → предвычисленный хэш; `defrecord` → struct со смещениями; shape inference для литеральных мап. См. §3 — вывод живёт в общем аналиторе, не в компиляторе.

**Чистота (анализ эффектов транзитивно по закрытому миру):** fusion/deforestation пайплайнов `map/filter/reduce` → один цикл (легально: порядок эффектов lazy seq не гарантирован); strictness (lazy seq, потребляемая тут же → eager); CSE, вынос инвариантов; частичное вычисление литералов/конфигов/регэкспов. Автоматическая ленивость чистых `def` — см. §4 «Var и ленивые def»; требует сводки эффектов на top-level форму.

**Иммутабельность:** авто-transient'ы (reuse/FBIP), `borrowing`-конвенция, Sendable blanket, кэши хэша/равенства.

**Поток управления:** `recur` → цикл, самохвостовые вызовы → TCO (безопасно: отличие только в глубине стека), деструктуринг → прямые обращения, `case` → switch, не убегающие замыкания без контекста.

**Приоритет:** прямая линковка → вывод типов → fusion → авто-transient'ы. Первые два дают большую часть скорости, дальше LLVM.

**Что ломается:** `resolve`, `ns-publics`, `eval` → статические таблицы или ошибка компиляции; `with-redefs` — тесты в интерпретаторе.

### Что переносится в интерпретатор (load-time, локально)
Резолв варов при загрузке с эпохой (inline cache без JIT), деструктуринг, `case`-switch, constant folding, локальные unboxed-узлы в `loop`, арность/apply, TCO, авто-transient'ы (свойство рантайма), не убегающие замыкания. С оговоркой: fusion через список интринсиков с инвалидацией; локальный анализ эффектов; кэш AST между запусками. Не переносится: всё, что требует закрытого мира → рантайм-кэши (мономорфный inline cache на протоколах). Бюджет: локальные проходы — микросекунды, в REPL можно все; квадратичное — только в компилятор.

### JIT — нет. PGO — да.
Минусы JIT: на iOS невозможен; прогрев; память (code cache, профили, stack maps); недетерминизм (deopt storm посреди анимации); второй компилятор со своими багами; проектировать под него надо с первого дня; батарея и RWX-память. **Замена:** профиль собирается в dev-режиме интерпретатором (типы на call site, реализации протоколов, горячие ветки) → компилятор делает спекулятивную специализацию с guard'ами статически. Теряется только адаптация к данным, которых в dev не было.

### Инлайнинг без JIT
Проблема JVM с tuples — специфика JIT: инлайнинг HotSpot зависит от inline cache на сайте; три класса → мегаморфный → itable-стаб ~10 нс. У нас тип известен статически или по тегу, и оба пути инлайнятся.
- Операции рантайма (`nth`, `get`, `+`, `first`) — интринсики. Представление известно → прямой код; нет → inline tag-switch: маска по заголовку, быстрые ветки inline, медленный путь — вызов. Switch инлайнится на каждом сайте, ~1 нс; статический компилятор может позволить себе разбухание кода, которое JIT не может.
- Пользовательские функции: закрытый мир → прямые вызовы → инлайнит LLVM; маленькие чистые — `always_inline`. Higher-order с литеральной `fn` → после fusion цикл с телом inline.
- Каталог функциональных оптимизаций (GHC: оптимизатор ≈ инлайнер + то, что он разблокирует): beta-reduction, case-of-case; worker/wrapper = наши два входа (боксовый + примитивный, как `IFn$LL`); специализация по тегу/типу; fusion = инлайнинг higher-order до исчезновения промежуточных структур; let-floating, strictness, eta-expansion, join points (= `musttail`-блоки). Сверху Koka/Lean: Perceus, reuse, defunctionalization.
- Не инлайнится: `(f x)` с `f`-значением неизвестного происхождения — цена первоклассных функций, у Swift с замыканиями та же. Лечится PGO-спекуляцией: `if (f == foo) { тело foo } else { call }` — JIT-овский inline cache, выписанный статически. Протоколы — так же: известный набор реализаций → switch, тела inline.

### Бэкенд: C через clang
swiftc медленный на 80% из-за type checker, который сгенерированному коду не нужен. Варианты: явный Swift (3–5× быстрее, всё равно секунды); SIL (нестабилен, нужен frontend); **C через clang (10–50× быстрее swiftc, Chicken/Nim/Ferret)**; LLVM IR напрямую (jank, максимум контроля, больше работы). Начинать с C, IR — когда C-семантика начнёт мешать.

Что C даёт сверх Swift: `__attribute__((musttail))` (гарантированный tail call, у Swift нет), неатомарный RC, свой аллокатор и layout, computed goto для интерпретатора, ошибки как return-код (не дороже `throws`), ASan из коробки, `#line` в `.clj`.

`borrowing`/`consuming` не нужны: ownership выведен, в C выражается отсутствием `inc`/`dec` (Perceus). OSSA оптимизировал Swift-ARC, которого больше нет. LLVM-оптимизации (инлайнинг, LTO, векторизация) остаются через clang.

## 7. Память

### RC vs GC — честно
- Для аллокационно-тяжёлого функционального кода **GC быстрый**: bump-аллокация, nursery-сборка ∝ живым объектам, никаких записей в счётчики. Наивный RC — самая медленная схема. Perceus/Lean хвастаются «скоростью GC», потому что до них RC до неё не дотягивал; обгоняют за счёт reuse. Цена GC — память 2–5× и паузы.
- **Rust быстр не потому, что освобождает, а потому, что не аллоцирует.** Rust на `im` (Arc-HAMT) в 10–50× медленнее `Vec`. Разрыв с идиоматичным Rust — свойство модели данных, не памяти. Закрывается там, где анализ превращает персистентную операцию в мутацию.
- Честная цель: там, где линейность доказана — Rust; где данные разделяются — паритет с любым языком на тех же структурах; не проиграть GC на промежуточных аллокациях за счёт аллокатора и reuse.

### На каждое значение три вопроса (ARC отвечает на все в рантайме самым дорогим способом)
1. **Убегает ли?** Нет → регион/стек, без счётчика. Да → heap.
2. **Единственный ли владелец?** Да → reuse/мутация. Нет → копия пути.
3. **Пересекает ли поток?** Нет → неатомарный. Да → атомарный.

Escaping — главная проблема для *потока управления*; для *данных* главная — sharing (32 retain — это вопрос 2, не 1).

### Что убирает анализ без аннотаций (Perceus / Lean 4 «Counting Immutable Beans»)
- **Borrow inference:** параметр только читается → +0. Убирает большую часть ARC на вызовах. Параметр утекает в результат → owned; вызывающий на последнем использовании → consume. Это и есть «inout»: `x = f(consume x)` — указатель вошёл, указатель вышел, счётчик не тронут.
- **Точные drop/dup** в точке последнего использования — то, что делает рантайм-проверку `count == 1` *успешной*, а не *ненужной*. Koka/Lean уникальность не доказывают, они ставят проверку (одна загрузка + сравнение) и следят, чтобы счётчик был 1.
- **Reuse:** проверка на каждом узле пути (не только корне) — мутируем до первого разделённого узла. Точнее transient'ов с edit-token; в компилированном коде transient'ы почти не нужны.
- **Escape analysis:** локальный для замыканий (переданы в известный интринсик → не убегают, O(1)); межпроцедурно — одна bottom-up проходка по графу вызовов (Go делает это на каждой компиляции). Дефолт — «убегает».
- **Регионы (Tofte–Talpin, MLKit, не Google ML Kit):** bump-аллокатор на скоуп, сброс при выходе, объекты без заголовка. Не убегающая копия узла заимствует детей — memcpy 10 нс без единого retain. Инвариант: heap-узел никогда не указывает на региональный; `original` переживает регион. Ловушка region leak в циклах → сброс на итерации `loop/recur` или fallback на RC. Промоушен в heap на неизвестной границе — консервативно или явно на выходе.
- **Стек:** для не убегающих объектов фиксированного маленького размера (бокс, замыкание с k захватами, tuple); регион — для не убегающих любого размера; куча — для убегающих. Порог из-за стека iOS (main 1 МБ, фоновые 512 КБ, корутины 64 КБ) — `alloca` переменного размера опасен. RC на стековом объекте — no-op: компилятор inc/dec не эмитит, флаг `stack` в заголовке — страховка. Интерпретатору недоступно. На таблицу бенчмарка (§4) не влияет — узлы результата `assoc` убегают по определению. Лучше стека — регистры (unboxed скаляры).

Лестница: fusion убирает временное совсем → регион делает временное бесплатным → reuse делает линейное мутацией → RC только на том, что живёт в двух версиях одновременно. Аннотации (`^:linear`) — только как гарантия, не как условие.

### Что остаётся и надо делать инженерно
- Drop большой структуры синхронный O(n) в UI-потоке → отложенное освобождение в фоновую очередь, итеративные деструкторы.
- Циклы: lazy seq обнуляет `fn` после реализации (как Clojure); замыкания над иммутабельным циклов не образуют.
- Горячие счётчики (корень разделяемой мапы, core-функции, keyword'ы) → неатомарный/biased.

### Свой GC — перебор для v1
Теряет reuse (нет счётчика), детерминизм (паузы в 8 мс бюджете), простой интероп (два heap'а, handle table для Swift-held значений, несобираемые циклы через границу — задача уровня WebKit JS↔DOM). Даёт bump только если перемещающий, а перемещение требует точных корней. Mono на iOS с SGen доказывает, что GC на iOS возможен, но там весь heap свой. **Решение:** свой заголовок + пул + RC как политика; дверь для неперемещающего Immix-подобного остаётся открытой, если профиль потребует. Скорее всего — никогда.

## 8. Что отвергнуто и почему

| Идея | Почему нет |
|---|---|
| Транспиляция в Swift-исходник | swiftc медленный, атомарный ARC, `Any`-бокс, всё равно нужны стабы |
| Swift-классы для Clojure-значений | закрывает свой RC/аллокатор/заголовок навсегда |
| Swift-замыкания как Clojure-fn | одна арность, нет IFn/meta/identity/apply, атомарный контекст |
| Honest-конформансы из `deftype` в компиляторе | расхождение семантик с интерпретатором |
| Actor для атома | `swap!` становится `await` |
| CAS-атом | retain/release гонка на указателе, hazard pointers ради JVM-дизайна |
| JIT | iOS; замена — PGO из dev-профиля |
| Свой GC | см. §7 |
| `<!!`/`>!!` | блокировка кооперативного пула |
| Генерация покрытия всего Swift SDK | дженерики не эрейзятся; никто не сделал |
| `delay` + `@` как способ ленивых глобалов | ленивость встроена в Var, синтаксис не нужен |
| Явный `declare` для forward-ссылок | hoisting имён при загрузке файла; в REPL-форме — по-прежнему ошибка |
| Вывод типов только в компиляторе / отдельный анализатор | один аналитор-библиотека с тремя клиентами: интерпретатор, компилятор, LSP |
| SoA для вектора мап одного shape'а | `nth` хуже базы, персистентность ломается; место — явный dataset-тип |
| Порог 8 ключей как у `PersistentArrayMap` | 32: сравнение указателей, не JVM-`equals`; DTO с бэкенда — 5–25 полей |
| `defrecord` как единственный ответ на struct-like мапы | не покрывает данные с границы, церемония `map->User`; record = именованный shape |

## 10. Первые шаги (по порядку)
1. **Бенчмарк HAMT** — сделано (§4): свой RC + пул 2–3× на `assoc` против `TreeDictionary`; аллокатор важнее счётчика.
   - **1b. Бенчмарк shapes/tuples.** Struct-like набор: 5–8 keyword-полей, `(:field m)` моно- и полиморфно, `(assoc m :field v)`, `(update m :count inc)` при уникальной и разделённой ссылке — против Swift-struct и `[String: Any]`, плюс `defrecord`. Tuples: `[x y]` create/destructure, `(map (fn [[k v]]))` над мапой из 8 и 1000 ключей, `zipmap` — против кортежа и `[(K, V)]`. Цели: доступ к полю ≤2 нс, update при уникальности ≤10 нс, не убегающая пара — 0.
2. Ядро на C: значения, заголовок, size-class аллокатор, HAMT/vector, RC неатомарный + biased.
3. Reader → analyzer → closure-компилирующий интерпретатор с локальными оптимизациями. Теневой стек.
   - **3b. Метрика покрытия типов** (§3): доли известный тип / shape / неизвестно в аналиторе и моно/поли/мегаморфных сайтов в рантайме на реальном `.cljc`-приложении — до того, как оптимизатор написан под гипотезу.
4. Мост уровня 1 (ObjC-рантайм) + `Value` + `Codable`-энкодер. `reify` на `@objc`.
5. core.async на IOC + свои каналы.
6. Компилятор в C: закрытый мир, прямая линковка, вывод типов, `#line`. Тесты через компилятор в CI.
7. Borrow inference + reuse. Потом fusion, регионы.
8. Адаптеры Swift-протоколов и генератор стабов; dev-client флоу.
